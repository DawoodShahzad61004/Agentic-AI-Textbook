BUG: Raw Context Returned as a Successful Final Answer
Brief Description

When ENABLE_ANSWER_DRAFT_CREATION=False, the agent skips the answer synthesis phase and returns the compressed/retrieved chunks directly as the final answer. Despite never generating a user-facing answer, the run is still reported as successful (Quality signal: OK).

This creates a false-positive success condition:

No answer was generated.
No reasoning/synthesis occurred.
No quality validation occurred.
Yet the run is treated as a successful answer generation.

As a result, users receive raw retrieval output rather than an actual answer, and the system incorrectly believes the query was answered successfully.

Configuration

In config.py:

ENABLE_ANSWER_DRAFT_CREATION = False

RETRIEVE → COMPRESS → DRAFT → JUDGE

  ↓
return compressed context

RETRIEVE

COMPRESS
  ↓
DRAFT
  ↓
JUDGE
  ↓
FINAL ANSWER

[PHASE: DRAFT] disabled — returning compressed context as final answer

which confirms the bypass occurred.

Success Reporting

Later in the run summary:

Quality signal : OK

even though:

ENABLE_ANSWER_QUALITY_CHECK = False

and no answer was actually drafted.

What Should Be Happening

Treat draft generation as mandatory.

ENABLE_ANSWER_DRAFT_CREATION == False

or

quality = "NOT_GENERATED"

  ↓

The current behavior corrupts multiple downstream systems:

Feedback Store

and later become training data.

Self-Learning

SelfLearner distills interactions whose quality is "OK":

The agent currently equates:

Those are fundamentally different states.

A retrieved/compressed context is merely evidence.

From this, what can u tell me about the concept and the terminology of "retry after exponential delay"

"Retry after exponential delay" (more commonly called Exponential Backoff) is a retry strategy used when an operation fails temporarily, especially with:

API rate limits (429 errors)
Network failures
Timeouts
Temporary server errors (500, 502, 503, 504)
Basic Idea

Instead of retrying immediately:

❌ Bad:

Try 1 -> fail
Retry immediately -> fail
Retry immediately -> fail
Retry immediately -> fail

You progressively wait longer between retries:

✅ Exponential Backoff:

Try 1 -> fail
Wait 1 second

Try 2 -> fail
Wait 2 seconds

Try 3 -> fail
Wait 4 seconds

Try 4 -> fail
Wait 8 seconds

Try 5 -> fail
Wait 16 seconds

The delay grows exponentially:

delay = base_delay × (2 ^ retry_number)

Example:

Attempt	Delay
1	1 sec
2	2 sec
3	4 sec
4	8 sec
5	16 sec
Why It Exists

Imagine your RAG system sends 100 requests to Groq.

Groq responds:

429 Too Many Requests

If every client retries immediately:

Client A -> retry now
Client B -> retry now
Client C -> retry now
...

The server gets hammered again.

Exponential backoff spreads requests out:

Client A -> 1s
Client B -> 2s
Client C -> 4s
Client D -> 8s

Giving the service time to recover.

Jitter

Real systems almost never use pure exponential backoff.

Instead they add jitter (randomness).

Without jitter:

100 clients fail at same time
all wait 4 sec
all retry at same time

Still creates a spike.

With jitter:

Client A -> 3.7 sec
Client B -> 4.4 sec
Client C -> 5.1 sec
Client D -> 3.2 sec

Retries become distributed.

Example:

import random

delay = (2 ** attempt) + random.uniform(0, 1)
Retryable vs Non-Retryable Errors

A key concept:

Retryable (Transient)

Temporary problem.

Examples:

429 Rate Limit
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
Network Connection Error
Timeout

Retry makes sense.

Non-Retryable (Permanent)

Retrying won't help.

Examples:

401 Unauthorized
403 Forbidden
404 Not Found
Invalid JSON Schema
Bad API Key
Malformed Request

Should fail immediately.

import random
import time

BASE_DELAY = 1
MAX_DELAY = 30

for attempt in range(MAX_RETRIES):

    try:
        return api_call()

    except TransientError:

        delay = min(
            BASE_DELAY * (2 ** attempt),
            MAX_DELAY
        )

        jitter = random.uniform(0, delay * 0.25)

        time.sleep(delay + jitter)

Terminology:

Retry → Try again after failure.
Retry Limit → Maximum number of attempts.
Backoff → Waiting before retrying.
Exponential Backoff → Delay doubles each retry.
Jitter → Random variation added to delay.
Transient Error → Temporary failure worth retrying.
Permanent Error → Failure that should not be retried.
Retry Budget → Total retries allowed.
Rate Limiting → Server intentionally slowing/rejecting requests.
Circuit Breaker → Stops retries entirely when a service is repeatedly failing.

what are other common methods other than backoff and exponential backoff?

In distributed systems, APIs, cloud services, and AI systems, Exponential Backoff is just one member of a much larger family of retry strategies.

1. Immediate Retry

Retry instantly.

Attempt 1 -> fail
Retry immediately
Pros
Fastest recovery if failure was a one-time glitch.
Cons
Can hammer the server.
Terrible for rate limits.
Used For
Very cheap local operations.
Occasional network hiccups.
2. Fixed Delay Retry

Wait the same amount every time.

Attempt 1 -> fail
Wait 5s

Attempt 2 -> fail
Wait 5s

Attempt 3 -> fail
Wait 5s
Formula
delay = constant

Example:

delay = 5
Pros
Simple.
Predictable.
Cons
Not adaptive.
3. Linear Backoff

Increase delay linearly.

Attempt 1 -> wait 1s
Attempt 2 -> wait 2s
Attempt 3 -> wait 3s
Attempt 4 -> wait 4s
Formula
delay = base × attempt

Example:

delay = 2 * attempt

Produces:

2s
4s
6s
8s
Pros
Gentler than exponential.
Doesn't explode quickly.
Cons
Can still overload systems under heavy contention.
4. Exponential Backoff

The famous one.

1s
2s
4s
8s
16s
Formula
delay = base × 2^attempt

Most common in:

AWS
Google Cloud
OpenAI
Groq
Kubernetes
5. Exponential Backoff + Jitter

Industry standard.

Instead of:

4s
4s
4s
4s

for all clients:

3.7s
4.2s
4.8s
3.3s
Why?

Avoids the Thundering Herd Problem.

6. Retry-After Strategy

Server tells you exactly when to retry.

Example HTTP response:

429 Too Many Requests

Retry-After: 15

Meaning:

Don't retry for 15 seconds.

Your uploaded code already supports this idea:

_retry_after_seconds()

which reads the HTTP Retry-After header.

7. Hybrid Strategy

Many production systems combine:

delay =
max(
    exponential_backoff,
    retry_after_header
)

Your code is doing exactly this:

delay = max(exponential, retry_after)

inside _rate_limit_delay().

This is usually better than pure exponential backoff.

8. Fibonacci Backoff

Uses Fibonacci sequence.

1
1
2
3
5
8
13
21
Formula
F(n) = F(n-1) + F(n-2)
Pros

Growth is smoother.

Cons

Less common.

9. Random Retry

Pure randomness.

delay = random.uniform(1, 10)

Examples:

3.2s
7.9s
2.1s
5.4s

Mostly used when:

Large distributed clusters
Leader elections
Consensus protocols
10. Incremental Retry

Add a constant amount each time.

1s
3s
5s
7s
9s

Formula:

delay = initial + increment * attempt

A variation of linear backoff.

11. Adaptive Retry

System dynamically changes behavior based on load.

Example:

Low load      -> retry quickly
Medium load   -> retry slower
High load     -> retry much slower

Used by:

AWS SDKs
Modern cloud clients
Database drivers
12. Token Bucket Retry

Often paired with rate limiting.

Each retry consumes a token.

10 retry tokens available

Retry #1 -> token used
Retry #2 -> token used
...
No tokens left -> stop retrying

Prevents retry storms.

13. Circuit Breaker Pattern

Not technically a retry strategy, but closely related.

Instead of:

Fail
Retry
Fail
Retry
Fail
Retry

You do:

Fail many times

OPEN CIRCUIT

Stop calling service entirely

Wait:

30 seconds

Then:

Try one request

Success -> close circuit
Failure -> keep open

Popular libraries:

Hystrix
Resilience4j
Polly
14. Hedged Requests

Instead of retrying after failure:

Request A

Wait a little:

Request B

Take whichever finishes first.

Used heavily by:

Google
Amazon
Large search systems
