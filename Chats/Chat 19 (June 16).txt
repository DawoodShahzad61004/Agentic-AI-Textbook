7. Graph Definition
graph/workflow.py
from langgraph.graph import StateGraph, START, END

from state.graph_state import GraphState

from nodes.node_a import node_a
from nodes.node_b import node_b
from nodes.node_c import node_c
from nodes.node_d import node_d

from routers.routing import route_from_a


def build_graph():

    builder = StateGraph(GraphState)

    builder.add_node("A", node_a)
    builder.add_node("B", node_b)
    builder.add_node("C", node_c)
    builder.add_node("D", node_d)

    builder.add_edge(START, "A")

    builder.add_conditional_edges(
        "A",
        route_from_a,
        {
            "B": "B",
            "C": "C",
        },
    )

    builder.add_edge("B", "D")
    builder.add_edge("C", "D")

    builder.add_edge("D", END)

    return builder.compile()

consider this project's updated architecture, and give a plan on how to convert this LangChain app to LangGraph app. There should be no plotting, instead it should be designed as if its being designed from scratch using the concepts purely of LangGraph

I’ll treat this as a clean LangGraph design, not as “wrap the current loop in a graph.” The goal is to convert the current implicit phase machine into explicit state, nodes, edges, and retry paths.

Thought for 23s
LangGraph conversion plan

Your current app is already conceptually a graph. run_agent() has phases: RETRIEVE → COMPRESS → ANSWER → JUDGE → FINAL, with possible loop-back from JUDGE to RETRIEVE when the answer is insufficient . In LangGraph, do not preserve this as one big function. Split every phase into a node.

1. Define one central RAGState

Create a typed graph state like:

class RAGState(TypedDict):
    query: str
    messages: list
    tried_queries: set[str]
    failed_variants: list[str]

    document_chunks: list[dict]
    learned_qa_chunks: list[dict]
    compressed_document_chunks: list[dict]
    compressed_learned_qa_chunks: list[dict]

    draft_answer: str
    final_answer: str
    quality: str

    sources: list[dict]
    variants: list[dict]
    prior_thumbdowns: list[dict]

    total_retrievals: int
    iterations: int
    error: str | None

The important design rule: state replaces shared mutable dictionaries like agent_state. In the current code, retrieval, compression, messages, embeddings, and compress_done are stored in a mutable agent_state dictionary . In LangGraph, each node should receive state and return only the fields it updates.

2. Keep infrastructure as services, not graph nodes

These should stay as normal classes/functions injected into the graph:

EmbeddingManager
VectorStore
RAGRetriever
FeedbackStore
SelfLearner
LLM clients

Reason: these are dependencies, not workflow steps. For example, VectorStore initializes Chroma and stores document embeddings , while RAGRetriever already retrieves documents and learned QA separately . LangGraph should orchestrate them, not replace them.

3. Create these main nodes
load_feedback_context
generate_query_variants
retrieve_documents
validate_retrieval
accumulate_chunks
merge_similar_retrieval_chunks
decide_retrieve_or_compress
compress_learned_qa
compress_documents
build_compressed_context
draft_answer
judge_answer
final_answer
log_interaction
maybe_distill
return_no_context

This is the clean LangGraph version of the current architecture.

4. Separate document and learned-QA tracks

Keep the two-track design. Your retriever already returns:

{"documents": documents, "learned_qa": learned_qa}

and stores the last document chunks and learned-QA chunks separately . In LangGraph, preserve this separation all the way until final context formatting.

Graphically, think:

retrieve_documents
        ↓
validate documents  +  validate learned_qa
        ↓
accumulate documents + accumulate learned_qa
        ↓
compress documents  + compress learned_qa
        ↓
build precedence context

Do not mix learned QA with normal documents early. Learned QA should remain a high-priority track until final answer generation.

5. Convert tools into graph nodes

Your current retrieve_documents and compress_context are exposed as LLM tools . In the LangGraph design, they should become deterministic graph nodes.

Instead of asking the LLM to decide:

Should I call retrieve_documents?
Should I call compress_context?

the graph should decide:

Have we retrieved enough?
Have we hit MAX_TOTAL_RETRIEVALS?
Do we have chunks?
Should we compress now?

This is one of the biggest benefits. The workflow becomes controlled by code, not by tool-calling behavior.

6. Use conditional edges for control flow

Main graph:

START
  ↓
load_feedback_context
  ↓
generate_query_variants
  ↓
retrieve_documents
  ↓
validate_retrieval
  ↓
accumulate_chunks
  ↓
merge_similar_retrieval_chunks
  ↓
decide_retrieve_or_compress
      ├── more retrieval needed → generate_query_variants
      ├── no chunks → return_no_context
      └── enough context → compress_documents_and_learned_qa
  ↓
build_compressed_context
  ↓
draft_answer
  ↓
judge_answer
      ├── OK → final_answer
      ├── insufficient + budget left → generate_query_variants
      └── insufficient + no budget → final_answer_or_insufficient
  ↓
log_interaction
  ↓
maybe_distill
  ↓
END

This directly replaces your manual phase variable.

7. Make compression a subgraph

Your compression pipeline already has NAC, DC, and LBC stages, controlled by flags like ENABLE_NAC_COMPRESSION, ENABLE_DC_COMPRESSION, and ENABLE_LBC_COMPRESSION . In LangGraph, make this a reusable subgraph:

compression_subgraph:
    input chunks
      ↓
    maybe_nac
      ↓
    maybe_dc
      ↓
    maybe_lbc
      ↓
    output compressed chunks

Then call it twice:

compress_learned_qa → compression_subgraph
compress_documents  → compression_subgraph

This keeps the learned-QA and document tracks independent.

8. Make validators normal nodes

Your validators already exist for retrieval, merge, redundancy, and LBC safety . In LangGraph, do not hide them inside large helper functions. Use them as explicit quality gates:

retrieve_documents → validate_retrieval → keep/drop chunks
merge_chunks → validate_merge → retry merge or keep originals
dc_scan → validate_redundancy → remove only confirmed redundancy
lbc_compress → validate_lbc → accept/reject compression
draft_answer → judge_answer → final or retrieve again

This makes failure paths visible.

9. Use checkpointing where it actually helps

Use LangGraph checkpoints after expensive or failure-prone stages:

after query variant generation
after each retrieval round
after retrieval validation
after retrieval merge
after compression
after draft answer
after answer judge
after feedback logging
after distillation

The highest-value checkpoints are after retrieval and compression because those are expensive and involve LLM calls, vector search, validation, and chunk processing.

10. Migration order

Do it in this order:

1. Create RAGState.
2. Move current run_agent local variables into RAGState.
3. Extract retrieval into a retrieve_documents_node.
4. Extract retrieval validation into validate_retrieval_node.
5. Extract accumulation/merge into separate nodes.
6. Extract compression into a compression subgraph.
7. Extract draft, judge, and final answer into separate nodes.
8. Add conditional edges.
9. Add checkpointing.
10. Remove LLM tool-calling for retrieve/compress.
11. Keep CLI/batch runner as graph.invoke(query).
12. Add feedback and distillation nodes at the end.

The cleanest LangGraph version is not:

It should be:

The LLM should generate query variants, merge chunks, compress chunks, judge quality, and write answers. But the graph should control when each step happens. That is the main architectural improvement.

consider the config file. It has 18 switches (boolean constants). Should they be a part of the state? How can i know what to put in the state and what not? Answer briefly

Short rule:

Put something in LangGraph state only if it can change during execution or must be passed between nodes.

Do not put something in state if it is a configuration, dependency, or constant.

Your 18 config booleans

These should generally NOT be part of the state. They belong in configuration.

Examples:

ENABLE_NAC_COMPRESSION
ENABLE_DC_COMPRESSION
ENABLE_LBC_COMPRESSION
ENABLE_RETRIEVAL_VALIDATION
ENABLE_AUTO_DISTILLATION

These are architecture settings, not runtime data.

Instead:

graph = workflow.compile()

graph.invoke(
    initial_state,
    config={"configurable": {...}}
)

or inject them into nodes from a config object.

Good candidates for State

Things that evolve as the graph runs:

query
variants
retrieved_chunks
validated_chunks
compressed_chunks
draft_answer
judge_result
retrieval_count
iteration_count
final_answer
error

These are produced by one node and consumed by another.

Bad candidates for State

Things that don't change during a run:

MAX_TOTAL_RETRIEVALS
MAX_ITERATIONS
RETRIEVAL_TOP_K
RETRIEVAL_TOP_L
COMPRESS_MIN_TOKENS

ENABLE_*

These are configuration values.

Also avoid putting service objects into state:

EmbeddingManager
VectorStore
RAGRetriever
LLM
FeedbackStore

These are dependencies, not workflow data. They should be injected into nodes. The current architecture already treats them as infrastructure services rather than query-specific data.

Simple test

Ask:

"If I checkpoint this graph and resume tomorrow, does this value represent the current progress of this specific run?"

Yes → State
No, it's a setting or dependency → Config / injected service

For your project, I'd expect <20 fields in state but almost none of the constants from config.py to be there.
