Here are the bottlenecks in both apps:

app (simple RAG pipeline)
Embedding generation (CPU) — EmbeddingManager runs SentenceTransformer locally on CPU if no CUDA. No caching; every query re-encodes. (embedding_manager.py:32)

Synchronous ChromaDB query — Single blocking .query() call with no connection pooling or async path. (retriever.py:165)

LLM call latency + rate-limit sleep — llm_invoke wraps Groq with time.sleep(delay) on rate-limit retries, blocking the calling thread for potentially tens of seconds. (llm_caller.py:348)

Compression pipeline (NAC → DC → LBC) — O(N) LLM calls — Each stage fires one LLM call per chunk/window sequentially. With validation enabled, every call gets a second judge LLM call. For K chunks: up to 3K LLM calls + 3K judge calls before the answer. (context_compression.py:687-692)

Re-embedding after merge — After NAC merges chunks, a fresh embedding is generated for the merged content synchronously. (context_compression.py:133)

app_workflow (LangGraph pipeline)
All of the above, plus:

Query variant fan-out — An LLM call generates N variants before retrieval begins; then N separate embedding+retrieval calls run (parallelized as LangGraph sends, but each still waits on Groq). (graph.py:130-134)

Extra LLM hops in answer pipeline — generate_draft → check_answer_quality → generate_answer → auto_distillation adds 3–4 sequential LLM calls after compression. (graph.py:190-207)

Dual compression tracks still sequential within each track — Documents and Learned QA run NAC→DC→LBC in parallel with each other, but each track's pipeline is fully sequential internally.

LangGraph state serialization overhead — Every node boundary serializes/deserializes the full GraphState, which grows as chunks accumulate through the pipeline.

Biggest impact bottlenecks ranked: LLM call count in compression (NAC+DC+LBC with judges) > rate-limit sleeps > CPU embedding on each query variant > synchronous ChromaDB calls.

Answer briefly:
Explain the implementation of ThreadPoolExecutor so far in the session
Every blocking call that could stall the pipeline indefinitely — llm.invoke(), collection.query(), and model.encode() — was wrapped with the same pattern:


with concurrent.futures.ThreadPoolExecutor(max_workers=1) as _executor:
    _future = _executor.submit(blocking_call, *args, **kwargs)
    try:
        result = _future.result(timeout=TIMEOUT_SECONDS)
    except concurrent.futures.TimeoutError:
        raise CustomTimeoutError(...)
Why it works: The blocking call runs on a background thread. The calling thread blocks on _future.result(timeout=N) — if the result doesn't arrive within N seconds, concurrent.futures.TimeoutError is raised on the calling thread, which we immediately convert to a domain-specific exception (LLMResponseTimeoutError, RetrievalTimeoutError, EmbeddingEncodingTimeoutError).

Key design choice — re-raise vs. return:

LLM and retrieval timeouts return a safe fallback (LLMResult(ok=False) / []) so the graph node continues without crashing.
Embedding timeout re-raises, because there's no meaningful fallback for a missing embedding — the caller must decide how to handle it.
Caveat: ThreadPoolExecutor enforces the timeout on the waiting side only. The background thread running the blocked call continues until it finishes or the process exits — Python has no safe way to hard-kill a thread. This is acceptable here because Groq/ChromaDB/SentenceTransformer calls will eventually self-terminate.
