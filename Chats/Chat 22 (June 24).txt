Your problem is shared quota contention.

Groq rate limits are applied at the organization level, not independently per API request/user. Limits include RPM, RPD, TPM, TPD, and sometimes separate input/output TPM limits. Multiple parallel requests are independently retrying against the same shared Groq token bucket, without global coordination.

Exponential backoff helps only after failure. It does not prevent requests from colliding again.

1. Add a global LLM rate limiter / token scheduler

API Request 1 ┐

API Request 3 ┘

reset_tokens_time
retry_after
estimated_input_tokens
reserved_output_tokens

Here's exactly what changed and why each piece is correct.

FIFO gate (_gate_acquire / _gate_release)
Replaces threading.Semaphore. A queue.Queue holds threading.Event objects — one per waiting thread. When a thread calls _gate_acquire, if no thread is currently active it takes the gate immediately. Otherwise it creates its own Event, puts it in the queue, and blocks on event.wait(). When _gate_release is called, it does queue.get_nowait() and calls event.set() on the oldest entry — waking exactly the thread that has been waiting the longest. _llm_active stays True during the handoff so there's never a gap where two threads could both see the gate as free.

Global reset timestamp (_token_reset_until)
A single float (monotonic epoch) protected by its own lock. When any thread gets a 429, _rate_limit_delay calls _update_token_reset(delay), which writes time.monotonic() + delay into it — only ever moving it forward, never backward. Then, every thread that acquires the gate calls _wait_for_token_window() before touching Groq. It reads the deadline, computes remaining = deadline - time.monotonic(), and sleeps only the delta still outstanding. If the window has already passed, remaining is negative and the sleep is skipped entirely.

The practical effect on your scenario:

Thread A: gets response, window now exhausted.
Thread B: acquires gate → _wait_for_token_window() → remaining=0 → calls Groq → gets 429
          → _rate_limit_delay writes deadline (e.g. now+7s) into _token_reset_until
          → releases gate → re-enters queue at the back
Thread C: acquires gate → _wait_for_token_window() → remaining=6.3s → sleeps 6.3s
          → calls Groq → gets response  ← no wasted 429
Thread B: acquires gate → _wait_for_token_window() → remaining=0 (window passed)
          → calls Groq → gets response
Jitter and random removed
Jitter's sole purpose was to de-synchronize threads so they didn't re-collide after sleeping. With strict FIFO ordering there is no collision possible — only one thread can ever be calling Groq at a time — so jitter is pure unnecessary latency. Both random and LLM_RATE_LIMIT_BACKOFF_JITTER_SECONDS are removed. Note that LLM_RATE_LIMIT_BACKOFF_JITTER_SECONDS can stay in your config.py untouched — it's just no longer imported here.

But right now a retrying thread calls _gate_acquire again at the top of the loop, which puts its new Event at the tail of the queue. Any thread that arrived while Thread A was being processed jumps ahead of it.

2. The gap you're asking about. When Thread A re-enters the queue, it does so immediately after getting the 429 — no sleep, no waiting. So the queue looks like:

[Thread A (retry)] [Thread B] [Thread C] ...
Thread B acquires the gate, calls _wait_for_token_window(), sleeps the reset delta, calls Groq successfully, then releases. Thread A is next — by this point the window has already been waited out by Thread B, so _wait_for_token_window() returns immediately and Thread A calls Groq right away. So in this specific case, no, there's no gap for Thread A specifically — it benefits from Thread B having already waited.

But the real problem is the ordering one: Thread A re-enters at the back. If Threads C, D, E arrived while Thread A was being processed, they all go ahead of Thread A's retry. That violates your FIFO-for-retries requirement.

The fix is to give retrying threads a priority slot — they should skip the queue and go to the front, not the back. The cleanest way to do this is a two-level structure: a retry-priority deque at the front, and the normal arrival queue behind it. _gate_release checks the priority deque first before the regular queue.

Here's a precise account of every structural decision.

Gate: _gate_acquire / _gate_release_to_next
The FIFO queue structure is unchanged. What changed is when _gate_release_to_next is called. Previously it was in a finally block — meaning it fired after every attempt including ones that got 429. Now it is called in exactly two places: after _apply_cooldown on a terminal success/failure, and in the LLMRateLimitAbortError path. A thread that gets a 429 and has more attempts remaining simply loops back to _wait_for_token_window without ever releasing — it stays at the front for the entire duration of its retries.

llm_invoke structure
_gate_acquire is called once, before the retry loop. The loop itself never re-acquires. This is the key structural change — the gate and the retry loop are now at different levels of nesting, which is what makes "stay at the front" possible without a separate priority queue.

_gate_acquire()          ← once, before the loop
for attempt in 1..N:
    _wait_for_token_window()
    result = _invoke_once()
    if 429 and attempts remain:
        _rate_limit_delay()  ← writes deadline into _token_reset_until
        continue             ← loop back, still holding the gate
    _apply_cooldown()        ← sleep floor while still holding gate
    _gate_release_to_next()  ← now hand off
    return result
_apply_cooldown
Called while the gate is still held — the cooldown sleep happens before the next thread is signalled. This is what makes it a true floor between consecutive calls rather than a suggestion.

The logic reads x-ratelimit-remaining-tokens, x-ratelimit-limit-tokens, and x-ratelimit-reset-tokens from the successful response headers to compute token_base. The current _cooldown_floor is then adjusted:

had_429=True → double (or use token_base * 2 if floor was zero)
clean_streak >= 3 → halve, reset streak
Result is clamped to [_COOLDOWN_MIN=0, _COOLDOWN_MAX=30]
Final floor is max(adjusted, token_base) — the token state is always a hard floor regardless of the streak arithmetic
If the queue is empty, the floor and streak both reset to zero — no cooldown enforced when there's no contention.

One thing to watch
_parse_token_headers reads from result.response.response_metadata["headers"] — the path LangChain's ChatGroq uses to expose raw response headers. If your LangChain version stores them differently, the fallback path (_raw_response.headers) covers the other common location. If neither path yields headers, token_base falls back to 0.0 and the cooldown arithmetic still works correctly — it just won't have a token-state floor for that call, relying only on the doubling/halving history.
