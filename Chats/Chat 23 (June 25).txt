The core problem: a shared budget
Groq gives you a token budget — think of it like a prepaid phone balance. Every API call you make spends some of that balance. Groq refills it on a fixed timer (roughly every 60 seconds). If you spend it all before the timer resets, Groq says "stop, wait" — that's the 429 error (HTTP's way of saying "Too Many Requests").
Now your server is handling multiple user requests at the same time, and each one is making LLM calls. They're all drawing from the same shared balance simultaneously. That's the problem.

The FIFO gate: taking turns
To prevent everyone from hitting Groq at once, the code makes all threads line up and take turns — like a single checkout lane. Only one thread gets to call Groq at a time. This is the FIFO gate (First In, First Out — whoever waited longest goes next).

What a 429 means in practice
When a thread gets a 429, Groq also tells you when the budget will refill — it includes a timestamp in the response headers. One of those headers is x-ratelimit-reset-tokens, and it says something like "51.45s" — meaning: the token budget resets in 51.45 seconds from now.
The code stores that deadline globally as _token_reset_until. Before any thread is allowed to call Groq, it checks: has that deadline passed yet? If not, it sleeps until it has. This is _wait_for_token_window.
