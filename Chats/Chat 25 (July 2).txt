The prompt constrains source, not confidence or scope. The final-answer prompt in generate_answer.py is:

Question: {user_input}

Answer:
"Use only the provided context" restricts where facts may come from, but says nothing about how much to say relative to how much evidence exists. There's no instruction to hedge, to state when coverage is partial, to refuse, or to scale answer length to evidence volume. So the model does what LLMs default to: it produces a fluent, complete-sounding answer regardless of whether it's standing on ten chunks or one. One chunk mentioning "safety features" is enough of a seed for the model to pattern-complete a plausible full list — and nothing in the prompt discourages that. The prompt treats one chunk and ten chunks identically.

The draft path often bypasses even that prompt. Note the branch at the top of generate_answer: if state.get("draft") exists, it's used verbatim (answer = draft) and the grounding-focused prompt above never runs. The one gate that could catch this is advisory, not blocking. check_answer_quality runs the GROUNDING_PROMPT judge, which returns OK or INSUFFICIENT. But look at how the verdict is used:

In route_after_quality_check: an INSUFFICIENT verdict routes to retry only if ENABLE_SUB_QUERY_GENERATION is on and retry_count < LLM_RESPONSE_RETRY_LIMIT. Once the retry budget is spent (or sub-query generation is off), the code falls through to return "generate_answer" — explicitly commented "best-effort draft." The fabricated answer ships anyway.

What the grounding judge actually checks. GROUNDING_PROMPT gives the judge exactly two criteria:

1. Relevance — does the answer address what the user actually asked?
2. Grounding — are the key claims in the answer traceable to the retrieved chunks (not invented)?

The answer-quality judge has none of this rigor, despite guarding the thing the user actually sees.

Why "key claims traceable" lets a mostly-fabricated answer through. The word "key" does real damage here. It gives the judge implicit permission to sample-check rather than exhaustively verify. A 200-word answer built from one true chunk (e.g. "the vehicle includes automatic emergency braking") plus four invented ones (lane departure warning, blind-spot monitoring, etc.) will very plausibly get an OK:

The judge reads the answer, sees the one true, well-grounded claim, confirms it's traceable, and — because the instruction only asks about "key claims" rather than all claims — has no explicit mandate to check every remaining sentence individually.

The judge also has no per-claim output field to force it to enumerate claims one by one. Free-text single-sentence verdicts don't require that discipline; a JSON schema with a fabricated_claims: [] array does, because the model has to actually populate or empty that list.

No completeness bar at all. Relevance and per-claim traceability are orthogonal to completeness/calibration; the prompt has no third axis for "does the answer's scope match the evidence's scope," which is precisely the failure this issue is about.

No visibility into evidence volume. Root cause: combine_tracks has two incoming edges, and LangGraph doesn't always merge them into one call
graph.py:167-179 wires two parallel tracks into combine_tracks:


validate_LBC_documents  → combine_tracks
validate_LBC_learned_qa → combine_tracks
LangGraph only fuses two predecessors into a single downstream call when they finish in the same superstep. Here they can't, structurally: the documents track is NAC → DC → LBC (3 stages), the learned_qa track is DC → LBC (2 stages, no NAC). Different depths → different supersteps → combine_tracks fires once per track as it finishes, not once total.

The log proves it — same request, combine_tracks fires twice back-to-back:


14:10:44  [COMBINE_TRACKS] learned_qa=4  documents=0  combined=4   ← learned_qa track alone
14:10:46  [COMBINE_TRACKS] learned_qa=4  documents=2  combined=6   ← now documents track has landed
combine_tracks.py itself has no guard — it just reads whatever is currently in compressed_learned_qa_chunks/compressed_document_chunks and returns. It trusts the graph to call it once with both ready; the graph doesn't honor that.

Answers to your first three questions, directly:

Why so many drafts/answers — every combine_tracks firing routes through route_after_combine → generate_draft (routes.py:64-77), since compressed_docs is non-empty as soon as either track has results. Two combine_tracks firings per cycle → two generate_draft calls per cycle, compounded further by full-cycle retries (see below).
Why drafts happen before all compression finishes — this is that same bug: the first combine_tracks/generate_draft fires as soon as the faster track (learned_qa) finishes, while the documents track is still mid-compression. That first draft is generated from a partial context (documents=0).
Does combine_tracks wait for both parallel flows? — No. It's declared as a fan-in point but doesn't actually behave as a barrier, because the two branches have unequal step-depth. It fires once per completing branch.

Does "strong" always mean bigger?

No.

Parameter count and capability are correlated, but they are not the same.

Briefly explain "online in-context learning over the harness state"

Let's break it into pieces.

Online

The agent learns while it is still performing the task, not after it finishes.

Instead of:

Play
↓
Finish
↓
Analyze mistakes
↓
Improve
↓
Restart

it does:

Play
↓
Analyze recent actions
↓
Improve
↓
Keep playing
↓
Repeat

No restart is needed.

In-context learning

The model isn't changing its neural network weights (it's not retraining).

Instead, it changes the information available in its context window, such as:

Updated system prompt
New memory entries
New skills
New sub-agents

The model behaves differently because its context has improved, not because the model itself has been retrained.

Harness state

The paper defines the harness state as:

Harness State H =
{
    Prompt,
    Sub-agents,
    Skills,
    Memory
}

These four components together represent everything surrounding the LLM that guides its behavior.

Putting it all together

"Online in-context learning over the harness state" means the agent continuously improves its prompt, memory, skills, and sub-agents during execution, causing it to behave better without changing the model's weights or restarting the task.

For example:

The agent gets stuck walking in circles.
The Refiner notices this.
It adds a new navigation rule to memory and creates a navigate_to_goal() skill.
On the very next steps, the agent sees these updates in its context and starts using them.

The LLM itself hasn't changed—only the harness state it reads before making decisions has changed. That is the essence of online in-context learning over the harness state.
