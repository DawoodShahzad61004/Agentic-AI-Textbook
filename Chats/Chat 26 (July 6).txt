This diagram shows one training iteration of SEAL’s outer RL loop. The main idea is:

The model tries multiple ways of teaching itself, tests which ways actually help, and then learns to generate better self-teaching strategies in the future.

Here is the flow:

1. Ctx (Context) → LM θₜ

The model receives some context/input data. For example, this could be a passage containing new information.

LM = Language Model
θ (theta) = the model's parameters/weights
t = the current training iteration

So θₜ basically means:

the current version of the model

2. The model generates multiple SEs

The model generates several possible:

SE = Self-Edit

For example:

SE₁, SE₂, SE₃

A self-edit is essentially the model proposing:

"Here is how I should learn from this new information."

Depending on the task, this might mean generating better training data or choosing training settings.

3. Each Self-Edit creates a temporarily updated model

Each SE is used to fine-tune a separate copy of the current model:

SE₁ → updated model θₜ′

SE₂ → updated model θₜ†

SE₃ → updated model θₜ#

Don't worry about the different symbols (′, †, #). They simply mean:

three differently updated versions of the same original model.

So conceptually:

Current Model + SE₁ → Updated Model Version 1

Current Model + SE₂ → Updated Model Version 2

Current Model + SE₃ → Updated Model Version 3

4. Test all three updated models

Each updated model is given a test.

In the diagram:

Version 1 → correct answer ✓
Version 2 → correct answer ✓
Version 3 → wrong answer ✗

This tells us which self-edits actually helped the model improve.

5. Create RL training data

The results become:

State → Action → Reward

In this diagram:

State = Ctx + θₜ → the context and current model
Action = SE → the self-edit generated by the model
Reward = ✓ / ✗ → whether that self-edit successfully improved performance

6. Update the original model

Finally, the successful self-edits are used to train the original model:

θₜ → θₜ₊₁

Meaning:

Current Model → Improved Model

The improved model should now become better at generating useful self-edits in the next iteration.

The whole diagram in simple words

Give the model some information → let it generate multiple ways of teaching itself → temporarily train separate copies using each method → test those copies → identify which self-teaching methods worked → train the original model to generate more successful self-edits in the future.

The most important thing to understand is that the outer RL loop is not directly teaching the model to answer questions better. It is teaching the model:

how to generate better methods (Self-Edits) for updating and teaching itself.

That is why this is closely related to meta-learning: "learning how to learn."

These three concepts are closely connected, and the terminology can be confusing because SFT is a type of fine-tuning, while LoRA is a technique for making that fine-tuning cheaper.

The relationship is:

Fine-tuning = broad process
SFT = a type of fine-tuning
LoRA = an efficient technique used to perform fine-tuning

1. What is Fine-Tuning?

An LLM has billions of numerical parameters/weights (θ). During initial training, the model learns by repeatedly:

Training Data → Model → Prediction → Calculate Error → Update Weights

After this initial training, suppose we want the model to learn something new.

For example:

Input:  What is the capital of Pakistan?
Target: Islamabad

The model processes the input and generates an answer. We compare its prediction against the desired answer and calculate a loss:

Loss = a numerical measurement of how wrong the model's predictions were.

Then an optimization algorithm uses the loss to determine how the model's parameters should change:

Training Data
      ↓
     Model θ
      ↓
   Prediction
      ↓
Compare with Target
      ↓
Calculate Loss
      ↓
Backpropagation
      ↓
Optimizer updates parameters
      ↓
Updated Model θ′

This process is repeated over many training examples.

That is the basic idea of fine-tuning.

2. What is SFT?

SFT = Supervised Fine-Tuning.

The important word is supervised.

It means that we provide the model with examples of the behavior/output we want it to learn.

For example:

Input:
What is the capital of Pakistan?

Desired Output:
Islamabad

Another example:

Input:
Explain gravity simply.

Desired Output:
Gravity is the force that pulls objects toward each other.

We have:

Input → Desired Output

The desired output provides the supervision.

The model is trained to become more likely to generate that desired output.

How is SFT actually done?

At a simplified level:

Step 1: Give the model training data

Suppose:

Question: What is the capital of Pakistan?
Answer: Islamabad
Step 2: Convert text into tokens

Conceptually:

"What is the capital of Pakistan? Islamabad"

↓

[Token 1, Token 2, Token 3, ...]
Step 3: The model predicts the next tokens

LLMs fundamentally perform:

Next-token prediction.

For example:

What → is
What is → the
What is the → capital
...
capital of Pakistan? → Islamabad
Step 4: Calculate loss

The model's predictions are compared against the actual desired tokens.

If the model assigns low probability to the correct tokens:

High Loss

If it assigns high probability to the correct tokens:

Low Loss

Step 5: Backpropagation

The loss is propagated backward through the neural network to calculate:

Which parameters contributed to the error, and in which direction should they change?

This is called:

Backpropagation

Step 6: Optimizer updates parameters

An optimizer, such as Adam, uses the calculated gradients to update the parameters:

θ → θ′

The process repeats:

Forward Pass
     ↓
Prediction
     ↓
Calculate Loss
     ↓
Backpropagation
     ↓
Calculate Gradients
     ↓
Optimizer
     ↓
Update Parameters

That is essentially SFT.

3. The problem with normal/full fine-tuning

Suppose an LLM has:

7 billion parameters.

In full fine-tuning, you may update all 7 billion parameters.

Conceptually:

Original Model

θ₁
θ₂
θ₃
θ₄
...
θ₇ billion

↓

Fine-Tuning

↓

All parameters can change

This is computationally expensive.

You need large amounts of:

GPU memory;
compute;
storage.

This is where LoRA comes in.

4. What is LoRA?

LoRA = Low-Rank Adaptation.

The main idea is:

Freeze the original model's parameters and train a much smaller number of additional parameters instead.

So instead of:

7 Billion Original Parameters
          ↓
     Update all of them

LoRA does:

7 Billion Original Parameters
          ↓
        FREEZE
    (don't change them)

          +

Small Trainable LoRA Parameters
          ↓
     Update only these

The result is:

Much cheaper fine-tuning.

A simple analogy

Imagine the original LLM is a huge 10,000-page textbook.

Full Fine-Tuning

You modify and rewrite the original textbook itself.

Original Textbook
       ↓
Rewrite thousands of pages
       ↓
Updated Textbook

This is expensive.

LoRA Fine-Tuning

Instead, you keep the original textbook unchanged and add a relatively small set of specialized notes that modify how certain information is interpreted.

Original Textbook (Frozen)
           +
Small Set of Trainable Notes
           ↓
Adapted Knowledge

Not technically exact, but this is a useful mental model.

5. Slightly more technical explanation of LoRA

Inside an LLM, there are large matrices of parameters.

Suppose one matrix is:

W

Normally, during full fine-tuning:

W → Update W

LoRA freezes W.

Instead, it learns a small change:

ΔW

So the effective parameter matrix becomes:

W + ΔW

But directly learning ΔW could still be expensive.

Therefore, LoRA represents it using two much smaller matrices:

ΔW = BA

Therefore:

W′ = W + BA

You don't need to deeply understand the matrix mathematics yet.

The important point is:

Original large matrix W remains frozen.

Only:

Small matrices A and B are trained.

6. So what does "SFT using LoRA" mean?

This is the most important part for understanding the SEAL paper.

Remember:

SFT tells us what training process/objective we are using.

LoRA tells us which parameters we efficiently update.

Therefore:

SFT using LoRA = Perform supervised fine-tuning, but instead of modifying all original model parameters, freeze them and train small LoRA adapter parameters.

The process becomes:

Training Data
      ↓
Model + LoRA
      ↓
Prediction
      ↓
Calculate SFT Loss
      ↓
Backpropagation
      ↓
Calculate Gradients
      ↓
Optimizer
      ↓
Update ONLY LoRA Parameters
      ↓
Adapted Model
7. Now connect this to SEAL

This is where everything should come together.

Suppose the context is:

Passage about the Apollo Program

The current model:

LM θₜ

generates a Self-Edit:

SE₁:

1. Jerome Wiesner was Kennedy's science advisor.
2. Wiesner opposed manned spacecraft flights.
3. The Apollo program faced internal opposition.

These generated sentences become:

Supervised fine-tuning data.

Now SEAL performs:

θ′ₜ ← SFT(θₜ, SE₁)

But in practice, it uses LoRA to make this efficient.

So conceptually:

Original Model θₜ
       +
Self-Edit SE₁ as Training Data
       ↓
Supervised Fine-Tuning
       ↓
Using LoRA
       ↓
Temporary Adapted Model θ′ₜ

More precisely:

              SE₁
               ↓
         Training Data
               ↓

    Original Model θₜ
      [FROZEN WEIGHTS]

               +

    LoRA Adapter Parameters
       [TRAINABLE]

               ↓

        Forward Pass

               ↓

        Calculate Loss

               ↓

       Backpropagation

               ↓

Update LoRA Parameters Only

               ↓

   Adapted Temporary Model θ′ₜ

Then SEAL asks the temporary model questions:

Who was Kennedy's science advisor?

↓

Jerome Wiesner ✓

This tells SEAL:

The Self-Edit successfully helped the model learn.

8. One subtle but important point about SEAL

You might now wonder:

"Wait, earlier we said θₜ → θ′ₜ, but if LoRA freezes θₜ, aren't the original parameters unchanged?"

Yes. This is an excellent distinction.

Mathematically, the paper simplifies the notation and calls the adapted model's parameters:

θ′

But with LoRA, conceptually the adapted model is:

Original Frozen Parameters θ

+

Trained LoRA Adapter Parameters

Together, these behave as the adapted model LMθ′.

So when reading:

θ′ ← SFT(θ, SE)

you can mentally understand it as:

Take model θ, attach/train LoRA adapters using the Self-Edit, and obtain an adapted model θ′.

The final relationship to remember
                    FINE-TUNING
                         │
              ┌──────────┴──────────┐
              │                     │
             SFT                  Other Types
      (Supervised Fine-Tuning)    of Fine-Tuning
              │
              │
        Can be performed
              │
              ▼
            LoRA
    (efficiently train only
    a small set of parameters)

Or, even simpler:

Fine-tuning: The general process of adapting a pretrained model.

SFT: Fine-tuning by training the model on desired examples/data using supervised learning.

LoRA: A parameter-efficient way to perform that fine-tuning without updating all the original model weights.

And specifically in the SEAL knowledge incorporation inner loop:

Self-Edit generates synthetic data → SFT defines how the model learns from that data → LoRA makes that SFT computationally cheaper → temporary adapted model is tested → result becomes the reward for the Self-Edit.

0.00001

Here, 0.00001 is the learning rate.

It can also be written as:

1e-5 = 0.00001

The learning rate controls how large a change the optimizer makes to the trainable parameters during each training step.

Conceptually:

Large learning rate → bigger parameter updates

Small learning rate → smaller, more careful parameter updates

So, in the SEAL few-shot example:

learning rate: 1e-05

means that during SFT/LoRA fine-tuning, the optimizer updates the trainable LoRA parameters using a relatively small step size of 0.00001.

A simple analogy: if training is like walking downhill toward the lowest error (loss), the learning rate is your step size. Too large, and you may overshoot the best point; too small, and learning can be very slow.

This section discusses three main limitations of SEAL, followed by the authors' vision for future applications.

1. Catastrophic Forgetting

This is the most important limitation.

Catastrophic forgetting means:

When a model learns new information, the weight updates may cause it to forget information it learned previously.

For example:

Learn Passage 1
      ↓
Model knows Passage 1

Learn Passage 2
      ↓
Model knows Passage 2
but becomes worse at Passage 1

Learn Passage 3
      ↓
Model knows Passage 3
but becomes worse at Passages 1 and 2

Earlier SEAL experiments mostly tested self-edits individually/in isolation:

Original Model → Self-Edit → Updated Model → Test

But continual learning requires:

Model
 ↓
Learn Passage 1
 ↓
Learn Passage 2
 ↓
Learn Passage 3
 ↓
Learn Passage 4
 ↓
...

while still remembering everything learned previously.

The researchers therefore conducted an experiment:

Learn Passage 1 → Test Passage 1

Learn Passage 2 → Test Passages 1 and 2

Learn Passage 3 → Test Passages 1, 2 and 3

Learn Passage 4 → Test Passages 1, 2, 3 and 4

They discovered that performance on earlier passages gradually declined as more self-edits were applied.

So SEAL can repeatedly learn new information, but:

It does not yet have a strong mechanism for preventing new weight updates from damaging previously learned knowledge.

The authors suggest possible future solutions, such as reward shaping: instead of rewarding a self-edit only for learning new information, the reward could also penalize it for forgetting old information.

Conceptually:

Reward =
    Improvement on New Knowledge
              -
    Damage to Old Knowledge
2. Computational Overhead

The second limitation is that SEAL is computationally expensive.

Remember the normal RL flow:

Generate Output
      ↓
Check Output
      ↓
Calculate Reward

Checking the output might be relatively cheap.

SEAL's flow is much heavier:

Generate Self-Edit
      ↓
Create/Adapt Model
      ↓
Fine-Tune Model
      ↓
Run Model on Tests
      ↓
Evaluate Answers
      ↓
Calculate Reward

And remember, SEAL generates multiple candidate Self-Edits.

For example:

                SE₁ → Fine-tune Model → Test
               /
Current Model → SE₂ → Fine-tune Model → Test
               \
                SE₃ → Fine-tune Model → Test

Every candidate requires:

fine-tuning + inference/evaluation

The authors report that evaluating each Self-Edit takes approximately 30–45 seconds.

So if you generate hundreds or thousands of Self-Edits, the computational cost becomes huge.

This is a major limitation for scaling SEAL to very large models and datasets.

3. Context-Dependent Evaluation

This limitation concerns how SEAL calculates rewards.

Currently, every context C needs a corresponding evaluation task τ.

Remember:

(C, τ)

where:

C = Information to learn

τ = Test used to determine whether learning occurred

Knowledge Incorporation
C = Passage

τ = Questions + Correct Answers
Few-Shot Learning
C = Few-Shot Examples

τ = Held-Out Input + Correct Output

The problem is:

What happens if you have information but no test questions or correct answers?

Suppose you give SEAL:

10 million documents

You might not have:

Questions + Correct Answers

for every document.

Then how do you determine:

"Did this Self-Edit actually improve the model?"

Without τ, calculating the RL reward becomes difficult.

Therefore, the current SEAL implementation doesn't easily scale to:

large unlabeled datasets/corpora.

Proposed Solution

The authors suggest letting the model generate both:

Self-Edit
+
Evaluation Questions

For example:

                    ┌→ Generate Self-Edit
Passage → Model ────┤
                    └→ Generate Test Questions

Then:

Self-Edit
    ↓
Fine-Tune Model
    ↓
Ask Generated Questions
    ↓
Evaluate
    ↓
Reward

This could allow SEAL to learn from datasets that don't already contain human-created questions and answers.

Discussion and Conclusion

Now the authors move from limitations to their broader vision.

1. The "Data Wall"

Modern LLMs are trained on enormous amounts of human-generated internet data.

The problem is:

Eventually, we may run out of high-quality human-generated training data.

The paper calls this the:

Data Wall

Therefore, future improvements may increasingly depend on:

Synthetic Data Generation

Instead of:

Humans Create Data
        ↓
Train Model

we could have:

External Information
        ↓
Model Generates Useful Synthetic Data
        ↓
Model Trains on Synthetic Data
        ↓
Model Improves

SEAL contributes toward this direction because it doesn't merely generate synthetic data.

It learns:

What kind of synthetic data is actually useful for improving the model.

2. Future SEAL Synthetic-Data Generator

The authors imagine training a specialized model whose job is:

Generate extremely useful training data for other models.

Conceptually:

New Information
       ↓
SEAL Synthetic-Data Generator
       ↓
High-Quality Synthetic Training Data
       ↓
Train Future LLM

This is similar to the Teacher-Student architecture we discussed earlier.

3. LLMs Learning from Academic Papers

The authors give an interesting future possibility.

Imagine giving an LLM an academic paper.

Currently:

Academic Paper → Put in Context → Ask Questions

The model hasn't necessarily permanently learned the paper.

The authors imagine:

Academic Paper
      ↓
LLM reads it
      ↓
Generates explanations
      +
implications
      +
rewrites
      +
other useful synthetic data
      ↓
Fine-Tunes Itself
      ↓
Knowledge becomes internalized

So the model would figure out:

"How should I restructure this paper so that I can effectively learn its information?"

4. SEAL + Chain-of-Thought Reasoning

Modern reasoning models use RL to improve their reasoning processes.

For example:

Problem
   ↓
Reasoning / Chain-of-Thought
   ↓
Answer

SEAL focuses on something different:

New Information
   ↓
Generate Self-Edit
   ↓
Update Weights
   ↓
Improved Model

The authors suggest combining both.

For example:

Model starts reasoning
        ↓
Realizes it needs adaptation
        ↓
Generates Self-Edit
        ↓
Updates its weights
        ↓
Continues reasoning

Or:

Model completes reasoning
        ↓
Identifies useful knowledge
        ↓
Generates Self-Edit
        ↓
Updates its weights
        ↓
Remembers learning for future tasks

So:

Chain-of-Thought improves the current reasoning trajectory.

SEAL could internalize useful learning into the model's parameters for future tasks.

5. SEAL for Agentic Systems

This is probably the most relevant part to your current Agentic AI learning.

Imagine an AI agent operating for months.

It:

Interacts with Environment
        ↓
Performs Tasks
        ↓
Makes Mistakes
        ↓
Receives New Information
        ↓
Gains Experience

The problem with current agents is that the underlying LLM is generally static.

The agent may store experiences in:

memory;
databases;
vector stores;
context.

But the model's actual weights don't continuously improve from these experiences.

The authors imagine:

Agent Interaction
        ↓
Experience / New Information
        ↓
Generate Self-Edit
        ↓
Fine-Tune Model
        ↓
Agent's Model Improves
        ↓
Future Interactions
        ↓
More Experience
        ↓
More Self-Edits
        ↓
Further Improvement

This could produce:

Agents that continually adapt based on their interactions with the environment.

The three limitations in one view
Limitation	Problem
Catastrophic Forgetting	Learning new information damages previously learned knowledge
Computational Overhead	Every Self-Edit requires model fine-tuning and evaluation
Context-Dependent Evaluation	SEAL currently needs tests/ground-truth answers to calculate rewards

The biggest overall takeaway from the conclusion is:

Current LLMs are mostly static after training. SEAL explores a future where models can receive new information, determine how they should learn from it, update their own weights, and continually improve over time.

And this also reveals an important connection to the Continual Harness paper you studied earlier:

Continual Harness improves the external system around the model—prompts, tools, memory, strategies, etc.—while SEAL attempts to improve/adapt the model's internal weights.

That distinction—continually adapting the harness vs. continually adapting the model itself—is a very useful connection between the two papers.

Input context is small

Output explosion is the real danger
DC is asking the model to scan redundancy and return structured output. The model may over-generate huge JSON/list output, causing slow generation, memory pressure, or server timeout.
NAC and LBC are mostly fine
NAC calls finish in 3–8 seconds. LBC calls mostly finish in 2–9 seconds. DC is the abnormal one.

Main fix: reduce DC output risk. Set a real max_tokens/num_predict limit on the local server call, maybe 512 or 768 for DC, and make the DC prompt stricter: “return at most N groups, at most N sentences, JSON only, no explanations.”
