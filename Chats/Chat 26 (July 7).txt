## 1. The `VLM` class (`utils/agent_infrastructure/vlm_backends.py:2567-2680`)

`VLM` is a thin dispatcher, not an abstract class itself. It holds a `BACKENDS` dict (line 2570) mapping `"openai"→OpenAIBackend`, `"anthropic"→AnthropicBackend`, `"openrouter"→OpenRouterBackend`, `"gemini"→GeminiBackend`, `"vertex"→VertexBackend`. All backends inherit from the ABC `VLMBackend` (line 54), which declares two abstract methods: `get_query(img, text, module_name)` and `get_text_query(text, module_name)` (lines 58-70).

`VLM.__init__` (2578) picks a backend class (auto-detecting from the model name via `_auto_detect_backend`, 2618, if `backend="auto"`) and instantiates it with `tools=self.tools, system_instruction=...`. `VLM.get_query`/`get_text_query` (2633, 2660) simply forward to `self.backend.get_query`/`get_text_query`, catching exceptions to log errors that the backend itself didn't already log. So the "unification" happens by having every concrete backend implement the same two-method contract and return the same result shape: a plain `str` when no tools are configured, or a "Gemini-like adapter" object (`.candidates[0].content.parts[...]` with `.text`/`.function_call`) when tools are configured.

**Gemini path** (`GeminiBackend.get_query`, 2320-2446): builds `content_parts = [text, image]` (images upscaled 4x via `_prepare_image`, 2203), calls `self.model.generate_content(content_parts, tool_config={"function_calling_config": {"mode": "ANY"}})` through `_call_generate_content` (2249, with retry/backoff for 429/5xx). Since Gemini's native SDK response already has `candidates[0].content.parts[].function_call/.text`, no adapter is needed — the raw `google.generativeai` response is returned as-is when `self.tools` is set.

**Anthropic path** (`AnthropicBackend.get_query`, 733-818): builds `messages=[{"role":"user","content":[{"type":"text",...},{"type":"image","source":{"type":"base64","media_type":"image/png","data":...}}]}]`, calls `client.messages.create(model=..., system=[{"type":"text","text":...,"cache_control":{"type":"ephemeral"}}], messages=..., tools=self._tools_anthropic, tool_choice={"type":"auto"})` via `_call_messages` (700). Anthropic's native response (`response.content` = list of `text`/`tool_use` blocks) is *not* Gemini-shaped, so `_anthropic_response_adapter` (558-605) converts each `tool_use` block into a `function_call` part (via shared helper `_openai_tool_call_part`, 73) and each `text` block into a text part (`_openai_text_part`, 87), then wraps them into synthetic `Content`/`Candidate`/`ResponseAdapter` objects (built with `type(...)`) so downstream agent code can treat all backends identically.

OpenAI (Responses API, `_openai_responses_adapter`, 170) and OpenRouter (Chat Completions, `_openrouter_response_adapter`, 977) use the same adapter trick for their own response shapes.

## 2. Emulator wiring / GAME_TYPE

`game_type = os.environ.get("GAME_TYPE", "emerald").lower()` (app.py:51). `setup_environment()` (app.py:578) branches on it: for `"red"` it imports `RedEmulator` from `pokemon_red_env.red_emulator` with ROM `PokemonRed-GBC/pokered.gbc`; otherwise it imports `EmeraldEmulator` from `pokemon_env/emulator.py` with ROM `Emerald-GBAdvance/rom.gba` (app.py:583‑594), then calls `env.initialize()`. `EmeraldEmulator.__init__`/`initialize()` (emulator.py:373‑472) loads the ROM into libmgba (`mgba.core.load_path`), sets up a video buffer, and instantiates `PokemonEmeraldReader(self.core, milestone_tracker=...)` as `self.memory_reader` (emulator.py:458) — this is the RAM-reading half of the emulator wrapper.

## 3. `/state` and `get_game_state` call chain

`GET /state` (app.py:1381) calls `env.get_comprehensive_state()` (100ms-cached, emulator.py:903), which — if `self.memory_reader` exists — delegates to `PokemonEmeraldReader.get_comprehensive_state(screenshot)` (memory_reader.py:2503), which reads map tiles (`read_map`), `read_coordinates`, `read_location`, `read_money`, `read_badges`, battle/dialog state, etc. directly from GBA RAM, then attaches the PIL screenshot into `state["visual"]["screenshot"]`. `/state` layers on porymap-derived ASCII map data and location connections.

The MCP variant `mcp_get_game_state` (:2822) instead calls `game_tools.get_game_state_direct(env, format_state_for_llm, ...)` (game_tools.py:116): it grabs `current_obs` (latest frame from the game loop) or falls back to `env.get_screenshot()`, calls `env.get_comprehensive_state(screenshot=...)`, then runs `format_state_for_llm` (`utils/state_formatter.py`) to build the ASCII map / text block, base64-encodes the screenshot, and merges in `direct_objectives_manager` guidance before returning.

## 4. `press_buttons` flow / frame-advance

`mcp_press_buttons` (:3117) normalizes/validates button names, strips `WAIT`, then builds an `ActionRequest` and calls `take_action` (:1088), which appends `{button, speed, hold_frames, release_frames}` dicts to the global `action_queue` (does not step the emulator itself). The actual stepping happens in `game_loop()` (app.py:769), running in the main thread: it pops queue entries, holds each button for `hold_frames` (SPEED_PRESETS: fast/normal/slow, app.py:158‑163) by calling `step_environment()` → `env.run_frame_with_buttons(actions_pressed)` (emulator.py:565, sets keys, `core.run_frame()`, clears keys) each loop iteration, then applies a `release_frames` no-input delay, sleeping `1/current_fps` per frame (app.py:908). This is a request-driven queue but continuously stepped/drained by the always-running `game_loop`.

## 5. Objectives

`direct_objectives_manager` (a `DirectObjectiveManager` from `agents/objectives.py`, global at app.py:63) is lazily created in `mcp_get_game_state`/`mcp_complete_direct_objective`/etc. It loads either a `categorized_full_game` sequence (story/battling/dynamics sub-sequences with separate indices) or a legacy single sequence, persisted via `auto_save()`/`objectives.json` cache. `mcp_complete_direct_objective` (:3218) fetches current state, marks the current objective completed (`_mark_objective_completed`), advances `story_index`/`battling_index`/`dynamics_index` (or `current_index` in legacy mode) (:3317‑3369), and appends the "plan more objectives" placeholder (`_build_story_planning_objective`, :78) when a sub-sequence is exhausted. `mcp_get_progress_summary` (:4131) aggregates completed milestones, current objective status (`get_sequence_status`), completed-objective history from `completed_objectives.json`, and memory overview into one payload for the LLM.

## 6. Background loop vs request-driven stepping

There is exactly one continuous stepper: `game_loop()` runs in the **main thread** (started via `game_loop(manual_mode=False)` at app.py:4889) and is the only place `step_environment`/`env.run_frame_with_buttons` gets called — it always ticks at `1/current_fps` even with an empty queue (idle frames pass empty `actions_pressed`). Two additional daemon threads run alongside: `run_fastapi_server` (uvicorn, app.py:4853) serving all HTTP/WS routes, and `periodic_milestone_updater` (app.py:445, started at :4849) which every 5s does a lightweight `env.check_and_update_milestones` pass without touching the frame stepping. So HTTP requests only enqueue actions/read cached state; the emulator itself is advanced by the perpetual `game_loop`, not per-request.</result>

3. Core Components
Model/LLM usage
utils/agent_infrastructure/vlm_backends.py defines one VLM class that dispatches to a per-provider backend (GeminiBackend, AnthropicBackend, OpenAIBackend, OpenRouterBackend, VertexBackend), all implementing the same two-method interface: get_query(image, text) / get_text_query(text). Tool declarations are written once in a Gemini-style dict schema ({"type_": "STRING"/"OBJECT"/...}) and each backend translates them into its own native tool-calling format at init. Non-Gemini backends wrap their native response (Anthropic's tool_use blocks, OpenAI's Responses API) into a synthetic Gemini-shaped object (candidates[0].content.parts[].function_call) so the rest of the agent code never branches on backend.

Agent loop / decision-making
A single ReAct-style loop: get observation → build prompt → one VLM call → execute any tool calls it requested → log → repeat. There's no separate "planner" LLM by default; planning is delegated on-demand to a planner subagent (_run_planner_loop, PokeAgent.py:1289) which runs its own mini-loop with a restricted toolset and calls replan_objectives on the server.

Tools / harness / scaffolding
agents/tools/registry.py is a flat list of tool dicts, each tagged with which --scaffold values may use it (pokeagent gets pathfinding/walkthrough/wiki; simple/continualharness get generic primitives like run_skill/run_code/process_subagent; simplest gets almost nothing). build_tools_for_scaffold() filters this list per run. This is literally how the paper's ablations (H_expert, H_min, H_auto) are implemented — same code, different tool/prompt subsets.

The paper's core contribution: HarnessEvolver
agents/utils/harness_evolver.py is only active for --scaffold continualharness --enable-prompt-optimization. Every ~25–100 steps (or on-demand via the evolve_harness tool), evolve() runs four independent LLM-analysis passes over the recent trajectory window (trajectory_history.jsonl):

_evolve_prompt — rewrites the system/base prompt (delegates to PromptOptimizer.optimize_prompt).
_evolve_subagents — LLM proposes create/update/retire ops on the subagent registry, applied to subagents.json.
_evolve_skills — same CRUD pattern for executable "skills" (skills.json).
_evolve_memory — same for long-term memory entries (memory.json).
Each pass is one text_vlm.get_text_query() call parsed as JSON, wrapped in try/except so failures in one pass don't block the others. Results are appended to evolution_log.jsonl as an audit trail.

Dataset/environment setup
There's no dataset in the ML sense — the "environment" is the actual Pokémon ROM run through mGBA/PyBoy. PokemonEmeraldReader (pokemon_env/memory_reader.py) reads game state directly out of emulated RAM (coordinates, badges, party, map tiles) rather than parsing pixels.

Training/fine-tuning/evaluation loop
There's no gradient-based training in this part of the codebase — it's inference-time, in-context adaptation (the README mentions an online DAgger + PRM pipeline for weight training as future/separate work, not implemented in the files explored here). "Evaluation" is just running an episode and tracking milestone/objective completion and step count.

Reward/scoring/validation
No numeric RL reward. Progress is tracked via hardcoded DirectObjective sequences (agents/objectives/direct_objectives.py) with completion_condition strings (e.g. "location_contains_route_101"), plus milestone constants (MILESTONE_PHASES in pokemon_env/emulator.py). The model itself calls complete_direct_objective to self-report completion; a subagent_verify can double-check claims.

Logging, memory, checkpoints
Memory: memory.json/skills.json/subagents.json under .pokeagent_cache/{run_id}/, CRUD'd both by the agent (process_memory tool) and by the harness evolver.
Trajectory log: trajectory_history.jsonl — one line per step (reasoning, action, pre-state, outcome).
LLM logs/cost: llm_logger.py writes per-call JSONL to llm_logs/ and maintains cumulative_metrics.json (tokens, cost via a hardcoded per-model pricing table).
Checkpoints/backups: checkpoint.state (emulator save state) + backup_manager.py zips the whole cache dir to backups/{run_id}/...zip on objective completion, restorable via --backup-state.
Bootstrap: a finished run can export its evolved memory/skills/subagents/prompt so a new run can start from it via --bootstrap-from.

Refiner: code vs. paper

"Refiner" is the paper's name (arXiv:2605.09998, Karten et al., 2026) for what the code calls HarnessEvolver. Key findings from tracing the runtime path against the paper's description:

Two trigger paths, only one in the paper's excerpt. The automatic per-step schedule (should_evolve: 25-step warmup, then every 25 steps up to step 200, every 100 after) matches the paper's "every F steps after warm-up W." But there's also an agent-invocable evolve_harness tool (agents/tools/registry.py:559 → PokeAgent._execute_evolve_harness) that bypasses the schedule entirely — not mentioned in the fetched paper text.
Trajectory window ≠ trigger interval. The paper's notation τ_{t−F:t} implies the window size equals the trigger interval F. In code these are decoupled: the schedule is hardcoded, while the window size (num_trajectory_steps) is the independently configurable --optimization-window-length.
Only 2 of the paper's 4 failure signatures are hand-coded. Tool-call failures (_extract_tool_failures) and navigation loops/blocked movement (_format_trajectories_for_analysis's coordinate comparisons) are explicit detectors. "Stalled objectives" and "missed exploration" have no dedicated code — they're left for the VLM to infer from raw trajectory text during the same call that generates edits.
The four-pass structure matches exactly: prompt rewrite → subagent CRD → skill codify/repair → memory add/update/demote, same order, same per-component semantics (including that skills and memory have no delete path, matching the paper's "demotes importance" language for memory).
CRUD lands through BaseStore, synchronously saving each store to JSON on every mutation — with two implementation bugs (a return-type mismatch on add(), a falsy-value filter dropping 0/""/False updates) that are bugs against the store's own contract, not paper-vs-code mismatches.

pokeagent — full tool set, built-in subagents, expert prompt (H_expert-adjacent)
simple — minimal (H_min): no built-in subagents, orchestrator owns replan_objectives directly
simplest — bare minimum: only press_buttons + process_memory
continualharness — H_min plus the evolve_harness tool; becomes H_CH when --enable-prompt-optimization runs the Refiner
autonomous_cli — legacy alias for pokeagent
vision_only — separate VisionOnlyAgent class, no map/pathfinding tools
Concretely, a scaffold determines: which tool declarations build_tools_for_scaffold() (agents/tools/registry.py) exposes, which system-prompt file agents/prompts/paths.py resolves, and whether the subagent registry starts seeded with built-ins or empty (EXCLUDE_BUILTIN_SUBAGENTS). It's the paper's H (harness) variable — scaffold = a specific harness instantiation.

In this paper, do they discuss after which certain threshold/change were they updating the harness, and how were they changing the harness exactly?

Short answer:

Yes, they explain when the harness is updated.
Partially, they explain how it is updated at a high level.
No, they do not provide the concrete algorithm, prompts, thresholds, or decision rules used by the Refiner. Those details are abstracted away.
1. When do they update the harness?

The paper does not use a performance threshold like:

"if success rate < X%"
"if reward drops below Y"
"if stuck for Z steps"

Instead, the update schedule is time-based.

The paper states:

Every F steps after a warm-up of W steps, the Refiner reads the recent trajectory and updates the harness.

So the flow is

Warmup (W steps)

↓

Every F steps:

Read recent trajectory

↓

Analyze failures

↓

Update harness

↓

Continue gameplay

Notice that F and W are never specified anywhere in the paper.

So we know updates are periodic, but not how often.

2. What causes an update?

Not "performance dropped."

Instead:

Every refinement cycle, the Refiner examines the last trajectory window

τ(t−F : t)

and searches for failure signatures.

Specifically, they mention:

navigation loops
tool-call failures
stalled objectives
missed exploration opportunities

So the trigger is simply

Every F steps

↓

Look for failures

↓

If found,
generate edits

The paper does not say

"Only update if failure score > threshold."

It appears the Refiner runs every scheduled interval regardless.

3. How exactly is the harness changed?

This is actually the core algorithm.

The harness has four editable components:

Prompt
Sub-agents
Skills
Memory

The Refiner performs CRUD operations on each.

A. Prompt

It rewrites the system prompt according to observed failures.

Example:

Old prompt

↓

Agent repeatedly gets lost

↓

New prompt adds stronger navigation instructions

The paper simply says:

rewrite the prompt conditioned on identified failures and trajectory.

It never explains:

prompt template
optimization method
reflection prompt
LLM prompt

It

creates new ones
edits existing ones
deletes unused ones

Example from the paper:

Initially:

Battle Agent

Later becomes

Master Battle Agent

↓

delegates to

- offense checker
- defense checker
- switching checker
- status checker

Figures 4, 12 and 13 show these structural rewrites.

The paper says the Refiner

creates reusable skills from successful behavior
repairs broken code
fixes exceptions
updates navigation tools

Example:

move_to()

↓

smart_BFS()

↓

robust_BFS()

↓

A* wrapper

Figures 8 and 16 illustrate continual refinement of navigation skills.

It

adds new memories
updates stale memories
lowers priority of obsolete memories

Example:

Brock uses Onix

↓

store

↓

Later:

finished Brock

↓

lower importance

Exactly how "importance" is computed is never explained.

4. Is there any scoring function?

No.

Unlike RL papers, they never define something like

score = α navigation
      + β battle
      + γ exploration

There is no mathematical objective for refinement.

The paper only says the Refiner identifies "failure signatures."

This is one of the biggest missing details.

The paper says it performs four passes:

Prompt
Sub-agents
Skills
Memory

What makes a skill "successful"?

Those decision policies are not described.

Again, no.

it codifies skills from successful sequences.

No.

No.

Figures 3 and 11 provide indirect evidence of the refinement process:

Updates occur continuously throughout long runs rather than only at the beginning.

Overall assessment

The paper gives a clear architectural framework but leaves many implementation details unspecified.

What it specifies well
The harness is updated periodically (every F steps after W warm-up).
The Refiner analyzes a recent trajectory window.
It looks for failure signatures such as navigation loops, tool failures, stalled objectives, and missed exploration.
It edits four harness components (prompt, sub-agents, skills, memory) using CRUD-style operations.
What it does not specify
The values of F and W.
Any performance or reward threshold that triggers updates.
The prompts or algorithms used by the Refiner.
How failures are detected internally.
The criteria for creating, updating, or deleting harness components.
Quantitative thresholds for "successful sequences," "productive use," or memory prioritization.

So the paper explains what the Continual Harness does and when it runs at a high level, but not the concrete implementation that determines exactly how each refinement decision is made.
