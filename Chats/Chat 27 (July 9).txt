Short answer: Langfuse self-hosted (OSS core) is the default choice for your case. Phoenix if you're eval/experiment-heavy. OTel is not an alternative — it's the transport layer underneath both.

The category error first
OpenTelemetry is not a competitor to Langfuse/Phoenix. It's a spec + SDK + wire protocol (OTLP). You still need a backend to receive, store, and render traces. So the real decision is:

Instrumentation: OTel GenAI semconv (vendor-neutral) vs. a vendor SDK
Backend: Langfuse / Phoenix / Jaeger / Grafana Tempo / SigNoz / Datadog
The strategic move is: instrument once with OTel, keep the backend swappable. Both Langfuse and Phoenix accept OTLP. That means you never repeat the migration you're doing right now.

Caveat from production: OTel's GenAI semantic conventions are still churning. Attribute names (gen_ai.prompt vs gen_ai.input.messages, etc.) have moved multiple times. If you go pure-OTel, pin your semconv version and expect a breaking rename per year. Vendor SDKs shield you from this at the cost of lock-in.

What I'd actually build
Given student-learning app, on-prem/no-egress requirement, likely small team:

App
 └─ OpenLLMetry / OpenInference instrumentation (OTel semconv)
      └─ OTLP exporter
           └─ OTel Collector  ← PII redaction processor here
                ├─ Langfuse (LLM observability, primary)
                └─ [optional] Tempo/Jaeger (infra correlation)
Why the Collector in the middle, non-negotiable for your domain: you're processing student data. FERPA/COPPA/GDPR territory. The Collector is where you run a transform or redaction processor to strip PII from prompt payloads before it hits any storage. Doing this in app code means every new call site is a leak waiting to happen. Doing it at the Collector means one enforcement point.

This is the single most important architectural point in your whole setup, and none of the three tools you were suggested makes it obvious. Instrument → Collector → backend. Not app → backend directly.

Second reason for the Collector: fan-out and swap. You can run Langfuse and Phoenix in parallel for two weeks, decide, and kill one. Zero app changes.

On your existing *.debug.log files
Don't throw them away and don't keep them as the source of truth. Two things:

They're your fallback. Tracing backends go down. Traces get dropped (OTel batch processors drop on backpressure by design — queue_size exceeded → span dropped, silently). A structured JSONL log on local disk is a durable, boring, always-works record. Keep writing it.
Migrate the format, not the practice. Move from freeform .debug.log to structured JSONL where each line carries trace_id and span_id from the active OTel context. Now your logs and your traces join. When something goes wrong at 2am, you grep the log, pull the trace_id, and paste it into Langfuse. This is the pattern every mature observability setup converges on and almost nobody sets up on day one.

Tradeoff that will actually bite you
Sampling. A student-learning app has bursty load (everyone opens the app at 8pm). LLM traces are fat — full prompt + full completion + retrieved chunks. A single RAG trace can be 50–200KB. At scale, storage cost is not the LLM API cost, but it's not nothing, and ClickHouse ingestion is where Langfuse v2 users hit walls.

Do not use head-based sampling (traceidratio). You'll sample away exactly the pathological traces you need. Use tail-based sampling in the Collector: keep 100% of errors, 100% of high-latency, 100% of low-eval-score, and ~5% of the boring successful ones. This is a Collector tail_sampling processor. It requires all spans for a trace to hit the same Collector instance, so if you scale to multiple Collectors you need a load-balancing exporter in front, keyed on trace_id. That's the gotcha nobody mentions until you've already scaled out.

Decision
You want production observability, cost tracking, prompt iteration, and you can run 4 containers → Langfuse.
You are solo, want minimal ops, and your main pain is "is my RAG retrieving the right chunks and are my answers good" → Phoenix.
Either way: instrument with OTel semconv, route through a Collector, keep the JSONL logs correlated by trace_id.
Start with Phoenix if you want to be running in an hour. Move to Langfuse when you need prompt versioning and per-student cost attribution. The Collector makes that move cost you a config file, not a sprint.

Answer briefly and in simple terms:

Why cant we _TracingHandler is unable to show logs from the logging module in the LangSmith?
Show less
It's not actually unable to — it does successfully send them. We confirmed this by querying LangSmith's API directly: a real run had 43 log events attached, in order, with full messages.

The real limit is on LangSmith's side, not the code: their web UI simply doesn't have a place to display custom events on this account/plan — not in the trace panel, not in Attributes, not as timeline markers. The data reaches LangSmith fine; their UI just never renders it.

That's why we built trace_events.py — it reads those same events back via the API, bypassing the UI gap entirely.
