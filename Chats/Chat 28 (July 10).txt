Root cause: the Langfuse callback never reaches your actual LLM calls.

In main.py and api.py, langfuse_handler is only attached at the top level:


rag_app.invoke(state, config={"callbacks": [langfuse_handler]})
LangGraph propagates that config to node functions only if the node function's signature accepts a second config: RunnableConfig parameter. None of your nodes do — generate_answer.py:21 and every other node (generate_draft.py, query_variants.py, check_answer_quality.py, dc.py, lbc.py, nac.py, validators.py, self_learner.py) is defined as def node(state: GraphState) -> dict, with no config param.

Then, even if a node had config, it wouldn't matter — the actual model call in llm_caller.py:

llm_invoke() (line 834) and _invoke_once() (line 292) have no config/callbacks parameter at all
The real call is llm.invoke(messages, **kwargs) at llm_caller.py:317 — config is never forwarded
It's also dispatched through a ThreadPoolExecutor (line 316), which wouldn't inherit ambient callback context even if LangChain relied on that instead of explicit passing
So the CallbackHandler you're passing in is a no-op — it's never wired to anything that actually calls the LLM. That's why nothing shows up in the Langfuse GUI (Phoenix tracing likely works fine since that's presumably instrumented at the HTTP/SDK level via setup_phoenix_tracing(), which is a different mechanism).

Fix requires threading config: RunnableConfig through every node → llm_invoke() → _invoke_once() → llm.invoke(messages, config=config, **kwargs), touching ~9 files.

Yes — Langfuse has its own decorator, @observe (from langfuse), equivalent to LangSmith's @traceable:


from langfuse import observe

@observe()
def my_node(state):
    ...
Wrap any function with it and it becomes a traced span automatically — same ambient/automatic feel as LangSmith, no manual config/callback plumbing needed for that function. It nests correctly under whatever parent span is active (including the LangChain CallbackHandler-created trace), so you could decorate your node functions directly instead of (or in addition to) the callback-based wiring we just fixed.

One caveat from the skill docs: @observe() captures all function arguments as trace input by default — use langfuse.update_current_span(input=...) to scope it down if a function takes things like API keys/config objects you don't want logged.

    ) -> None:

The actual bug
It's not a callback/context issue — it's that Langfuse's SDK silently evicts Phoenix's exporter from the shared OpenTelemetry pipeline.

The chain, verified line-by-line:

phoenix.otel.register() (called in phoenix_tracing.py:10) installs its SimpleSpanProcessor (the gRPC exporter to Phoenix) as the global TracerProvider's span processor, but flags it internally as a "default" placeholder (_default_processor = True). Phoenix's own log even warns about this: "Using a default SpanProcessor. add_span_processor will overwrite this default."

Langfuse v3+ (installed: 4.13.2, already latest) rewrote its SDK to be OTel-native. When get_langfuse_handler() constructs CallbackHandler(), Langfuse's _init_tracer_provider() (langfuse/_client/resource_manager.py:644) checks the global provider — sees a real one already registered (Phoenix's) — and correctly reuses it rather than creating a separate one. Polite behavior, so far.

But then it calls tracer_provider.add_span_processor(langfuse_processor) on that same shared provider (resource_manager.py:265). Because it's Phoenix's TracerProvider subclass, that call triggers Phoenix's own override (phoenix/otel/otel.py):


def add_span_processor(self, *args, replace_default_processor=True, **kwargs):
    if self._default_processor and replace_default_processor:
        self._active_span_processor.shutdown()
        self._active_span_processor._span_processors = tuple()  # removed
        self._default_processor = False
    return super().add_span_processor(*args, **kwargs)
This shuts down and deletes Phoenix's gRPC exporter, then attaches only Langfuse's processor.

I proved this directly by inspecting the live processor list:


processors before langfuse: (<phoenix.otel.otel.SimpleSpanProcessor ...>,)
processors after langfuse:  (<langfuse._client.span_processor.LangfuseSpanProcessor ...>,)   # Phoenix's is just gone
From that point, every span (LangGraph nodes, LLM calls, everything) only ever reaches Langfuse. Nothing crashes, no exception anywhere — the query pipeline runs and answers normally — so it's invisible unless you inspect OTel internals like I did.

No version fix available: both packages are already on latest (langfuse 4.13.2, arize-phoenix-otel 0.16.1). This isn't a regression that got patched later — it's the current behavior of both.

Langfuse Scores, Datasets, and Annotations

I reviewed the current Langfuse documentation and then checked Langfuse’s GitHub repository, issues, discussions, and relevant Stack Overflow results. The three concepts are tightly connected:

Production traces
      │
      ├── Human annotations ──► Scores
      │
      ├── Automated evaluators ──► Scores
      │
      └── Selected examples ──► Datasets
                                    │
                                    ▼
                              Dataset experiments
                                    │
                                    ▼
                                  Scores

The key distinction is:

Scores are the actual stored evaluation results.
Annotations are one method by which humans create scores and comments.
Datasets contain reusable test cases that you run through your application in experiments.
1. Scores
1.1 What a score is

A Langfuse score is the universal data object used to represent an evaluation result.

A score can come from:

A human reviewer
End-user feedback
An LLM-as-a-Judge
A deterministic code evaluator
An external evaluation pipeline
An experiment run

Every score normally has:

A name, such as correctness, helpfulness, or hallucination
A value
A data type
A parent object
An optional comment
An optional Score Config
Optional metadata

A score references exactly one of the following:

Trace
Observation
Session
Dataset run

Trace-level scoring is the most common because it evaluates one complete application interaction. Observation-level scoring is more granular and can evaluate an individual LLM call, retrieval operation, tool invocation, or another step inside the trace.

Tool-selection correctness
Faithfulness of one generation
Correctness of a particular agent node

When creating an observation-level score through the SDK or API, you should provide both:

trace_id
observation_id

The trace ID is required because the observation belongs to that trace.

Session-level score

Evaluates a collection of related interactions.

Examples:

Did the user’s issue get resolved over the entire conversation?
Was the multi-turn conversation coherent?
Did the agent eventually accomplish the session goal?
Dataset-run-level score

Evaluates the experiment as a whole rather than one individual test item.

Examples:

Overall pass rate
Mean accuracy
Aggregate quality
Total experiment cost
Regression status

Langfuse distinguishes these from per-item experiment scores, which are associated with individual experiment results.

1.3 Score data types

Langfuse currently supports four score data types.

Type	Stored value	Suitable for
NUMERIC	Float	Accuracy, relevance, similarity, helpfulness
CATEGORICAL	Predefined string	Correct, partially correct, incorrect
BOOLEAN	0 or 1	Pass/fail, hallucinated/not hallucinated
TEXT	Free-form text	Qualitative reviewer notes
Numeric score

Examples:

correctness = 0.85
relevance = 4.0
toxicity = 0.02

A numeric value must be submitted as a float when using the SDK/API.

Numeric scores are best when the concept genuinely forms a continuum. For example:

0.0–1.0 relevance
1–5 helpfulness
0–100 confidence
Categorical score

Examples:

answer_quality = "excellent"
classification = "partially_correct"
severity = "high"

Categories should be defined in a Score Config so reviewers and automated systems use the same allowed values.

Boolean score

Examples:

contains_hallucination = false
passed_json_validation = true
user_satisfied = true

At the API/data-model level, boolean scores are represented as 0 or 1.

Text score

Examples:

"The answer is accurate but omits the final safety recommendation."

Text scores are useful for exploratory qualitative labeling or “open coding.” However, Langfuse does not support text scores in:

Score Analytics
Experiments
LLM-as-a-Judge evaluators

The reason is that arbitrary free-form text cannot be meaningfully averaged, aggregated, or compared statistically. Text scores are constrained to 1–500 characters when controlled by a Score Config.

1.4 Score Configs

A Score Config is the schema or rubric definition for a score.

It standardizes:

Score name
Data type
Numeric range
Allowed categorical values
Text-length restrictions

For example:

Name: correctness
Type: CATEGORICAL
Allowed values:
- correct
- partially_correct
- incorrect

Or:

Name: relevance
Type: NUMERIC
Minimum: 0
Maximum: 1

Score Configs are important because without them different users or evaluators might produce incompatible values:

Reviewer A: relevance = 4
Reviewer B: relevance = 0.8
Reviewer C: relevance = "good"

That data would be difficult to compare.

With a config:

relevance = float between 0 and 1

all values follow the same schema.

Score Configs can be created through:

Langfuse UI
Public API

They are immutable after creation. A config can be archived and restored, but not freely rewritten. Immutability helps prevent historical scores from silently changing meaning.

Important production implication

Do not create one generic score called quality whose meaning changes over time.

Use versioned or explicit names such as:

answer_correctness_v1
answer_correctness_v2
retrieval_relevance_v1

Alternatively, archive the old Score Config and introduce a new one when the rubric changes.

1.5 Ways of creating scores

Langfuse documents five main score-generation paths.

1. Manual scores through the UI

A reviewer opens a:

Trace
Observation
Session
Experiment result

They click Annotate, select a configured score, enter the value, and optionally add a comment.

2. Annotation queues

Reviewers process assigned or selected traces in a structured queue. This is preferable when many examples need systematic human review.

3. Scores through SDK/API

Your application or evaluation pipeline directly creates a score.

Conceptually:

langfuse.create_score(
    trace_id=trace_id,
    name="correctness",
    value=0.9,
    data_type="NUMERIC",
    comment="Answer matches the reference."
)

A score can be submitted before the associated trace has arrived. It appears in the score table and is linked when a trace with the matching trace ID is eventually ingested.

4. LLM-as-a-Judge

An evaluator model receives:

Input
Application output
Evaluation rubric
Optionally the reference/expected output
Optionally retrieved context

It returns a numeric, categorical, or boolean score with reasoning. Langfuse can evaluate observations, traces, and experiment results using this method.

5. Code evaluators

A deterministic function calculates the result.

Examples:

Exact match
Regex match
JSON validation
Schema validation
Citation count
Keyword coverage
Latency threshold
Tool-use correctness

This is often preferable to LLM-as-a-Judge where a deterministic answer exists.

1.6 Scores versus comments

A score is a structured evaluation result.

A comment is primarily a collaborative note or discussion item.

Comments can be attached to:

Traces
Observations
Sessions
Prompts

They support activities such as:

Flagging anomalies
Recording debugging notes
Discussing prompt changes
Documenting edge cases
Coordinating between team members

A score’s comment field explains that specific score, whereas the broader comments feature supports general conversation around the object.

Example:

Score:
correctness = "partially_correct"

Score comment:
"The answer correctly explains JWT validation but omits key rotation."

General trace comment:
"@backend-team This failure started after deployment 2.7."
1.7 User feedback is also stored as scores

Explicit user feedback includes:

Thumbs up/down
Star ratings
Like/dislike
User-reported correctness

Implicit feedback can include:

Copying an answer
Retrying the request
Abandoning the response
Accepting a suggestion
Time spent reading

Both can ultimately be represented as scores.

For example:

user_feedback = true

or:

user_rating = 4

These scores can then be used to:

Filter traces
Build annotation queues
Select bad traces for datasets
Compare automated evaluators against real user preferences
1.8 Duplicate scores and idempotency

By default, repeatedly submitting similarly named scores can create multiple score records. This may be intentional when you want:

Multiple human reviewers
Multiple judge models
Repeated evaluations
Historical evaluator outputs

However, it can be a problem if retries accidentally duplicate the same result.

Langfuse supports assigning a caller-generated score ID or idempotency identifier. Reusing that ID allows the existing score to be updated rather than creating another independent score.

A practical ID pattern is:

<trace-id>:<score-name>:<evaluator-version>

For example:

trace-123:correctness:judge-v2

A GitHub issue documented confusion between id in the REST API and score_id in some Python SDK signatures. Therefore, use the field name expected by your installed SDK version rather than blindly copying an example written for another API version.

Recommended approach

Create deterministic score IDs for automated evaluation:

trace_id + score_name + evaluator_version

For independent human reviews, do not use the same ID for every reviewer:

trace_id + score_name + reviewer_id

Otherwise, the second reviewer could overwrite the first reviewer’s score.

1.9 Score Analytics

Langfuse includes a Scores → Analytics area for examining evaluation data.

For a single score, it can show:

Total count
Mean or mode
Standard deviation
Score distribution
Trend over time
Evaluation coverage

For two compatible scores, it can show:

Numeric comparisons
Pearson correlation
Spearman correlation
Mean absolute error
Root mean square error
Heatmap comparison
Categorical and boolean comparisons
Confusion matrix
Cohen’s Kappa
F1 score
Overall agreement

A match exists when both selected scores are attached to the same parent object.

For example:

Trace A:
human_correctness = "correct"
judge_correctness = "correct"

These form one matched pair.

This is especially useful for validating whether an LLM judge agrees with human reviewers.

Current Score Analytics limitations

According to the documentation:

It is currently a beta feature.
Only two scores can be compared at once.
The scores must have the same data type.
Text scores are not supported.
Queries expected to exceed 100,000 scores may use random sampling.
Scores using different scales can technically be compared, but MAE and RMSE become misleading.

For example, comparing:

score_A: 0–1
score_B: 1–10

without normalization makes the absolute-error statistics difficult to interpret.

2. Datasets
2.1 What a Langfuse dataset is

A Langfuse dataset is a managed collection of test cases used to evaluate an LLM application.

A dataset contains multiple Dataset Items.

Each item may contain:

Input
Expected output
Metadata
Source trace ID
Source observation ID
Media attachments

Expected output is optional.

Example:

{
  "input": {
    "question": "What is an adjustable-speed drive?"
  },
  "expected_output": {
    "answer": "A device that controls motor speed by varying supplied power."
  },
  "metadata": {
    "domain": "industrial automation",
    "difficulty": "basic"
  }
}

Datasets are designed to provide:

Reusable regression tests
Benchmarks
A shared source of truth
Controlled prompt/model comparison
Production-derived test cases
2.2 Datasets are not training datasets by default

Langfuse datasets are primarily evaluation datasets, not automatically model-training datasets.

They are commonly used for:

Prompt evaluation
RAG evaluation
Agent regression testing
Model comparison
Pipeline comparison
Pre-deployment checks

You may export or reuse the information for fine-tuning, but Langfuse’s experiment workflow mainly treats the dataset as test input and expected behavior.

2.3 Creating a dataset

A dataset can be created using:

Langfuse UI
Python SDK
JavaScript/TypeScript SDK
Public API

It can include:

Name
Description
Metadata

Example metadata:

{
  "author": "evaluation-team",
  "domain": "customer-support",
  "language": "English",
  "version": "2026-Q3"
}

Metadata should record enough information to understand:

Where the dataset came from
Who owns it
What it evaluates
How expected outputs were created
Which application version it targets
2.4 Creating dataset items

Dataset items can be created in several ways.

Manually through the UI

Useful for small curated gold-standard datasets.

Through SDK/API

Useful for:

Synthetic dataset generation
Migration from an existing evaluation system
Automated test-set construction
Batch ingestion
Through CSV upload

The UI supports CSV imports for text and structured JSON items.

The upload is intended for:

Inputs
Expected outputs
Metadata

It is not intended as a way to upload already-generated experiment outputs. If outputs have already been generated, the recommended route is to use the Experiments SDK so that those outputs are represented as experiment results.

From production traces

A highly useful workflow is:

Identify a failed or important production trace.
Select a relevant observation or the complete trace.
Add it to a dataset.
Preserve its input.
Have an expert provide the correct expected output.
Use it in future regression tests.

Dataset items can retain:

source_trace_id
source_observation_id

This maintains provenance between the test case and the production behavior that caused it to be created.

Batch creation from observations

From the Observations table, you can:

Filter observations.
Select multiple records.
Choose Actions → Add to dataset.
Select or create a dataset.
Map observation fields into dataset fields.
Preview the result.

Field mapping supports:

Entire fields
JSON-path extraction
Custom objects assembled from several fields

This is useful for converting large numbers of production retrievals or generations into evaluation cases.

2.5 Dataset schema validation

Langfuse supports JSON Schema validation for dataset inputs and expected outputs.

This allows a dataset to enforce structures such as:

{
  "type": "object",
  "required": ["question"],
  "properties": {
    "question": {
      "type": "string"
    },
    "user_level": {
      "type": "string",
      "enum": ["beginner", "intermediate", "advanced"]
    }
  }
}

Schema validation helps prevent cases such as:

Item 1 input: {"question": "..."}
Item 2 input: {"query": "..."}
Item 3 input: "plain string"

Without a consistent schema, experiment code becomes fragile.

Important limitation

Dataset item changes create new dataset versions, but dataset schema changes currently do not create versions. Therefore, changing the schema can alter how the current dataset is interpreted without producing a new item-version snapshot.

A safer practice is to create a new dataset or clearly version the dataset name after a breaking schema change.

2.6 Dataset folders

Datasets can be arranged into virtual folders by using slashes in their names.

Examples:

rag/retrieval/basic
rag/retrieval/adversarial
rag/generation/faithfulness
agents/tool-selection
customer-support/refunds

The folders are virtual; the full string remains the dataset name.

For JavaScript/TypeScript or direct API path parameters, names containing slashes may need URL encoding:

encodeURIComponent("rag/retrieval/basic")

Otherwise, the slash may be interpreted as a URL path separator.

2.7 Dataset versioning

Langfuse automatically creates a new dataset version when an item is:

Added
Updated
Deleted
Archived

Versions are timestamp based.

You can retrieve:

The latest dataset state
The dataset as it existed at a specified timestamp

Conceptually:

dataset = langfuse.get_dataset(
    name="rag/regression",
    version=version_timestamp
)

This is important because experiments should be reproducible. A prompt run performed against 100 items should not later appear to have used 120 items merely because the dataset was expanded.

What versioning covers

It versions dataset-item state.

What it does not cover

It does not version the dataset’s JSON schemas.

The UI also provides a version view under the dataset’s Items area.

Recommended production practice

Record all of the following for every experiment:

dataset name
dataset version timestamp
application commit SHA
prompt version
model and model parameters
evaluator version
experiment run name
2.8 Multi-modal datasets

Dataset input, expected_output, and metadata can contain media, including:

Images
Audio
Video
Documents
Other file types

The SDK handles media upload and stores a Langfuse media reference in the item.

Current documented requirements include:

Python SDK >= 4.10.0
JS/TS client >= 5.6.0

Multi-modal items are supported in SDK-based experiments.

However, UI-based prompt experiments do not yet support dataset items with media attachments. CSV upload is also intended for textual and structured JSON content rather than multi-modal files.

3. Dataset Runs and Experiments
3.1 What happens when a dataset is executed

A dataset is static test data.

An experiment executes your application against that test data.

A dataset run records the experiment.

Conceptually:

Dataset
  ├── Item 1 ──► Application ──► Actual output ──► Scores
  ├── Item 2 ──► Application ──► Actual output ──► Scores
  └── Item 3 ──► Application ──► Actual output ──► Scores

A dataset run groups the outputs and scores so different application versions can be compared.

3.2 SDK experiment runner

The current SDK experiment runner is the recommended high-level method.

It can handle:

Iterating through dataset items
Calling your application task
Creating traces
Linking traces to dataset items
Running evaluators
Recording scores
Creating a dataset run
Supporting run comparison in the UI

It supports:

Langfuse-hosted datasets
Local datasets

For a Langfuse-hosted dataset, the SDK automatically creates a dataset run visible in Langfuse.

For a local dataset, traces and evaluation scores can still be logged, but a hosted dataset run is not created in the same way because the dataset is not managed by Langfuse.

3.3 UI prompt experiments

Langfuse can also run prompt experiments through the UI.

For a dataset to work with a prompt:

The dataset item’s input must be a JSON object.
The JSON keys must match the variables expected by the prompt.

For example:

Prompt:

Use the following documentation:

{{documentation}}

Question: {{question}}

Dataset input:

{
  "documentation": "An adjustable-speed drive controls motor speed...",
  "question": "What does an ASD do?"
}

An item using:

{
  "context": "...",
  "query": "..."
}

would not directly match those prompt variables without adapting the field mapping.

3.4 Per-item versus run-level scoring

Suppose a dataset has 100 items.

You may create per-item scores:

Item 1 correctness = 1
Item 2 correctness = 0
...
Item 100 correctness = 1

You can also create a run-level score:

overall_pass_rate = 0.87

These serve different purposes:

Score level	Meaning
Dataset run item	Quality of one individual test case
Dataset run	Quality of the entire experiment

Do not store a run-wide average as though it belonged to one random trace.

4. Annotations
4.1 What annotation means in Langfuse

Annotation is the human evaluation process.

A reviewer examines a:

Trace
Observation
Session
Dataset experiment result

and then adds:

One or more scores
Optional score comments
Potentially a corrected expected output
Potentially broader discussion comments

Therefore:

Annotation = human activity/workflow
Score = structured object produced by that activity

An annotation is not a completely separate evaluation-data object comparable to a score. The human judgment is saved using Langfuse’s score system.

4.2 Direct manual annotation

For occasional review:

Open a trace, observation, or session.
Click Annotate.
Select a Score Config.
Enter the score.
Add an optional comment.
Save.

This is appropriate for:

Debugging one trace
Reviewing a particular user complaint
Examining an incident
Adding a quick human baseline

It becomes inefficient when hundreds or thousands of traces must be reviewed. For that use case, annotation queues are more appropriate.

5. Annotation Queues
5.1 Purpose

Annotation Queues provide a structured human-review workflow for domain experts.

They are useful for:

Reviewing selected production traces
Assigning work to reviewers
Applying consistent score rubrics
Capturing corrected outputs
Building human-labeled evaluation data
Calibrating LLM judges against human judgment

A queue requires one or more Score Configs. These define what reviewers must evaluate.

5.2 Creating a queue

The documented process is:

Create a new Annotation Queue.
Give it a name.
Add an optional description.
Select Score Configs.
Optionally assign users.

Example:

Queue: RAG Faithfulness Review

Required dimensions:
- answer_correctness: categorical
- faithfulness: numeric 0–1
- hallucination: boolean
- reviewer_note: text
5.3 Adding items

You can add:

Traces
Observations
Sessions

Items can be added individually or in bulk.

Bulk workflow
Open traces, sessions, or observations.
Use filters.
Select records.
Choose Actions → Add to queue.
Select the annotation queue.
Single-item workflow

Open the item and use the Annotate dropdown to place it in a queue.

5.4 Processing queue tasks

A reviewer sees an annotation card for every queued item.

They:

Inspect the trace, observation, or session.
Add the configured scores.
Add comments or corrected information where needed.
Click Complete + next.
Continue until the queue is complete.

The queue interface also supports keyboard-driven processing, with an in-product shortcut guide available by pressing ?.

5.5 Corrected outputs and gold-standard data

One of the most important annotation workflows is capturing what the model should have produced.

Example:

Application output:
"JWTs are always encrypted."

Human correction:
"JWTs are usually signed but are not necessarily encrypted."

That corrected output can become:

A dataset’s expected output
A gold-standard reference
Training data for a later fine-tuning process
Input for evaluating an LLM judge
A regression test

This produces a valuable loop:

Production failure
      ↓
Human annotation
      ↓
Corrected output
      ↓
Dataset item
      ↓
Experiment
      ↓
Improved application

Langfuse explicitly describes annotation queues as useful for adding corrected outputs and aligning LLM-as-a-Judge evaluations with human annotations.

7. GitHub Findings and Practical Limitations

The official documentation explains the intended model well, but GitHub issues reveal operational limitations and edge cases.

7.1 Duplicate queue items

An open GitHub issue reports that the same trace can be added to the same human annotation queue multiple times.

The consequence is:

Duplicate pending tasks
Duplicate human work
Distorted queue statistics
Potentially repeated scores

This was reported for self-hosted Langfuse v3.150.0 in April 2026.

Recommendation

Before programmatically adding an item:

Maintain your own queue-assignment record, or
Query existing queue membership where supported, or
Apply a metadata/tagging convention before enqueueing.

Do not assume that the queue itself always enforces uniqueness.

7.2 Limited queue visibility from tracing tables

A GitHub issue described the lack of an easy Annotation Queue filter in the tracing view. The reporter wanted to identify which traces had already been assigned to a queue and was considering tags as a workaround.

Recommendation

When creating a human-review workflow at scale, consider storing explicit metadata such as:

{
  "review_pipeline": "rag-faithfulness-v2",
  "review_candidate": true
}

However, Langfuse observation tags are immutable after ingestion, so decide tagging and metadata conventions at ingestion time rather than depending on later UI editing.

7.3 Queue assignment API and user IDs

A GitHub issue reported difficulty assigning annotation queue work programmatically by email. The API expected internal userId values, while retrieving member IDs programmatically could require functionality unavailable in some self-hosted licensing configurations.

Practical implication

Before designing an automated reviewer-assignment system, verify:

Your Langfuse edition
Your management API access
Whether member IDs are available
Whether assignment by email is supported in your deployed version

Do not assume that an email address can always be passed directly to the queue-assignment endpoint.

7.4 Annotation queues and self-hosted editions

A self-hosting issue involving a missing annotation_queues table was closed with the explanation that annotation queues were tied to the Enterprise Edition/commercial licensing for that deployment context.

Because Langfuse’s editions and licensing may evolve, verify the feature matrix for the exact version you deploy.

The broader lesson is:

Open-source/self-hostable product
does not necessarily mean
every UI workflow is available in every self-hosted edition.
7.5 Permissions in self-hosted environments

One GitHub issue reported organization owners being unable to perform project-level operations such as:

Creating annotation queues
Creating datasets
Creating dashboards

The report concerned self-hosted version 3.79.0 and was treated as a permissions bug.

Recommendation

Distinguish:

Organization-level role
Project-level membership
Project-level permissions

When a user cannot create datasets or queues, do not immediately assume the feature is missing; inspect project membership and the deployed version as well.

7.6 Dataset-run scaling issue

A recent GitHub issue reported dataset-run metric queries exceeding ClickHouse memory limits in projects with large volumes of scores or observations. The issue could appear even when only one run was visible because the backend query still scanned substantial data.

Production implications

For very large deployments:

Avoid placing all unrelated workloads in one enormous project.
Use time-range filters where possible.
Consider project separation by application or environment.
Monitor ClickHouse memory.
Keep Langfuse updated.
Benchmark experiment comparison pages with production-scale data.
7.7 Dataset-run metadata update limitation

A GitHub feature request noted that updating a dataset run’s description or metadata after creation was not straightforward through the API. The reported workaround involved creating a dummy trace/run item, which polluted the experiment.

Recommendation

Determine run metadata before the experiment begins:

{
  "git_sha": "abc123",
  "prompt_version": "support-v7",
  "retriever_top_k": 8,
  "model": "model-name",
  "temperature": 0,
  "evaluator_version": "correctness-v3"
}

Do not depend on being able to fill in all experiment documentation later.

7.8 Experiment trace-linking issues

A historical GitHub issue reported that traces did not link correctly when running dataset experiments through a Vercel AI SDK-based setup.

Even when a library claims automatic experiment tracing, verify that each result actually has:

A trace
A dataset item association
A dataset run association
Expected scores
Correct parent-child observations

Run a small three-item experiment before launching a large benchmark.

7.9 Score API naming changes

The GitHub issue concerning id versus score_id demonstrates a broader concern: Langfuse’s SDK and API evolve.

The current documentation also notes that newer Python and JavaScript/TypeScript SDKs changed several auto-generated API namespaces and removed older aliases.

Recommendation

Pin SDK versions:

langfuse==<tested-version>

or:

"@langfuse/client": "<tested-version>"

Then consult the matching SDK reference rather than mixing examples from:

Legacy Python SDK
Current Python SDK
REST API
JavaScript SDK
Old blog posts
8. Stack Overflow Findings

Stack Overflow currently contains relatively little high-quality discussion specifically about Langfuse Scores, Datasets, or Annotation Queues.

Most Langfuse questions there concern:

Tracing setup
LangChain/LangGraph integration
SSL and endpoint configuration
Connecting user feedback to the correct trace
.NET integration
Multi-agent trace structure

Therefore, GitHub issues and the official Langfuse documentation are currently much stronger sources for these three features.

One relevant practical discussion involved user feedback being linked only to the latest trace. If users rated an older message, the application could accidentally attach the feedback to the most recent trace instead.

Core lesson from that problem

Always preserve the trace or observation ID corresponding to each UI message.

Incorrect design:

Store only:
latest_trace_id

Then every feedback click affects the latest response.

Correct design:

Message 1 → trace_id_1
Message 2 → trace_id_2
Message 3 → trace_id_3

When the user rates Message 1, submit the score using trace_id_1.

For chat applications, it is often even better to maintain:

session_id
message_id
trace_id
generation_observation_id

This lets you attach:

Message feedback to the generation observation
Interaction feedback to the trace
Conversation-resolution feedback to the session
9. Recommended Score Design

Avoid creating random score names as evaluation needs arise.

Define an evaluation taxonomy.

9.1 RAG example
Retrieval-level scores
retrieval_relevance: NUMERIC 0–1
retrieval_coverage: NUMERIC 0–1
retrieval_contains_answer: BOOLEAN
retrieval_domain_match: CATEGORICAL

Attach these to the retrieval observation.

Generation-level scores
faithfulness: NUMERIC 0–1
citation_correctness: NUMERIC 0–1
contains_hallucination: BOOLEAN
answer_style: CATEGORICAL

Attach these to the generation observation.

Trace-level scores
answer_correctness: NUMERIC 0–1
helpfulness: NUMERIC 1–5
task_completed: BOOLEAN
user_feedback: BOOLEAN
Session-level scores
issue_resolved: BOOLEAN
conversation_quality: NUMERIC 1–5
unnecessary_turns: NUMERIC
9.2 Agent example
tool_selection_correct: BOOLEAN
tool_arguments_correct: BOOLEAN
plan_quality: NUMERIC 0–1
task_completed: BOOLEAN
unsafe_action_attempted: BOOLEAN
final_answer_correctness: NUMERIC 0–1

Attach tool-related scores to the tool observation rather than only scoring the entire trace.

9.3 Evaluator naming

Do not use exactly the same name for substantially different evaluators without recording the evaluator identity.

Better:

correctness_human
correctness_judge_gpt5_v2
correctness_exact_match

This makes Score Analytics comparisons straightforward.

Alternatively, use a common semantic score name with consistent metadata, but ensure your querying and dashboards can separate evaluator sources.

10. Recommended Dataset Design

A useful dataset item should include more than input and expected output.

Example:

{
  "input": {
    "query": "What is an adjustable-speed drive?",
    "conversation_history": [],
    "user_level": "beginner"
  },
  "expected_output": {
    "required_concepts": [
      "motor speed control",
      "varying supplied frequency or voltage",
      "energy and process control"
    ],
    "reference_answer": "..."
  },
  "metadata": {
    "domain": "industrial automation",
    "language": "en",
    "difficulty": "basic",
    "source": "production_failure",
    "failure_type": "acronym_disambiguation",
    "review_status": "expert_verified"
  }
}

For RAG, expected output does not always need to be one exact paragraph. It can contain:

Required facts
Forbidden claims
Expected citations
Expected document IDs
A reference answer
Acceptable answer variants

This supports more reliable evaluation than strict string equality.

11. Recommended Annotation Process
Stage 1: Write an explicit rubric

Weak rubric:

Score answer quality from 1 to 5.

5 = Correct, complete, grounded, and directly answers the question.

12. Common Mistakes
Mistake 1: Treating annotations and scores as unrelated features

Annotations create scores. The score is the stored result.

Mistake 2: Scoring everything only at trace level

This hides whether the problem came from:

Retrieval
Tool selection
Generation
Final formatting

Use observation-level scores when diagnostic detail matters.

Mistake 3: Using numeric scores without defining the scale

correctness = 4 is meaningless unless reviewers know whether the scale is:

0–5
1–5
0–10

Use Score Configs.

Mistake 4: Uploading model outputs as dataset expected outputs

Expected output means the desired/reference output, not merely an output your model happened to generate.

Generated results belong in experiment runs.

Mistake 5: Mutating datasets without recording versions

An experiment is not reproducible unless the dataset version is known.

Mistake 6: Using text scores for metrics

Text scores cannot be averaged or compared in Score Analytics.

Use a categorical or numeric score plus a comment.

Mistake 7: Accidentally overwriting independent reviewers

Do not reuse one deterministic score ID across multiple human annotators.

Mistake 8: Attaching feedback to the latest trace

Map every visible message to its own trace or observation ID.

Mistake 9: Relying only on an LLM judge

Calibrate the judge against human-reviewed examples.

Mistake 10: Assuming every self-hosted edition includes annotation queues

Verify edition, licensing, version, and project permissions before designing around the feature.

Human Annotation vs LLM-as-a-Judge

Many beginners think these are competitors.

They are actually complementary.

Human Annotation	LLM Judge
Slow	Fast
Expensive	Cheap
Highest quality	Good quality
Expert knowledge	Pattern matching
Gold standard	Approximation
Used for benchmark creation	Used for large-scale automation

A common production workflow is:

100,000 traces

↓

LLM Judge scores everything

↓

Select worst 500 traces

↓

Humans review those

↓

Create gold labels

↓

Compare LLM Judge with humans

This keeps costs manageable while maintaining quality.

Human Annotation in Your Agentic RAG System

Given your architecture with retrieval, validation, compression, and answer generation, a practical annotation schema could include:

Stage	What to Annotate
Retrieval	Were the retrieved documents relevant?
Merge	Was any important context lost during merging?
Compression	Did compression remove essential information?
Final Answer	Was the answer correct and complete?
Grounding	Was every claim supported by the retrieved context?
Hallucination	Did the answer introduce unsupported information?
Readability	Was the explanation clear and well-structured?
Citations	Were citations accurate and sufficient?
Overall	Would you trust this answer for a student?

By collecting these annotations over time, you'll build a high-quality evaluation corpus that can be used to validate future changes to your pipeline, compare different retrieval or prompting strategies, and even calibrate or improve your LLM-as-a-Judge evaluators. This is why human annotation remains a core component of production AI quality assurance, even in systems that rely heavily on automated evaluation.
