1. Your application’s Python logs

These are your logger.info(), logger.warning(), and similar calls.

Your configured run_logs files

They do not appear automatically in the Langfuse dashboard.

2. Langfuse SDK debug logs

Langfuse’s SDK can produce its own debug messages, such as exporting spans, processing batches, authentication errors, or flushing telemetry. LANGFUSE_DEBUG=true enables diagnostic output from the Langfuse SDK.

These SDK messages typically appear in your application console or application log files. They are intended to debug the Langfuse integration itself.

They are not uploaded and displayed as your application logs inside Langfuse.

Several GitHub issues discuss Langfuse SDK messages appearing in developers’ Python logs and difficulties controlling their verbosity. That confirms that SDK logging is standard process logging, separate from observations stored in the Langfuse UI.

3. Langfuse observation log levels

Langfuse observations support the levels:

DEBUG
DEFAULT
WARNING
ERROR

They can also carry a statusMessage.

Example custom handler

The following illustrates the architecture for the current Langfuse SDK API:

import logging
import traceback
from typing import Optional

from langfuse import get_client


PYTHON_TO_LANGFUSE_LEVEL = {
    logging.DEBUG: "DEBUG",
    logging.INFO: "DEFAULT",
    logging.WARNING: "WARNING",
    logging.ERROR: "ERROR",
    logging.CRITICAL: "ERROR",
}


class LangfuseLoggingHandler(logging.Handler):
    def __init__(
        self,
        level: int = logging.WARNING,
        include_exception: bool = True,
    ):
        super().__init__(level=level)
        self.langfuse = get_client()
        self.include_exception = include_exception

    def emit(self, record: logging.LogRecord) -> None:
        try:
            # Prevent an infinite feedback loop.
            if record.name.startswith(("langfuse", "opentelemetry")):
                return

            message = record.getMessage()

            metadata = {
                "python_level": record.levelname,
                "logger": record.name,
                "module": record.module,
                "function": record.funcName,
                "line": record.lineno,
                "pathname": record.pathname,
                "process_id": record.process,
                "thread_name": record.threadName,
            }

            request_id = getattr(record, "request_id", None)
            if request_id:
                metadata["request_id"] = request_id

            if record.exc_info and self.include_exception:
                metadata["exception"] = "".join(
                    traceback.format_exception(*record.exc_info)
                )

            event = self.langfuse.start_observation(
                as_type="event",
                name=f"log:{record.name}",
                metadata=metadata,
                level=PYTHON_TO_LANGFUSE_LEVEL.get(
                    record.levelno,
                    "DEFAULT",
                ),
                status_message=message,
            )
            event.end()

        except Exception:
            # Logging must never crash the application.
            self.handleError(record)

The exact accepted parameters can vary slightly with your installed Langfuse SDK version, so the implementation must be matched to that version. The overall mechanism remains the same.

Better filtering than just log level

A logging filter lets you decide exactly what reaches Langfuse.

class LangfuseLogFilter(logging.Filter):
    EXCLUDED_LOGGERS = {
        "httpx",
        "httpcore",
        "urllib3",
        "pymongo",
    }

    def filter(self, record: logging.LogRecord) -> bool:
        if record.name.startswith("langfuse"):
            return False

        if record.name in self.EXCLUDED_LOGGERS:
            return False

        return record.levelno >= logging.WARNING

def filter(self, record):
    if record.levelno >= logging.WARNING:

    return getattr(record, "send_to_langfuse", False)

Concurrency considerations

Your API uses:

await asyncio.to_thread(_ctx["rag_app"].invoke, ...)

asyncio.to_thread() copies the current contextvars context into the worker thread. That generally allows the active OpenTelemetry context to travel with the graph execution.

This matters because multiple requests could run simultaneously:

Request A → Trace A → Worker thread A → Logs belong to Trace A
Request B → Trace B → Worker thread B → Logs belong to Trace B

You must not store the “current trace” in a normal global variable:

current_trace = trace  # unsafe

A global variable could be overwritten by another request, causing Request A’s logs to appear under Request B’s trace. OpenTelemetry context and Python contextvars are designed to prevent that cross-request contamination.

Your request_id system should also be implemented using contextvars, not a mutable global variable.

Handling logs outside a trace

Some application logs occur when no request trace exists:

logger.info("MongoDB client initialized")
logger.info("Vector store initialized")
logger.info("LangGraph RAG API ready")

These happen during startup. There are two possible behaviors.

Option A: Ignore untraced logs

The Langfuse handler checks whether an active trace exists. If none exists, it skips the record. Startup logs remain in normal files and console output.

This is usually preferable.

Option B: Create standalone Langfuse traces

Each startup log could create its own trace:

Trace: application-startup
├── MongoDB initialized
├── Vector store initialized
└── API ready

This can be useful, but requires a deliberately created startup span around initialization. Otherwise, each event may become an isolated trace and pollute the trace list.

I recommend ignoring ordinary startup logs and creating one dedicated startup trace only if startup diagnostics are operationally important.

Preventing recursive logging

This is a critical issue.

The Langfuse SDK itself uses Python logging:

logging.getLogger("langfuse")

Suppose your handler receives this SDK log:

Langfuse request failed

The handler attempts to send it to Langfuse. That attempt creates another Langfuse SDK log, which the handler tries to send again:

Langfuse request failed
→ handler sends to Langfuse
→ Langfuse logs another failure
→ handler sends that failure
→ repeated recursion

Always exclude at least:

if record.name.startswith("langfuse"):
    return

It is also sensible to exclude:

"opentelemetry"
"httpx"
"httpcore"
"urllib3"

depending on which libraries Langfuse uses internally.

Failure isolation

Logging should never break the RAG application.

If Langfuse is unavailable:

The LLM workflow should continue.
The API should still return an answer.
File logging should still work.
The custom handler should silently handle its own failure.

Therefore:

try:
    # Create Langfuse event
except Exception:
    self.handleError(record)

Do not raise exceptions from emit().

Also, avoid calling:

logger.exception(...)

inside the handler’s own exception block, because that would pass through the same handler again. Use handleError() or direct sys.stderr output when debugging the handler itself.
