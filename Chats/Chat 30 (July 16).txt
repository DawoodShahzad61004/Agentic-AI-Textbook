Marker-PDF configuration and header/footer handling

I inspected Marker’s current repository, configuration parser, converter pipeline, renderers, header/footer block classes, layout builder, relabeling processor, and relevant GitHub issues.

The most important conclusion is:

Marker does not remove headers and footers through text matching or a simple “remove repeated lines” option. Its layout model classifies regions as PageHeader or PageFooter, and the renderer excludes those block types from the final output by default.

This distinction matters because if Marker misclassifies a real heading as PageHeader, that content disappears. Conversely, if a repeated header is classified as ordinary Text, it remains in the output.

The findings below reflect the current master branch. Marker’s configuration surface evolves regularly, so pin the marker-pdf version in production.

1. Marker is more than a “PDF loader”

Marker is fundamentally a document-conversion pipeline. It converts PDF, DOCX, PPTX, XLSX, images, HTML, and EPUB into:

Markdown
HTML
Hierarchical JSON
Flattened chunks suitable for RAG

Its pipeline is approximately:

For a PDF, PdfConverter builds the document using:

LayoutBuilder
LineBuilder
OcrBuilder
StructureBuilder
A sequence of processors
A renderer

See the current PdfConverter source.

In a LangChain or RAG application, “Marker loader” normally means a wrapper that calls Marker and turns its output into framework-specific Document objects. The actual parsing behavior still comes from Marker’s converter configuration.

2. How headers and footers actually work
2.1 Layout classification

Marker’s layout model identifies different page regions and assigns block types such as:

Text
SectionHeader
PageHeader
PageFooter
Footnote
Table
Form
Figure
Picture
Equation
ListItem
TableOfContents
ComplexRegion

For headers and footers, the key types are:

BlockTypes.PageHeader
BlockTypes.PageFooter

The layout model supplies both:

The predicted block type
Alternative predictions and confidence values through top_k
The region’s bounding polygon

Therefore, removal depends primarily on correct layout detection—not on recognizing that the same sentence appears on multiple pages.

2.2 Default behavior: exclude both

The PageHeader and PageFooter block classes have:

ignore_for_output: bool = True

Therefore, both are excluded from rendered output by default.

The relevant implementations are:

PageHeader
PageFooter

The defaults are defined by BaseRenderer:

keep_pageheader_in_output = False
keep_pagefooter_in_output = False

See BaseRenderer.

2.3 PageHeaderProcessor does not remove headers

The name can be misleading.

PageHeaderProcessor only moves blocks classified as PageHeader to the beginning of each page’s structure. It does not determine which regions are headers and does not delete them.

The renderer later decides whether they appear in the output.

See PageHeaderProcessor.

2.4 Footnotes are not page footers

Marker distinguishes:

PageFooter: repeated or peripheral footer material, such as a page number
Footnote: meaningful note content associated with the document text

This is an important distinction for academic papers. Removing page footers should not automatically remove scholarly footnotes.

3. Header/footer configurations

The principal options are:

Configuration	Default	Effect
keep_pageheader_in_output	False	Include regions classified as PageHeader
keep_pagefooter_in_output	False	Include regions classified as PageFooter
paginate_output	False	Insert page separators into output
block_relabel_str	Empty	Relabel low-confidence layout blocks
output_format	markdown	Choose Markdown, HTML, JSON, or chunks
debug_layout_images	False	Save layout visualizations
debug_json	False	Save/debug document structure
force_ocr	False	OCR the whole document
strip_existing_ocr	False	Remove embedded OCR text and OCR again
Scenario A: remove headers and footers

This is already Marker’s default:

config = {
    "keep_pageheader_in_output": False,
    "keep_pagefooter_in_output": False,
}

CLI:

marker_single input.pdf

You normally do not need to supply either configuration explicitly.

Scenario B: preserve both
config = {
    "keep_pageheader_in_output": True,
    "keep_pagefooter_in_output": True,
}

CLI:

marker_single input.pdf \
  --keep_pageheader_in_output \
  --keep_pagefooter_in_output

Because Marker dynamically generates CLI options from annotated component fields, check the installed version:

marker_single --help

If the options are unavailable as direct flags in your installed release, use a JSON configuration file.

marker_config.json:

{
  "keep_pageheader_in_output": true,
  "keep_pagefooter_in_output": true
}

Then:

marker_single input.pdf --config_json marker_config.json
Scenario C: preserve headers but remove footers

This is often useful for technical documents where the header contains:

Component ID
Tender/RFT number
Product name
Chapter context
Confidentiality classification
Document revision
config = {
    "keep_pageheader_in_output": True,
    "keep_pagefooter_in_output": False,
}
Scenario D: remove headers but preserve footers
config = {
    "keep_pageheader_in_output": False,
    "keep_pagefooter_in_output": True,
}

This can be useful if the footer contains document identifiers or revision information rather than only page numbers.

4. Correct Python configuration

For production code, use ConfigParser and pass all generated components to the converter:

from marker.config.parser import ConfigParser
from marker.converters.pdf import PdfConverter
from marker.models import create_model_dict
from marker.output import text_from_rendered

config = {
    "output_format": "markdown",
    "keep_pageheader_in_output": True,
    "keep_pagefooter_in_output": False,
    "paginate_output": True,
}

config_parser = ConfigParser(config)

converter = PdfConverter(
    config=config_parser.generate_config_dict(),
    artifact_dict=create_model_dict(),
    processor_list=config_parser.get_processors(),
    renderer=config_parser.get_renderer(),
    llm_service=config_parser.get_llm_service(),
)

rendered = converter("input.pdf")
text, metadata, images = text_from_rendered(rendered)

print(text)

A common implementation error is to create a configuration dictionary but never pass it to PdfConverter. This does nothing:

config = {"keep_pageheader_in_output": True}

converter = PdfConverter(
    artifact_dict=create_model_dict()
)

The configuration must be provided through config=.

The official pattern is documented in the repository README.

5. Recommended configuration for your RAG system

For your Agentic RAG pipeline, I would not immediately discard all headers.

Start with JSON or chunks output and preserve header/footer blocks during experimentation:

config = {
    "output_format": "json",
    "keep_pageheader_in_output": True,
    "keep_pagefooter_in_output": True,
    "paginate_output": True,
    "add_block_ids": True,
    "debug_layout_images": True,
    "debug_json": True,
}

This lets you inspect:

Which text Marker classified as PageHeader
Which content it classified as PageFooter
Bounding polygons
Page IDs
Block IDs
Block ordering
False positives and false negatives

After inspecting representative documents, choose one of these policies:

Policy 1: remove everything classified as header/footer

Best for:

Books with repeating titles
Academic papers with journal names
Documents with ordinary page numbers
Clean, consistent layouts

Risk: valuable identifiers may disappear.

Policy 2: retain headers and remove them downstream

Best for production RAG.

Preserve header blocks from Marker, then apply your own rules:

Remove exact or normalized repetitions.
Preserve headers containing document IDs.
Preserve headers that change by section.
Store header information as chunk metadata.
Do not embed page numbers into semantic content.
Attach section-specific headers to the chunks beneath them.
Policy 3: preserve headers in metadata only

This is usually the best RAG architecture.

For each chunk:

{
  "page": 17,
  "section": "Technical Requirements",
  "page_header": "RFT 6000042656 — EPC Rejuvenation Project",
  "page_footer": "Revision 3 — Confidential",
  "content": "The contractor shall..."
}

Then:

Embed content and possibly section.
Retain identifiers in metadata.
Use metadata for filtering and citations.
Avoid repeated boilerplate dominating vector similarity.

This balances context preservation with retrieval quality.

6. When header/footer removal fails
6.1 Header classified as ordinary text

If a header remains in the output, Marker probably classified it as:

Text
SectionHeader
Table
Picture
Another block type

The keep_pageheader_in_output flag cannot remove a block that was never classified as PageHeader.

Recommended diagnosis:

marker_single input.pdf --debug --output_format json

Then inspect the block type and polygon.

6.2 Real content classified as a page header

If text is missing, Marker may have classified it as PageHeader, after which the default renderer silently excludes it.

Temporarily enable:

{
  "keep_pageheader_in_output": true,
  "keep_pagefooter_in_output": true,
  "output_format": "json",
  "debug_layout_images": true
}

If the missing content reappears, the root cause is layout classification rather than OCR failure.

6.3 Scanned documents

In scanned PDFs, the layout model may see the header region, but OCR still has to recognize its contents.

Try:

config = {
    "force_ocr": True,
    "keep_pageheader_in_output": True,
    "keep_pagefooter_in_output": True,
}

If the PDF already has a broken OCR layer:

config = {
    "strip_existing_ocr": True,
    "keep_pageheader_in_output": True,
    "keep_pagefooter_in_output": True,
}

Do not casually enable both strategies across an entire production corpus without testing. Full OCR increases:

Runtime
GPU/CPU consumption
Recognition variability
Risk of changing already-correct digital text
Potential math improvements, but also occasional OCR artifacts
6.4 Header rendered as an image

If a decorative or scanned header is classified as Picture, header-specific configuration will not control it.

Options include:

Keep image extraction and process the image separately.
Use OCR.
Enable LLM image description.
Relabel the block.
Implement a custom processor based on location and content.
6.5 Alternating left/right headers

Books commonly place headers differently on odd and even pages. Geometric rules that only look at one x-position will fail. Marker’s layout detection is more flexible than a fixed crop, but downstream repetition removal must normalize both variants.

6.6 First-page headers

The first page frequently contains:

Document title
Company
Author
Tender number
Revision
Classification

These may look geometrically like headers but are semantically important. Avoid deleting top-of-page text solely based on position.

7. Using block_relabel_str

Marker includes a heuristic relabeling processor. Its configuration format is:

OriginalType:NewType:ConfidenceThreshold

Example:

config = {
    "block_relabel_str": (
        "PageHeader:Text:0.70,"
        "PageFooter:Text:0.70"
    )
}

The behavior is subtle:

Marker inspects the confidence of the original predicted label.
If the original-label confidence is above the supplied threshold, it keeps the original label.
If confidence is not above the threshold, it changes the block to the target type.

Therefore, the example means:

If Marker is not sufficiently confident that a block is a PageHeader or PageFooter, treat it as ordinary text.

This can reduce false-positive deletion, but it may also retain genuine boilerplate.

The implementation is in BlockRelabelProcessor.

A conservative configuration might be:

config = {
    "block_relabel_str": (
        "PageHeader:Text:0.80,"
        "PageFooter:Text:0.80"
    ),
    "keep_pageheader_in_output": False,
    "keep_pagefooter_in_output": False,
}

Interpretation:

High-confidence header/footer predictions remain excluded.
Lower-confidence predictions become ordinary text and remain visible.

Do not choose 0.80 blindly. Measure it against a labeled validation set from your own PDFs.

10. Custom header/footer processor

If your documents follow stable templates, a custom processor can outperform generic layout classification.

For example, you might:

Inspect blocks within the top 7% or bottom 7% of a page.
Normalize their text.
Compare normalized text across pages.
Remove only blocks repeated on enough pages.
Preserve document IDs and changing section headers.
Store preserved identifiers as metadata.

A robust normalizer might:

Lowercase text
Collapse whitespace
Strip page numbers
Strip dates only when appropriate
Normalize punctuation
Replace digit sequences with placeholders
Use fuzzy similarity cautiously

Example conceptual rule:

is_candidate = (
    block_top < page_height * 0.07
    or block_bottom > page_height * 0.93
)

is_repeated = normalized_text_frequency >= 0.60 * total_pages

But several edge cases require additional rules:

Odd/even page headers
Chapter headers that change
Very short documents
Blank pages
Rotated pages
Section-specific templates
Page number-only blocks
Legal disclaimers
Confidentiality markings
Revision numbers that change
Tables reaching the footer region

For production, do not delete candidates immediately. First assign:

block.metadata["suspected_boilerplate"] = True

Then remove them during rendering or RAG ingestion after validation.

11. GitHub issue findings

The repository’s issue history confirms that header/footer behavior remains a practical concern.

Issue #851 requested retaining headers when paginated Markdown is generated because technical-document headers can contain component identifiers essential for RAG. It was closed as completed, corresponding to the current keep-header configuration.
Issue #929 reports difficulty getting PageHeader and PageFooter into output through configuration. It remained open when inspected, indicating that configuration/version usage can still be confusing.
Issue #737 describes scanned-document headers and footers being omitted even when they contain valuable text. This illustrates that “ignore headers” is sometimes data loss rather than cleanup.
Issue #556 discusses missing text and includes an older, extensive Marker configuration. It is also a warning against blindly copying issue-era configurations into newer versions.

The community evidence supports a central production lesson:

Header/footer removal is a document-policy decision, not universally desirable preprocessing.

This splitter breaks Markdown-like text into chunks of at most CHUNK_SIZE characters while trying to preserve meaningful structure.
The key idea is: separators are attempted in priority order, recursively.
Split at headings first.
If a resulting section is still too large, split it at horizontal rules.
If still too large, split it into paragraphs.
Then list items.
Then lines.
Then words.
Finally, individual characters.
It does not apply every separator to the entire document immediately. Lower-priority separators are used only when higher-level splitting still leaves oversized pieces.
How chunk creation works
Conceptually:
document
  → heading sections
      → oversized section rules
          → oversized paragraphs
              → oversized list items
                  → oversized lines
                      → words
                          → characters
After splitting, neighboring pieces are merged while their combined length remains within CHUNK_SIZE. The splitter tries to retain approximately CHUNK_OVERLAP characters from the preceding chunk when constructing the next one.
For example, given:
# Installation

Install the package.

- Create a virtual environment
- Run the installation command

# Usage

Run the application.
It prefers producing chunks around # Installation and # Usage. If the installation section is too large, it tries paragraphs and list items before breaking sentences into words.
Separator breakdown
r"\n(?=#{1,6}\s)"
Splits before Markdown ATX headings:
# Heading
## Heading
...
###### Heading
The lookahead (?=...) locates a newline followed by 1–6 # characters and whitespace. Because it looks ahead, the heading itself remains part of the following section.
It will not recognize an indented heading such as:
  ## Heading
r"\n(?=(?:-{3,}|\*{3,}|_{3,})[ \t]*(?:\n|$))"
Splits before Markdown horizontal rules:
---
***
___
It accepts three or more matching rule characters and optional trailing spaces or tabs.
r"\n\n+"
Splits at paragraph boundaries: two or more consecutive newline characters.
r"\n(?=\s*[-*+]\s+)"
Splits before unordered list items:
- item
* item
+ item
    - nested item
The \s* allows indentation, so nested bullets are recognized.
r"\n(?=\s*\d+[.)]\s+)"
Splits before numbered list items:
1. item
2) item
    3. nested item
It supports one or more digits followed by either . or ).
r"\n"
If the previous structural boundaries are insufficient, split into individual lines.
r"[ \t]+"
If a line is still too large, split it at runs of spaces or tabs—effectively into words.
""
Last-resort character splitting. This ensures that even a huge unbroken string can be constrained to CHUNK_SIZE.
Other parameters
length_function=len
Chunk size is measured in Python characters, not tokens or bytes. Therefore, a chunk of 1,000 characters may correspond to very different token counts depending on its content.
is_separator_regex=True
The separator strings are interpreted as regular expressions. Without this, patterns such as (?=...), \s, and \d would be treated as literal text.
chunk_overlap=CHUNK_OVERLAP
The splitter attempts to carry some ending content from one chunk into the next. This helps retrieval because information near a chunk boundary appears in both chunks. The exact overlap can be smaller than requested when structural pieces or separators do not combine neatly.
The most important point is that this configuration favors document structure over arbitrary fixed-width cutting, but still guarantees a fallback down to character-level splitting.

This function estimates the number of tokens in a string using a regular expression:

def _count_tokens(text: str) -> int:
    """Count deterministic lexical tokens without a model-specific tokenizer."""
    return len(re.findall(r"\w+|[^\w\s]", text, flags=re.UNICODE))
Function definition
def _count_tokens(text: str) -> int:
_count_tokens is the function name.
The starting underscore indicates that it is intended for internal use.
text: str says the input should be a string.
-> int says the function returns an integer.
How the counting works
re.findall(r"\w+|[^\w\s]", text, flags=re.UNICODE)

re.findall() returns every substring matching either side of |:

\w+ matches one or more word characters, including letters, digits, and underscores.
[^\w\s] matches one character that is neither a word character nor whitespace. In practice, it counts punctuation and symbols individually.
| means “or.”
flags=re.UNICODE makes word matching Unicode-aware, supporting non-English characters.

For example:

text = "Hello, world!"

Matches:

["Hello", ",", "world", "!"]

Therefore:

_count_tokens("Hello, world!")  # 4

Another example:

_count_tokens("RAG uses top_k=5.")

Matches:

["RAG", "uses", "top_k", "=", "5", "."]

Result: 6.

Important limitation

This does not count actual LLM tokens. It counts lexical units according to fixed rules. Real model tokenizers may split text differently:

"unbelievable"

This function counts it as one token, while an LLM tokenizer might divide it into multiple subword tokens.

The function is useful when you need a fast, deterministic, tokenizer-independent approximation. The same text will always produce the same count, regardless of which LLM is being used.

Consider i used a LLM-tokenizer. What would its split be?

text = "Hello, world!"

The exact split depends on the specific LLM tokenizer. A likely tokenization is:

text = "Hello, world!"
["Hello", ",", " world", "!"]

Notice that the space before world is usually included in the " world" token rather than stored as a separate token.

So the result would likely be 4 LLM tokens:

Token	Content
1	"Hello"
2	","
3	" world"
4	"!"

Your regex-based function also returns four items:

["Hello", ",", "world", "!"]

The difference is that the regex ignores whitespace, whereas many LLM tokenizers encode whitespace as part of the following token.

However, another tokenizer could produce something like:

["Hello", ",", " world", "!"]

or split Hello into smaller subwords. You need the tokenizer associated with your exact model to determine the authoritative split.
