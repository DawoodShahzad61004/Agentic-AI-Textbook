Good — I found the root cause of all three symptoms. They're three independent things, and the KeyboardInterrupt is not from you.

1. First file — maximum recursion depth exceeded
This is a RecursionError raised inside Marker, not in your runner. Look at the log lines right before it:


Table OCR failed for block /page/28/Table/6
Table processing stats: {'tables_pdftext': 19, 'tables_ocr': 36, 'tables_ocr_failed': 1, 'tables_total': 56}
Overflow in columns: 0 >= 3 or rows: 1 >= 1
FAILED: ...: maximum recursion depth exceeded
56 tables in one document, one of them failing OCR and then hitting the "Overflow in columns/rows" merge path. Marker's table structure builder recurses while reconciling cells, and this document's dense/degenerate tables drove it past Python's default recursion limit (1000). It's triggered by the document content, not by your environment or GPU. Your runner did exactly the right thing — caught it and moved on. This matches the caveat already in CLAUDE.md that Marker corrupts/loops on dense cross-page tables.

2. Second file — A worker process died while extracting ...
Surya (which Marker 2.0.0 uses) runs inference in a separate spawned process (the spawn.py backend in surya/inference/backends/spawn.py). That worker process crashed hard — almost always an out-of-memory kill (GPU VRAM on the RTX 5050, or system RAM) or a native crash in the inference server, on a 250-page PDF right after the first document already stressed things. The parent can only observe that the pipe closed, hence the generic message. As it says, workers=None (in-process) would surface the real traceback instead of hiding it behind a dead pipe.

3. The KeyboardInterrupt — surya did it to itself, not you
This is a genuine bug in surya's cleanup on Windows. The traceback lands here:


spawn.py, line 131, in _stop_process
    time.sleep(0.5)
KeyboardInterrupt
Look at _stop_process:


os.kill(pid, 15)          # SIGTERM
for _ in range(20):
    try:
        os.kill(pid, 0)   # "still alive?" — POSIX idiom
    except ProcessLookupError:
        return
    time.sleep(0.5)
That os.kill(pid, 0) is the POSIX way to poll whether a process is alive. But on Windows, signal 0 is CTRL_C_EVENT (signal.CTRL_C_EVENT == 0). So os.kill(pid, 0) doesn't check liveness — it sends a Ctrl+C event to the shared console process group. Your parent Python process is attached to that same console, so it receives the Ctrl+C and raises KeyboardInterrupt — which surfaces in the time.sleep(0.5). (For the same reason, the "graceful" os.kill(pid, 15) above doesn't send SIGTERM either; on Windows any non-0/1 signal just TerminateProcesses.)

So: you pressed nothing. Surya's atexit cleanup ran when the script exited, tried to tear down the spawned inference server using POSIX signal idioms that mean something completely different on Windows, and effectively fired a Ctrl+C at your own terminal. It's cosmetic — it happens after both conversions already failed, during shutdown ("Exception ignored in atexit callback" means Python swallowed it). It has zero effect on the results.

* Root cause 1: `_structural_cut`'s heading-hierarchy rule (Rule 2) located a subsection run's closing boundary by searching only for the *next same-level* heading; when a document uses a heading level exactly once (e.g. one-off `#####` subsections inside a single `####` clause), no same-level sibling exists anywhere else in the document, so the search fell back to end-of-document and the rule concluded the run never closes — dropping subsections that actually already fit. Fixed by also accepting the next *shallower* heading as a valid closing boundary.
* Root cause 2: the "keep a list with its lead-in paragraph/heading" helpers required the list to be flat (single indentation level), so a list with any nested sub-item was invisible to the check and fell through to generic size-based cutting. Renamed and relaxed `_flat_list_section_after_heading`/`_flat_list_section_after_paragraph` (now `_list_section_after_*`) to detect lists regardless of nesting, and added `_top_level_item_boundaries()` so the oversized-list fallback splits on top-level pointers only, keeping nested children attached to their parent pointer.
* While verifying with a full round-trip check (every chunk must reappear in the preprocessed text with nothing left over), found that the first version of `_top_level_item_boundaries()` silently dropped content: when the starting cursor was itself mid-way through a nested run (left there by a previous cut), the returned boundaries never included the cursor itself, so everything between it and the next true top-level pointer vanished. Fixed by always forcing the start position in as the first boundary. Confirmed zero dropped content across all four real documents in `marker_results/` after the fix.
* The user then pointed out that clause 5.4's heading and lead-in were still getting stranded at the end of the *previous* chunk while its subsections started the next one — Rule 2 was dropping only the first dropped subsection, not the parent heading that introduces it. Added `_enclosing_heading_start()`: when a subsection run gets pushed forward, the immediately-preceding shallower heading (if it directly owns the run, nothing else in between) is pulled forward with it, so the whole section starts fresh together.
* That exposed a second, latent bug in the same rule: once a subsection hierarchy resolves *before* the size limit (now much more common thanks to the shallower-heading fix above), the "otherwise" branch returned the raw, unsnapped character limit instead of a safe boundary — producing a mid-word cut in unrelated trailing prose that just happened to follow the hierarchy. Fixed by falling through to the existing paragraph/word-boundary rules instead of returning early. Re-verified the round-trip check (still zero dropped content) and the full pipeline on all four documents.

#### 2026-07-21 — Upgrade Marker to 2.0.0 and rebuild the GPU/inference environment

* Started from a chunk-quality problem, not an environment one: running headers and footers were entering `marker_results/` and degrading chunk boundaries. Research topic 6 had already established that Marker's `keep_pageheader_in_output=False` default only suppresses blocks the layout model classified as `PageHeader`, so a header labelled `Text` or `SectionHeader` is unreachable by configuration. Verified against the installed 1.10.2 tree that no `MarginaliaProcessor` existed and sketched a local geometric processor as a workaround; discarded it once `marker-pdf` was upgraded to 2.0.0, where the upstream implementation ships in the default PDF pipeline with stricter guards (ADR-009).
* The upgrade turned out to be architectural rather than a version bump. surya-ocr 0.22.1 no longer runs the VLM in-process; it spawns a separate inference server speaking OpenAI-compatible chat completions and selects the backend from hardware. Every conversion failed immediately with a Docker connection error, because an NVIDIA GPU selects the vllm backend, which runs as a container (BUG-017). Rejected Docker/vllm as impractical against 8 GB of laptop VRAM and installed llama.cpp `llama-server` b10068 (CUDA 13.3 build plus cudart) instead, forcing `SURYA_INFERENCE_BACKEND=llamacpp` from `codes/marker_test.py` before the marker import.
* Three further failures followed, each surfacing only after the previous was cleared. Guided layout decoding sends a JSON schema llama.cpp cannot convert to a GBNF grammar, so every request returned `failed to parse grammar` until `SURYA_GUIDED_LAYOUT=false` was set (BUG-018). Appending the llama.cpp directory to the user `PATH` did not reach the already-running IDE terminal, so binary resolution kept failing; a `LLAMA_CPP_BINARY` fallback to the default install path was added rather than hard-coding a machine-specific path. And a stale `torchaudio 2.11.0+cu128`, orphaned by restoring Torch to `2.13.0+cu130`, killed the `ocr_error` server subprocess behind an opaque 300-second health-check timeout — its ABI-broken extension passing `transformers`' installed-not-importable guard (BUG-019).

## ADR-010 · Chunk by packing a structural tree, not by selecting boundaries against a size limit

| Field | Detail |
|---|---|
| **Decision** | Rewrite `temp_split()` as a two-phase algorithm: parse the document once into a tree of structural units (sections nested by ATX heading level; within each section its own tables, lists and paragraphs), then pack those units greedily into chunks. Retire the rule-based boundary selector (`_structural_cut()` and its eight supporting helpers) entirely. |
| **Date** | 2026-07-22 |
| **Context** | The hand-authored rule set from 2026-07-17 had been extended six times against real RFT output and was still producing two classes of defect the user reported directly: chunks far below `CHUNK_SIZE` sitting next to content that would have fitted (a 64-character opening chunk), and sections torn in half at a subsection boundary (clause 5.4 split between `Technical Bids` and `Commercial Bids`). See BUG-022. |
| **Options Considered** | Add a minimum-fill rule to `_structural_cut()` (rejected: the seventh patch to a rule set whose rules already contradict each other — `_list_section_after_heading()` deliberately emits an under-full chunk, so a global minimum-fill rule would have to carve out exceptions for its own siblings) · Keep boundary selection but fix the deepest-ATX-level heuristic (rejected: the heuristic is a proxy for section ownership and only works when heading levels are well-formed, which Marker's are not — BUG-021 — so it would stay one malformed document away from the same failure) · **Parse-then-pack over a structural tree (chosen)** |
| **Chosen Solution** | `_build_tree()` produces `_Node` units; `_pack()` fills a chunk with whole sibling units until the next would not fit, then moves that unit forward intact; `_split_node()` opens a unit up only when it does not fit an empty chunk by itself, and only one level at a time. A heading always travels with the first unit beneath it (`_extend_start()`), so no depth of splitting can strand one. A pending buffer that holds only headings, or that sits in front of a unit about to be opened anyway, is handed into that unit rather than published early (`_lead_in_fits()`). Tables stay atomic at any size; oversized lists split on top-level pointers, keeping nested children with their parent. |
| **Rationale** | The user's stated intent — "fill each chunk with as many characters as `CHUNK_SIZE` permits, but never separate a heading from its content or split a logical section; if the complete next section cannot fit, move the entire section to the next chunk" — is literally the definition of greedy packing over a containment tree. Expressing it that way makes the two reported defects unrepresentable rather than patched: a chunk closes only when the next whole unit does not fit, and a unit is only ever divided along boundaries the document itself declares. It also removed 202 lines and eight helpers whose interactions were the actual source of the bugs. |
| **Impact** | Chunk boundaries change document-wide; existing `chunk-runs/` reports are not comparable. Chunk count on the current two-document corpus fell from 1,949 to 1,051 as chunks became fuller. Verified lossless by whitespace-normalised round trip across `marker_results/`, `docling_results/` and `unstructured_results/` (nine files), with every oversize chunk confirmed to be a table. The splitter remains experimental — there is still no test suite, and verification means re-running `ingest.py` and reading the report. |

### Rules for table chunking

1. **If the complete table fits**

   If `whole_table_size <= CHUNK_SIZE`, store the complete serialized table as one chunk.

2. **General chunk-size rule**

   If the table does not fit:

   * Measure the size of the final serialized chunk, including all repeated headers.
   * Preserve complete rows, columns, and cells whenever possible.
   * Add as much table content as possible without exceeding `CHUNK_SIZE`.
   * Preserve multi-level or merged headers in their complete applicable form.

3. **Table with column headers only — split horizontally by rows**

   * Repeat the complete column headers at the beginning of every chunk.
   * Add as many complete consecutive data rows as can fit.
   * Start the next chunk with the same column headers, followed by the remaining rows.

4. **Table with row headers only — split vertically by columns**

   * Repeat the complete row headers in every chunk.
   * Add as many complete consecutive data columns as can fit.
   * Start the next chunk with the same row headers, followed by the remaining columns.

5. **Table with both column and row headers — split horizontally by rows**

   * Repeat the complete column headers in every chunk.
   * Preserve the applicable row header with each data row.
   * Add as many complete consecutive rows as can fit.
   * Continue with the remaining rows in the next chunk, again repeating the column headers.
   * If the table has multi-level row or column headers, repeat the complete applicable hierarchy.

6. **Table with neither column nor row headers — split horizontally by rows**

   * Add as many complete consecutive rows as can fit.
   * Continue the next chunk with the remaining rows.
   * Do not generate artificial row names, column names, or positional labels.

7. **Oversized row**

   If one complete row cannot fit:

   * Split the row into groups of consecutive cells or columns.
   * Place as many complete cells as possible in each chunk.
   * Repeat the row header if one exists.
   * Include the applicable column headers for the cells placed in each chunk.
   * Do not immediately create one chunk per cell unless only one cell can fit.

8. **Oversized column**

   If one complete column cannot fit:

   * Split the column into groups of consecutive cells or rows.
   * Place as many complete cells as possible in each chunk.
   * Repeat the column header if one exists.
   * Include the applicable row headers for the cells placed in each chunk.
   * Do not immediately create one chunk per cell unless only one cell can fit.

9. **Oversized individual cell**

   If an individual cell, together with its applicable headers, exceeds `CHUNK_SIZE`:

   * Split only the cell’s content.
   * Prefer structural boundaries in this order:

     1. Paragraph boundaries
     2. List-item boundaries
     3. Sentence boundaries
     4. Word or token boundaries
   * Repeat the applicable row and column headers with every resulting piece.
   * Do not add a fragment index.

## ADR-011 · Bound tables by `CHUNK_SIZE` too, re-serializing them with repeated headers

| Field | Detail |
|---|---|
| **Decision** | Remove the standing exemption that let a Markdown table be emitted whole at any size. A table that does not fit is now split into several chunks, each re-serialized with the headers that apply to the cells it carries. Splitting is by row when the table has column headers (or none), by column when it has only row headers, and descends to cell groups and then to content inside a single cell when a row, column, or cell is itself too large. |
| **Date** | 2026-07-22 |
| **Context** | Every prior chunker in this project treated a table as one indivisible retrieval unit, on the grounds that a header row separated from its data is worse than an oversized chunk. That produced 38 chunks above the limit across the two-document corpus, the largest 10,071 characters — well past the context budget any downstream retrieval step would allocate to a single chunk, so the guarantee was protecting a unit that could not actually be used. |
| **Options Considered** | Keep the exemption (rejected: an unusable chunk is not a preserved one) · Split tables blindly by row without repeating headers (rejected: every piece after the first loses the column names, which is exactly the failure the exemption existed to prevent) · Slice table pieces out of the source verbatim (rejected: verbatim slices cannot carry a repeated header, and Marker pads columns to the widest cell — alignment rows of 800+ characters occur here — so a verbatim piece spends most of its budget on padding) · **Re-serialize with normalized padding and repeated headers (chosen)** |
| **Chosen Solution** | `_split_table()` parses the table into a header stack, an alignment row, and data rows, then dispatches on which headers exist. Padding and the alignment row are normalized on output; the size limit is measured on the emitted chunk, not on the source it came from. Orientation is decided by `_has_column_headers()` and `_has_row_headers()`, the latter a documented heuristic (Markdown has no row-header syntax) that only chooses between splitting axes and whether a row label is repeated. Fallbacks descend in order: whole rows → cell groups within a row (`_split_across_columns`) → content within one cell (`_split_cell`, preferring paragraph, then list-item, then sentence, then word boundaries). Any heading introducing the table repeats on every piece, since each piece is meant to stand alone. |
| **Rationale** | Repeating the headers is what makes splitting safe: the reason tables were exempt was that a bare row block is uninterpretable, and a repeated header removes that objection at a cost of a few dozen characters per chunk. Normalizing padding is not cosmetic — the RFT summary table is 5,922 characters of source that carries 1,823 characters of content, so normalization alone brings many tables back under the limit and satisfies rule 1 without any split at all. |
| **Impact** | No chunk in the corpus now exceeds `CHUNK_SIZE`, down from 38. Chunk count rose from 1,051 to 1,069. Split tables are no longer byte-identical to their source: padding is normalized, alignment rows are rewritten to `---`, and headers appear more than once — so the strict round-trip check used since 2026-07-20 no longer applies to them and was replaced by a per-line survival check (every source row, normalized to its rendered form, must appear in some chunk). Content can only be lost inside a single cell that exceeds the limit on its own, which no table in the current corpus does. Supporting changes: `_table_cells()` now honours escaped and code-span pipes so column indices are correct, and `_table_spans()` extends backwards over rows above the alignment row so multi-level header stacks are captured and repeated in full. |

Root cause — two paths, not one
The obvious one: #### **APPENDIX 1** is a sibling of #### **BID TIMETABLE**, not its parent. So it becomes a heading-only unit, gets buffered onto the tail of the previous chunk, and is published there when the following section turns out too large to join it.

Measuring first showed 43 of 1,042 chunks had this shape, so I fixed the class rather than the instance. That took it to 5 — and the 5 survivors were a different path: a heading-only unit that is the last child of a section, flushed by the inner _pack() after its loop while the outer document still had text. The tell was that every one was followed by a shallower heading. _pack() had no way to know text followed, so _pack()/_split_node() now carry a tail_open flag and return the trailing run instead of emitting it, letting the caller place it in front of what it introduces.

Both paths now go through _trailing_heading_start(). Notably, when the next node is a table, the carried heading becomes part of the prefix repeated on every table piece — which is why chunk 13 above opens with both APPENDIX 1 and BID TIMETABLE.

This guard existed in the pre-ADR-010 algorithm and I dropped it in the rewrite; the replacement only checked for a buffer holding only headings, not one merely ending in them. That's on me — recorded as BUG-023 rather than quietly patched.

## 1. Splitter rewritten: boundary selection → parse-then-pack (ADR-sized)

Replaced the hand-authored `_structural_cut()` rule set (2026-07-17, extended six times) with a two-phase algorithm: `_build_tree()` parses the document into `_Node` units (sections nested by ATX level; within each, its own tables/lists/paragraphs), `_pack()` fills each chunk with whole sibling units until the next will not fit, `_split_node()` opens a unit only when it cannot fit an empty chunk alone, one level at a time. `_extend_start()` makes a heading travel with the first unit beneath it at every depth; `_lead_in_fits()` hands a short pending buffer into a unit about to be opened rather than closing early.

- Triggered by two user-reported defects: a **64-character opening chunk** next to ~1,500 characters that would have fitted, and clause 5.4 torn between its `Technical Bids` and `Commercial Bids` subsections.
- Cause: `_structural_cut()` picked the *deepest* ATX level in the window and pushed that run forward; `_enclosing_heading_start()` then pulled the cut back to the `#` title. Deepest-level is a proxy for section ownership that only works when heading levels are well-formed.
- Rejected: patching `_structural_cut()` with a minimum-fill rule (its own siblings, e.g. `_list_section_after_heading()`, deliberately emit under-full chunks, so the rules already contradicted each other).
- Removed `_structural_cut()` + 11 helpers. `ingest.py` 1,176 → 974 lines, no unreferenced functions.
- Marker corpus 1,949 → **1,051** chunks (CHUNK_SIZE=1600).

## 2. Heading-level inversion in `preprocessing()` (bug-sized)

`_apply_heading_branch()` took the promoted level from whichever block Marker had already written as a heading. Marker emitted `### 5.6`/`### 5.7` while leaving 5.1–5.5 as plain text, so the whole run was promoted to level 3 — *shallower* than the `#### **5. INSTRUCTIONS TO BIDDERS**` section containing it. Every clause parsed as a sibling of its own parent; `_promote_italic_sublabels()` compounded it via `last_level + 1`.

Fixed by treating an existing prefix as a floor and raising it to at least the enclosing heading's level (`_enclosing_heading_level()`), clamped to 6.

**Decided against `enclosing + 1` on evidence, not taste** — worth recording, this is the kind of "felt right at the time" call: `+1` is the semantically obvious choice, but diffing `preprocessing(dataset/input.md)` against `dataset/expected-output.md` showed `+1` deviating on **84 heading lines**, while level-with-the-parent reproduced the ground truth's levels exactly (400 vs 604 differing diff lines overall). Level-with-parent is sufficient because a section heading owning nothing is never stranded — the packer carries a headings-only buffer forward.

## 3. Tables brought under `CHUNK_SIZE` (ADR-sized)

Removed the standing exemption that let a table be emitted whole at any size. User supplied nine rules; implemented in `_split_table()` and friends.

- Exemption's measured cost: **38 chunks over the limit**, largest **10,071 characters**.
- Corpus survey that drove the design: Marker pads columns to the widest cell, producing **alignment rows up to 897 characters** of dashes; the RFT summary table is **5,922 source characters carrying 1,823 characters of content**.
- Therefore re-serialize rather than slice verbatim — a slice cannot carry a repeated header, and most of its budget is padding. Normalizing padding alone satisfies rule 1 for many tables: that 5,922-char table becomes **1,527 + 296** in two chunks.
- Orientation: by row with column headers / both / neither (rules 3, 5, 6); by column with only row headers (rule 4). Fallbacks descend whole rows → cell groups in a row (7) → rows in a column (8) → inside one cell (9: paragraph → list item → sentence → word).
- `_has_row_headers()` is an explicit heuristic (Markdown has no row-header syntax); it only picks the axis and whether a label repeats, so a wrong guess degrades rather than corrupts.
- Two supporting fixes: `_table_cells()` now honours escaped and code-span pipes (harmless when tables were atomic, wrong once cells are addressed by index); `_table_spans()` extends backwards over rows above the alignment row so multi-level header stacks are captured and repeated.
- Rules 7, 8, 9 are **unreachable in this corpus** (longest single row 897 chars; no table has a fully empty header row), so they were validated against a synthetic suite covering all nine rules plus multi-level headers and escaped pipes. One table in the corpus has a doubled separator row.
- **Verification method changed**: split tables are deliberately not byte-identical (padding normalized, alignment rewritten, headers repeated), so the strict round-trip check used since 2026-07-20 no longer applies to them. Replaced by a per-line survival check — every source line, normalized to its rendered form (`_render_row(_table_cells(line))` for rows), must appear in some chunk.
- Content can now be lost only inside a single cell exceeding the limit alone; no corpus table does.
- Marker corpus 1,051 → **1,069** chunks (CHUNK_SIZE=1600).

## 4. Chunks closing on a heading (bug-sized)

A chunk could end on a heading whose content began the next chunk — e.g. ending `#### **APPENDIX 1**` with `#### **BID TIMETABLE**` + table following. **43 of 1,042** chunks (CHUNK_SIZE=2400).

Two distinct paths, found by measuring rather than assuming:
- Most: `APPENDIX 1` is a *sibling* of `BID TIMETABLE`, so it becomes a heading-only unit buffered onto the previous chunk. Fixed in `_pack()`'s flush via a restored `_trailing_heading_start()`. → 5 left.
- The remaining 5: a heading-only unit that is the *last* child of a section, flushed after the inner `_pack()` loop while the outer document still had text. Tell: each was followed by a *shallower* heading. Fixed by giving `_pack()`/`_split_node()` a `tail_open` flag and returning the run instead of emitting it. → **0**.

Note the predecessor algorithm had a `_trailing_heading_start()` guard; the ADR-010 rewrite dropped it and replaced it with a check for a buffer holding *only* headings, which does not catch a buffer merely *ending* in one. That regression is mine and should be recorded as such.

The correct solution is an adaptive, structure-preserving table chunker—not a single fixed rule such as “10 rows per chunk.”

Because the meaning of each table is unknown, the algorithm must avoid pretending it understands the table semantically. It should preserve observable structure, use deterministic heuristics, and maintain enough metadata for later reconstruction.

Recommended algorithm
Core principle
Apply constraints in this order:

Preserve the document and table identity.

Preserve headers and row–column relationships.

Keep complete logical rows whenever possible.

Pack the maximum number of rows within the token budget.

Split columns only when a single row cannot fit.

Split individual cells only as a last resort.

Maintain explicit links among all fragments of the same table.

The approach should produce:

ordinary text chunks;

small whole-table chunks;

large table row-block chunks;

two-dimensional blocks for very wide tables;

atomic cell fragments for pathological oversized cells;

table-level discovery chunks for semantic retrieval.

High-level pipeline


Phase 1: Parse Markdown structurally
Do not detect tables using a loose expression such as “lines containing pipes.” Pipes may occur in code blocks, inline code, escaped text, or ordinary prose.

Use a Markdown parser that exposes an abstract syntax tree, such as:

Python: markdown-it-py

JavaScript/TypeScript: remark, unified, mdast

Rust: pulldown-cmark

The parser should identify:

headings and heading levels;

paragraphs;

lists;

fenced code blocks;

block quotes;

tables;

HTML tables, if allowed;

source line offsets.

Maintain the active heading path while traversing the document:

Document
└── Section 4
    └── Equipment Requirements
        └── Cooling Systems
A table found under this hierarchy should inherit:

{
  "heading_path": [
    "Section 4",
    "Equipment Requirements",
    "Cooling Systems"
  ]
}
This surrounding context can be more valuable for retrieval than the table cells themselves.

Phase 2: Identify each logical table
Assign every table an independent identity:

document_id = doc-17
table_id = doc-17-table-004
Never combine adjacent tables merely because they have compatible column counts. Different tables may serve completely different purposes.

For each table, collect the following:

document ID;

table ID;

nearest preceding heading path;

explicit table caption, if available;

preceding explanatory paragraph;

following explanatory paragraph or footnote, if applicable;

original Markdown;

source line range;

source page numbers, if inherited from PDF conversion metadata;

table ordinal within the document.

A configurable surrounding-context window is useful, but it should respect Markdown block boundaries:

Table context =
    heading path
    + caption
    + nearest relevant preceding paragraph
    + table
    + directly attached notes/footnotes
Do not indiscriminately attach several surrounding paragraphs to every child chunk; that wastes the token budget and dilutes embeddings.

Phase 3: Normalize without destroying the source
Preserve two forms:

Original table representation for citation and reconstruction.

Normalized structured representation for chunking and retrieval.

A useful internal model is:

Table:
    table_id
    heading_path
    caption
    header_rows
    body_rows
    notes
    original_markdown

Row:
    row_id
    cells
    source_line_start
    source_line_end

Cell:
    value
    original_value
    column_index
    header_path
Variable column counts
Strict Markdown tables are normally rectangular. If rows contain different numbers of parsed cells, one of the following is probably true:

trailing empty cells were omitted;

escaped pipes were parsed incorrectly;

OCR damaged the row;

the table contains pseudo-merged cells;

multiline content was split incorrectly;

the input is not valid Markdown-table syntax.

Handle this conservatively.

Normalization rules
Let:

expected_columns = len(parsed_header_columns)
For each row:

If it has fewer cells, append explicit missing values.

If it has more cells, do not silently discard or merge them.

Record a validation warning.

Preserve the original row.

Attempt repair only through deterministic parsing rules.

If repair is uncertain, mark the row as irregular.

Example:

{
  "row_id": "table-4-row-12",
  "expected_columns": 6,
  "actual_columns": 8,
  "parse_status": "irregular",
  "original_markdown": "| ... |"
}
Do not use an LLM to silently “repair” production data. If an LLM-assisted repair is introduced, retain the original version, confidence, model/version, and audit trail.

Phase 4: Resolve header context
The algorithm cannot assume that the first column is an ID or that each row is an independent record. However, it can preserve known syntax.

For a normal Markdown table:

treat the header row before the delimiter as the column-header row;

preserve alignment markers;

map every cell to its corresponding header;

retain empty header names using stable generated labels.

For example:

| Item | 2025 |     |
|------|------|-----|
| A    | 40   | 50  |
may normalize to:

Column 1: Item
Column 2: 2025
Column 3: Unnamed column 3
Do not invent a semantic name for the third column.

If hierarchical headers came from HTML or extraction metadata, flatten their full paths:

Revenue > 2025 > Q1
Revenue > 2025 > Q2
Cost > 2025 > Q1
Every child chunk must repeat the applicable headers.

Phase 5: Define token budgets correctly
Use the same tokenizer as the embedding model whenever possible.

Define:

MAX_CHUNK_TOKENS = embedding_model_limit - safety_margin
But reserve some of that capacity for repeated context:

CONTENT_BUDGET = (
    MAX_CHUNK_TOKENS
    - tokens(table_identity)
    - tokens(heading_path)
    - tokens(caption)
    - tokens(headers)
    - tokens(required_notes)
)
For example:

MAX_CHUNK_TOKENS = 800
SAFETY_MARGIN = 50
The usable row budget might only be 600–700 tokens after headers and metadata are serialized.

Character counts are not reliable substitutes for model tokens, especially with:

Unicode;

long numbers;

identifiers;

source code;

multilingual text;

Markdown punctuation.

Phase 6: Classify the table by physical size
Classification should be based on serialized token size, not a hardcoded number of rows or columns.

Case A: Entire table fits
If this fits:

table context + caption + headers + all body rows + notes
emit one whole-table chunk.

This is preferable for small tables because it preserves comparisons and cross-row relationships.

Case B: Table is too large, but every individual row fits
Use token-aware greedy row packing.

Each chunk contains:

table identity;

heading path;

caption or concise table context;

complete headers;

complete consecutive rows;

applicable notes;

row range;

parent table ID.

Case C: At least one row does not fit
The table is probably very wide or contains a very large cell.

Apply:

safe/key-column detection;

column grouping;

row packing within each column group;

cell fragmentation only if still necessary.

Phase 7: Token-aware row packing
This is the primary strategy for large, tall tables.

duplicate retrieval;

conflicting evidence;

accidental double counting;

increased storage;

misleading aggregation.

Prefer no physical row overlap. If neighboring rows are needed at query time, dynamically expand the retrieved range:

retrieved rows: 31–45
expanded context: 29–47
This provides contextual overlap without permanently duplicating rows.

Phase 12: Retrieval algorithm
Because user queries can vary, use hybrid retrieval rather than semantic vectors alone.

Query flow
Run dense semantic retrieval over:

Run lexical retrieval such as BM25 over:

Merge results using reciprocal-rank fusion or a weighted method.

Group results by table_id.

Deduplicate overlapping row/column blocks.

Expand the most relevant children with:

headers;

neighboring rows;

sibling column blocks when required.

Rerank the expanded candidates.

Pass an evidence package to the answering model.

Route calculation queries to structured execution.

product codes;

exact monetary amounts;

nearly identical numeric records;

abbreviations;

formulas.

def chunk_markdown_document(document, config, tokenizer):
    ast = parse_markdown(document.content)

    text_chunks = []
    table_chunks = []

    heading_path = []

    for block in ast.blocks:
        if block.type == "heading":
            heading_path = update_heading_path(heading_path, block)

        elif block.type == "table":
            table = parse_and_normalize_table(
                block=block,
                document_id=document.id,
                heading_path=heading_path,
            )

            validate_table(table)

            table_chunks.append(
                build_table_discovery_chunk(table, config, tokenizer)
            )

            full_table = serialize_complete_table(table)

            if fits(full_table, config.max_chunk_tokens, tokenizer):
                table_chunks.append(build_whole_table_chunk(table))
                continue

            if all(
                row_fits_with_headers(
                    table, row, config.max_chunk_tokens, tokenizer
                )
                for row in table.body_rows
            ):
                table_chunks.extend(
                    pack_rows(
                        table,
                        config.max_chunk_tokens,
                        tokenizer,
                    )
                )
                continue

            anchors = select_anchor_columns(table, config)

            column_groups = create_safe_column_groups(
                table=table,
                anchor_columns=anchors,
                max_tokens=config.max_chunk_tokens,
                tokenizer=tokenizer,
            )

            for group in column_groups:
                if group.requires_cell_fragmentation:
                    table_chunks.extend(
                        fragment_oversized_cells(
                            table,
                            group,
                            config.max_chunk_tokens,
                            tokenizer,
                        )
                    )
                else:
                    table_chunks.extend(
                        pack_rows_for_columns(
                            table=table,
                            selected_columns=group.columns,
                            anchor_columns=anchors,
                            max_tokens=config.max_chunk_tokens,
                            tokenizer=tokenizer,
                        )
                    )

        else:
            add_block_to_heading_aware_text_chunks(
                text_chunks,
                block,
                heading_path,
                config,
                tokenizer,
            )

    chunks = text_chunks + table_chunks

    assign_stable_ids(chunks)
    validate_chunk_sizes(chunks, tokenizer, config)
    validate_table_coverage(chunks)
    validate_reconstruction_links(chunks)

    return chunks

Important design decisions
Do not semantically group unknown rows using an LLM by default
Because table purpose and relationships are unknown, LLM-based clustering can:

separate a subtotal from its components;

merge unrelated rows;

reinterpret empty cells incorrectly;

hallucinate category relationships;

vary across model versions.

Use observable boundaries and stable identifiers first. Semantic grouping can be added as a secondary, non-destructive index.

Do not use one chunk-size policy for every table
A three-row table and a 5,000-row table should not be forced through the same strategy. The token budget is a constraint; table structure determines boundaries.

Do not split columns unless necessary
Row splitting retains all attributes for a record and is normally easier to retrieve. Column splitting is required only when:

the table is extremely wide;

a complete row exceeds the budget;

distinct column groups are independently useful.

Keep headers even when repetition costs tokens
Removing repeated headers saves space but makes retrieved fragments ambiguous. Retrieval precision is usually worth the additional storage.

Keep table and prose chunking separate
A Markdown document should not be treated as one flat character stream. Tables require specialized chunking, while prose should remain heading-, paragraph-, and sentence-aware.

Final recommendation
For your unknown and highly variable documents, implement this hierarchy:

Whole table
    ↓ if too large
Maximum complete consecutive rows per chunk
    ↓ if one row is too large
Anchor columns + token-aware column groups
    ↓ if one cell is still too large
Structure-aware cell fragments
Add parent–child retrieval and three representations:

table-discovery metadata;

detailed table blocks;

normalized structured table data.

The most important rule is:

Preserve identifiable table structure first, maximize chunk utilization second, and infer semantics only when evidence is strong.

This provides a safe general-purpose foundation even when table dimensions, purposes, row relationships, column meanings, and user query styles are unknown.
