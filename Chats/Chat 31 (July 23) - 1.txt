The final solution
Three independent changes, each targeting a different failure:

Recursion (file 1) — raised limit plus a real stack behind it. Measured markdownify burns ~1.99 frames per DOM nesting level, so the default 1000 buys ~480 levels of nested HTML; depth 501 broke, 481 survived. Verified the depth is bounded (it can't exceed the tag count): DOM depths of 1001, 3001 and 8001 all convert at limit 20000. So the limit bump is a genuine fix, not a band-aid. Mechanism: markdownify parses with Python's html.parser, which does not auto-close unclosed inline tags, so each one swallows the rest of its block as a child — exactly one extra level per unclosed tag.

Dead worker (file 2) — pdftext_workers=1 (marker_test.py:223). pdftext sizes its pool as min(pdftext_workers, pages // 10) and only skips the ProcessPoolExecutor when that lands ≤ 1, so every document here (154/192/250 pages) was getting 4 spawned workers, and one dying took the whole conversion with it. Batching kept as a fallback only — convert_batched (marker_test.py:170) runs on the exception path, not by default, because slicing costs cross-page context (a table spanning a boundary gets split). The coding agent discovered that two different PDF files were failing for two completely different reasons. At first, the errors and warning messages were mixed together, which made the real causes harder to identify.

The short version
File 1 failed because its generated HTML was nested too deeply.
File 2 failed because one of several PDF text-extraction processes crashed.

File 1: The recursion error
What does “maximum recursion depth exceeded” mean?

Recursion happens when one function calls another function, which calls another, and so on. Python keeps track of these calls using a stack.

Python normally allows approximately 1,000 nested function calls. If the program goes beyond this limit, Python stops it with:

RecursionError: maximum recursion depth exceeded

Marker was converting the document into Markdown. During this process, it used markdownify to process HTML.

The PDF had HTML similar to this:

<i>
  <i>
    <i>
      <i>
        Text

Some inline tags such as <i> were not properly closed. Therefore, each new tag became a child of the previous one, creating a very deeply nested structure.

Why not simply increase Python’s recursion limit?

The original idea was:

sys.setrecursionlimit(20000)

However, there are two limits involved:

Python’s recursion limit — the maximum number of calls Python permits.
The operating system’s thread stack — the actual memory available for those calls.

Raising only Python’s limit is dangerous. Python may allow additional calls, but Windows may not have enough stack memory to hold them. Instead of receiving a useful Python error, the entire program could suddenly terminate without a traceback.

The actual fix

The conversion now runs inside a separate thread with:

A higher Python recursion limit.
A larger amount of real stack memory.

In simple terms, the solution did both:

Allow more nested calls + provide enough memory for those calls

The agent tested the behavior and found that Markdown conversion uses roughly two Python calls for each HTML nesting level.

Therefore:

A recursion limit of 1,000 supports approximately 480 nested HTML levels.
A limit of 20,000 provides enough room for several thousand levels.

Testing also showed that the nesting was extremely deep but finite, rather than truly infinite. This means increasing the limit and stack size is a legitimate fix.

Why a 512 MB thread stack was not used

The agent initially considered allocating a 512 MB stack to the thread.

However, CPython does not allow a thread stack that large through threading.stack_size(). Instead of automatically lowering the value, Python raises a ValueError.

Testing found:

Approximately 255 MB was the maximum accepted value.
128 MB was selected as a safer default.
User-provided values are restricted so they cannot exceed the supported maximum.
Why inspecting the repeated calls did not prove infinite recursion

The agent initially tried to determine whether the recursion was:

Truly infinite, or
Very deep but eventually terminating.

It attempted to determine this by examining the repeating functions in the error stack.

That approach does not work reliably.

For example, a function that recursively counts to 5,000 may show the same repeated function call as a function that never stops:

def finite(n):
    if n == 0:
        return
    finite(n - 1)

The stack looks repetitive in both situations. Therefore, the shape of the stack cannot distinguish between deep and infinite recursion.

The more useful test is:

Run with one recursion limit.
Record the depth where it fails.
Increase the limit.
See whether it completes or fails again near the new limit.

In this case, it completed with a sufficiently high limit, proving that the recursion was bounded.

The table warning was not the cause

Immediately before the crash, the logs showed something like:

Table OCR failed for block /page/28/Table/6

That made it look as though table processing caused the crash.

However, Marker is designed to catch that table error, log it, and continue. The table-processing stage later reported that it completed successfully.

The actual recursion error happened about 3.5 seconds later in:

marker/renderers/markdown.py

Therefore:

The table OCR failure may reduce the quality of one table.
The column overflow warning may affect formatting.
Neither warning crashed the conversion.
The actual crash happened while generating Markdown.

This is an important distinction: the message nearest to a crash is not necessarily its cause.

The file-search problem

The agent searched Marker's installed files using ripgrep, but it returned no matches.

The searches were misleading because Marker's files were inside:

.venv-marker/

That folder was ignored by Git. By default, ripgrep also skips files and directories ignored by Git.

So “no matches” did not mean the text was absent. It meant the tool had not searched those files.

The agent repeated the search using PowerShell’s Select-String, which does not follow the same Git-ignore behavior, and found the relevant code immediately.

Why PDF length was not causing the recursion

One theory was that malformed HTML accumulated across the entire document.

For example:

Page 1 adds two unclosed tags
Page 2 adds two more
Page 3 adds two more
...
250 pages eventually create excessive nesting

Testing proved this theory wrong.

A completed block-level element resets the nesting. This means malformed tags in one block generally do not accumulate into later blocks.

The actual rule is:

Recursion depth depends on the single worst block,
not on the total number of pages.

For example:

200 blocks containing 10 unclosed tags each only reached a depth of approximately 11.
One block containing hundreds of unclosed tags produced very deep nesting.
Adding 1,000 normal blocks before or after that bad block did not change its nesting depth.

Therefore, splitting the PDF into smaller page ranges would not fix File 1. The problematic block would remain deeply nested regardless of which batch contained it.

File 2: The worker process died

File 2 failed earlier, while text was being extracted from the PDF. It never reached the GPU-based processing stages.

Marker’s pdftext component was creating multiple independent worker processes. For these large documents, it created four workers.

Conceptually:

Main conversion
├── Text worker 1
├── Text worker 2
├── Text worker 3
└── Text worker 4

If any one worker suddenly died, the entire text-extraction job failed with:

A worker process died while extracting

The fix was:

pdftext_workers = 1

With only one worker, pdftext avoids creating the multi-process worker pool. This removes the unstable multi-process behavior.

The trade-off is that text extraction may be slower, but it is more reliable.

Why batching did not fix the worker problem

The agent considered processing the PDF in 50-page batches.

However, pdftext calculates its worker count using approximately:

min(pdftext_workers, pages // 10)

For a 50-page batch with a configured maximum of four workers:

min(4, 50 // 10)
min(4, 5)
= 4 workers

Therefore, each batch would still use four worker processes. A worker could still die, producing the same failure.

Setting pdftext_workers=1 directly targets the real problem.

Why batching is still available as a fallback

Batching was retained, but it is only attempted if normal conversion fails.

It is not used by default because splitting a PDF can damage cross-page context. For example, if a table begins on page 49 and continues onto page 50, splitting there may cause Marker to treat it as two unrelated tables.

So the chosen order is:

Try converting the whole PDF normally.
Apply the recursion and worker fixes.
Use batching only as a fallback after an exception.
Two additional reliability improvements
Skip completed files

The program now uses file modification times to identify files that were already converted successfully.

This means that if one file fails after several hours, rerunning the script will skip completed files instead of converting everything again.

Immediately print logs

Python’s print() normally buffers some output. Marker’s own logs were appearing immediately on stderr, while custom messages remained waiting in buffered stdout.

This made the live output appear out of order.

Using:

print(..., flush=True)

forces messages to appear immediately, making debugging easier.

Final fixes at a glance

"""Does unclosed inline markup make html.parser nest, and how deep can markdownify go?"""
import sys, threading, traceback
from bs4 import BeautifulSoup
from markdownify import MarkdownConverter


def dom_depth(node, d=0):
    kids = [c for c in getattr(node, "children", []) if getattr(c, "name", None)]
    return d if not kids else max(dom_depth(k, d + 1) for k in kids)


def probe(n):
    """n unclosed <i> tags in a row -> how deep is the resulting DOM?"""
    html = "<p>" + ("<i>word " * n) + "</p>"
    soup = BeautifulSoup(html, "html.parser")
    return html, dom_depth(soup)


def frames_per_level():
    """Empirically: how many Python frames does markdownify burn per DOM level?"""
    sys.setrecursionlimit(1000)
    for n in (50, 100, 200, 300, 400, 600):
        html, depth = probe(n)
        try:
            MarkdownConverter().convert(html)
            print(f"  {n:4d} unclosed <i> -> DOM depth {depth:4d} -> converted OK")
        except RecursionError as e:
            tb = traceback.extract_tb(e.__traceback__)
            print(
                f"  {n:4d} unclosed <i> -> DOM depth {depth:4d} -> RecursionError "
                f"at {len(tb)} frames (~{len(tb)/max(depth,1):.1f} frames/level)"
            )
            return depth
    return None

"""Exact depth at which markdownify breaks, and whether a raised limit fixes it."""
import sys, threading, traceback
from bs4 import BeautifulSoup
from markdownify import MarkdownConverter


def dom_depth(soup):
    """Iterative, so measuring never itself hits the recursion limit."""
    best, stack = 0, [(soup, 0)]
    while stack:
        node, d = stack.pop()
        best = max(best, d)
        for c in getattr(node, "children", []):
            if getattr(c, "name", None):
                stack.append((c, d + 1))
    return best

    return "<p>" + ("<i>word " * n) + "</p>"

File 1: The recursion error
What does “maximum recursion depth exceeded” mean?

Recursion happens when one function calls another function, which calls another, and so on. Python keeps track of these calls using a stack.

Python normally allows approximately 1,000 nested function calls. If the program goes beyond this limit, Python stops it with:

RecursionError: maximum recursion depth exceeded

Marker was converting the document into Markdown. During this process, it used markdownify to process HTML.

The PDF had HTML similar to this:

<i>
  <i>
    <i>
      <i>
        Text

Some inline tags such as <i> were not properly closed. Therefore, each new tag became a child of the previous one, creating a very deeply nested structure.

Why not simply increase Python’s recursion limit?

The original idea was:

sys.setrecursionlimit(20000)

However, there are two limits involved:

Python’s recursion limit — the maximum number of calls Python permits.
The operating system’s thread stack — the actual memory available for those calls.

Raising only Python’s limit is dangerous. Python may allow additional calls, but Windows may not have enough stack memory to hold them. Instead of receiving a useful Python error, the entire program could suddenly terminate without a traceback.

The actual fix

The conversion now runs inside a separate thread with:

A higher Python recursion limit.
A larger amount of real stack memory.

In simple terms, the solution did both:

Allow more nested calls + provide enough memory for those calls

The agent tested the behavior and found that Markdown conversion uses roughly two Python calls for each HTML nesting level.

Therefore:

A recursion limit of 1,000 supports approximately 480 nested HTML levels.
A limit of 20,000 provides enough room for several thousand levels.

Testing also showed that the nesting was extremely deep but finite, rather than truly infinite. This means increasing the limit and stack size is a legitimate fix.

Why a 512 MB thread stack was not used

The agent initially considered allocating a 512 MB stack to the thread.

However, CPython does not allow a thread stack that large through threading.stack_size(). Instead of automatically lowering the value, Python raises a ValueError.

Testing found:

Approximately 255 MB was the maximum accepted value.
128 MB was selected as a safer default.
User-provided values are restricted so they cannot exceed the supported maximum.
Why inspecting the repeated calls did not prove infinite recursion

The agent initially tried to determine whether the recursion was:

Truly infinite, or
Very deep but eventually terminating.

It attempted to determine this by examining the repeating functions in the error stack.

That approach does not work reliably.

For example, a function that recursively counts to 5,000 may show the same repeated function call as a function that never stops:

def finite(n):
    if n == 0:
        return
    finite(n - 1)

The stack looks repetitive in both situations. Therefore, the shape of the stack cannot distinguish between deep and infinite recursion.

The more useful test is:

Run with one recursion limit.
Record the depth where it fails.
Increase the limit.
See whether it completes or fails again near the new limit.

In this case, it completed with a sufficiently high limit, proving that the recursion was bounded.

min(pdftext_workers, pages // 10)

For a 50-page batch with a configured maximum of four workers:

min(4, 50 // 10)
min(4, 5)
= 4 workers

Therefore, each batch would still use four worker processes. A worker could still die, producing the same failure.

Setting pdftext_workers=1 directly targets the real problem.

Why batching is still available as a fallback

Batching was retained, but it is only attempted if normal conversion fails.

It is not used by default because splitting a PDF can damage cross-page context. For example, if a table begins on page 49 and continues onto page 50, splitting there may cause Marker to treat it as two unrelated tables.

So the chosen order is:

Try converting the whole PDF normally.
Apply the recursion and worker fixes.
Use batching only as a fallback after an exception.
Two additional reliability improvements
Skip completed files

The program now uses file modification times to identify files that were already converted successfully.

This means that if one file fails after several hours, rerunning the script will skip completed files instead of converting everything again.

Immediately print logs

Python’s print() normally buffers some output. Marker’s own logs were appearing immediately on stderr, while custom messages remained waiting in buffered stdout.

This made the live output appear out of order.

Using:

print(..., flush=True)

forces messages to appear immediately, making debugging easier.

Final fixes at a glance
Problem	Actual cause	Fix
File 1 recursion error	One HTML block had extremely deep nesting caused by unclosed inline tags	Higher recursion limit plus a larger thread stack
File 2 dead worker	One of several PDF text-extraction processes crashed	Set pdftext_workers=1
Reprocessing completed files	Script restarted every conversion	Skip outputs that are already up to date
Confusing live logs	Standard output was buffered	Use flush=True
Possible fallback failures	Some files may still fail normally	Retry using batches only after failure

The central lesson is that the agent stopped relying on guesses based on nearby log messages and tested each theory directly. Those tests showed that the table warning and document length were distractions: the real problems were deeply nested HTML in File 1 and unstable parallel text extraction in File 2.

from pathlib import Path

from marker.converters.pdf import PdfConverter
from marker.models import create_model_dict
from marker.output import text_from_rendered


PROJECT_ROOT = Path(__file__).resolve().parent.parent
SOURCE_DIR = PROJECT_ROOT / "source"
OUTPUT_DIR = PROJECT_ROOT / "marker_results"


def output_path_for(source_path: Path) -> Path:
    relative_path = source_path.relative_to(SOURCE_DIR)
    return (OUTPUT_DIR / relative_path).with_suffix(".md")


def main() -> None:
    source_files = sorted(path for path in SOURCE_DIR.rglob("*") if path.is_file())
    if not source_files:
        raise SystemExit(f"No source files found in: {SOURCE_DIR}")

    OUTPUT_DIR.mkdir(parents=True, exist_ok=True)
    converter = PdfConverter(artifact_dict=create_model_dict())
    print(f"Marker converter initialized. Found {len(source_files)} source file(s).")

    converted = 0
    failures: list[tuple[Path, Exception]] = []

    for source_path in source_files:
        output_path = output_path_for(source_path)
        output_path.parent.mkdir(parents=True, exist_ok=True)
        print(f"Converting: {source_path.relative_to(PROJECT_ROOT)}")

        try:
            rendered = converter(str(source_path))
            markdown_output, _, _ = text_from_rendered(rendered)
            output_path.write_text(markdown_output, encoding="utf-8")
            converted += 1
            print(f"Markdown written to: {output_path.relative_to(PROJECT_ROOT)}")
        except Exception as error:
            failures.append((source_path, error))
            print(f"FAILED: {source_path.name}: {error}")

    print(f"Marker complete: {converted} converted, {len(failures)} failed.")
    if failures:
        raise SystemExit(1)


if __name__ == "__main__":
    main()
