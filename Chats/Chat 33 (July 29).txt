An “officially supported persistent LangGraph store” means a database-backed implementation of LangGraph’s standard BaseStore interface.

Instead of LangMem talking directly to your custom ChromaDB collections, it talks to a standard API:

store.put(namespace, key, value)
store.get(namespace, key)
store.search(namespace, query=...)
store.delete(namespace, key)

The actual data is persisted in a database such as PostgreSQL, MongoDB, or Redis. LangGraph’s current documentation lists PostgresStore, MongoDBStore, and RedisStore as production persistent stores. InMemoryStore is intended mainly for development/testing.

What the LangGraph Store contains

A store holds long-term memories as structured JSON-like records:

namespace = ("user_123", "learned_qa")
key = "memory_abc123"

value = {
    "question": "What does ASD mean in this document?",
    "answer": "ASD means adjustable speed drive.",
    "created_at": "2026-07-29T14:00:00Z",
    "confidence": 0.91,
    "source_interaction_ids": ["interaction_456"],
    "memory_type": "learned_qa"
}

The namespace works somewhat like a folder or collection:

("user_123", "learned_qa")
("user_123", "failure_lessons")
("global", "learned_qa")

LangMem can then search this store, compare new information with existing memories, and perform updates, consolidation, or deletion.

Store versus checkpointer

These are two different persistence mechanisms in LangGraph:

Component	Stores
BaseStore	Long-term memories shared across conversations
Checkpointer	Temporary/execution state of an individual LangGraph thread
MongoDB interaction collections	Your raw user interactions, feedback, and audit history
ChromaDB	Embedded document chunks or searchable learned knowledge

For example:

graph = builder.compile(
    store=memory_store,
    checkpointer=checkpointer
)

An embedding model.
The memory fields to embed.

from langgraph.store.mongodb import (
    MongoDBStore,
    create_vector_index_config,
)
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2"
)

index_config = create_vector_index_config(
    embed=embeddings,
    dims=384,
    fields=["question", "answer"],
    relevance_score_fn="cosine",
)

store = MongoDBStore.from_conn_string(
    conn_string=MONGODB_URI,
    db_name="memora",
    collection_name="long_term_memories",
    index_config=index_config,
)

Then:

results = store.search(
    ("global", "episodic_examples"),
    query="How should ambiguous technical abbreviations be handled?",
    limit=5,
)

MongoDBStore will:

Query
  → generate query embedding
  → run MongoDB Vector Search
  → return semantically similar memories

Without index_config, this is not semantic search:

store.search(
    ("global", "episodic_examples"),
    filter={"status": "active"},
)

That only performs normal MongoDB metadata filtering.

Build a small, self-contained reference implementation called memora_mini: a LangGraph agentic-RAG graph with a LangMem-style long-term memory layer implemented natively. This is a sandbox/reference project, not a production system — favour clarity and small files over completeness. 

Background

This is a scaled-down sibling of an existing larger project (RAG-Work). That project has a LangGraph RAG pipeline with a self-learning learned_qa ChromaDB collection, thumbdown-based failure memory, and a multi-stage context-compression pipeline. Its memory layer has known structural problems that this sandbox exists to prototype fixes for:

Memory is insert-only — no update, invalidation, consolidation, or decay. A bad distilled entry is permanent.
Failure memory (thumbdowns) is keyed on an exact normalized query string, so semantically equivalent follow-up queries don't match.
Provenance fields (track, evidence_type) exist but are advisory — nothing depends on them being correct, so they drift.
There is no semantic memory (domain facts) and no procedural memory (learned prompt rules).

We adopt LangMem's memory taxonomy and its store interface, and implement both natively. We reject the LangMem SDK's manager layer because of a hard constraint (below). Do not import or install the langmem package.

Hard constraints — these are non-negotiable
Local LLM server only. A single OpenAI-compatible chat-completions endpoint (CUSTOM_API_BASE, model ~llama-3.1-8b-instruct). Every LLM role routes here.
No tool-calling anywhere. Do not pass tools= or functions=, do not call .bind_tools(), do not use trustcall, do not use structured-output helpers that compile to tool schemas. Structured output is obtained by asking for plain JSON in the prompt and repairing the response (see json_fix.py).
No embeddings endpoint on that server. All embeddings come from a local sentence-transformers model — all-MiniLM-L6-v2, 384-dim. Never call a remote embeddings API.
Everything runs locally. No cloud services of any kind — no MongoDB Atlas, no hosted vector DB, no remote tracing. The parent project operates under a hard no-data-egress constraint and this sandbox inherits it.
The model never proposes a delete. The LLM emits classifications only; all destructive decisions are made deterministically in Python.
Assume an 8B model. Every LLM call must ask for either a short JSON array or a single enum value. Never ask one call to extract, reconcile, and consolidate at once — decompose into steps small enough to be reliable.
Storage — ChromaDB only

Local persistent ChromaDB is the only datastore. Do not add MongoDB, SQLite, Postgres, or flat files.

The store interface

Define a MemoryStore Protocol with exactly these four methods, and keep the signatures byte-compatible with LangGraph's BaseStore:

python
def put(self, namespace: tuple[str, ...], key: str, value: dict) -> None: ...
def get(self, namespace: tuple[str, ...], key: str) -> Item | None: ...
def search(self, namespace: tuple[str, ...], *, query: str | None = None,
           filter: dict | None = None, limit: int = 10) -> list[SearchItem]: ...
def delete(self, namespace: tuple[str, ...], key: str) -> None: ...

The signature compatibility is deliberate: if a tool-calling-capable model becomes available later, a thin BaseStore subclass over the same Chroma collections lets LangMem's managers drop in without touching any caller.

ChromaMemoryStore implements it. Requirements:

One factory function creates every collection, and it pins hnsw:space = "cosine". There must be no other code path that creates a Chroma collection. (In the parent project a collection was accidentally created at L2 while scores were computed as 1 - distance, which is only correct for cosine; that silently corrupted ranking for months.) On startup, assert every opened collection reports cosine and fail loudly otherwise.
Namespace → collection name via a single deterministic mapping ("__".join(namespace)).
search() supports metadata filter (Chroma's where) and semantic query, either alone or together. query=None means metadata-only filtering via get(where=...).
Map the four verbs onto Chroma as: put → upsert; get → get(ids=[key]); search → query or get depending on whether query is set; delete → delete(ids=[key]).
Metadata-only updates must not re-embed. Bumping hit_count / last_hit_at uses Chroma's update() with metadata only. This runs on every recall, so it must be cheap.
Strength-based recall

Wrap search() in memory/recall.py with a client-side re-rank:

score = similarity * (1 + w_hits * log1p(hit_count)) * recency_decay(last_hit_at)

Weights and half-life go in config.py. Over-fetch from search() (say 3× limit) before re-ranking. Every returned item gets hit_count incremented and last_hit_at refreshed — this is what lets unused memories fade.

delete() is for operator cleanup only. The normal lifecycle is supersede: set active=False and superseded_by=<new_key> on the old record, insert the new one. All recall filters active=True by default.

Memory model

Four namespaces, each backed by its own Chroma collection:

Namespace	LangMem type	Contents
("memora", "<domain>", "episodic")	episodic	Distilled Q&A pairs from successful interactions
("memora", "<domain>", "semantic")	semantic	Domain facts and disambiguation rules
("memora", "global", "failure")	episodic (negative)	Consolidated thumbdown records
("memora", "global", "procedural")	procedural	Proposed prompt revisions (stored, never auto-applied)

<domain> is a config constant (default "demo"), not a user ID — this is a single-user local system, so the segmentation axis is corpus domain.

The source corpus lives in a separate Chroma collection documents and is not a memory namespace. It is read-only at query time and reached through the retriever, not through the store.

Memory formation pipeline

Runs offline — triggered every LEARN_EVERY_N successful interactions or on the learn command. Never in the request path. Three stages, and it runs over both episodic and failure memories (same code path, different namespace and schema):

Extract (memory/extract.py) — one LLM call per interaction. Output: a JSON array of at most MAX_CANDIDATES_PER_INTERACTION candidates, validated against the target schema.
Classify (memory/classify.py) — for each candidate, recall its top-3 nearest neighbours in the same namespace, then one LLM call per (candidate, neighbour) pair returning exactly one enum token: DUPLICATE | CONTRADICTS | REFINES | UNRELATED. Anything unparseable after repair becomes UNRELATED (fail-safe: insert rather than mutate).
Apply (memory/apply.py) — pure Python, no LLM. Fixed mapping:
DUPLICATE   -> no-op; bump the existing entry's hit_count
REFINES     -> supersede the existing entry with a merged record
CONTRADICTS -> supersede, and append both versions to the audit log
UNRELATED   -> insert as new

Safety guards, all config-driven: cap operations per run (MAX_OPS_PER_RUN); drop any op referencing a key that isn't in the store; refuse to supersede an entry whose hit_count exceeds PROTECTED_HIT_COUNT unless the same CONTRADICTS verdict recurs on a later run (track contradiction_strikes on the record); and DRY_RUN_MEMORY_OPS = True by default — log every proposed operation as structured JSON and write nothing.

Failure memory specifically

Thumbdowns are consolidated, not accumulated. Ten thumbdowns on the same theme must collapse into one entry, not ten near-duplicates. Two extra requirements:

Summarize at write time. Derive a short missing_information field from the raw user_feedback — that field, not the raw feedback text, is what feeds prompt injection. Raw feedback is the wrong shape for redirecting retrieval.
Cap injection at MAX_FAILURE_INJECTIONS (default 2), selected by strength score. Semantic matching surfaces more hits than exact-string matching did, and the parent project already hit prompt-bloat problems past roughly 1,800 tokens against an 8B instruction-following ceiling.
Schemas

Pydantic models in memory/schemas.py, registered in the JSON-repair schema registry:

EpisodicMemory — question, answer, track ("documents" | "learned_qa"), evidence_type ("animal_model" | "observational" | "rct" | "meta_analysis" | "unspecified"), source_paths: list[str], confidence: float.
FailureMemory — original_query, bad_answer, user_feedback, missing_information, failed_variants: list[str].
SemanticFact — subject, fact, disambiguates: list[str] | None (e.g. an acronym with two meanings in the corpus).
PromptRevision — target_prompt, proposed_text, rationale, approved: bool (default False).
ClassificationVerdict — a single enum field.

Store-managed fields common to all (hit_count, last_hit_at, active, superseded_by, contradiction_strikes, memory_type) live in a shared base model. Note that Chroma metadata values must be scalars — flatten or JSON-encode list fields on write and decode on read, in the store layer, not at call sites.

track and evidence_type must be load-bearing: at least one retrieval path filters on them, so a wrong value produces a visible retrieval miss rather than silently rotting.

Graph

A LangGraph StateGraph, ~6 nodes, linear with one conditional edge:

load_memory -> retrieve -> generate -> judge -> (INSUFFICIENT & budget left ? retrieve : log_interaction) -> END
load_memory — recall semantic facts relevant to the query, and failure memories for semantically similar prior failures (no exact-string matching anywhere).
retrieve — two tracks kept separate end-to-end: the documents collection and the episodic namespace. Do not merge or co-rank them.
generate — combine the two tracks only here, at the context boundary, learned-QA section first under an explicit precedence rule, document section second. Inject failure memories as positive redirection built from missing_information ("prior attempts missed X; seek X"), not as a list of things to avoid — negative-only phrasing measurably fails to change model behaviour.
judge — one LLM call returning a single enum: OK | INSUFFICIENT. Retry budget MAX_ITERATIONS = 2.
log_interaction — persist the interaction record; increment the reflection counter.

Acceptance criteria

python demo.py must run start to finish against a fresh store, with clear console output at each step:

Ingests 3–5 small text files from corpus/ (include a fixture where one acronym has two unrelated meanings across two documents).
Asks a question → answers from documents only (episodic namespace empty).
Runs learn in dry-run mode → prints proposed memory operations, writes nothing, counts unchanged.
Re-runs learn with DRY_RUN_MEMORY_OPS=False → episodic namespace populated.
Asks a semantically different rephrasing of the same question → episodic memory is recalled, proving search isn't string-matching.
Thumbs down an answer, then asks a differently-worded version of the same question → failure memory is recalled and the generation prompt contains positive redirection built from missing_information. This is the BUG-009 regression check.
Files three more thumbdowns on the same theme, runs learn → they consolidate into one failure entry, not four. Print before/after counts.
Feeds a contradicting interaction → shows a CONTRADICTS verdict, a supersede op, the old record flipped to active=False with superseded_by set, and the audit-log entry.
Prints final stats showing consolidation kept the active-entry count below the raw candidate count.

        super().__init__(f"model.encode() for '{model_name}' did not complete within {timeout:.0f}s.")


class EmbeddingManager:
    def __init__(self, model_name: str = "all-MiniLM-L6-v2"):
        self.model_name = model_name
        self.model = None
        self.device = "cuda" if torch.cuda.is_available() else "cpu"
        self._load_model()

    def _load_model(self):
        try:
            self.model = SentenceTransformer(self.model_name, device=self.device)
            logger.info(
                f"Model '{self.model_name}' loaded on {self.device}. "
                f"Embedding dimension: {self.model.get_embedding_dimension()}"
            )
            if self.device == "cuda":
                logger.info("GPU: %s", torch.cuda.get_device_name(0))
            else:
                logger.info("CUDA not available; running on CPU.")
        except Exception:
            logger.exception(f"Error loading model '{self.model_name}'")
            raise

    def generate_embedding(self, text, batch_size: int = 32, show_progress=False) -> np.ndarray:
        if self.model is None:
            raise ValueError("Model not loaded.")
        logger.debug(f"  [embedding] calling model.encode() on '{self.model_name}'")
        try:
            t0 = time.perf_counter()
            with concurrent.futures.ThreadPoolExecutor(max_workers=1) as _executor:
                _future = _executor.submit(
                    self.model.encode,
                    text,
                    batch_size=batch_size,
                    show_progress_bar=show_progress,
                    convert_to_numpy=True,
                    normalize_embeddings=True,
                    device=self.device,
                )
                try:
                    result = _future.result(timeout=EMBEDDING_ENCODING_TIMEOUT_SECONDS)
                except concurrent.futures.TimeoutError:
                    raise EmbeddingEncodingTimeoutError(self.model_name, EMBEDDING_ENCODING_TIMEOUT_SECONDS)
            logger.debug(
                f"  [embedding] model.encode() on '{self.model_name}' took "
                f"{time.perf_counter() - t0:.3f}s"
            )
            return result
        except EmbeddingEncodingTimeoutError as e:
            logger.error(
                f"  [embedding] model.encode() for '{e.model_name}' did not complete within "
                f"{e.timeout:.0f}s (EMBEDDING_ENCODING_TIMEOUT_SECONDS={EMBEDDING_ENCODING_TIMEOUT_SECONDS})"
                f" — aborting encoding."
            )
            raise
        except Exception:
            logger.exception("Error generating embedding")
            raise

    def get_embedding_dimension(self) -> int:
        if self.model is None:
            raise ValueError("Model not loaded.")
        return self.model.get_embedding_dimension()
    
    def cosine_similarity(self, vec_a: np.ndarray, vec_b: np.ndarray) -> float:
        """Compute cosine similarity between two vectors."""
        if vec_a.shape != vec_b.shape:
            raise ValueError("Vectors must have the same shape.")
        if np.linalg.norm(vec_a) == 0 or np.linalg.norm(vec_b) == 0:
            return 0.0
        return float(np.dot(vec_a, vec_b) / (np.linalg.norm(vec_a) * np.linalg.norm(vec_b)))

# Memora: Self-Learning Agentic RAG

A locally-running, self-improving Retrieval-Augmented Generation system with an agentic query loop, LLM-as-judge context compression, and a thumbdown-driven feedback mechanism that gets better with use.

Two independent agent implementations share one vector store — and can each ingest into it — see [Two Implementations, One Knowledge Base](#two-implementations-one-knowledge-base) below.

---

## What Problem It Solves

Standard single-pass RAG pipelines have three hard limits: they cannot self-correct when the first retrieval is poor, they repeat the same bad answers across sessions, and they never learn from user feedback. This project addresses all three by replacing the linear retrieve → prompt → answer flow with an **agentic loop**, a **three-stage context compression pipeline** (NAC → DC → LBC), and a **self-learning mechanism** that distills verified Q&A pairs back into the knowledge base.

The system was built and stress-tested on a domain-specific corpus (ASD clinical data, research PDFs, patient datasets, and engineering documents), but the architecture is corpus-agnostic.

---

## Two Implementations, One Knowledge Base

**Both agents read and write one shared ChromaDB store** at `data/vector_store/` (two collections: `documents` and `learned_qa`). Ingestion has two entry points that populate that same store, so you run whichever fits and a document ingested once is visible to both agents:

- `app/ingest.py` — the original LangChain ingestion (discover → chunk → embed → store); the simplest one-shot path.
- `app_workflow/`'s **switchable** ingestion pipeline (`app_workflow/ingestion/`, exposed as `POST /ingest`) — adds a selectable loader (Unstructured **or** the isolated GPU **Marker** PDF→Markdown microservice) and splitter (recursive **or** Marker-Markdown-aware custom), all in-memory, chosen via the `ENABLE_MARKER_LOADER` / `ENABLE_CUSTOM_SPLITTER` switches (both default off). See [Marker PDF Service](#marker-pdf-service).

Two separate agent implementations are built **on top of** that same store:

| | `app/` | `app_workflow/` |
|---|---|---|
| Orchestration | Hand-rolled 4-phase state machine | LangGraph `StateGraph` |
| Query fan-out | Sequential | Parallel (`Send` per query variant) |
| Observed latency (10-query benchmark, see `Status.md` 2026-06-25) | ~28 min total avg | ~14 min total avg (~2× faster; retrieval is the dominant gap) |
| HTTP API | `app/api.py` — port 8000 | `app_workflow/api.py` — port 8001 |
| Status | Original implementation, fully maintained | Actively developed; recommended for new work |

They are functionally independent (separate `config.py`, `llm_setup.py`, `feedback_store.py`, etc.) but read and write the **same** `data/vector_store/` and the **same** MongoDB database, so a document ingested once, or a Q&A pair distilled by one pipeline, is immediately visible to the other.

---

## Key Features

- **Agentic retrieval loop** — iterative query reformulation and evidence accumulation; stops when quality is satisfied or the retrieval budget is exhausted
- **Two-track retrieval** — source `documents` and self-learned `learned_qa` are retrieved, validated, deduplicated, and compressed as independent channels, combined only at the LLM context boundary with an explicit learned-QA-takes-precedence rule
- **Three-stage context compression** — Neighbor-Aware Compression → Deduplication Compression → LLM-Based Compression, each with an LLM-as-judge validator
- **Self-learning** — after every N successful interactions, verified Q&A pairs are distilled back into the `learned_qa` ChromaDB collection and used in future retrievals
- **Switchable ingestion with an optional GPU Marker service (`app_workflow/`)** — `app_workflow/` adds its own ingestion pipeline (`POST /ingest`) that selects between the Unstructured loader and an isolated GPU **Marker** PDF→Markdown microservice, and between recursive and Marker-Markdown-aware custom splitting, via the `ENABLE_MARKER_LOADER` / `ENABLE_CUSTOM_SPLITTER` switches (both default off). Marker runs out-of-process because its `transformers`/CUDA stack is incompatible with the app's Python 3.14 embedding environment. See [Marker PDF Service](#marker-pdf-service).
- **Multi-tier LLM output repair** — a 5-stage pipeline (`fix_llm_output.py`) recovers structured JSON from malformed LLM output (markdown fences, truncation, wrong types, code instead of JSON, etc.) before it reaches Pydantic validation
- **Thumbdown persistence** — bad answers are logged with full query variants and user feedback; subsequent identical queries block the entire prior failing search trajectory
- **Single custom LLM endpoint (`app_workflow/`)** — all four roles (`llm`, `llm_tool`, `judge_llm`, `json_fix_llm`) are routed to one self-hosted, OpenAI-compatible endpoint (`CUSTOM_API_BASE`). Groq and the Hugging Face Inference Providers router were both evaluated for `judge_llm`/`json_fix_llm` and retired after a head-to-head latency/reliability benchmark showed the HF router degrading validator quality under quota pressure (see `Status.md` 2026-07-08). Query-variant generation no longer uses tool-calling — it asks the LLM for a plain JSON array, parsed via `fix_llm_output`. `app/` uses Groq (`llama-3.1-8b-instant`) exclusively for all roles.
- **Three tracing backends (`app_workflow/`)** — LangSmith, Langfuse, and self-hosted Arize Phoenix are supported. Langfuse and Phoenix capture the shared LangChain/LangGraph operation hierarchy; application log records are also mirrored into active traces. See [Setting Up Tracing](#setting-up-tracing) for credentials, feature flags, and the current backend-combination limitation.
- **Structured error handling** — `LLMResult` dataclass with an `LLMErrorKind` taxonomy, a FIFO serialization gate, and adaptive-cooldown retry across both pipelines
- **MongoDB-backed persistence** — interaction history, thumbdowns, and failed query variants are stored transactionally (replacing the original flat-file JSON/JSONL design)

## ADR-001 — Embedding Model: `all-MiniLM-L6-v2`

| Field | Detail |
|---|---|
| **Decision** | Use `sentence-transformers/all-MiniLM-L6-v2` as the sole embedding model for the entire pipeline |
| **Date** | April 2025 |
| **Context** | The project needed a fast, locally-runnable embedding model to convert document chunks and user queries into dense vectors for semantic similarity search. The model had to run on-device (CUDA-enabled) and produce consistent-dimension outputs throughout the pipeline. |
| **Options Considered** | `all-MiniLM-L6-v2` (384-dim, fast, lightweight) · `all-mpnet-base-v2` (768-dim, higher quality) · `text-embedding-3-small` via OpenAI API (cloud, latency, cost) · `bge-small-en-v1.5` (similar size) |
| **Chosen Solution** | `all-MiniLM-L6-v2` |
| **Rationale** | Fast inference on CUDA (GPU-accelerated). Only 6 transformer layers — sub-100ms encode per batch. 384-dim vectors are compact enough for efficient HNSW indexing. Pretrained on large semantic similarity corpora, adequate for domain-specific retrieval. No API calls required — fully local. |
| **Impact** | Embedding dimension fixed at **384** across the entire project. Changing the model at any point would require re-ingesting all documents (the HNSW index dimension cannot change in-place). Lives in `embedding_manager.py`. |

## ADR-002 — Vector Store: ChromaDB

| Field | Detail |
|---|---|
| **Decision** | Use ChromaDB with local persistent storage as the vector database |
| **Date** | April 2025 |
| **Context** | Needed a vector store for storing 384-dim embeddings of document chunks and supporting fast approximate nearest-neighbor (ANN) retrieval. Required Python-native API, metadata filtering support, and local persistence without a running server process. |

## ADR-003 — Classic RAG → Agentic RAG Architecture

| Field | Detail |
|---|---|
| **Decision** | Replace the linear classic RAG pipeline with a full Agentic RAG loop |
| **Date** | April 2025 |
| **Context** | The initial pipeline was a fixed single-pass: `embed query → retrieve → prompt → answer`. This approach had no ability to self-correct when retrieval was poor, no query reformulation, and no quality gate. |
| **Options Considered** | **Classic RAG** (simple, linear, deterministic) · **Agentic RAG** (LLM decides when/how to retrieve, iterative, self-correcting) · **HyDE** (Hypothetical Document Embeddings, generate before retrieval) |
| **Chosen Solution** | Agentic RAG with a structured iteration loop (max 6 iterations) and LangChain tool-calling |
| **Rationale** | The agent can decide *whether* to retrieve, *how many times*, *with what query reformulations*, and *when to stop*. This eliminates single-point-of-failure retrieval: if one query retrieves poor chunks, the agent reformulates and tries a different angle. The quality check gate (`check_answer_quality`) catches hallucinations before returning answers. |
| **Impact** | Defined the entire architecture of `agent_query.py`. Justified the creation of `tools.py`, `self_learner.py`, and `feedback_store.py`. Introduced the MAX_ITERATIONS=6 and MAX_TOTAL_RETRIEVALS=5 hard limits to prevent runaway loops. |

Answer briefly:
The ChromaMemoryStore u have built, does it use LangMem's own

No — it copies the signatures, not the implementation.

Not LangMem's functions. Those four verbs are actually LangGraph's BaseStore API; LangMem doesn't define them, it consumes a BaseStore. memora_mini imports nothing from langmem and doesn't subclass BaseStore either.
What it is: protocol.py declares a plain typing.Protocol with those method signatures held byte-compatible (same names, same order, same keyword-only markers). chroma_store.py is a from-scratch implementation mapping them onto Chroma: put→upsert, get→get(ids=), search→query or get(where=), delete→delete(ids=).
Why bother matching: so the swap stays cheap. If a tool-calling-capable model ever becomes available, a thin real BaseStore subclass over the same collections lets LangMem's managers drop in without touching any caller. tests/test_store.py::test_store_satisfies_the_protocol asserts the parameter list to keep that true.
There's also one method that is deliberately not in the interface: update_metadata(), the no-re-embed hit_count bump used on every recall.

Answer briefly:
The features like updation of memories, resolving conflicting memories etc. Are these managed by this?
Yes — but by our own code, not by anything in LangMem.

Implemented here:

Update/conflict resolution — classify.py asks the LLM for one enum per (candidate, neighbour) pair: DUPLICATE | CONTRADICTS | REFINES | UNRELATED. apply.py turns that into a write via a fixed Python table — duplicate bumps, refines merges, contradicts supersedes, unrelated inserts.

Answer briefly:
Tell me about "trustcall"...what it is and how does LangMem uses it etc etc
What it is: trustcall is a small library from the LangChain orbit for getting reliable structured output out of an LLM — its pitch is "tenacious tool calling." You give it a schema; it binds that schema as a tool, validates the result, and on failure feeds the validation errors back for a repair round.

Its actual trick: repairs are JSON Patch (RFC 6902) operations, not full regenerations. The model emits {"op": "replace", "path": "/answer", ...} instead of re-emitting the whole object. Two payoffs:

Cheap error recovery on long extractions — you don't pay to regenerate a large object over one bad field.
Updating an existing record becomes a first-class operation: hand it the current document plus new information and it patches in place.
How LangMem uses it: that patch mode is LangMem's update mechanism. create_memory_manager / create_memory_store_manager pass your Pydantic schemas to trustcall, which decides per-item whether to insert a new memory or emit a patch against an existing one — that's how LangMem does "enrich/update rather than duplicate."

Why it's disqualifying here: every one of those steps rides on tool-calling — schemas bound via .bind_tools(), plus internal patch tools. There's no plain-JSON fallback path. Your endpoint has no tool-calling, so trustcall can't run, so LangMem's managers can't run.

What we did instead: split its one job into two smaller ones an 8B model can do — classify.py returns a single enum token, apply.py does the patching deterministically in Python. Coarser than a JSON Patch, but no tool schema and no nondeterminism in the write path.

1. Can we use LangMem without trustcall?
No. create_memory_manager / create_memory_store_manager call trustcall internally as a hard dependency — there's no flag or plain-JSON code path around it. To use LangMem without trustcall you'd have to skip its manager layer entirely and only reuse lower-level pieces (its Store/namespace conventions), writing your own extraction/patch logic on top — which is essentially what classify.py/apply.py already do.

2. Can we call trustcall's tools directly instead of handing them to the LLM?
Not meaningfully. Its internal tools (PatchDoc, PatchFunctionErrors, etc.) are tool schemas meant to be bound to a tool-calling model and filled in by it — generating the patch is the LLM's job, not a deterministic function you invoke yourself. If you already know what should change, you don't need trustcall's tool at all; you'd just call the underlying jsonpatch library directly. So they're "available" as importable Python objects, but not "accessible" as standalone utilities — divorced from an LLM filling in the arguments, there's nothing for them to do.
