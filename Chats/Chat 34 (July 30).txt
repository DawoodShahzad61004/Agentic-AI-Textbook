Root cause found. Your Wi-Fi adapter is configured with fe80::1 (a link-local IPv6 address on your router) as its DNS resolver, and Windows prefers IPv6 resolution first. Testing that resolver directly 5x in a row: it timed out on attempts 1–2, then succeeded on 3–5 — it's genuinely flaky/overloaded, not something on your end.

Contrast: 192.168.1.1 (same router, over IPv4) is also configured but only gets tried as fallback after the IPv6 one times out (~2s per failed query, ×3 retries in nslookup's default behavior — matches the delay you saw).

So: it's your router's IPv6 DNS service intermittently failing to resolve/forward queries, most likely because the router is slow or dropping requests to its upstream (ISP) resolver over IPv6, while its own IPv4 path and any cached/common domains (google.com) are fine.

Two ways to stop it from biting you:

Quick app-level fix: point Python/the OS at a reliable public resolver (8.8.8.8 / 1.1.1.1) instead of the router, at least for this network adapter.
Router-level fix: the router itself is the flaky resolver — a reboot of the router, or disabling its IPv6 DNS advertisement, would address it for all apps, not just this one.

1. Persistent storage and raw interactions

The Docker stack includes PostgreSQL with pgvector and a persistent Docker volume. You do not need MongoDB. You must configure credentials, but the database container is included. Removing the Docker volume deletes the stored data. See the self-hosted server README.

However, Mem0 should not be described as storing “all interactions.”

With the default infer=True, Mem0:

receives conversation messages;
uses an LLM to extract useful memory statements;
stores those extracted memories.

Therefore, it is a memory database, not necessarily your authoritative conversation-history database. You should continue storing complete interactions in MongoDB if you need full transcripts, feedback records, auditability, or reprocessing.

You can use infer=False to store the supplied messages directly without LLM extraction:

memory.add(
    messages,
    user_id="user-123",
    infer=False
)

This path embeds and persists messages without calling the LLM. See Memory.add().

2. Positive and negative episodic memories

Mem0 can persist both successful examples and failure lessons, but “positive” and “negative” are not distinct built-in OSS memory classes.

For your system, you could use metadata:

metadata={
    "memory_kind": "failure_lesson",
    "quality": "negative",
    "source": "user_thumbdown"
}

Mem0’s POSITIVE, NEGATIVE, and VERY_NEGATIVE feedback feature belongs to the Mem0 Platform/client feedback API. It rates a stored memory; it does not automatically convert a negative interaction into a reusable failure lesson. See the feedback documentation.

Thus, you would still need your own pipeline to turn a thumb-down into something useful such as:

When answering queries about X, do not use Y because it caused Z; instead, apply A.

Then store that lesson in Mem0.

3. CRUD and consolidation

Mem0 provides explicit operations to:

add memories;
retrieve one or all memories;
update memories;
delete individual memories;
delete memories by scope;
inspect memory history.

But the description of “automatic consolidation” needs qualification. In the current OSS v3 addition pipeline, Mem0 retrieves related memories, asks the LLM for additive memory extraction, and performs hash-based duplicate checking. That is useful extraction and deduplication, but it is not necessarily full semantic merging of multiple memories into one continuously rewritten summary.

For your failed_variants and user_thumbdowns, you may still need a scheduled consolidation process that combines repeated failure lessons into a concise procedural memory.

4. Semantic search

Yes. Mem0 embeds the query and searches persistent vector storage. Current OSS search can combine:

vector similarity;
BM25 keyword score, when supported by the vector store;
entity-based score boosts;
optional reranking;
metadata filters.

PostgreSQL/pgvector is listed as supporting the keyword-search component, so the included server backend can provide hybrid retrieval. See the search implementation documentation.

5. Does your LLM need tool-calling?

No. Current Mem0 OSS v3 does not require the memory-extraction LLM to call tools.

The present pipeline calls the LLM with:

response_format={"type": "json_object"}

It then parses a JSON response containing extracted memories. It does not pass a tool definition in that extraction call. Therefore, your model needs to reliably produce structured JSON—not native function/tool calls.

There are three possibilities:

Your server supports OpenAI-compatible response_format

Normal infer=True operation should be possible.

Your model returns valid JSON but rejects response_format

You may need a small Mem0 provider adapter or OpenAI-compatible proxy that removes the unsupported parameter while keeping the JSON instructions.

Your model cannot reliably return structured JSON

Use infer=False and perform memory extraction using your existing distillation pipeline before passing the final memory text to Mem0.

One additional complication: the standard self-hosted server image currently bundles only OpenAI, Anthropic, and Gemini LLM providers by default. Using Ollama, vLLM, or your own OpenAI-compatible local server may require adding its dependency/provider configuration and rebuilding the server image. See the self-hosted setup documentation.

For your architecture, the safest arrangement is:

MongoDB
  └── Complete interactions and feedback—the source of truth

Your distillation pipeline
  ├── Successful QA/example memories
  └── Consolidated failure lessons

Mem0 + PostgreSQL/pgvector
  └── Persistent, searchable long-term memories

So your non-tool-calling local LLM does not automatically disqualify Mem0. The important test is whether it can produce reliable JSON—or whether you use infer=False.

Mem0 shipped a new memory algorithm ("v3") in April 2026 that changed the write pipeline substantially, and the answers you have look like they describe the pre-v3 version plus some Platform-only features.

1. Persistent storage — mostly correct
The server/ Docker Compose stack bundles Postgres with pgvector (image pgvector/pgvector:pg17, data on a named postgres_db volume), the FastAPI API on 8888, and now a mem0-dashboard container on 3000. No MongoDB, no external DB. POSTGRES_* env vars override it, as you had.

Two corrections worth knowing before you docker compose up:

JWT_SECRET is now required — auth is on by default, and the server refuses to start without it. AUTH_DISABLED=true exists for local dev only. POSTGRES_PASSWORD is likewise mandatory now.
Neo4j is gone. Blog posts describing "three containers: API, Postgres, Neo4j" are stale. In v3, external graph store support was removed from the open-source SDK entirely (~4000 lines, including Neo4j/Memgraph/Kuzu/AGE/Neptune) and replaced by built-in entity linking that stores entities in a parallel {collection}_entities collection in your existing vector store.
One conceptual point: this persists extracted facts, not your raw interactions. If you want verbatim turns stored, pass infer=False on add() — more on that below.

2. Positive/negative episodic memory — this one is wrong for self-hosted
The Feedback API is a Platform-only feature. It lives on MemoryClient (the hosted client): client.feedback(memory_id=..., feedback="POSITIVE", feedback_reason=...), documented under Platform → Features → Feedback Mechanism. The OSS Memory class and the self-hosted REST server don't expose it. Nor is there an episodic-vs-semantic type field or any valence tagging in the OSS store — the memory-type taxonomy in the docs is conceptual framing, not a schema. 
GitHub

If you want positive/negative episodic memories locally, you implement it yourself: store the valence in metadata on add() and filter on it at search time. That works fine, it's just your code, not a Mem0 feature.

3. CRUD yes — "consolidation" no longer means what that answer says
CRUD is fine: add, get, get_all, update, delete, delete_all, history, all exposed over REST too.

But automatic write-time consolidation was removed in v3. Extraction is now single-pass ADD-only: one LLM call, no UPDATE/DELETE. add() returns ADD events only, and the ADD-only model means memories accumulate — when information changes, the new fact is stored alongside the old one, and retrieval handles ranking. What remains at write time is thin: the top-10 related existing memories are passed in as deduplication context, plus MD5 hash-based dedup that prevents exact duplicates.

So contradiction resolution moved from write time to ranking time. If your application needs genuine consolidation (merging or retiring superseded facts), you'll be building that on top of update/delete yourself.

4. Semantic search — correct, with a dependency catch
Hybrid search is now in OSS, not just Platform: semantic + BM25 keyword + entity matching, scored in parallel and fused into one score. But it degrades silently if you don't install the extras — without spaCy (pip install "mem0ai[nlp]" plus python -m spacy download en_core_web_sm) you get semantic-only: no entity extraction, no BM25 lemmatization. BM25 is a boost signal, not a recall expander: only semantic results are candidates.

Also mind the new v3 defaults, which will change your results: top_k dropped from 100 to 20, threshold from None to 0.1, rerank from True to False, and entity IDs must now go inside a filters dict — passing user_id= as a top-level kwarg to search() raises ValueError.

5. Tool calling — not required. This is the important correction.
Mem0's memory pipeline needs reliable JSON output, not tool calls. Look at the Ollama provider: tools is an optional parameter (if tools: params["tools"] = tools), and when Mem0 asks for JSON it uses Ollama's native structured-output path — params["format"] = "json" plus an appended nudge, "Please respond with valid JSON only." The core pipeline calls with response_format={"type": "json_object"}, and failures show up as JSON parse errors, not missing-tool errors — as in the open issue where the vLLM provider drops response_format and memory extraction fails with Invalid JSON response: Expecting value: line 1 column 1.

GitHub

The part of Mem0 that genuinely did require tool calling was graph memory — and as noted, that's been deleted from OSS. The docs line "these models support tool calling" is a recommendation on a page that predates the change, not a hard gate.

Practical implications for your no-tool-call local model:

Prefer an OpenAI-compatible endpoint over the native providers. Serve your model via vLLM's or Ollama's OpenAI-compatible API and configure provider: "openai" with a custom base URL. That path forwards response_format correctly and sidesteps issue #4607. It also matters because the shipped server container only bundles packages for openai, anthropic, and gemini LLMs — adding another provider means editing server/requirements.txt, extending BUNDLED_LLM_PROVIDERS in server/main.py, and rebuilding the image. Using the openai provider against localhost avoids all of that.
Use constrained decoding if your server supports it (vLLM guided JSON / Ollama format). Small models drift on JSON structure; grammar constraints make malformed output impossible.
infer=False is your escape hatch. m.add(messages, user_id="alice", infer=False) stores raw messages without inference — no LLM call at all on the write path. You still get embeddings, persistence, and semantic search; you just lose automatic fact extraction. You can pair this with your own extraction step if you want control.
