Good context — you already know StateGraph, nodes-as-functions, conditional routing. That part transfers directly. What's new is just: a node is a function that shells out instead of one that calls an LLM.

The pattern, in three pieces:

Wrap each CLI as a plain Python function, same signature shape as any node you've already written — (state: GraphState) -> dict. Inside, subprocess.run([...], capture_output=True).
python
def agent_a_node(state: GraphState) -> dict:
    result = subprocess.run(
        ["claude", "-p", state["current_task"],
         "--output-format", "json",
         "--permission-mode", "acceptEdits"],
        cwd=state["repo_path"], capture_output=True, text=True, timeout=1800,
    )
    payload = json.loads(result.stdout)
    return {"last_output": payload, "quota_a": read_quota_a()}

def codex_node(state: GraphState) -> dict:
    result = subprocess.run(
        ["codex", "exec", state["current_task"], "--json"],
        cwd=state["repo_path"], capture_output=True, text=True, timeout=1800,
    )
    return {"last_output": json.loads(result.stdout), "quota_b": read_quota_b()}
builder.add_node("agent_a", agent_a_node) — identical to wiring in an LLM node.

Copilot is the odd one out — it has no scriptable headless CLI in the same sense (gh copilot suggest is interactive/advisory, not agentic-loop capable). Treat it as a tool call inside a node rather than its own node: shell out to gh copilot suggest, parse the suggestion, feed it back into state for the primary agent to apply. Don't expect it to own a task end-to-end the way Claude Code/Codex can.
Return values become graph state, not chat history. state["last_output"], state["quota_a"] flow into your existing route_next conditional edge exactly like any other state field already does in app_workflow/. That's the whole integration — LangGraph doesn't know or care that the "reasoning" happened outside the process. To it, agent_a_node looks identical to judge_llm_node.
One thing to carry over from your project specifically: you already have services/operation_tracing.py bounding what gets logged into traces. Route subprocess stdout/stderr through the same policy before it lands in a checkpoint — CLI output can be large and you don't want it blowing up your Langfuse/Phoenix payloads or your SQLite checkpoint size.

Weighed shared skill placement strategies and prompt injection reliability
Weighed shared skill placement strategies and prompt injection reliability
Yes — but the native "put a file somewhere and it's auto-discovered" mechanism differs per agent, and in headless/subprocess mode you shouldn't trust auto-discovery at all. Two layers:

Layer 1 — one canonical file, not two. Keep a single source of truth outside either agent's convention:

repo/
├── skills/
│   └── graphify/
│       ├── SKILL.md
│       └── scripts/...
├── .claude/skills/graphify -> ../../skills/graphify   # symlink
└── AGENTS.md                                          # references skills/graphify/SKILL.md
Claude Code discovers skills under .claude/skills/, so a symlink into your canonical folder satisfies that convention without duplicating content. Codex has no native skills folder — it reads AGENTS.md at repo root — so AGENTS.md just needs a line like "Before graph-related tasks, read skills/graphify/SKILL.md." One file, two doorways.

Layer 2 — don't rely on that in your LangGraph pipeline. Auto-discovery is a nicety for interactive sessions; it's not guaranteed to trigger reliably in a one-shot -p/exec headless call, and you have no visibility into whether it fired. Since your orchestrator already constructs the prompt string before calling subprocess.run, just read the skill and inject it explicitly — deterministic, agent-agnostic, and you can log exactly what was sent:

python
def load_skill(name: str) -> str:
    return (SKILLS_DIR / name / "SKILL.md").read_text()

def agent_a_node(state: GraphState) -> dict:
    prompt = f"{load_skill('graphify')}\n\n---\n\nTask: {state['current_task']}"
    result = subprocess.run(["claude", "-p", prompt, "--output-format", "json"], ...)
Same function serves the Codex node — same string, same skill, no dependency on either CLI's discovery quirks working the same way. Treat the symlink/AGENTS.md setup as a fallback for when a human runs the agent interactively outside your graph, not as the mechanism your orchestrator depends on.
