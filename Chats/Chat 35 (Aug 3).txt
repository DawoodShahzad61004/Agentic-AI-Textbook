# Build Guide — Multi-Agent Orchestration for Bhai-To-Bhai

Written 2026-08-03. Audience: someone building their first multi-agent system.
Complements `Architecture.md` (target shape) and `Decisions.md` (why). This file is about **how to actually build it, and in what order.**

---

## 0. The mental model (read this first)

The instinct is to think of this as an AI problem. It isn't. **It's a job scheduler with unreliable, expensive, non-deterministic workers.**

Swap the vocabulary and it becomes familiar:

| Your term | What it really is |
|---|---|
| Coding agent | A worker process that may die at any moment |
| Token budget | A per-worker resource quota with a refill window |
| Handoff | Task migration between workers after preemption |
| Canonical task context | The durable job record — the only thing that survives a worker death |
| Check runner | The acceptance test that decides "done", because workers lie |
| Git worktree | The worker's scratch space |

Every hard problem in this project is a distributed-systems problem: crash recovery, idempotency, resource accounting, state reconciliation, deadlock/livelock. The LLM part — writing a prompt, shelling out to `claude -p` — is genuinely the easy part and will take maybe 5% of your effort.

**Consequence:** if you find yourself deep in prompt engineering in week one, you're working on the wrong layer.

---

## 1. The one design decision everything else hangs on

> "If one task unexpectedly takes too many tokens and the coding agent's limit is reached, the other coding agent would resume the work."

Here is the naive design, which almost everyone builds first:

```
agent runs ──▶ finishes ──▶ writes a handoff summary ──▶ next agent reads it
```

**This fails at exactly the moment you built it for.** An agent killed by a rate limit never reaches "finishes." It never writes the summary. You get nothing.

The fix is to invert it:

> **Never summarize on exit. Always reconstruct on entry.**

The handoff packet must be *derivable at any instant* from durable artifacts that are written continuously during the run — not produced by the dying agent as its last act. Concretely, four things must be durable-by-construction:

1. **The worktree** — commits are the ground truth of what physically got done. Instruct the agent to commit after every logical step; additionally have the orchestrator auto-commit on a timer (`git add -A && git commit -m "wip: auto"`). A `SIGKILL`ed agent still leaves you a diff.
2. **The plan** — the task is decomposed into ordered steps *before* execution, stored in Mongo, each marked `pending`/`in_progress`/`done`. Death at step 4 means the next agent starts at step 4, not step 1.
3. **The event stream** — run the CLI with streaming JSON output and persist each event to Mongo **as it arrives**, not after process exit. A killed process still leaves its full transcript.
4. **The check results** — last known pass/fail state, tied to a commit SHA.

If those four are durable, "agent A died, agent B resumes" is just: build a packet from (1)+(2)+(3)+(4), hand it to B. It works identically whether A exited cleanly, was rate-limited, timed out, or you closed your laptop.

**Build this first. Everything else is decoration on top of it.**

---

## 2. Token budgets: your abstraction is wrong (and that's fine)

You said routing is driven by "token budgets of the coding agents." The complication: the four agents don't have comparable budgets, and none of them exposes "tokens remaining" as a number you can query.

| Agent | What actually limits you | Queryable? |
|---|---|---|
| Claude Code | Rolling usage windows (subscription) or $/token (API key) | No — usage is reported *per call*, remaining is not exposed |
| Codex | Rate-limit windows (ChatGPT plan) or $/token (API key) | No |
| Gemini CLI | Free tier is **request-count** limited (per-minute and per-day), not token limited | No |
| DeepSeek | Pure $/token, effectively unbounded until money runs out | Balance only |

So don't model "tokens remaining." Model a **Budget Ledger** with a normalized state per agent:

```python
{
  "agent": "claude",
  "limit_type": "rolling_window",   # rolling_window | daily_requests | monetary | none
  "window": "5h",
  "limits":   {"tokens": 1_500_000, "requests": None, "usd": None},   # YOU configure these
  "consumed": {"tokens": 812_003,   "requests": 47,   "usd": 0.0},    # derived from runs
  "state": "available",             # available | degraded | exhausted | cooldown
  "cooldown_until": None,           # ISO timestamp, set on reactive detection
}
```

Update it two ways, and understand which one is authoritative:

- **Proactive (an estimate):** parse `usage` out of each call's JSON result, accumulate. Used for *pre-emptive* routing — "don't start a job I estimate at 200k tokens on an agent I think has 40k of headroom."
- **Reactive (the truth):** the agent exits non-zero with a rate-limit message. Mark `exhausted`, set `cooldown_until`, fail over. **This is the signal you trust.** Your proactive estimate will drift; vendors count tokens in ways you can't fully replicate.

Two rules that will save you real money:

- **Reserve headroom.** Route to an agent only if `estimated_cost × 1.5 < remaining`. A mid-task death is expensive twice over: you lose the partial work *and* you pay a cold-start handoff on the next agent.
- **Switching is not free — the router must price it in.** Returning to an agent that already has a native session is cheap (it resumes with its own context). Switching vendors means a cold start plus a full context packet. Prefer to *wait or return* over switching, unless the agent is genuinely exhausted.

Keep the rate-limit detection patterns in **config, not code** — vendors reword their error messages and you don't want a code change every time.

```yaml
# config/limit_signals.yaml
claude:
  exit_codes: [1]
  stderr_patterns: ["rate limit", "usage limit reached", "quota exceeded"]
  cooldown: "5h"
gemini:
  stderr_patterns: ["RESOURCE_EXHAUSTED", "quota"]
  cooldown: "24h"
```

**One caveat on DeepSeek:** it's a *model*, not an agentic coding CLI. To use it as a coding agent you must pair it with a harness that accepts a custom OpenAI-compatible endpoint (Aider, OpenCode, and similar). Verify this in the spike phase before designing it into your router — or scope it to non-agentic roles (reviewer, summarizer, planner) where a plain API call is sufficient. Its low cost makes it the natural **fallback of last resort** when everything else is in cooldown.

## 3. Langflow vs. LangGraph — flagging a contradiction

Your stack table says **Langflow**. Your own **ADR-002 chose LangGraph**. These are different tools and the difference matters here:

- **Langflow** is a visual, drag-and-drop builder over LangChain. Excellent for prototyping and for showing someone a flow diagram.
- **LangGraph** is a durable state-machine runtime: cycles, conditional edges, checkpointers, interrupts, resume-from-checkpoint.

What this project needs from that layer is: cycles (fix → recheck → fix), conditional routing on agent state, checkpoint/resume after crash, mid-run interruption, and nodes that block for minutes on a subprocess. That's LangGraph's exact feature list and outside Langflow's comfort zone — and once every node is custom Python wrapping a subprocess, the visual layer stops paying rent.

**My recommendation:** LangGraph as the engine. If you want the visual surface, add Langflow later as an authoring/monitoring UI over it — optional chrome, not the runtime.

**My stronger recommendation for v0:** use *neither* yet. The workflow you've described is a linear pipeline with a retry loop. That's ~200 lines of plain Python around a Mongo state document, and you will understand every line of it. Frameworks don't help with the three things that are actually hard here — the adapter layer, the handoff packet, and the budget ledger — and a framework you adopted before you understood the problem becomes a cage. Introduce LangGraph in Phase 4 when you add real branching and parallelism, and you'll adopt it knowing exactly which of its features you need.

Either way: this contradicts ADR-002, so it needs a new ADR recording the change and the reasoning.

**Similarly on Claw Orchestrator:** ADR-003 already has it unresolved pending hands-on evaluation. Don't resolve it from documentation. For v0 you don't need an execution-layer dependency at all — `subprocess.run` gets you through Phase 3. Adopt one only when you can name the specific problem it solves that your own code doesn't.

## 4. The adapter interface

This is the most important interface in the system. Keep it small; every agent must fit behind it.

```python
from typing import Protocol, Literal
from dataclasses import dataclass
from pathlib import Path

StoppedReason = Literal[
    "completed",          # agent finished on its own
    "budget_exhausted",   # rate/quota limit hit  → failover
    "timeout",            # wall-clock exceeded   → failover or retry
    "no_output",          # watchdog fired, hung  → kill, failover
    "crashed",            # non-zero, not a limit → retry same agent once
    "interrupted",        # human or orchestrator stop
]

@dataclass
class AgentResult:
    stopped_reason: StoppedReason
    session_id: str | None      # native resumable id, for same-agent resumption
    usage: dict                 # {input_tokens, output_tokens, cache_read, usd}
    events_path: str            # where the streamed transcript landed
    exit_code: int
    stderr_tail: str

class AgentAdapter(Protocol):
    name: str
    def run(
        self,
        prompt: str,
        worktree: Path,
        session_id: str | None,   # resume this native session if provided
        timeout_s: int,
    ) -> AgentResult: ...
```

`stopped_reason` is the entire basis of your routing logic. Get its taxonomy right and the router is a small, readable function. Get it wrong — e.g. collapsing `timeout` and `budget_exhausted` — and you'll fail over when you should retry, and burn quota.

Note what is *not* in the interface: nothing about "did the agent succeed at the task." The adapter reports how the **process** ended. Whether the **work** is correct is the check runner's job, and only the check runner's.

## 5. The handoff packet

Assembled fresh on every agent entry, in this order. Order matters — put stable content first (prompt caching works on prefixes) and the most salient content last (recency).

1. **Objective + acceptance criteria** — verbatim from Mongo, never paraphrased by an agent.
2. **Constraints, non-goals, and decisions already made** — so agent B doesn't relitigate agent A's architecture choices.
3. **Injected skills** (per ADR-001) — but see the filtering note below.
4. **Plan with step status** — done / in progress / remaining.
5. **Current git state** — `git log --oneline` since task base, plus the diff.
6. **Dead ends** — "X was tried and fails because Y; do not retry." Wildly underrated. Without it, agent B confidently reattempts exactly what killed agent A. This alone prevents most cross-agent thrash.
7. **Latest check failures** — verbatim error text, never summarized. The exact stack trace is the highest-signal content in the whole packet.
8. **The next step, as an imperative** — one clear instruction, not a menu.

Two disciplines:

**Budget the packet itself.** Every handoff costs tokens on the receiving agent — the very resource you're managing. Measure packet size and cap it. If the diff exceeds ~500 lines, send `git diff --stat` plus the full diff of only the files relevant to the current step.

**Filter skills by stage.** ADR-001 (inject explicitly, don't rely on auto-discovery) is the right call, but "inject all skills always" will quietly become your largest recurring cost. A reviewer doesn't need the graphify indexing skill. Map stage → skill set in config.

Structuring the packet as *static prefix (1–3) then dynamic suffix (4–8)* also makes vendor prompt caching effective on repeat calls to the same agent — a real, measurable cost reduction, not a micro-optimization.

## 6. Data model (MongoDB)

```
tasks           _id, objective, acceptance_criteria[], constraints[],
                status, base_commit, worktree_path, created_at

plans           task_id, steps[{idx, description, status, owner_agent,
                attempts, acceptance}]

runs            _id, task_id, step_idx, agent, stage, session_id,
                prompt_ref, started_at, ended_at, usage{}, stopped_reason,
                exit_code                      ← the ledger's source of truth

events          run_id, seq, ts, type, payload  ← append-only, written DURING run

checks          task_id, commit_sha, command, exit_code, stdout_tail,
                stderr_tail, ts

dead_ends       task_id, description, why_it_failed, discovered_by, ts

locks           worktree_path, holder_run_id, acquired_at   ← one agent per worktree
```

Design notes:

- **Derive the budget ledger from `runs`; don't maintain a separate mutable counter.** Aggregating `runs` inside the current window is crash-safe, auditable, and reconstructible after any failure. Cache it in memory if it gets slow, but the collection stays the source of truth.
- **Idempotency on restart:** any `run` with `started_at` but no `ended_at` is an orphan from a crash. On boot, mark it `stopped_reason: "unknown"` and force plan reconciliation from git state. Never assume an interrupted run did nothing — it probably wrote files.
- **`events` is append-only and written during the run.** If you buffer and write at the end, you've rebuilt the failure mode from §1.
- **`locks` is not optional.** Two agents in one worktree corrupts it. One worktree, one active agent, enforced by a lock document with a holder and a heartbeat.

## 7. Build order

Do not build the architecture diagram top-down. Build a thin working spine, then thicken it.

### Phase 0 — Spikes (one day, before any design work)

Four questions whose answers determine whether the design is even buildable. Answer them with your hands, not with documentation.

- **S1 · Headless invocation.** Run each of the four agents once, non-interactively, capturing structured output. Confirm you can extract: session id, token usage, exit code. Record the exact flags in `Research.md`. *(For DeepSeek: confirm which harness you'll wrap it in.)*
- **S2 · Resumption.** Resume a prior session with each CLI. Confirm it actually retains context.
- **S3 · Limit detection.** Deliberately exhaust a quota — or force the error — and record the exact exit code and stderr text. This is your reactive detector's ground truth, and you cannot guess it.
- **S4 · Worktree containment.** Run an agent inside a git worktree and confirm it doesn't write outside it.

If S1 or S3 fails for an agent, that agent cannot be a first-class citizen in this system. Better to learn that on day one.

### Phase 1 — One agent, one task, end to end
Task in Mongo → create worktree → run Claude Code → run check runner → record pass/fail. No routing, no failover, no second agent. **This is the spine.** Nothing else works until this does.

### Phase 2 — Adapter interface + a second agent
Now the abstraction gets a real test. Add Codex behind the same `AgentAdapter`. Anything that only fits one agent is a leak — fix it now, at two agents, not later at four.

### Phase 3 — Budget ledger + failover
Reactive limit detection, cooldowns, ledger derived from `runs`, and the resume-with-another-agent path from §1. **At the end of this phase your headline feature works.** Test it by setting an artificially tiny budget and watching the handoff happen on a real task.

### Phase 4 — Multi-stage workflow
planner → implementer → reviewer → fixer, with routing policy and the reviewer≠implementer constraint. This is where LangGraph earns its place, if you want it.

### Phase 5 — Parallelism, observability, human gates
Multiple worktrees running concurrently (this is where worktrees actually pay off), Phoenix/OTel tracing, approval checkpoints.

Phases 1–3 are the project. Phases 4–5 are what make it pleasant.

## 8. Pitfalls

Ordered roughly by how likely they are to bite you.

- **Summarize-on-exit** — covered in §1. The single most common fatal design.
- **Infinite fix loops** — implementer → checks fail → fixer → checks fail → forever, burning every budget you have. Cap attempts per step (3), then escalate to a *different* agent, then to a human. Non-negotiable; add it in Phase 1, not later.
- **Trusting the agent's "done"** — never parse completion from prose. Exit codes only. Your architecture already says this; it will be tempting to compromise when the check runner is annoying to configure. Don't.
- **Two agents, one worktree** — corruption. Use the lock.
- **Flaky tests** — nondeterministic checks trigger fixer loops on code that was already correct, and the agent will "fix" working code to satisfy a test that was going to pass anyway. Quarantine flaky tests before onboarding a repo.
- **Hung vs. slow** — indistinguishable without instrumentation. Two watchdogs: wall-clock timeout per run, and a no-output timeout (no events for N minutes → kill).
- **Handoff bloat** — packets grow silently until handoffs cost more than the work. Log packet token count on every handoff and watch the trend.
- **Agent escapes the worktree** — edits global config, `~/.gitconfig`, other repos. Restrict tool permissions per agent; consider containers for anything unattended.
- **Windows friction** — you're on Windows 11, and git worktrees plus long paths plus CRLF plus POSIX-assuming agent CLIs will cost you days. **Run the orchestrator in WSL2.** This is the highest-leverage environment decision available to you.
- **Secrets** — each CLI has its own auth. Keys live in the environment, never in a prompt, never in Mongo. Agents read prompts; assume anything in a prompt is logged somewhere.

# Bhai-To-Bhai

An open-source, locally deployable orchestration platform that coordinates multiple *existing* coding agents (Claude Code, Codex, Gemini CLI, OpenCode/Aider, and other adapters) to complete software-engineering tasks end-to-end — from initial planning through final verification — instead of implementing its own coding agent.

# Build Guide — Multi-Agent Orchestration for Bhai-To-Bhai

Written 2026-08-03. Audience: someone building their first multi-agent system.
Complements `Architecture.md` (target shape) and `Decisions.md` (why). This file is about **how to actually build it, and in what order.**

---

## 0. The mental model (read this first)

The instinct is to think of this as an AI problem. It isn't. **It's a job scheduler with unreliable, expensive, non-deterministic workers.**

Swap the vocabulary and it becomes familiar:

| Your term | What it really is |
|---|---|
| Coding agent | A worker process that may die at any moment |
| Token budget | A per-worker resource quota with a refill window |
| Handoff | Task migration between workers after preemption |
| Canonical task context | The durable job record — the only thing that survives a worker death |
| Check runner | The acceptance test that decides "done", because workers lie |
| Git worktree | The worker's scratch space |

Every hard problem in this project is a distributed-systems problem: crash recovery, idempotency, resource accounting, state reconciliation, deadlock/livelock. The LLM part — writing a prompt, shelling out to `claude -p` — is genuinely the easy part and will take maybe 5% of your effort.

**Consequence:** if you find yourself deep in prompt engineering in week one, you're working on the wrong layer.

---

## 1. The one design decision everything else hangs on

> "If one task unexpectedly takes too many tokens and the coding agent's limit is reached, the other coding agent would resume the work."

Here is the naive design, which almost everyone builds first:

```
agent runs ──▶ finishes ──▶ writes a handoff summary ──▶ next agent reads it
```

**This fails at exactly the moment you built it for.** An agent killed by a rate limit never reaches "finishes." It never writes the summary. You get nothing.

The fix is to invert it:

> **Never summarize on exit. Always reconstruct on entry.**

The handoff packet must be *derivable at any instant* from durable artifacts that are written continuously during the run — not produced by the dying agent as its last act. Concretely, four things must be durable-by-construction:

1. **The worktree** — commits are the ground truth of what physically got done. Instruct the agent to commit after every logical step; additionally have the orchestrator auto-commit on a timer (`git add -A && git commit -m "wip: auto"`). A `SIGKILL`ed agent still leaves you a diff.
2. **The plan** — the task is decomposed into ordered steps *before* execution, stored in Mongo, each marked `pending`/`in_progress`/`done`. Death at step 4 means the next agent starts at step 4, not step 1.
3. **The event stream** — run the CLI with streaming JSON output and persist each event to Mongo **as it arrives**, not after process exit. A killed process still leaves its full transcript.
4. **The check results** — last known pass/fail state, tied to a commit SHA.

If those four are durable, "agent A died, agent B resumes" is just: build a packet from (1)+(2)+(3)+(4), hand it to B. It works identically whether A exited cleanly, was rate-limited, timed out, or you closed your laptop.

**Build this first. Everything else is decoration on top of it.**

## 2. Token budgets: your abstraction is wrong (and that's fine)

You said routing is driven by "token budgets of the coding agents." The complication: the four agents don't have comparable budgets, and none of them exposes "tokens remaining" as a number you can query.

| Agent | What actually limits you | Queryable? |
|---|---|---|
| Claude Code | Rolling usage windows (subscription) or $/token (API key) | No — usage is reported *per call*, remaining is not exposed |
| Codex | Rate-limit windows (ChatGPT plan) or $/token (API key) | No |
| Gemini CLI | Free tier is **request-count** limited (per-minute and per-day), not token limited | No |
| DeepSeek | Pure $/token, effectively unbounded until money runs out | Balance only |

So don't model "tokens remaining." Model a **Budget Ledger** with a normalized state per agent:

```python
{
  "agent": "claude",
  "limit_type": "rolling_window",   # rolling_window | daily_requests | monetary | none
  "window": "5h",
  "limits":   {"tokens": 1_500_000, "requests": None, "usd": None},   # YOU configure these
  "consumed": {"tokens": 812_003,   "requests": 47,   "usd": 0.0},    # derived from runs
  "state": "available",             # available | degraded | exhausted | cooldown
  "cooldown_until": None,           # ISO timestamp, set on reactive detection
}
```

Update it two ways, and understand which one is authoritative:

- **Proactive (an estimate):** parse `usage` out of each call's JSON result, accumulate. Used for *pre-emptive* routing — "don't start a job I estimate at 200k tokens on an agent I think has 40k of headroom."
- **Reactive (the truth):** the agent exits non-zero with a rate-limit message. Mark `exhausted`, set `cooldown_until`, fail over. **This is the signal you trust.** Your proactive estimate will drift; vendors count tokens in ways you can't fully replicate.

Two rules that will save you real money:

- **Reserve headroom.** Route to an agent only if `estimated_cost × 1.5 < remaining`. A mid-task death is expensive twice over: you lose the partial work *and* you pay a cold-start handoff on the next agent.
- **Switching is not free — the router must price it in.** Returning to an agent that already has a native session is cheap (it resumes with its own context). Switching vendors means a cold start plus a full context packet. Prefer to *wait or return* over switching, unless the agent is genuinely exhausted.

Keep the rate-limit detection patterns in **config, not code** — vendors reword their error messages and you don't want a code change every time.

```yaml
# config/limit_signals.yaml
claude:
  exit_codes: [1]
  stderr_patterns: ["rate limit", "usage limit reached", "quota exceeded"]
  cooldown: "5h"
gemini:
  stderr_patterns: ["RESOURCE_EXHAUSTED", "quota"]
  cooldown: "24h"
```

**One caveat on DeepSeek:** it's a *model*, not an agentic coding CLI. To use it as a coding agent you must pair it with a harness that accepts a custom OpenAI-compatible endpoint (Aider, OpenCode, and similar). Verify this in the spike phase before designing it into your router — or scope it to non-agentic roles (reviewer, summarizer, planner) where a plain API call is sufficient. Its low cost makes it the natural **fallback of last resort** when everything else is in cooldown.

## 3. Langflow vs. LangGraph — flagging a contradiction

Your stack table says **Langflow**. Your own **ADR-002 chose LangGraph**. These are different tools and the difference matters here:

- **Langflow** is a visual, drag-and-drop builder over LangChain. Excellent for prototyping and for showing someone a flow diagram.
- **LangGraph** is a durable state-machine runtime: cycles, conditional edges, checkpointers, interrupts, resume-from-checkpoint.

What this project needs from that layer is: cycles (fix → recheck → fix), conditional routing on agent state, checkpoint/resume after crash, mid-run interruption, and nodes that block for minutes on a subprocess. That's LangGraph's exact feature list and outside Langflow's comfort zone — and once every node is custom Python wrapping a subprocess, the visual layer stops paying rent.

**My recommendation:** LangGraph as the engine. If you want the visual surface, add Langflow later as an authoring/monitoring UI over it — optional chrome, not the runtime.

**My stronger recommendation for v0:** use *neither* yet. The workflow you've described is a linear pipeline with a retry loop. That's ~200 lines of plain Python around a Mongo state document, and you will understand every line of it. Frameworks don't help with the three things that are actually hard here — the adapter layer, the handoff packet, and the budget ledger — and a framework you adopted before you understood the problem becomes a cage. Introduce LangGraph in Phase 4 when you add real branching and parallelism, and you'll adopt it knowing exactly which of its features you need.

Either way: this contradicts ADR-002, so it needs a new ADR recording the change and the reasoning.

**Similarly on Claw Orchestrator:** ADR-003 already has it unresolved pending hands-on evaluation. Don't resolve it from documentation. For v0 you don't need an execution-layer dependency at all — `subprocess.run` gets you through Phase 3. Adopt one only when you can name the specific problem it solves that your own code doesn't.

## 4. The adapter interface

This is the most important interface in the system. Keep it small; every agent must fit behind it.

```python
from typing import Protocol, Literal
from dataclasses import dataclass
from pathlib import Path

StoppedReason = Literal[
    "completed",          # agent finished on its own
    "budget_exhausted",   # rate/quota limit hit  → failover
    "timeout",            # wall-clock exceeded   → failover or retry
    "no_output",          # watchdog fired, hung  → kill, failover
    "crashed",            # non-zero, not a limit → retry same agent once
    "interrupted",        # human or orchestrator stop
]

@dataclass
class AgentResult:
    stopped_reason: StoppedReason
    session_id: str | None      # native resumable id, for same-agent resumption
    usage: dict                 # {input_tokens, output_tokens, cache_read, usd}
    events_path: str            # where the streamed transcript landed
    exit_code: int
    stderr_tail: str

class AgentAdapter(Protocol):
    name: str
    def run(
        self,
        prompt: str,
        worktree: Path,
        session_id: str | None,   # resume this native session if provided
        timeout_s: int,
    ) -> AgentResult: ...
```

`stopped_reason` is the entire basis of your routing logic. Get its taxonomy right and the router is a small, readable function. Get it wrong — e.g. collapsing `timeout` and `budget_exhausted` — and you'll fail over when you should retry, and burn quota.

Note what is *not* in the interface: nothing about "did the agent succeed at the task." The adapter reports how the **process** ended. Whether the **work** is correct is the check runner's job, and only the check runner's.

## 5. The handoff packet

Assembled fresh on every agent entry, in this order. Order matters — put stable content first (prompt caching works on prefixes) and the most salient content last (recency).

1. **Objective + acceptance criteria** — verbatim from Mongo, never paraphrased by an agent.
2. **Constraints, non-goals, and decisions already made** — so agent B doesn't relitigate agent A's architecture choices.
3. **Injected skills** (per ADR-001) — but see the filtering note below.
4. **Plan with step status** — done / in progress / remaining.
5. **Current git state** — `git log --oneline` since task base, plus the diff.
6. **Dead ends** — "X was tried and fails because Y; do not retry." Wildly underrated. Without it, agent B confidently reattempts exactly what killed agent A. This alone prevents most cross-agent thrash.
7. **Latest check failures** — verbatim error text, never summarized. The exact stack trace is the highest-signal content in the whole packet.
8. **The next step, as an imperative** — one clear instruction, not a menu.

Two disciplines:

**Budget the packet itself.** Every handoff costs tokens on the receiving agent — the very resource you're managing. Measure packet size and cap it. If the diff exceeds ~500 lines, send `git diff --stat` plus the full diff of only the files relevant to the current step.

**Filter skills by stage.** ADR-001 (inject explicitly, don't rely on auto-discovery) is the right call, but "inject all skills always" will quietly become your largest recurring cost. A reviewer doesn't need the graphify indexing skill. Map stage → skill set in config.

Structuring the packet as *static prefix (1–3) then dynamic suffix (4–8)* also makes vendor prompt caching effective on repeat calls to the same agent — a real, measurable cost reduction, not a micro-optimization.

## 6. Data model (MongoDB)

```
tasks           _id, objective, acceptance_criteria[], constraints[],
                status, base_commit, worktree_path, created_at

plans           task_id, steps[{idx, description, status, owner_agent,
                attempts, acceptance}]

runs            _id, task_id, step_idx, agent, stage, session_id,
                prompt_ref, started_at, ended_at, usage{}, stopped_reason,
                exit_code                      ← the ledger's source of truth

events          run_id, seq, ts, type, payload  ← append-only, written DURING run

checks          task_id, commit_sha, command, exit_code, stdout_tail,
                stderr_tail, ts

dead_ends       task_id, description, why_it_failed, discovered_by, ts

locks           worktree_path, holder_run_id, acquired_at   ← one agent per worktree
```

Design notes:

- **Derive the budget ledger from `runs`; don't maintain a separate mutable counter.** Aggregating `runs` inside the current window is crash-safe, auditable, and reconstructible after any failure. Cache it in memory if it gets slow, but the collection stays the source of truth.
- **Idempotency on restart:** any `run` with `started_at` but no `ended_at` is an orphan from a crash. On boot, mark it `stopped_reason: "unknown"` and force plan reconciliation from git state. Never assume an interrupted run did nothing — it probably wrote files.
- **`events` is append-only and written during the run.** If you buffer and write at the end, you've rebuilt the failure mode from §1.
- **`locks` is not optional.** Two agents in one worktree corrupts it. One worktree, one active agent, enforced by a lock document with a holder and a heartbeat.

## 7. Build order

Do not build the architecture diagram top-down. Build a thin working spine, then thicken it.

### Phase 0 — Spikes (one day, before any design work)

Four questions whose answers determine whether the design is even buildable. Answer them with your hands, not with documentation.

- **S1 · Headless invocation.** Run each of the four agents once, non-interactively, capturing structured output. Confirm you can extract: session id, token usage, exit code. Record the exact flags in `Research.md`. *(For DeepSeek: confirm which harness you'll wrap it in.)*
- **S2 · Resumption.** Resume a prior session with each CLI. Confirm it actually retains context.
- **S3 · Limit detection.** Deliberately exhaust a quota — or force the error — and record the exact exit code and stderr text. This is your reactive detector's ground truth, and you cannot guess it.
- **S4 · Worktree containment.** Run an agent inside a git worktree and confirm it doesn't write outside it.

If S1 or S3 fails for an agent, that agent cannot be a first-class citizen in this system. Better to learn that on day one.

### Phase 1 — One agent, one task, end to end
Task in Mongo → create worktree → run Claude Code → run check runner → record pass/fail. No routing, no failover, no second agent. **This is the spine.** Nothing else works until this does.

### Phase 2 — Adapter interface + a second agent
Now the abstraction gets a real test. Add Codex behind the same `AgentAdapter`. Anything that only fits one agent is a leak — fix it now, at two agents, not later at four.

### Phase 3 — Budget ledger + failover
Reactive limit detection, cooldowns, ledger derived from `runs`, and the resume-with-another-agent path from §1. **At the end of this phase your headline feature works.** Test it by setting an artificially tiny budget and watching the handoff happen on a real task.

### Phase 4 — Multi-stage workflow
planner → implementer → reviewer → fixer, with routing policy and the reviewer≠implementer constraint. This is where LangGraph earns its place, if you want it.

### Phase 5 — Parallelism, observability, human gates
Multiple worktrees running concurrently (this is where worktrees actually pay off), Phoenix/OTel tracing, approval checkpoints.

Phases 1–3 are the project. Phases 4–5 are what make it pleasant.

## 8. Pitfalls

Ordered roughly by how likely they are to bite you.

- **Summarize-on-exit** — covered in §1. The single most common fatal design.
- **Infinite fix loops** — implementer → checks fail → fixer → checks fail → forever, burning every budget you have. Cap attempts per step (3), then escalate to a *different* agent, then to a human. Non-negotiable; add it in Phase 1, not later.
- **Trusting the agent's "done"** — never parse completion from prose. Exit codes only. Your architecture already says this; it will be tempting to compromise when the check runner is annoying to configure. Don't.
- **Two agents, one worktree** — corruption. Use the lock.
- **Flaky tests** — nondeterministic checks trigger fixer loops on code that was already correct, and the agent will "fix" working code to satisfy a test that was going to pass anyway. Quarantine flaky tests before onboarding a repo.
- **Hung vs. slow** — indistinguishable without instrumentation. Two watchdogs: wall-clock timeout per run, and a no-output timeout (no events for N minutes → kill).
- **Handoff bloat** — packets grow silently until handoffs cost more than the work. Log packet token count on every handoff and watch the trend.
- **Agent escapes the worktree** — edits global config, `~/.gitconfig`, other repos. Restrict tool permissions per agent; consider containers for anything unattended.
- **Windows friction** — you're on Windows 11, and git worktrees plus long paths plus CRLF plus POSIX-assuming agent CLIs will cost you days. **Run the orchestrator in WSL2.** This is the highest-leverage environment decision available to you.
- **Secrets** — each CLI has its own auth. Keys live in the environment, never in a prompt, never in Mongo. Agents read prompts; assume anything in a prompt is logged somewhere.

Yes — Ralph supports this natively, though not automatically for a plain "check my plan" request. It's built into the architecture but you need to trigger it. Here's how it actually works based on that guide.

The mechanism: three node types
The doc defines three node types, and this is the key: skill runs synchronously as an actual command execution (plan, execute, verify — these run in your host CLI, i.e. Claude Code), cli runs via maestro delegate as a background CLI delegate execution — this is the agent-switching mechanism, and decision is Ralph re-evaluating results to decide whether to continue or insert a fix loop.

So a Ralph chain isn't locked to one agent. Individual steps in the chain can be typed cli, which hands that step off to a different backend CLI (Codex, Gemini, etc.) via maestro delegate, running in the background while the rest of the session continues. You can see this directly in the session schema — the example status.json shows steps with "type": "skill" and lists "cli" as a valid alternative type alongside "decision".

How your plan → codex-review → implement → codex-review sequence would look
Ralph's own quality pipeline already has a review stage baked into the lifecycle — plan → execute → verify → ◆post-verify → business-test → ◆post-business-test → review → ◆post-review → test-gen+test — but by default that review step runs as a skill (i.e., in Claude Code), not necessarily delegated to Codex. To get Codex specifically as the reviewer, you have two paths:

1. Use quick mode's CLI-review stage, which is explicitly designed to call out to a different CLI: quick mode is verify → CLI-review, skipping business-test, test-gen, test. That "CLI-review" step is the cli node type — a delegate call, not an in-host skill. This is the fastest way to get an external-agent check without writing custom config.

2. Insert your own cli delegate steps at the plan and implementation checkpoints via maestro delegate, targeting Codex explicitly. The delegate-async guide (which I referenced earlier but haven't fully verified the exact flag syntax for) covers this — the general shape is something like:

maestro delegate --agent codex --task "review this plan for gaps" --input <plan-artifact>
Ralph's decision nodes (the ◆ checkpoints) then read that delegate's output file the same way they read verification.json or review.json for its own skills, and decide pass/fail/retry from it.

What this gets you, concretely
Run it in quick mode so the review stage delegates out:

/maestro-ralph "implement OAuth2 refresh tokens" --quality quick
Chain becomes: plan (Claude, skill) → execute (Claude, skill) → verify (Claude, skill) → ◆post-verify → CLI-review (delegated to Codex, cli type) → ◆post-review (Ralph reads Codex's verdict, inserts fix loop if BLOCK).

That gives you implementation checked by Codex automatically. To also get the plan checked by Codex before execution starts, you'd need to manually insert a cli delegate step between plan and execute — this isn't one of Ralph's built-in decision nodes (post-verify, post-review, post-test, post-milestone all sit after execution, not after planning), so plan-level cross-model review looks like something you'd configure yourself via maestro delegate, rather than get for free from Ralph's default chain.

Bottom line vs. flow-next
Ralph's cli node type proves maestro-flow's architecture supports mid-task agent switching — it's not bolted on. But the built-in decision gates are oriented around post-implementation quality (verify/review/test), not a plan-review gate before execution. Flow-next's plan-review and impl-review are explicit, named commands for exactly the two checkpoints you want, with Codex as the configured backend from setup — Ralph gets you there but requires assembling the plan-side check yourself via maestro delegate, since it isn't one of the five built-in decision nodes.

Yes — customizability is actually one of flow-next's named pillars: ⇶ Model routing — Any model, any role — just ask. It's not a fixed two-agent script; the plan/implement/review split you asked about is just the default configuration, and several layers are adjustable.

What you can customize
1. Which model reviews. Review backend is a config key, and it's not locked to Codex:

flowctl config set review.backend codex        # or: repoprompt, copilot, cursor
The README lists the review backends interchangeably — RepoPrompt, Codex, Copilot, or Cursor as second opinion — so you swap the reviewer per project, or per review type. plan-review and impl-review can theoretically point at different backends if you want, say, Codex to review implementation but a different tool to review plans.

2. Who implements. Default is host-only (Claude Code writes the code), but this is explicitly toggleable:

flowctl config set work.delegate codex
or invoked ad hoc with delegate:codex for a single work run — Opt-in: offload implementation to a local codex exec with delegate:codex (or work.delegate=codex config) — OFF by default, consent-gated, host keeps all judgment. So the four-way split you originally described (Claude plans, Codex checks, Claude implements, Codex checks) is one point on a spectrum — you could also do Codex-implements/Claude-reviews, or alternate per task.

3. Per-task / per-role overrides, not just global config. The feature list explicitly separates this out: Orchestration & model routing — tiered subagents, per-task reviewer routing, opt-in codex exec implementation offload, promptable overrides. "Per-task reviewer routing" means a single epic can route task A's review to Codex and task B's review to a different backend, rather than one global setting for the whole project. "Promptable overrides" means you can just ask in natural language for a one-off change without touching config — the model-routing tenet literally says "any model, any role — just ask."

4. Review timing granularity. You control whether review happens after every single task or once at the end of a batch:

/flow-next:work fn-1.1     # one task, review after it
/flow-next:work fn-1       # whole epic, one review at the end
This trades review tightness against overhead — Work task-by-task with review after each, or run an entire epic at once. Same guarantees either way.

5. Depth of the pipeline itself. You're not locked into plan→work→review. The full command surface includes interview (extra Q&A pass before planning), qa (opt-in live-app QA after work, before PR), spec-completion-review (a final gate checking the whole implementation against the original spec), and pilot/land/ralph-init for different levels of autonomy. You pick which stages actually run for a given task.

6. Autonomy level. Same gates, three different drivers: manual (/flow-next:work, you type each command), pilot (one pipeline stage per tick, driven by /loop 10m /flow-next:pilot), or Ralph (a fully autonomous overnight loop with hook-enforced guardrails). The plan-check-implement-check sequence stays identical across all three — you're just choosing how much you sit at the keyboard.

7. Platform, not just model. Since it's first-class on Claude Code, Codex, and Factory Droid (and works via compatibility on Grok Build and Cursor), you could flip which CLI is the host running the orchestration entirely — e.g., Codex as host, Claude Code as the reviewer — rather than only swapping the reviewer while Claude Code stays the driver.

Where the config actually lives
All of this is flowctl config keys plus optional per-invocation flags/phrases — no code changes, no forking the plugin. The authoritative reference for every knob is docs/orchestration.md in the repo (Steering all of it — model routing, review backends, delegation, loop chaining: docs/orchestration.md), which I haven't pulled the full contents of — if you want the exact list of config keys and their defaults rather than what's summarized in the README, that file is worth fetching directly before you commit to a setup.
