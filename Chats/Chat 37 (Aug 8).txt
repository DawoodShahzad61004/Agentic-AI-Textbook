What a worktree is
A git worktree is a second (third, Nth) working directory attached to the same repository. git worktree add <path> <branch> gives you a separate checkout on its own branch, sharing the one .git object store. Commits made in one are immediately visible as branches in all of them, but the files never collide.

That property is the whole reason this project uses them: a wave runs several coding agents concurrently, each editing files. Without isolation they'd overwrite each other in a single checkout. With worktrees, each agent gets a private directory and a private branch, and reconciliation is deferred to an explicit merge step.

The module
worktrees.py is a thin, non-raising wrapper over the git CLI:

git() (:56) shells out via subprocess.run with a timeout and returns a frozen GitResult(ok, stdout, stderr, returncode). FileNotFoundError → 127, timeout → 124. Nothing raises — the module docstring is explicit that a merge conflict is an outcome the merger agent exists to handle, not an exception the graph should die on.
Worktree (:47) is just (task_id, path, branch).
Everything else (create, commit_all, merge, remove, reset_branch, conflicted_files, head_sha, …) is a named git recipe returning GitResult.
Layout and naming
From config.py:234-239:

Root	<target_repo>/../.bhai-worktrees — a sibling, so git status in the target stays clean
Path	.bhai-worktrees/{run_id}-{task_id}
Task branch	bhai/{run}/{task}
Integration branch	bhai/{run}/integration
Lifecycle in the workflow
Wave start — node.py:119 calls ensure_integration_branch(). Wave 0 branches from the repo as it stands; wave N from whatever the merger has integrated. wave_base_sha is recorded from the branch, not HEAD, because the target repo may be checked out elsewhere.
Dispatch — dispatch.py:152, one wt.create(...) per task: git worktree add -B <branch> <path> <base>. A leftover path from an interrupted run is remove()d first (:180). Failure returns (None, result) so only that task is lost, not the wave.
Agent runs with cwd=worktree.path.
Forced commit — dispatch.py:190 commit_all() runs regardless of whether the agent succeeded, so a killed process still leaves a diff. Then head_sha + _changed_files(workdir, base) become the evidence the reviewer routes on — git's view of what changed, deliberately separate from the agent's prose claim.
Merge — merger/merge.py:187 merges each task branch into the integration branch with --no-ff. On conflict the repo is left conflicted on purpose (:211) — that's the state the merger agent is dispatched into; aborting would destroy what it needs to see.
Rework — _revert_rejected_attempt() (node.py:58) removes the stale worktrees and reset_branch()es integration back to wave_base_sha. Both halves are needed because the reviewer runs after the merger, so a rejected wave is already integrated. Task branches survive, so the rejected attempt stays inspectable.
Cleanup — as established, cleanup() is never called outside tests; directories accumulate.
There's an escape hatch: config.USE_GIT_WORKTREES = False puts everything in shared-workspace mode (dispatch.py:162) — agents work directly in the target checkout and the merger has nothing to merge.

What a SHA is
A commit's identity in git. When you commit, git hashes the tree contents, the parent commit(s), author, timestamp, and message into a 40-character hex digest — a1b2c3d4.... That digest is the commit's name. Two consequences matter here: it's immutable (change anything and it's a different commit), and it names an exact repository state you can always return to. [:8] in the logs is just the short form — enough to be unique in a normal repo.

Branches, by contrast, are mutable pointers to a SHA. bhai/m1/integration means "whatever commit that label currently points at" — which is exactly why the code stores SHAs, not branch names, when it needs a fixed point.

Where it's used
As evidence. worktrees.py:97 head_sha() is called after every task (dispatch.py:193) and stored on the outcome. Its docstring states the rule: "A pass or a fail with no commit behind it is not evidence (ADR-005)." An agent's claim that it did something is prose; a SHA is a thing you can check out and diff.

As a rewind point, at two scopes (state.py:149-158):

Field	Captured	Rewinds on
wave_base_sha	Where the integration branch stood before this wave merged	rework — reviewer rejects a wave
run_base_sha	Where it stood before any wave ran	replan — supervisor rejects the whole result
Both go through reset_branch(repo, branch, sha) (:140), which is checkout <branch> then reset --hard <sha>.

The two scopes exist for different failure modes. A rework needs the wave's own starting point — not wherever the discarded attempt left things — which is why node.py:137 captures it on the first attempt only (state.get(...) or <read it>). A replan needs to go all the way back, because the new plan is a fresh decomposition of the same goal; layered on the old implementation, agents would be asked to create files that already exist and would then read as "changed nothing" (planner/node.py:178-185).

One detail worth noting: node.py:137 reads the SHA via rev-parse <base> — the branch — rather than HEAD, because the target repository may be checked out on some entirely different branch while the orchestrator works.

And reset --hard discards nothing that matters: each task branch still points at what that agent produced, so a rejected attempt stays inspectable after the integration branch has moved off it.

1. How checkpointing is done
LangGraph's SqliteSaver, one database per run. main.py:272-282:


with SqliteSaver.from_conn_string(str(config.CHECKPOINT_DIR / f"{run_id}.sqlite")) as saver:
    graph = compile_graph(checkpointer=saver)
    thread = {"configurable": {"thread_id": run_id}, ...}
The run_id doubles as the LangGraph thread_id, which is why --resume <run-id> is enough to find the state. The comment there is explicit that the checkpointer isn't optional: it backs both the requirements interrupt() pause and crash-resume.

Granularity is the node. LangGraph writes a checkpoint after each node returns its state update. The nodes are the ones in graph.py:67-81 — requirements, clarify, plan, orchestrate, merge, review, advance_wave, supervise. Note that orchestrate is one node covering an entire wave — all its parallel tasks. That single fact drives most of the answer to your third question.

What goes in state is governed by one rule (state.py:3-6): "if this graph were checkpointed and resumed tomorrow, would this value represent the progress of this specific run?" Yes → state; no → config. So the wave cursor, verdicts, counters, wave_base_sha, run_base_sha, and active_worktrees are checkpointed; model names and deadlines aren't.

The second durability layer
The checkpoint isn't alone, because state is only durable at a node boundary. Three things are written eagerly to disk as they happen:

What	Where	Why
Events	append_event() artifacts.py:169 — one JSON line, flush()ed	Its docstring: "written on arrival, which is the difference between a killed run leaving evidence and leaving nothing"
Tasks	TASK-*.json, reloadable via load_tasks() :191	"for a resumed run that has no state in hand"
Learnings	append-only learnings.md	Four agents write it; overwrite would lose the earlier ones
And the real one: git. dispatch.py:190 runs commit_all() after every task regardless of whether the agent succeeded. That's ADR-005's premise, stated in the module docstring: "resumption must not depend on an outgoing agent behaving correctly under duress, and an agent killed mid-turn has committed nothing."

2. How checkpoints + worktrees combine
They cover the two halves of "where was I":

Checkpoint = position in the pipeline. Which wave, which attempt, the last verdict, the branch SHAs, and active_worktrees — a list of {task_id, branch, worktree, commit, ok} per task. state.py:145-147 says why that list exists: "so a crash leaves something to reconcile against actual git state rather than a guess."
Worktrees/branches = the work product. State can't hold file contents. It holds a branch name and a SHA; the branch is the durable artifact, and it survives the orchestrator process entirely.
So resume is: SQLite says "wave 2, attempt 1, integration branch at a1b2c3"; git holds the actual code. --resume passes None as the graph input (main.py:287), which is LangGraph's signal to continue from the stored checkpoint rather than start fresh.

A third thread ties in: vendor session ids. _sessions_from() (node.py:36) pulls each task's session_id from the last attempt so a rework resumes the same Claude/Codex session — otherwise "here's what you got wrong" refers to nothing. The adapters go out of their way to preserve that id even on failure: codex.py:190-204 keeps the thread id off a TimeoutExpired, because "it is what lets the retry resume the agent that was part-way through."

Depends on what got interrupted. These are genuinely different cases and the codebase handles them very differently.

(a) The agent hits its own limit; orchestrator still alive — fully recoverable
Token limit, deadline, crash of the CLI. The adapter returns AgentResult(ok=False, error_kind="timeout"|...) with the session id intact. run_task continues past it: commit_all() still runs, so the half-written file is committed to the task branch; head_sha and _changed_files still record what git saw. The outcome carries error_kind into the wave result, and a rework resumes that same vendor session on top of the already-committed partial work. This path is designed for and it works.

(b) Ctrl-C / process killed mid-wave — resumes, but loses the in-flight work
This is the weak spot, and it follows directly from orchestrate being a single node:

The wave's checkpoint is only written when wave_orchestrator_node returns, which is after future.result() for every task (dispatch.py:281). Kill it mid-wave and no checkpoint for that wave exists.
--resume therefore re-enters orchestrate at the last completed node boundary — the whole wave re-runs from scratch, not the surviving tasks only.
It won't crash on the leftovers: wt.create() sees the stale path, logs a warning and remove()s it (worktrees.py:180-184) — explicitly flagged as "a leftover from an interrupted run."
But that discards it. commit_all never ran, so uncommitted edits in the killed worktrees are deleted. Anything the agent committed itself survives as a dangling object, but worktree add -B <branch> resets the branch to base, so it's no longer reachable by name — reflog only.
The resumed wave also cold-starts the agents: sessions= is passed only if rework_comments (node.py:164), and a crash-resume has no review verdict, so the session ids sitting in the checkpoint go unused here.
There's no KeyboardInterrupt handler anywhere in the orchestrator — I checked. And because the pool is a with block, exiting it calls shutdown(wait=True): an interrupt raised in the main thread doesn't tear down the in-flight agent subprocesses, it waits for them. On Windows the console Ctrl-C event usually reaches the child processes too so they die quickly, but a kill of the parent alone won't be prompt.

(c) Between nodes — clean
Killed after orchestrate returned but before/during merge? The wave's checkpoint is written, task branches are committed, wave_base_sha is recorded. Resume picks up at merge and loses nothing.

Summary: checkpointing is durable and correct at wave granularity, and everything a completed task produced is safe in git. What isn't protected is a task that was mid-turn when the orchestrator itself died — that work is discarded and the wave re-runs whole. Making that recoverable would mean either committing worktrees on an interrupt handler, or splitting orchestrate so each task checkpoints independently.
