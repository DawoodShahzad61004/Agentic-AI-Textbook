The actual mechanism, found in orchestrator/adapters/codex.py:


completed = subprocess.run(argv, ..., timeout=spec.deadline_seconds, ...)
CPython's subprocess.run() on Windows, when the timeout fires, does this internally (not this project's code — stdlib):


except TimeoutExpired as exc:
    process.kill()
    if _mswindows:
        exc.stdout, exc.stderr = process.communicate()  # second, un-timed call
process.kill() calls TerminateProcess() on the immediate child only — that's cmd.exe running the npm codex.CMD shim. It does not touch the node.exe grandchild that cmd.exe spawned to actually run Codex (nor anything node.exe itself spawns). Nothing in codex.py or dispatch.py uses CREATE_NEW_PROCESS_GROUP, taskkill /T, or any tree-kill — confirmed by grep, zero hits.

So: cmd.exe dies, but node.exe survives and still holds the write end of the inherited stdout/stderr pipes. The stdlib's post-kill communicate() call blocks reading those pipes until EOF, which never comes because a live process still holds them open. That's the hang — it happens after the 300s deadline correctly fires internally, inside Python's own cleanup code, which is why the log shows nothing past the dispatch line: run_agent() never returns, so it never gets to log the timeout AgentResult.

This is a Windows-specific gap in codex.py's subprocess handling, consistent with (but a level more specific than) the docs/Bugs.md #23/#29 family of Windows .cmd-shim defects — worth adding as its own entry if you want it tracked, since none of the existing 32 cover a hang-past-deadline. The fix would be killing the process tree (taskkill /F /T /PID <pid> or CREATE_NEW_PROCESS_GROUP + CTRL_BREAK_EVENT) instead of relying on Popen.kill().

Answer briefly:
Can it be fixed? If yes, how?
Yes, it's fixable. The problem is that Python's stdlib subprocess.run(timeout=...) only kills the immediate child (cmd.exe running codex.CMD), not the node.exe grandchild that holds the pipes open — so cleanup hangs forever instead of returning the timeout result.

Fix: stop using subprocess.run()'s built-in timeout handling in orchestrator/adapters/codex.py and kill the whole process tree yourself:

Spawn with Popen(..., creationflags=subprocess.CREATE_NEW_PROCESS_GROUP) instead of subprocess.run.
Call process.communicate(timeout=spec.deadline_seconds) yourself.
On TimeoutExpired, instead of relying on process.kill(), run:

subprocess.run(["taskkill", "/F", "/T", "/PID", str(process.pid)])
(/T kills the whole tree — cmd.exe, node.exe, and anything Codex itself spawned.)
Then call process.communicate() again to drain the now-truly-closed pipes and build the AgentResult(error_kind="timeout", ...) as before.
Same fix should be applied to adapters/claude.py and adapters/maestro.py if they invoke .CMD/.bat shims the same way — the vulnerability is generic to any Windows npm-shim subprocess, not Codex-specific. Worth logging this as a new docs/Bugs.md entry once fixed, since none of the existing 32 cover a hang-past-deadline.

+def run_with_deadline(
+    argv: list[str],
+    *,
+    input: str | None,
+    cwd: str,
+    timeout: float,
+) -> subprocess.CompletedProcess:
+    """`subprocess.run`, but a deadline that actually stops the process.
+
+    Every vendor CLI here is an npm-installed `.cmd` shim: Windows runs it as
+    `cmd.exe`, which spawns a `node.exe` grandchild that does the real work and
+    holds the inherited stdout/stderr pipes open. `subprocess.run(timeout=...)`
+    on a timeout calls `Popen.kill()`, which is `TerminateProcess()` on that one
+    immediate child — `cmd.exe` dies, `node.exe` does not — and then, on
+    Windows, the stdlib does a second, un-timed `communicate()` to drain the
+    pipes. That call blocks forever: the pipe's write end is still open in the
+    surviving grandchild, so EOF never arrives. The result is indistinguishable
+    from the deadline never firing at all, because `run_agent` never gets to log
+    anything — the call it is blocked inside is stdlib cleanup, not this
+    project's code.
+
+    `taskkill /T` kills the whole tree by PID rather than one process, which is
+    what actually closes those handles and lets the drain finish.
+    """
+    creationflags = subprocess.CREATE_NEW_PROCESS_GROUP if os.name == "nt" else 0
+    process = subprocess.Popen(
+        argv,
+        stdin=subprocess.PIPE if input is not None else None,
+        stdout=subprocess.PIPE,
+        stderr=subprocess.PIPE,
+        text=True,
+        encoding="utf-8",
+        errors="replace",
+        cwd=cwd,
+        env=subprocess_env(),
+        creationflags=creationflags,
+    )
+    try:
+        stdout, stderr = process.communicate(input=input, timeout=timeout)
+    except subprocess.TimeoutExpired:
+        if os.name == "nt":
+            subprocess.run(
+                ["taskkill", "/F", "/T", "/PID", str(process.pid)],
+                capture_output=True,
+            )
+        else:
+            process.kill()
+        stdout, stderr = process.communicate()
+        raise subprocess.TimeoutExpired(argv, timeout, output=stdout, stderr=stderr)
+    return subprocess.CompletedProcess(argv, process.returncode, stdout, stderr)
