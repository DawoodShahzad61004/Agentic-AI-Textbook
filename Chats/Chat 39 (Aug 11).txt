Yes. From your screenshots, your VS Code already has the newer Bring Your Own Model / BYOK system, so you can add models that do not consume GitHub Copilot premium credits. VS Code now supports built-in providers such as OpenAI, Anthropic, Google, OpenRouter, Ollama, and Custom Endpoint, and extensions can register even more providers.

For what you're trying to do, I'd use one of these approaches:

Best completely free local option: Ollama + a coding model such as Qwen Coder.
Best free cloud option: a provider with a free API tier, added through OpenRouter/Google/etc. Availability and limits vary by provider.
Best for your existing local LLM setup: Custom Endpoint pointing VS Code directly at your OpenAI-compatible local server.
1. Easiest free option: Ollama

Since your screenshot shows Add Models → Ollama (Deprecated), I'd avoid relying on that older built-in entry and instead use Custom Endpoint or a current Ollama provider extension. VS Code's Custom Endpoint supports OpenAI-compatible Chat Completions/Responses endpoints, specifically for things such as self-hosted models.

For example, install Ollama and run:

ollama pull qwen3-coder:30b

or, if your machine can't comfortably run that:

ollama pull qwen2.5-coder:7b

http://localhost:11434/v1

Provider: Custom Endpoint

Custom endpoint models are specifically supported for self-hosted models and OpenAI-compatible servers.

how can I use these models, other than the local ones?

Those entries under CLOUD MODELS are models hosted by Ollama Cloud. They do not run on your RTX 5050 or consume your laptop's VRAM like the models under LOCAL MODELS. Ollama sends the request to its cloud servers and returns the response, while keeping essentially the same Ollama workflow/API.

Since they're already appearing in your Ollama UI, the easiest way is simply to select one—such as nemotron-3-ultra, glm-5.2, deepseek-v4-pro, or kimi-k3—and chat with it there.

From the terminal, you can use them like this:

ollama run nemotron-3-ultra:cloud

or:

ollama run glm-5.2:cloud
ollama run deepseek-v4-pro:cloud
ollama run kimi-k3:cloud

The :cloud suffix is important when explicitly referring to the cloud-hosted variant. For example, Ollama's own documentation uses commands such as:

ollama run minimax-m2:cloud

First, make sure you're signed in

Cloud models require authentication with your Ollama account, unlike the ordinary local API at localhost:11434.

You can check/update Ollama and then sign in from the Ollama app. With a recent Ollama version, cloud-model sign-in is integrated into the desktop experience; Ollama recommends version 0.17.6 or newer for newer cloud functionality.

Then try:

ollama run glm-5.2:cloud

If it starts prompting you, you're good.

You can also use them from Python

One useful thing about Ollama Cloud is that you don't need to rewrite your application around some completely different SDK.

For example:

from ollama import chat

response = chat(
    model="glm-5.2:cloud",
    messages=[
        {
            "role": "user",
            "content": "Explain mixture-of-experts models."
        }
    ],
)

print(response.message.content)

So an application that currently does:

model="qwen3:8b"

could instead use:

model="glm-5.2:cloud"

or:

model="deepseek-v4-pro:cloud"

The Ollama API architecture supports both local and cloud models.

REST API works too

Your program can still talk to your local Ollama endpoint:

http://localhost:11434

and Ollama handles the cloud model invocation.

For example:

curl.exe http://localhost:11434/api/chat `
  -H "Content-Type: application/json" `
  -d '{
    "model": "glm-5.2:cloud",
    "messages": [
      {
        "role": "user",
        "content": "Write a Python binary search implementation."
      }
    ]
  }'

Alternatively, Ollama exposes its cloud API directly at:

https://ollama.com/api

for authenticated cloud usage.

Promotion is refused while the source run is still active. So a decision the planner stages, or a learning one parallel coding agent stages mid-wave, is structurally invisible to maestro search/load for any other agent — including a sibling in the same still-running wave — until that run is sealed and someone explicitly runs maestro knowledge promote. There's no live, mid-run read-after-write path through this mechanism, by design (it's a deliberate review gate, not an oversight). Bottom line: the plumbing is sound and concurrency is safe, but Maestro's knowledge store cannot serve as the single live, mutually-visible context across parallel agents within one run — promotion is intentionally gated on the run being sealed. Building the shared-context goal on maestro knowledge stage/search as originally proposed won't work.
