Looking at your code, there are a few likely culprits for the slowness despite having a GPU.

The Main Issues
1. ChromaDB collection.add() is the real bottleneck

In vector_store.py, your add_document() method calls self.collection.add() inside the batch loop — one ChromaDB write per batch. ChromaDB's persistence layer (SQLite under the hood) is slow for frequent writes. The embedding step is fast on GPU, but the DB write dominates.

2. show_progress_bar=True adds overhead

In embedding_manager.py, the progress bar in generate_embedding() adds non-trivial I/O overhead when called repeatedly in a loop.

3. Batch size of 16 is too small for a modern GPU

The RTX 5050 has enough VRAM to handle much larger batches. With batch_size=16, you're underutilizing the GPU and paying the Python/CUDA kernel launch overhead on every tiny batch.

4. torch.cuda.empty_cache() called every batch

In vector_store.py line near the end of add_documents_in_batches, calling empty_cache() after every batch forces CUDA memory management overhead repeatedly. It's only needed if you're actually running out of VRAM.

Fixes
In ingest.py — increase batch size significantly:

python
BATCH_SIZE = 128  # was 16
In embedding_manager.py — disable the progress bar during batch ingestion:

python
def generate_embedding(self, text, batch_size: int = 32, show_progress: bool = False) -> np.ndarray:
    return self.model.encode(
        text,
        batch_size=batch_size,
        show_progress_bar=show_progress,  # only enable when needed
        convert_to_numpy=True,
        normalize_embeddings=True,
        device=self.device,
    )
In vector_store.py — embed everything first, then do a single bulk insert into ChromaDB:

python
def add_documents_in_batches(self, pdf_chunks, embedding_manager, batch_size=128):
    total = len(pdf_chunks)
    print(f"Embedding {total} chunks...")

    # Embed all at once — GPU handles this efficiently
    all_texts = [doc.page_content for doc in pdf_chunks]
    all_embeddings = embedding_manager.generate_embedding(all_texts, batch_size=batch_size)

    # Single bulk insert into ChromaDB
    print("Writing to vector store...")
    self.add_document(pdf_chunks, all_embeddings)
    print("Done.")
This eliminates the per-batch ChromaDB write overhead entirely and lets the GPU process all embeddings in one shot, which is dramatically faster.

Why This Helps
Problem	Before	After
GPU utilization	Many small batches of 16	One large pass, fully utilized
ChromaDB writes	N/batch_size writes	1 write
CUDA cache clears	N/batch_size times	0 times
The embedding step itself is likely already fast — the bottleneck is almost certainly the repeated small ChromaDB writes. The single bulk insert should give you the biggest speedup.

Yes, you can try 512, but whether it actually helps depends on a few things:

It will work if your documents' text chunks are short enough that 512 of them fit in VRAM simultaneously. With all-MiniLM-L6-v2 (a small model), this is very likely fine.

You'll hit diminishing returns around 256–512 for this particular model. The sentence-transformers library internally has a sweet spot, and beyond a certain point larger batches don't meaningfully increase GPU throughput.

You'll get a CUDA OOM error if you run out of VRAM. The RTX 5050 has 8GB, which is plenty for all-MiniLM-L6-v2 at 512 batch size — you'd be fine.

Practical recommendation: try this progression and watch your GPU utilization with nvidia-smi:

python
BATCH_SIZE = 256  # good starting point
# BATCH_SIZE = 512  # try this if 256 feels fast but you want more
The honest truth is that since you're now doing a single bulk insert (from the previous fix), the batch size only affects the embedding step, not the ChromaDB write. So going from 128 → 512 will give you a modest improvement at best — the bigger win was already eliminating the repeated DB writes. If your total corpus is under ~50k chunks, you likely won't notice much difference between 128 and 512.

Both files together make up your vector database — they're two halves of the same ChromaDB store:

chroma.sqlite3 — the metadata database. Stores document text, metadata (source, page, etc.), collection info, and IDs. This is what ChromaDB queries to filter and organize results.
a1c1f864-9b3d-45ac-bacc-208e39d0ce7b/ — the actual vector embeddings. This folder contains binary files (HNSW index) with the raw float vectors used for similarity search.
If you want to back up or move your vector store, you need both. Deleting either one breaks the store. The folder name is just ChromaDB's auto-generated UUID for your collection.

There's no single "best" value — it depends on your use case. But here's a practical framework for your specific case:

For 1386 chunks across 6 documents, that's ~231 chunks per document on average.

top_k	When to use
3–5	Narrow, factual questions with a single clear answer
5–10	General questions that may span multiple sections
10–20	Broad/summarization questions that need cross-document context
Your current default of top_k=3 is likely too low if your questions span multiple documents or sections. A good starting point for your corpus size is 5–8.

The more important lever is actually min_score. Rather than retrieving more chunks blindly, a well-tuned score threshold ensures the chunks you do retrieve are actually relevant. Your current default of 0.2 is very permissive — consider raising it to 0.35–0.5 depending on how specific your queries are.

Practical approach:

Set top_k=7 and min_score=0.35 as your new defaults
When you ask a question, look at the confidence scores being printed — if most retrieved docs are scoring below 0.4, your chunks aren't very relevant and you should look at your chunking strategy rather than increasing top_k further
Increasing top_k beyond ~15 on a 1386-chunk corpus will start injecting noise into the LLM context and actually hurt answer quality.

Looking at your output, the second query "use the csv dataset to give me some stats on Caucasian ASD patients" only retrieved chunks from the same PDF. This points to two separate problems.

Problem 1: CSV data isn't queryable via RAG
This is a fundamental limitation. Your CSV was ingested as raw text chunks — meaning a row like:

patient_id,ethnicity,age,diagnosis
1,Caucasian,12,ASD
2,Hispanic,9,ASD
gets chunked and embedded as prose. When you ask "give me stats on Caucasian patients", the embedding model can't do aggregation — it just finds the most semantically similar text chunks. Statistics (counts, averages, percentages) require computation, not text similarity. RAG is the wrong tool for this.

Problem 2: Your SEARCH_ROOTS in ingest.py likely caused duplicate ingestion
You have all four roots active now:

python
SEARCH_ROOTS = [
    Path("../data/pdfs"),
    Path("../data/textfiles"),
    Path("../data/csv"),
    Path("../data"),        # ← this catches EVERYTHING again
]
../data will re-discover files already found by the other three roots. The dict.fromkeys() deduplication only works if the paths are identical strings — if there's any path variation, you get duplicates in your vector store.

The Right Fix: Two-Track Architecture
For CSV data, bypass RAG entirely and use pandas directly in query.py:

python
# query.py — add at the top
import pandas as pd
import glob

def load_csv_data() -> pd.DataFrame | None:
    csv_files = glob.glob("../data/csv/*.csv")
    if not csv_files:
        return None
    return pd.concat([pd.read_csv(f) for f in csv_files], ignore_index=True)

def answer_csv_query(query: str, df: pd.DataFrame, llm: ChatGroq) -> str:
    # Send a sample of the CSV schema + data to the LLM to write pandas code
    sample = df.head(5).to_string()
    columns = list(df.columns)
    
    prompt = f"""You are a data analyst. Given this DataFrame with columns {columns}:

Sample data:
{sample}

Write Python pandas code to answer this question: {query}

Return ONLY the pandas code, no explanation."""
    
    code = llm.invoke(prompt).content.strip()
    # Strip markdown fences if present
    code = code.replace("```python", "").replace("```", "").strip()
    
    try:
        local_vars = {"df": df, "pd": pd}
        exec(code, local_vars)
        result = local_vars.get("result", "No result variable set.")
        return str(result)
    except Exception as e:
        return f"Error executing query: {e}\nGenerated code:\n{code}"
