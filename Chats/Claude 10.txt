Best-of-N and Monte Carlo Tree Search (MCTS)
These are reward-guided search methods — strategies where, instead of having the agent commit to a single action sequence, you sample multiple candidates and use a reward signal to pick the good ones.

Best-of-N (BoN) is the simpler of the two. The agent generates N candidate trajectories (or N candidate actions at a step), each one is scored by a reward model, and the highest-scoring one is selected. It's essentially "roll the dice N times, keep the best." In the paper's meta-evaluation (Section 5.1), they use BoN with n=8 to test whether ToolPRMBench scores correlate with real downstream gains — i.e., does a PRM that scores well on the benchmark actually help when used to pick among 8 sampled candidates?

Monte Carlo Tree Search (MCTS) is more sophisticated. Instead of independent samples, it builds a tree where each node is a state and each edge is a candidate action. The search expands promising branches by:

Selection — walk down the tree using reward estimates to pick promising paths
Expansion — add a new child node (a new candidate action)
Simulation/rollout — play out the trajectory to estimate value
Backpropagation — update reward estimates back up the tree
MCTS is more sample-efficient than BoN for long-horizon tasks because it concentrates compute on the branches that look promising rather than wasting samples on obviously-bad paths. This matters for tool-using agents, where trajectories can be 10+ steps and a bad early action poisons everything downstream.

The PRM is what makes both work — without step-level rewards, you'd only have a sparse signal at the very end of a trajectory, which gives you almost no information about where a long rollout went wrong.

The Four Types of Process Reward Models
The paper groups PRM approaches into four families, ordered roughly from "general-purpose" to "task-specialized":

1. LLM-as-a-judge — You take a strong general LLM (like GPT-5 or Claude) and prompt it to evaluate whether an agent's step is correct. No special training; you're just leveraging the model's reasoning ability through prompting. The advantage is zero training cost and broad applicability. The disadvantage is high inference cost per call and no guarantee the judge has been calibrated for your specific domain. In Table 2, the API-based LLMs (GPT-5, Claude-4.5-haiku, Gemini-2.5-flash) are essentially LLM-as-a-judge evaluators.

2. General PRMs — Reward models that have been trained (not just prompted) to score reasoning steps, but trained on broad domains like math problem-solving. Examples in the paper: Qwen2.5-Math-7B, Llemma-7b-prm, Math-shepherd. These were built for "is this math step correct?" and the question is whether that supervision transfers to "is this tool call correct?" The paper's results suggest it largely doesn't — these models cluster around 50% accuracy on ToolPRMBench, barely better than random.

3. Agent-specialized PRMs — Trained specifically for agent decision-making, but for a different agent domain than tool-using. WebShepherd-8B is the example here: it was built for web navigation agents (clicking buttons, filling forms, navigating pages). It's closer to tool-using than math is, but still shows weak transfer (49.2% average).

4. Tool-specialized PRMs — The paper's own contribution: ToolPRM-Base, ToolPRM-CoT, and ToolPRM-GRPO, all trained on tool-using preference pairs. These are the in-domain models, and unsurprisingly they perform best in their domain — ToolPRM-GRPO tops the leaderboard at 78.6% average, beating even GPT-5.

The progression illustrates a recurring lesson in reward modeling: specialization helps, but only when the training distribution actually matches the deployment distribution. A math PRM doesn't know what a malformed API call looks like, and a web agent PRM doesn't know about tool argument schemas. The paper's GRPO results also suggest how you train matters — RL produced a model that generalized to out-of-distribution tools (+21.8%) while the SFT-trained variants overfit and degraded on OOD (-13.6% to -20.4%).

def _safe_json_parse(raw: str) -> dict | None:
    if not raw:
        return None
    cleaned = _strip_code_fences(raw)

Claude responded: These are two defensive helpers that handle the gap between "what we asked the LLM for" and "what the LLM actually returns.
These are two defensive helpers that handle the gap between "what we asked the LLM for" and "what the LLM actually returns." Both validators ask for clean JSON, but LLMs frequently ignore that instruction in small ways that would crash a naive json.loads(). These two functions absorb the most common failure modes.

_strip_code_fences(s) handles the most frequent disobedience: the model wraps its JSON in markdown code fences even when told not to. Despite prompts saying "no markdown, no code fences," llama-3.1-8b-instant (and most models) will still occasionally return:

```json
{"verdict": "PASS", ...}
```
The first regex ^```(?:json)?\s* strips an opening ``` or ```json, and the second \s*```$ strips the closing ```. Now json.loads has a chance.

_safe_json_parse(raw) is the layered fallback for everything else that can go wrong. It tries three things in order:

Clean parse first — if the model behaved, this works immediately.
Regex fallback — re.search(r"\{.*\}", cleaned, re.DOTALL) grabs the first {...} block in the string and tries to parse just that. This catches cases where the model adds preamble or postamble despite instructions: "Sure, here's the JSON: {...}" or "{...}\n\nLet me know if you need anything else!". The re.DOTALL flag is what makes this work — without it, . doesn't match newlines and multi-line JSON objects would never match.
Return None — if both fail, the caller treats this as "UNKNOWN" verdict and the agent loop continues. No crash.
The reason both validators in validators.py route through _safe_json_parse rather than calling json.loads directly is exactly this: a JSON parse failure on a judge LLM should never bring down the main agent. The validator returns verdict="UNKNOWN", the calling code skips the optional feedback message, and the user still gets their answer. The judge's job is to help the loop, not to be a single point of failure for it.

One subtle thing about the regex \{.*\} — it's greedy by design. If the model returns nested objects, you want the outermost braces, not the first {...} you stumble across. Greedy matching gets you that. The downside: if the model returns two separate JSON objects in one response (rare), this would grab everything from the first { to the last } and fail to parse. That's an acceptable tradeoff — falling back to UNKNOWN is fine, and chasing every edge case here would be over-engineering.

Think about what the judge LLM is doing wrong. It reads the source chunks, reads the merged chunk, then answers the question "is anything missing?" — but it answers from memory of what it just read, not from directly checking the merged text again. The limitation is that it's not a hard enforcement — the model could still hallucinate a fake quote or skip the step. Good — I have a complete picture. Here's the full design and implementation plan.

The Core Idea
Neighbor-Aware Compression (NAC) works in two phases:

Phase 1 (ingest-time): Tag every chunk with chunk_seq (its sequential position within its source file) when storing to ChromaDB. This is a simple metadata addition.

Phase 2 (query-time): After retrieval+merging, scan accumulated_chunks for chunks that are consecutive neighbors from the same source (i.e. chunk_seq differs by 1). Merge those neighbor runs into a single contiguous block. This replaces N adjacent chunks with 1 richer chunk, compressing context without losing information — in fact gaining coherence, since you're restoring the original document flow.

Phase 1 — ingest.py: stamp chunk_seq on every chunk
The splitter processes one source file at a time implicitly, but split_documents gets a flat list. You need to track sequence per source. Change add_documents_in_batches and add_document to accept an explicit global_index per chunk (which becomes chunk_seq), or — simpler — stamp it during split_documents:

def split_documents(documents: list[Document]) -> list[Document]:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=CHUNK_SIZE,
        chunk_overlap=CHUNK_OVERLAP,
        length_function=len,
        separators=["\n\n", "\n", " ", ""],
    )
    chunks = splitter.split_documents(documents)
    print(f"Split {len(documents)} documents into {len(chunks)} chunks")

        chunk.metadata["chunk_seq"] = seq_counter[src]
        seq_counter[src] += 1

    return chunks

def _compress_neighbor_chunks(
    accumulated_chunks: list[dict],
    llm,
    embedding_manager,
    judge_llm,
) -> list[dict]:
    """
    Neighbor-Aware Compression: find runs of consecutive chunks from the
    same source (chunk_seq differs by 1) and merge each run into one block.

    Each chunk in accumulated_chunks must have:
        "content"   : str
        "source"    : str
        "embedding" : np.ndarray
        "chunk_seq" : int   ← stamped by ingest.py; may be absent for
                              learned_qa or merged chunks (those are skipped)
    """
    if not accumulated_chunks:
        return accumulated_chunks

    print(f"\n{_THIN}")
    print(f"  [NAC] Neighbor-Aware Compression — scanning {len(accumulated_chunks)} chunk(s)")
    print(_THIN)

    # ── 1. Separate chunks that carry chunk_seq from those that don't ─────────
    # Chunks without chunk_seq (learned_qa hits, already-merged chunks) are
    # passed through unchanged; only "raw" source chunks participate in NAC.
    eligible   = [(i, c) for i, c in enumerate(accumulated_chunks)
                  if isinstance(c.get("chunk_seq"), int)]
    ineligible = [(i, c) for i, c in enumerate(accumulated_chunks)
                  if not isinstance(c.get("chunk_seq"), int)]

    if not eligible:
        print(f"  [NAC] No chunks carry chunk_seq — skipping compression.")
        print(_THIN)
        return accumulated_chunks

    # ── 2. Sort eligible chunks by (source, chunk_seq) so neighbors are adjacent
    eligible.sort(key=lambda x: (x[1]["source"], x[1]["chunk_seq"]))

    # ── 3. Detect contiguous runs ─────────────────────────────────────────────
    runs: list[list[tuple[int, dict]]] = []   # each element = list of (orig_idx, chunk)
    current_run: list[tuple[int, dict]] = [eligible[0]]

    for orig_idx, chunk in eligible[1:]:
        prev_chunk = current_run[-1][1]
        same_source     = chunk["source"] == prev_chunk["source"]
        consecutive_seq = chunk["chunk_seq"] == prev_chunk["chunk_seq"] + 1

        if same_source and consecutive_seq:
            current_run.append((orig_idx, chunk))
        else:
            runs.append(current_run)
            current_run = [(orig_idx, chunk)]
    runs.append(current_run)

    neighbor_runs = [r for r in runs if len(r) > 1]
    solo_runs     = [r for r in runs if len(r) == 1]

    print(f"  [NAC] {len(neighbor_runs)} neighbor run(s) found | "
          f"{len(solo_runs)} singleton(s) pass through unchanged")
    for run in neighbor_runs:
        seqs = [c["chunk_seq"] for _, c in run]
        print(f"    run: source={run[0][1]['source']}  "
              f"seq={seqs[0]}→{seqs[-1]}  ({len(run)} chunks)")

    # ── 4. Merge each neighbor run ────────────────────────────────────────────
    result_chunks: list[dict] = []

    for run in runs:
        if len(run) == 1:
            result_chunks.append(run[0][1])
            continue

        source_chunks_for_merge = [c for _, c in run]
        feedback = ""
        merged = None

        for attempt in range(1, LLM_RESPONSE_RETRY_LIMIT + 1):
            print(f"\n  [NAC MERGE attempt {attempt}/{LLM_RESPONSE_RETRY_LIMIT}] "
                  f"{len(run)} chunks from '{run[0][1]['source']}'  "
                  f"seq {run[0][1]['chunk_seq']}→{run[-1][1]['chunk_seq']}")

            candidate = _merge_similar_chunks(
                source_chunks_for_merge,
                llm,
                embedding_manager,
                feedback=feedback,
            )

            check = validate_merge(
                source_chunks=source_chunks_for_merge,
                merged_chunk=candidate,
                judge_llm=judge_llm,
            )

            if check["verdict"] != "UNFAITHFUL":
                # Carry forward the chunk_seq range as metadata on the merged chunk
                candidate["chunk_seq_start"] = run[0][1]["chunk_seq"]
                candidate["chunk_seq_end"]   = run[-1][1]["chunk_seq"]
                # Remove chunk_seq so downstream NAC passes don't re-process it
                candidate.pop("chunk_seq", None)
                merged = candidate
                print(f"  [NAC MERGE] success on attempt {attempt} "
                      f"(verdict={check['verdict']})")
                break

            issues = []
            for claim in check.get("fabricated_claims", []):
                issues.append(f"- FABRICATED: \"{str(claim)[:200]}\"")
            for claim in check.get("dropped_claims", []):
                issues.append(f"- DROPPED: \"{str(claim)[:200]}\"")
            feedback = "\n".join(issues) or check.get("overall_reason", "Unfaithful merge.")
            print(f"  [NAC MERGE] attempt {attempt} rejected — retrying with feedback")

        if merged is None:
            # All attempts failed — keep originals rather than lose facts
            print(f"  [NAC MERGE] abandoned after {LLM_RESPONSE_RETRY_LIMIT} attempt(s) — "
                  f"keeping {len(run)} originals")
            result_chunks.extend(source_chunks_for_merge)
        else:
            result_chunks.append(merged)

    # ── 5. Append ineligible chunks unchanged ─────────────────────────────────
    result_chunks.extend(c for _, c in ineligible)

    saved = len(accumulated_chunks) - len(result_chunks)
    print(f"\n  [NAC] compression done: {len(accumulated_chunks)} → {len(result_chunks)} "
          f"chunk(s) ({saved} eliminated)")
    print(_THIN)

    return result_chunks

Two chunks can be semantically distinct overall (low cosine sim) but still share a redundant sub-passage — e.g., both chunks are 800 chars long, but 150 chars in the middle of each says essentially the same thing. Whole-chunk cosine similarity misses this entirely.

Here are concrete approaches, ordered by quality/complexity tradeoff:

Approach 1: Sentence-Level Cross-Chunk Overlap Detection
After NAC, split each accumulated chunk into sentences. For every sentence pair across different chunks, compute cosine similarity. If a sentence in chunk B is highly similar to one in chunk A, it's a candidate for removal from B.

How it would work:

Embed each sentence individually (or reuse your embedding manager)
Build a sentence-to-chunk index
For each chunk, flag sentences that have a near-duplicate in another chunk with sim ≥ threshold (e.g. 0.88)
Pass flagged chunks + their redundant sentences to an LLM with a targeted prompt: "Remove only these redundant sentences from chunk B, preserving everything else verbatim"
Validate with validate_merge before installing
Pros: Surgical. Only removes what's actually duplicated. Cons: O(n²) sentence pairs; can get expensive if you have many chunks. Mitigate by only comparing chunks from the same source file first, then cross-source.

Approach 2: TF-IDF / BM25 Fingerprinting on N-grams
Instead of semantic similarity, use lexical overlap — specifically, shingling (overlapping n-grams) with Jaccard similarity. This catches near-verbatim repeated passages that semantic embeddings might score low on (because the surrounding context dilutes the vector).

How it would work:

For each chunk, generate a set of character 5-grams or word 3-grams
Compute Jaccard similarity between all chunk pairs: |A ∩ B| / |A ∪ B|
If Jaccard ≥ threshold (e.g. 0.15–0.25 for partial overlap), flag the pair
Use an LLM to consolidate the overlapping region only
Pros: Zero additional model calls for detection. Very fast. Catches verbatim/near-verbatim repeats that embeddings miss. Cons: Misses paraphrased redundancy (same fact, different words). Good complement to cosine, not a full replacement.

Approach 3: LLM-Based Redundancy Scan (Targeted Prompt)
Skip detection heuristics entirely. After NAC, pass all accumulated chunks to an LLM with a structured prompt:

Given these N chunks, identify any facts, sentences, or passages 
that appear in more than one chunk. Return a JSON list of 
{"chunk_index": i, "redundant_sentence": "..."} for each redundant 
sub-passage. Do not flag facts that appear only once.
Then surgically remove flagged sentences from the lower-scored chunk (keep the one from the higher-similarity retrieval).

Pros: Catches paraphrased redundancy. No embedding overhead. Cons: Expensive in tokens for large accumulated_chunks sets. Works best as a single pass over the final accumulated set (post-NAC), not per-retrieval.

Approach 4: Sliding Window Embedding Comparison (Best Balance)
This is likely the sweet spot for your use case. Instead of embedding whole chunks, embed sliding windows of ~3–5 sentences from each chunk, then compare windows across chunks.

How it would work:

Chunk A → windows [A1, A2, A3, ...]
Chunk B → windows [B1, B2, B3, ...]
Compare Ai vs Bj for all i,j; if cos(Ai, Bj) ≥ 0.88 → sub-passage redundancy found
Pass only the flagged windows + their parent chunks to an LLM for surgical removal
Pros: Catches semantic paraphrases at the sub-chunk level. More precise than full-chunk cosine. Controllable cost (window count scales with chunk size, not corpus size). Cons: More implementation complexity than approaches 1–2.

Stage 1 (cheap, fast): Jaccard n-gram overlap to detect lexically similar sub-passages — catches verbatim repeats with zero LLM calls

Claude responded: Jaccard similarity is a measure of overlap between two sets.
Jaccard similarity is a measure of overlap between two sets.

The formula is simple:

J(A, B) = |A ∩ B| / |A ∪ B|

That is: the number of elements the two sets share, divided by the number of elements in either set. The result is always between 0 (no overlap) and 1 (identical sets).

In the context of text / your pipeline, you'd convert each chunk into a set of n-grams first, then compare those sets.

For example, using word bigrams on two sentences:

Chunk A: "early diagnosis improves outcomes" → {early_diagnosis, diagnosis_improves, improves_outcomes}
Chunk B: "early diagnosis leads to better results" → {early_diagnosis, diagnosis_leads, leads_to, to_better, better_results}
Intersection: {early_diagnosis} → size 1
Union: 7 unique bigrams → size 7
J = 1/7 ≈ 0.14
That's a low score, even though both sentences convey the same fact — which is exactly why Jaccard alone isn't sufficient for semantic paraphrase detection, and why I suggested pairing it with sentence-level cosine as a second stage.

Why it's useful as a Stage 1 filter:

It's purely lexical — no model calls, no embeddings, runs in microseconds
It's excellent at catching near-verbatim repeats (copy-pasted passages, slightly edited sentences)
A low threshold like 0.15–0.20 on character 5-grams (rather than words) is quite sensitive to shared phrases, even across differently structured sentences
Character n-grams are more robust than word n-grams because they're immune to minor spelling variations and tokenization differences
The key tradeoff versus cosine similarity on embeddings: Jaccard sees shared surface form, cosine sees shared meaning. They're complementary — Jaccard catches what cosine misses (verbatim overlap buried in long chunks), and cosine catches what Jaccard misses (paraphrase with different vocabulary).

What's Lost in the Bigram Sets

Even embeddings aren't fully reliable here. Natural Language Inference (NLI) — models explicitly trained to classify whether sentence B entails, contradicts, or is neutral to sentence A
Models like cross-encoder/nli-deberta-v3-base would correctly label A→B as CONTRADICTION, immediately disqualifying them from merging
This is fundamentally different from similarity — it reasons about logical relationship, not vector distance
In your pipeline, an NLI check before any merge decision would catch exactly this case — and it's a much cheaper call than a full LLM merge + validate cycle.
