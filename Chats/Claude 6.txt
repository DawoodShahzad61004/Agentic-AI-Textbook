It's a **benchmark test** used to measure how much general knowledge an LLM has across 57 different academic subjects, including:

## Tool-Use Capabilities

"Good tool use" in an LLM means the model reliably knows:

1. **When to call a tool** — vs just answering from memory
2. **Which tool to call** — e.g. `retrieve_documents` vs `check_answer_quality`
3. **What arguments to pass** — correctly structured JSON (e.g. `{"query": "..."}`)
4. **How to read the tool result** — and use it to continue reasoning

Poor tool use looks like:
- Calling `retrieve_documents` 5 times with the same query
- Passing garbage arguments that cause a `400 tool_use_failed` error (your code already handles this edge case!)
- Ignoring the tool result and making up an answer anyway
- Calling tools in the wrong order

## How `RecursiveCharacterTextSplitter` Works

It tries to split text using a **priority list of separators**, going from largest/most meaningful to smallest:

```
"\n\n"  →  "\n"  →  " "  →  ""
```

---

### The Algorithm (Step by Step)

**1. Try the first separator: `"\n\n"` (paragraph breaks)**

It splits the whole document on double newlines first.

```
"Intro paragraph.\n\nSecond paragraph.\n\nThird paragraph."
        ↓
["Intro paragraph.", "Second paragraph.", "Third paragraph."]
```

**2. Check each piece against `CHUNK_SIZE` (1000 chars)**

- If a piece is **≤ 1000 chars** → keep it, done ✅
- If a piece is **> 1000 chars** → recurse with the next separator (`"\n"`)

**3. Recurse down the separator list as needed**

```
"\n\n" didn't split it small enough?
  → try "\n"   (single newlines / line breaks)
    → try " "  (individual words)
      → try ""  (individual characters — last resort)
```

**4. Apply `CHUNK_OVERLAP` (200 chars)**

After splitting, adjacent chunks share 200 characters of overlap at their boundary:

```
[...........chunk 1............][overlap][...........chunk 2............]
                                 ←200→
```

This prevents a concept that straddles a boundary from being lost entirely.

---

### Concrete Example with Your Settings

Say you have a 2500-char paragraph with no `\n\n` breaks:

```
Step 1: Try "\n\n"  → whole thing is one piece, still 2500 chars  ❌
Step 2: Try "\n"    → splits into lines, each ~100 chars           ✅
Step 3: Merge lines back up until just under 1000 chars            ✅
Step 4: Apply 200-char overlap between resulting chunks            ✅
```

Result: ~3 chunks of ≤1000 chars, each sharing 200 chars with its neighbor.

---

### Why This Order of Separators Matters

| Separator | Splits on | Preserves |
|---|---|---|
| `"\n\n"` | Paragraphs | Most semantic meaning |
| `"\n"` | Lines | Sentence/list structure |
| `" "` | Words | Word boundaries |
| `""` | Characters | Nothing (last resort) |

The **recursive** part is key — it always tries to keep chunks as semantically whole as possible, only breaking at word/character level if absolutely forced to. This is much better for RAG than a naive "cut every 1000 chars" approach, because your retrieved chunks are more likely to contain complete thoughts.

## 4. Algorithms to Prioritize Retrieved Chunks

Your current system uses **cosine similarity** ranking (via ChromaDB distances). There are several better alternatives:

### A. BM25 (Sparse Retrieval)
- Keyword-frequency based, like traditional search engines
- Great at exact term matching that embeddings sometimes miss
- **Hybrid approach**: combine BM25 score + cosine similarity score

### B. MMR — Maximal Marginal Relevance
- Balances **relevance** vs **diversity**
- Avoids returning 5 chunks that all say the same thing
- Formula: pick next chunk that is relevant to query but dissimilar to already-selected chunks
- **Best fit for your pipeline** — easy to add to `retriever.py`

### C. Cross-Encoder Reranking
- A second, smaller model re-reads (query + each chunk) together and scores relevance
- Much more accurate than embedding similarity alone
- Popular models: `cross-encoder/ms-marco-MiniLM-L-6-v2`
- **Tradeoff**: slower, adds latency

### D. Reciprocal Rank Fusion (RRF)
- Combines rankings from multiple retrieval methods (e.g. BM25 + cosine)
- Simple formula, very effective
- Already partially relevant — your `retriever.py` merges `documents` + `learned_qa` collections, RRF would make that merger smarter

### E. Contextual Compression
- After retrieval, pass chunks through an LLM to extract only the sentences relevant to the query
- Reduces noise before the main LLM sees the context
- LangChain has a built-in `ContextualCompressionRetriever` for this

**Recommended upgrade path for your project:**
```
Current:  cosine similarity only
Step 1:   Add MMR (diversity)
Step 2:   Add BM25 hybrid scoring  
Step 3:   Add cross-encoder reranking on top-10, pass top-5 to LLM
```

## Why Small Models Struggle to Enforce Rules Over Long Conversations

### 1. Parameter Count = "Working Memory Capacity"

A model's parameters are essentially its ability to **hold and juggle multiple things simultaneously** during generation. 

```
8B  parameters  → limited juggling capacity
70B parameters  → much larger juggling capacity
```

When the conversation is short (iteration 1), the model easily holds:
- "I must follow these 6 rules"
- "I've done 2 retrievals so far"
- "The user asked about X"

As iterations grow, it now needs to track:
- All previous tool calls and their results
- Which queries it already tried
- How many retrievals remain
- The accumulating context of retrieved chunks
- The original rules

The 8B model starts **dropping the rules** to make room for tracking the growing conversation — like a person trying to remember too many things at once and forgetting the original instructions.

---

### 2. Attention Dilution

Every token in the context competes for the model's attention. As the conversation grows across iterations:

```
Iteration 1 context:  500 tokens   → rules get ~high attention share
Iteration 4 context:  3,000 tokens → rules get ~6x less attention share
```

The system prompt tokens are the same — but they now represent a **smaller fraction** of the total context. The model's attention naturally shifts toward the most recent content (latest tool results, latest assistant message) because that's what's most immediately relevant to "what do I say next."

---

### 3. Instruction Following is a Learned Behavior, Not Hard-Coded

The model doesn't have an actual rule engine — it doesn't literally "check" constraints before acting. It learned to follow instructions by seeing millions of examples of instruction-following during training.

But that training had a distribution — most examples were **short, simple instruction following**. Long multi-turn agentic loops with strict tool-use rules were far rarer in training data. So the model is essentially **extrapolating** into territory it's less trained on, and it drifts.

A 70B model saw more of this in training and has more capacity to generalize — so it holds up better.

---

### 4. No Explicit State Tracking

Your rules say things like:
> *"Never call retrieve_documents more than 5 times total"*

A human would keep a mental counter. The model has **no actual counter** — it has to infer how many times it's called the tool by re-reading the conversation history and counting. As the history grows noisier across iterations, this counting becomes unreliable.

This is why your code enforces it **externally**:

```python
if total_retrievals >= MAX_TOTAL_RETRIEVALS:
    result = "Retrieval limit reached. Use what you have to answer."
```

You're essentially compensating for the model's inability to reliably self-enforce this rule — which is exactly the right design decision.

No matter what the prompt says, a small 8B model will sometimes generate duplicate queries simultaneously. Catch it in code — add this in `run_agent()` right after line `tool_calls = resp_tool_calls[:MAX_TOOL_CALLS_PER_ITERATION]`:

```python
# Deduplicate retrieve_documents calls within a single iteration
seen_queries = set()
deduped = []
for tc in tool_calls:
    if tc["name"] == "retrieve_documents":
        q = tc["args"].get("query", "").strip().lower()
        if q in seen_queries:
            print(f"  [DEDUP] Blocked duplicate query: \"{tc['args'].get('query')}\"")
            continue
        seen_queries.add(q)
    deduped.append(tc)
tool_calls = deduped
```
