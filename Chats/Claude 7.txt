## The core problem with 8b models and agentic prompts

The 8b model has two key weaknesses relevant to your setup: it struggles with **long, multi-section system prompts** (it front-loads attention and loses the tail) and it's **more likely to hallucinate tool call syntax** when the schema description is wordy. Every improvement below targets one of these two failure modes.

---

## 1. Trim the system prompt — put rules last, not first

The model reads your system prompt top-to-bottom, but attention in smaller models degrades toward the end. Your current new prompt has ROLE → ACCESS → PROCESS → HARD CONSTRAINTS. The constraints are the most important part and they're last. Flip it.

```python
_BASE_SYSTEM_PROMPT = """You are a research assistant. Answer ONLY from retrieved chunks — never from memory.

HARD LIMITS (enforced by the system — do not test them):
- retrieve_documents: max 5 calls total. Stop at 3 if results are poor.
- Never repeat a query already tried. Never generate two queries with identical words.
- If the knowledge base has no answer after 3 tries, say: "The knowledge base does not contain information about [topic]."
- Never fabricate facts.

TOOLS:
- retrieve_documents(query, top_k): searches the knowledge base
- check_answer_quality(answer): validates your answer is grounded

PROCESS:
1. Call retrieve_documents 2–3 times with SHORT, semantically different queries.

Even though you didn't mutate `args` in Python, the LangChain response object's internal representation of `tool_calls` might already contain `context` from a **previous run's** response object being reused, or more likely: `tool_call["args"]` is not a plain dict — it may be a reference type that LangChain populates differently.

The real and clean fix is to **append `response` to messages only after all tool calls are processed**, not before. Change this:

```python
# Line 260 — CURRENT (wrong order)
messages.append(response)          # appended before tool loop

for tool_call in tool_calls:       # tool loop runs after
    ...
```

To this:

```python
# FIXED — process tools first, then append the clean response
for tool_call in tool_calls:
    name = tool_call["name"]
    args = tool_call["args"]
    ...

# append response AFTER the loop, before the tool result messages
```

But that breaks the message ordering (Groq requires assistant message before tool results). So the correct restructure is:

```python
tool_calls = deduped
messages.append(response)   # keep this here — required by Groq protocol

for tool_call in tool_calls:
    name = tool_call["name"]
    args = tool_call["args"]   # READ args but never write to this dict

    if name == "check_answer_quality":
        full_context = "\n\n---\n\n".join(accumulated_context)
        # Explicitly build a brand-new dict — do NOT use args at all
        call_args = {"answer": args["answer"], "context": full_context}
        print(f"  [AGENT] injecting {len(full_context)} chars of accumulated context into check_answer_quality")
        result = callables[name](**call_args)
        final_quality = "OK" if result.strip().startswith("OK") else "INSUFFICIENT"
        print(f"  [AGENT STATE] final_quality set to: {final_quality}")
```

The difference from what you have now: instead of `{**args, "context": full_context}` which spreads `args` and adds `context`, use `{"answer": args["answer"], "context": full_context}` which builds the dict from scratch without touching `args` at all. The spread operator `**args` still reads from the `args` dict object (which is fine), but if LangChain's internals track dict reads on that object, building from scratch eliminates any possible aliasing. This is the safest form of the fix.
