Short answer: there's no explicit cosine-similarity computation anywhere in your code. The similarity ranking happens implicitly inside ChromaDB, and you convert its distance to a similarity score in one place.

Here's the actual flow:

1. Embeddings are L2-normalized at creation time (embedding_manager.py):

python
return self.model.encode(
    text,
    ...
    normalize_embeddings=True,   # <-- unit vectors
    ...
)
Once vectors are unit-length, Euclidean distance and cosine distance are monotonically related, so ranking by either is equivalent.

2. Chroma does the actual similarity search (retriever.py, _query_collection):

python
results = collection.query(
    query_embeddings=[query_embedding.tolist()],
    n_results=min(top_k, collection.count()),
    include=["documents", "metadatas", "distances"],
)
Chroma uses HNSW under the hood with whatever distance metric the collection was configured with. You never specified one when creating the collections in vector_store.py and self_learner.py (no hnsw:space in metadata), so Chroma defaults to L2 (squared Euclidean) — not cosine. Because your embeddings are normalized, this still produces the correct cosine ranking, but the raw distance value Chroma returns is squared L2, not 1 − cos(θ).

3. The only place you touch the score is right after that query, same file:

python
docs.append({
    ...
    "similarity_score": 1 - dist,
    "distance": dist,
})
This 1 - dist is the score that then drives:

the score_threshold filter inside retrieve() (default 0.2, raised to the same value in tools.retrieve_documents)
the sort order of merged results from documents + learned_qa
the confidence field in query.py's advanced_answer
the score printed in source listings
The subtle bug worth flagging: 1 - dist is only a valid cosine similarity if dist is cosine distance. With Chroma's default L2 space and normalized vectors, dist is actually ‖a − b‖² = 2 − 2·cos(θ), so 1 - dist = 2·cos(θ) − 1. Ranking is unaffected (it's monotonic), but absolute numbers are off — a "score" of 0.2 corresponds to cosine similarity 0.6, not 0.2. If you want the threshold and confidence numbers to mean what they look like, either:

create the collections with metadata={"hnsw:space": "cosine"}, in which case dist = 1 − cos(θ) and 1 - dist becomes true cosine similarity, or
compute similarity_score = 1 - dist/2 to convert squared-L2-on-unit-vectors into cosine similarity.
So to directly answer your question: the cosine-similarity check lives in retriever.py::_query_collection, in the 1 - dist line and the downstream score_threshold filter — but it's currently a proxy score, not literal cosine, because the collections aren't configured for cosine space.

Claude responded: Yes — once cosine space is actually active on the collection, that interpretation is exactly right for your similarity_score.
Yes — once cosine space is actually active on the collection, that interpretation is exactly right for your similarity_score.

The chain:

Cosine similarity itself is defined as cos(θ) = (a · b) / (‖a‖·‖b‖), and it ranges over [-1, 1] with the meaning you described: 1 = same direction, 0 = orthogonal/unrelated, -1 = opposite.
Chroma's cosine distance is dist = 1 - cos(θ), which ranges over [0, 2].
Your code computes similarity_score = 1 - dist, which algebraically just gives you back cos(θ).
So under cosine space, similarity_score carries exactly the [-1, 1] semantics you wrote.

One practical wrinkle worth knowing: with all-MiniLM-L6-v2 (and most modern sentence-transformer models), you essentially never see negative cosine similarities between real text chunks and a real query. The embedding space isn't centered around zero — the model packs nearly all natural-language content into a fairly narrow cone, so empirical similarities for unrelated text usually land in the 0.0–0.2 range, not near -1. Truly opposite vectors (-1) basically don't occur with this family of models.

So in theory your scale is [-1, 1] with the textbook meaning. In practice, for this model, you'll see something more like:

~0.7–1.0 → strong topical match
~0.4–0.7 → related, same domain
~0.2–0.4 → loosely related / shared vocabulary only
~0.0–0.2 → effectively unrelated
below 0 → rare; usually a sign of weird input (very short text, code vs prose mismatch, etc.)
This is also why your current score_threshold = 0.2 is quite permissive — it's letting through results that are barely above the "unrelated" floor for this model.

Claude responded: Good instinct — chunk-level deduplication is a real problem in your current setup, especially because you're merging results from documents and learned_qa, and…
Good instinct — chunk-level deduplication is a real problem in your current setup, especially because you're merging results from documents and learned_qa, and the agent issues multiple reformulated queries that often retrieve overlapping chunks.

Before picking a threshold, the right answer depends on what kind of duplication you're trying to catch, because there are three different things people mean by "similar chunks":

1. Exact / near-exact duplicates (same chunk retrieved twice via different queries, or chunk-overlap artifacts from your CHUNK_OVERLAP=200 splitter)

Threshold: 0.95+
This is almost always safe to merge — same text, possibly different IDs because of the overlap window or because a learned_qa distillation echoed the source.
2. Paraphrases / restatements of the same fact (a learned QA pair vs. its source chunk; two PDF passages saying the same thing in different words)

Threshold: 0.80–0.90
This is where it gets judgment-y. Merging here reduces redundancy in the LLM's context but risks dropping a chunk that has slightly different supporting detail.
3. Same topic, different facts (two chunks both about "ASD symptoms" but one lists behavioral signs and one lists diagnostic criteria)

Threshold: below ~0.75
You almost never want to merge these — they're the diversity you're trying to preserve.
For all-MiniLM-L6-v2 specifically, my recommendation:

Use ~0.88 as the merge threshold. Reasoning:

This model produces relatively high baseline similarities for any same-domain text (two random medical paragraphs might land at 0.5–0.7), so a threshold below ~0.80 will start collapsing genuinely distinct chunks.
Empirically, with MiniLM, chunks that are true paraphrases or near-duplicates cluster around 0.90+, while chunks that are merely "about the same topic" sit in the 0.7–0.85 range.
0.88 keeps you above the topical-overlap zone but catches paraphrases and the chunk-overlap artifacts your splitter creates.
A couple of implementation notes that matter more than the exact threshold:

Compare embeddings, not strings. Don't recompute — the chunks you've already retrieved have embeddings sitting in Chroma. But Chroma's query() doesn't return them by default. You have two options: (a) include "embeddings" in the include=[...] list in _query_collection, or (b) re-embed each chunk's text with embedding_manager.generate_embedding(). Option (a) is essentially free; option (b) costs a forward pass per chunk.

Use chunk ID first, embedding similarity second. You're already deduplicating on doc["id"] in retriever.py. That handles the case where the same chunk is retrieved by two different queries — no embedding comparison needed. The embedding-similarity check only needs to run for chunks with different IDs but near-identical content (which mostly happens at the documents ↔ learned_qa boundary, and at chunk-overlap boundaries within a single source file).

"Merging" is ambiguous — pick one. When two chunks are above threshold, you can either (a) keep the higher-scoring one and drop the other, or (b) concatenate them. (a) is almost always what you want; (b) just gives the LLM longer redundant context and inflates token counts. Your stated goal ("increase disparity") points squarely at (a).

Make it tunable. Hardcode it once and you'll regret it the first time you swap models. Put it next to MIN_SIMILARITY as MERGE_SIMILARITY = 0.88 and log when chunks get dropped — that telemetry will tell you within a session whether 0.88 is too tight or too loose for your actual corpus, and you can adjust from there.

If you want a starting heuristic to validate the threshold empirically: run 5–10 queries through your pipeline with full logging, eyeball the pairs that get flagged as duplicates at 0.88, and check whether you'd actually have wanted both kept. Adjust up if you're losing useful detail, down if obvious duplicates are slipping through.

def cosine_similarity(self, vec_a: np.ndarray, vec_b: np.ndarray) -> float:
        """Compute cosine similarity between two vectors."""
        if vec_a.shape != vec_b.shape:
            raise ValueError("Vectors must have the same shape.")
        if np.linalg.norm(vec_a) == 0 or np.linalg.norm(vec_b) == 0:

        return float(np.dot(vec_a, vec_b) / (np.linalg.norm(vec_a) * np.linalg.norm(vec_b)))

def _merge_similar_chunks(similar_chunks: list[dict], llm) -> dict:
    """Merge near-duplicate chunks into one consolidated chunk via LLM."""
    formatted_input = "\n\n".join(
        f"[Source: {c['source']}]\n{c['content']}" for c in similar_chunks
    )
    prompt = f"{_CHUNK_MERGE_PROMPT}\n\nINPUT CHUNKS:\n{formatted_input}"

    print(f"\n{_THIN}")
    print(f"  [CHUNK MERGE] consolidating {len(similar_chunks)} chunks")
    print(_THIN)

    try:
        response = llm.invoke([{"role": "system", "content": prompt}])
        raw = response.content.strip()
        cleaned = raw.replace("```json", "").replace("```", "").strip()
        parsed = json.loads(cleaned)
        return {
            "content": parsed["content"],
            "source": ", ".join(parsed.get("sources", [])),
            "embedding": None,  # caller must re-embed if needed for future merges
        }
    except (json.JSONDecodeError, KeyError, AttributeError) as e:
        print(f"  [CHUNK MERGE] failed ({e}), keeping first chunk")
        return similar_chunks[0]

        """Compute cosine similarity between two vectors."""

What the error actually was
The error message in your logs:

JSONDecodeError: Expecting value: line 1 column 1 (char 0)
This is Python's json library complaining that it tried to parse a JSON string but found nothing at the very first character (line 1, column 1, character 0). That specific error message — "Expecting value" at "char 0" — almost always means the input was an empty string "" or pure whitespace.

It does not mean the JSON was malformed. Malformed JSON gives different errors, like:

"Unterminated string" → quote was never closed
"Expecting ',' delimiter" → missing comma between items
"Expecting property name enclosed in double quotes" → bad key
"Expecting value at char 0" specifically means: I started reading and there was nothing to read.

Why the LLM returned empty content
Here's where understanding tool-use semantics matters. Modern LLM APIs let a model respond in two ways to a single prompt:

With text content — response.content = "some text", response.tool_calls = []
With tool calls — response.content = "", response.tool_calls = [{"name": "...", "args": {...}}]
When a model decides to invoke a tool, it puts nothing in content — the tool call is its response. This is by design.

llm = ChatGroq(...)
tool_schemas, callables = make_tools(retriever)
…and then later, the agent loop calls llm.invoke(messages, tools=tool_schemas). That tools=tool_schemas argument tells Groq's API: "this model has access to retrieve_documents and check_answer_quality — feel free to call them."

But here's the thing. When you call _merge_similar_chunks and it does:

python
llm.invoke([{"role": "system", "content": prompt}])
…you're using the same llm object. You didn't pass tools=[] to disable them. And LangChain's behavior in this case isn't perfectly clean — depending on internal state, the tool schemas may still be bound to the request.

Even if they're not bound on this specific call, there's a second issue: llama-3.1-8b-instant is a small, instruction-tuned, tool-trained model. It has been heavily trained to issue tool calls when it sees patterns it associates with tool use (system prompts that look like task specs, structured output requests, etc.). Sometimes it produces an empty response with no tool call simply because it got confused about whether to call a tool or generate text — and ended up doing neither cleanly.

The first call worked by luck. Subsequent calls — perhaps because the conversation context the underlying client tracks built up, or just because of small probabilistic differences in sampling — flipped to the "empty content" failure mode.

This is a really common pitfall when reusing one LLM object across different purposes in an agentic system. The model is configured for one job (tool use) and you're asking it to do another (structured text generation), without reconfiguring it.

How to fix it
The two solutions I gave you address this from two different angles:

Option A (separate LLM instance): Create a brand-new ChatGroq object that never had tool schemas attached. This isolates the merge job from the agent's tool-use configuration. Same model, different client, clean state.

Option B (bypass LangChain, use Groq client directly with JSON mode): Skip the LangChain abstraction entirely for this specific call and use Groq's native API. Critically, this lets you pass response_format={"type": "json_object"}, which is a server-side guarantee — Groq's API will refuse to return anything that isn't valid JSON. The model literally cannot produce empty content under this mode; it's constrained at the inference level.

Option B is stronger because it addresses both possible failure modes:

If the model wanted to call a tool → no tools are bound, can't happen.
If the model wanted to return prose → response_format forces JSON instead.
If the model wanted to return empty → response_format requires structured output, so empty isn't allowed.
You also get temperature=0.0 for free, which is correct for a deterministic merge task — you don't want the merger getting "creative" with the chunk content.

The general lesson
When debugging "the LLM returned weird output" issues, the diagnostic ladder is:

Did the response object actually contain what I expected? Print response.content, response.tool_calls, response.response_metadata. Don't assume — verify.
Is this happening every time or some of the time? Asymmetric failures point to state, not logic.
What is the LLM's available action space at this moment? If tools are bound, it might call them. If response_format is set, it might be constrained. If the system prompt mentions tools, it might issue them even when none are bound.
Am I reusing an object configured for another purpose? This is the most common mistake. LLM clients are usually purpose-built — query reformulation, classification, structured extraction, free-form generation are all different jobs and benefit from different configurations.
The error you saw was JSONDecodeError, but the bug was tool-binding leakage between two different uses of the same LLM client. The decoder error was just the downstream symptom — the real diagnosis happened by noticing that one print line was missing from your logs.

Good question — and the right answer depends on what kind of failure you're trying to catch. Let me break this down because "is the answer relevant to the query?" is actually three distinct checks, and each one wants a different tool.

What can go wrong between query and answer
Topic drift — user asked about ASD symptoms, answer is about ASD diagnosis criteria. Both are on-topic-ish, but the answer doesn't address the question.
Question-type mismatch — user asked "how" or "why," answer gives a "what." Definitional answer to a causal question.
Hallucination / ungroundedness — answer is fluent and topical but invents facts not in the chunks. (You already partially handle this in check_answer_quality.)
Relevance-to-query is mostly #1 and #2. Groundedness is #3 — separate concern, don't conflate them.

Why pure similarity search is the wrong tool here
Cosine similarity between the query embedding and the answer embedding will tell you they're in the same topic neighborhood. That's necessary but nowhere near sufficient. Two failure modes it misses badly:

High similarity, wrong answer. Query: "What are the side effects of drug X?" Answer: "Drug X is a beta-blocker used for hypertension, developed in 1985…" Embedding similarity will be very high (same entity, same domain), but the answer doesn't address side effects at all.
Low similarity, correct answer. Query: "Is it safe during pregnancy?" Answer: "Category C — animal studies showed teratogenic effects; avoid in first trimester." Lexically and semantically distant from "safe" and "pregnancy," but a perfect answer.
Sentence-transformer embeddings (you're using all-MiniLM-L6-v2) are trained for paraphrase/topical similarity, not for question-answer entailment. They'll give you a topical sanity check at best. Useful as a cheap pre-filter, useless as a verdict.

Keyword overlap is even worse — it's what check_answer_quality already does for groundedness, and you can see how brittle it is (the stop-word list, the magic threshold of 15). Don't repeat that pattern for relevance.

What an LLM judge actually buys you
An LLM call with a focused rubric can evaluate:

Does the answer address the specific thing asked (symptoms vs. causes vs. treatment)?
Does it match the question type (yes/no, list, explanation, comparison)?
Does it dodge or refuse implicitly?
This is exactly the kind of judgment LLMs-as-judges do well, and there's solid empirical literature showing they correlate well with human relevance ratings when the rubric is tight. The cost is one extra call per query — given your pipeline already does 3–6 LLM iterations per question, one more is marginal.

My recommendation: a two-stage gate
Use similarity as a cheap signal, LLM as the verdict. This is roughly how production RAG eval stacks (Ragas, TruLens, etc.) handle it.

Stage 1 — embedding similarity as a smoke test. Embed the query, embed the answer, take cosine. If it's catastrophically low (say, below 0.25–0.3 with your normalized MiniLM vectors), the answer is almost certainly off-topic — flag immediately, skip stage 2. This catches the egregious drift cases for free since you already have EmbeddingManager loaded.

Stage 2 — LLM judge for the actual relevance call. For everything that passes stage 1, run a small focused prompt. Something like:

Question: {query}
Answer: {answer}

Does the answer directly address what the question asks?
Reply with one of:
- RELEVANT: answer addresses the specific thing asked
- PARTIAL: answer is on-topic but doesn't address the specific ask
- IRRELEVANT: answer is off-topic or evasive
Then one sentence of justification.
Force a structured output (label + reason). Log the reason — it's gold for debugging and for your user_thumbdowns.json learning loop.

A few implementation notes specific to your codebase
You already have check_answer_quality doing groundedness checks. Keep that — it answers a different question ("is the answer supported by the chunks?"). Add check_answer_relevance(query, answer) as a separate tool, and have the agent call both before finalizing. They're orthogonal: an answer can be grounded but irrelevant (correct facts about the wrong thing), or relevant but ungrounded (right topic, hallucinated specifics).

Don't make the agent self-judge in the same call that produces the answer — there's well-documented bias where models rate their own output more favorably. Use a fresh LLM call with only the query and answer in context, no chunks, no history. That isolates the relevance question from the generation context.

For the threshold tuning, don't pick numbers from intuition. Pull 30–50 samples from your existing interactions.jsonl (you have the OK and USER_THUMBSDOWN labels already), compute cosine similarity for each, and look at the distribution. You'll see where the natural cutoff sits for your domain.

One last thing: if relevance fails, what should the agent do? You probably want it to retry with a reformulated query rather than just refusing — otherwise you're throwing away work. But cap the retries (you already have MAX_ITERATIONS = 6), and if the second attempt also fails relevance, return the standard "knowledge base does not contain information about [topic]" rather than a wrong answer dressed up as a right one.

So: LLM for the verdict, similarity as a cheap pre-filter, and keep relevance separate from groundedness.
