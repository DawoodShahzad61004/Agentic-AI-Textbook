## 1. Docling, Unstructured, and Marker conversion approaches

| Field | Detail |
|---|---|

## 3. Open-source loaders and routed production ingestion

| Field | Detail |
|---|---|
| **Topic** | Survey open-source loaders for mixed and complex files and identify a production-grade ingestion strategy beyond the current comparison scripts. |
| **Date** | 2026-07-14 |
| **Findings** | Docling is a strong primary multi-format parser because it preserves layout, hierarchy, reading order, tables, formulas, code blocks, images, captions, and metadata in a unified document model. Unstructured offers mature automatic type detection, typed elements, metadata, chunking, and configurable PDF strategies, but has a heavy dependency stack and materially different `fast`, `hi_res`, and OCR behavior. Apache Tika offers exceptionally broad format and metadata coverage but tends to flatten complex layouts, making it better as a fallback. Marker and MinerU specialize in high-fidelity, layout-heavy PDFs and can be computationally expensive. PyMuPDF4LLM is a faster path for ordinary digital PDFs. PaddleOCR or OCRmyPDF addresses scanned input. LlamaIndex Readers and LangChain Document Loaders are orchestration adapters whose parsing quality depends on their underlying engine; they do not independently guarantee table or layout fidelity. Haystack Converters provide another framework-integrated option. |
| **Conclusion** | No production router was implemented or formally adopted. The research recommendation is to avoid a single universal parser: inspect each file, route ordinary PDFs to a fast parser, use Docling for structured multi-format content, apply OCR to scans, retain Tika as a broad fallback, normalize results through framework adapters where useful, preserve page/section metadata, and quarantine low-confidence parses. File extension alone is insufficient because PDFs may be scanned, encrypted, malformed, multi-column, or table-heavy. |
| **Relevance to Project** | Explains why ADR-001 retains comparable native implementations and defines a possible evolution from the current scripts. The proposed router, confidence model, metadata contract, and quarantine path are future work documented in `Architecture.md`, not present capabilities. |

## 5. Marker quality across the expanded six-PDF corpus

| Field | Detail |
|---|---|
| **Topic** | Assess the end-to-end Marker workflow on six procurement, legal, engineering, and RAG PDFs totaling 251 pages. |
| **Date** | 2026-07-15 |
| **Findings** | Marker recovered ordinary prose well: the 91-page legal document yielded about 44,443 Markdown words from roughly 45,450 PDF words, and the RAG chapter yielded about 4,032 from roughly 4,023. It often retained emphasis, footnotes, colored text as plain text, simple tables, and much surrounding prose. Structural fidelity was substantially weaker: complex forms and merged tables were flattened, narrow headers fragmented into letters or syllables, heading levels were inconsistent, repeated page furniture entered the reading stream, page breaks and layout semantics were lost, and nested lists degraded. High aggregate word retention therefore cannot establish structural completeness. Asset export, encoding checks, page-aware cleanup, heading normalization, table-quality checks, and targeted source comparison at page/table boundaries are required. |

## 6. Marker header/footer configuration for RAG

| Field | Detail |
|---|---|
| **Topic** | Determine how Marker classifies, removes, preserves, and debugs page headers and footers. |
| **Date** | 2026-07-16 |
| **Findings** | Marker classifies page regions as `PageHeader` and `PageFooter`; the renderer excludes those types by default through `keep_pageheader_in_output=False` and `keep_pagefooter_in_output=False`. This is layout classification rather than repeated-text matching, so a real heading misclassified as a page header can disappear, while a running header classified as ordinary text remains. `paginate_output`, JSON/chunks output, block IDs, and debug layout/JSON artifacts can expose page and block structure. Low-confidence blocks can be relabeled, and headers/footers can be retained for downstream policy. Footnotes are a separate block type and should not be treated as page footers. |
| **Conclusion** | For RAG evaluation, preserve headers and footers initially, retain page/block metadata, and decide downstream whether each item should be content, metadata, or boilerplate. Repetition and geometry rules require validation for first pages, alternating headers, section-specific identifiers, scans, and technical document frames. Do not assume the default exclusion policy is lossless. |
| **Relevance to Project** | Explains both omitted repeated titles and intrusive running headers in the Marker report. The current `codes/marker_test.py` does not pass these diagnostic settings or retain structured page/block output; no production policy has been adopted. |

## 7. Markdown chunking experiments on Marker output

| Field | Detail |
|---|---|
| **Topic** | Explore how Marker-generated official-document Markdown should be divided without destroying heading, table, or nested-list structure. |
| **Date** | 2026-07-16 |
| **Findings** | The committed baseline used `RecursiveCharacterTextSplitter` with a 1,600-character target, 200-character overlap, and Markdown-oriented boundaries. Eight local runs then tested increasingly structural algorithms: heading-level descent, whole-table preservation, recursive splitting at shallow list indentation, prose fallback, table token diagnostics, and per-chunk `cl100k_base` counts. Run totals varied substantially (1,263–4,838 chunks before settling at 2,271 in the last three reports), showing that small policy changes materially alter the retrieval unit population. The custom implementation also exposed a core conflict: a hard size limit and an indivisible oversized table cannot both be guaranteed. The user rejected this implementation path and plans a separate rewrite; overlap was also removed from the intended design. |
| **Conclusion** | Heading hierarchy, list nesting, and table boundaries need explicit tests against real Marker irregularities before a splitter is adopted. Table completeness must have a defined oversized-table policy, token limits should use the target model tokenizer, and run reports should retain source, sequence, character, and token metrics. Chunking cannot restore content or relationships already lost during PDF conversion. |
| **Relevance to Project** | Frames `6e176b3` as a baseline rather than the final design, explains the ignored `chunk-runs/` evidence and `codes/count_table_tokens.py`, and prevents the abandoned custom splitter from being documented as accepted architecture. |

## 8. Iteratively authoring rule-based Markdown chunking boundaries

| Field | Detail |
|---|---|
| **Topic** | Determine why algorithmic approaches to section-by-section Markdown chunking (a reused recursive splitter, an LLM-generated complex splitter) failed, and evaluate a hand-authored rule set as a replacement. |
| **Date** | 2026-07-17 |
| **Findings** | Two earlier approaches to per-section chunking did not reach the intended behavior: reusing a recursive splitter from a separate project, and a Codex-generated splitter built from many interacting helper functions. Both were abandoned. Hand-typing rules for as many observed structural situations as could be enumerated — heading hierarchy and incomplete-subsection rollover, flat/nested list splitting by indentation, paragraph fallback boundaries, partial/oversized table handling, fenced-code exclusion, no overlap — and having the coding agent implement them as a single top-to-bottom `temp_split()` produced a workable draft on the first pass. A run against the then-committed heading/table/list splitter (`50208bc`) gave a comparison baseline of 1,273 chunks averaging 192.61 tokens. Four rounds of manually inspecting chunk reports against real RFT documents each surfaced one concrete misbehavior — a heading left dangling at the end of a chunk, a lead-in paragraph separated from the list it introduced, a table rule that dropped an intervening heading, a chunk ending on a heading when a table/list/paragraph followed — and each was fixed as one targeted rule addition rather than a rewrite. Chunk counts across the four iterations were 2,065; 2,066; 1,915; and 1,913, converging as the rules stabilized. This process also surfaced a Marker source defect: nested list sub-points are flattened to the same indentation as their parent pointer, which bounds how much list hierarchy the chunker can ever recover from Marker's output (BUG-012). |
| **Conclusion** | For this splitting problem, an explicit, example-driven rule set authored against real documents converged faster than either a reused generic algorithm or an LLM-generated complex implementation. Manually inspecting real chunk output and fixing one concrete failure at a time is the effective feedback loop; the design is still being refined and is not adopted as final. Chunk quality is bounded by Marker's own list-flattening defect, independent of the splitter's own logic. |
| **Relevance to Project** | Extends Research topic 7 from the rejected heading/table/list prototype to its rule-based replacement, explains the four uncommitted 2026-07-17 `chunk-runs/` reports, and links the chunking work back to Marker's source-conversion fidelity (BUG-010, BUG-011, BUG-012). |

## 9. Repairing Marker clause structure and validating against full-document ground truth

| Field | Detail |
|---|---|
| **Topic** | Determine how to give the Markdown splitter reliable heading and list structure when Marker renders numbered clauses inconsistently, and validate the repair against a full real RFT/contract document rather than small examples. |
| **Date** | 2026-07-20 |
| **Findings** | In RFT-style sources the only reliable "this is a heading" signal — PDF font size and weight — is already gone once Marker emits Markdown, so second-level numbered clauses (`5.1`, `5.3`, italic `*Technical Bids*:`) survive as bold-run paragraphs, and because bold is overloaded for inline defined terms ("**Company**", "**RFT**"), a blind "promote bold to heading" rule would create many false headings; whole-line anchoring is the safeguard. Two designs were weighed — boundary-only soft-heading detection inside the splitter versus an in-memory `preprocessing()` normalization pass — and the latter was adopted (ADR-007) because it can also rejoin clause bodies fragmented across blank lines and supply missing list structure, while never rewriting the on-disk `.md`. Validation moved from two hand-authored before/after examples to a ~2,700-line `marker_results/input.md` / `expected-output.md` ground-truth pair (a full RFT plus its General Terms and Conditions contract body), which exposed defects the toy examples could not: alphabetic/roman marker families chained across unrelated sections (BUG-013), fully-nested marker edits overlapping and scrambling output (fixed with BUG-013), an unconditional forward-merge that concatenated unrelated glossary definitions (BUG-014), and inline `<span id="…">` anchors glued to line starts breaking detection (addressed by adding `_extract_leading_spans()`). Diffing output against ground truth fell from 1,596 to ~830 changed lines. Inspecting real chunk output separately surfaced two `temp_split()` boundary failures driven by user feedback — one-off deep subsections (a single `#####` level inside one `####` clause) whose run "never closed" under a same-level-only search, and lists with any nesting being invisible to the keep-list-with-lead-in helpers — plus a parent-heading that stayed stranded when its subsections were deferred (fixed with `_enclosing_heading_start()`), a data-loss bug in the new top-level-item boundary helper (BUG-015), and a mid-word cut when a hierarchy resolved before the size limit and the rule returned the raw, unsnapped character limit. Each was fixed as a targeted rule change and re-verified with a full round-trip check (every emitted chunk reappears in the preprocessed text with nothing left over) across all four local documents. |
| **Conclusion** | Font-derived heading signal cannot be recovered from Marker Markdown, so structure must be reconstructed heuristically; a whole-line-anchored, in-memory normalization pass is a workable best-effort repair, but must be validated against full real documents, since small examples hide global-scoping, unconditional-merge, and edit-overlap failures. A round-trip no-loss invariant is the effective guard against silent data loss and corruption during both preprocessing and splitting. One ambiguity is unresolved: "RFT Number: [...]" page-footer boilerplate merges inconsistently in the ground truth itself, with no punctuation or structural signal distinguishing the cases, so it was flagged to the user rather than special-cased by guesswork. Repair remains bounded by Marker's own list-flattening defect (BUG-012). |
| **Relevance to Project** | Extends Research topic 8 from splitter rule authoring to source-structure normalization; motivates ADR-007 and the `preprocessing()` stage documented in `Architecture.md`; and records BUG-013 through BUG-015. The transforms are scoped to the observed RFT/contract patterns and remain experimental, not a general Markdown normalizer. |

## 10. Marker 2.0.0 as a VLM-server pipeline, and what the upgrade cost and delivered

| Field | Detail |
|---|---|
| **Topic** | Establish whether Marker can positionally remove running headers/footers that its layout model misclassifies, and characterize what changes when `marker-pdf` moves from 1.10.2 to 2.0.0 on a single-GPU laptop. |
| **Date** | 2026-07-21 |
| **Findings** | The header problem was correctly diagnosed in Research topic 6 as a classification problem, not a configuration one: under 1.10.2 the renderer defaults already suppress `PageHeader`/`PageFooter` blocks, so anything still appearing was never labelled as such. Marker 2.0.0 adds `MarginaliaProcessor` to the default PDF pipeline, which relabels a block as marginalia only when it satisfies every one of four positional guards — entirely inside the top/bottom margin zone, extremal on the page (nothing above a header, nothing below a footer), running-head sized, and short — each guard protecting a specific real-content case. Verified against the regenerated corpus at shipped defaults: the old 1.10.2 output preserved in `dataset/input.md` opens with a bare `RFT Number: [6000042656 (ENQ22-108)` running-header line and contains 23 such standalone lines; the 2.0.0 output of the two 250-page volumes contains none — the surviving `RFT Number:` occurrences are all legitimate form fields inside tables. Mojibake also disappeared (0 occurrences of the `â€` sequence, against the 26 recorded in topic 5), while broken image references persist (259 across the two files), confirming those were two independent defects. The upgrade is architectural rather than incremental. surya-ocr 0.22.1 no longer runs the VLM in-process: it spawns a separate inference server speaking OpenAI-compatible chat completions and picks the backend from hardware — vllm (Docker) on any NVIDIA GPU, llama.cpp otherwise — while the non-VLM models (text detection, OCR-error DistilBert, rf-detr fast layout) remain torch-side, making it a hybrid. `PdfConverter` also derives its `mode` from the active device (`balanced` on CUDA, `fast` on CPU/MPS), so a CPU-only Torch build silently selects a *different extraction pipeline* rather than merely running slower; the two modes differ in layout model (VLM vs rf-detr), reading-order source (learned head vs the PDF character stream via pdftext), OCR granularity (whole-page promotion vs per-block repair), table acceptance threshold (0.75 vs 0.5), and inline-math OCR. `OrderProcessor` was also dropped from the default pipeline. Migration cost four distinct failures — a Docker requirement that blocked all conversion, a JSON-Schema-to-GBNF grammar rejection, an ABI-orphaned `torchaudio` that killed a server subprocess behind an opaque health-check timeout, and a renderer recursion crash on a VLM-reconstructed table (BUG-017 through BUG-020). Two diagnostic lessons recur: out-of-process servers hide tracebacks, so `~/.cache/datalab/surya/*.log` is the real error surface; and `torch.cuda.is_available()` alone is insufficient on a Blackwell (sm_120) card, since it can report `True` on a wheel lacking matching kernels — an actual matmul is the only reliable check. |
| **Conclusion** | The upgrade achieved the objective: running headers and footers are removed by `MarginaliaProcessor` at shipped defaults, with no tuning of `header_zone`, `max_height_frac`, or `max_chars` required for this document family. The cost is that the Marker leg of this harness is now an operated service rather than a library call — external binary, spawned server, ~1.5 GB of model downloads, and process lifecycle to manage — and that quality and throughput are governed by a device-derived `mode` default that must be pinned explicitly for results to be reproducible (ADR-008). `fast` mode is not a cheaper version of `balanced`; it is a different pipeline whose output was rejected here on structural grounds. Any comparison across `marker_results/` files produced before and after 2026-07-21 is invalid, and header removal is now confirmed to be independent of both mode and scheduling. |
| **Relevance to Project** | Supersedes the "no production policy has been adopted" position in topic 6 for headers/footers specifically, and revises topic 4's CUDA guidance for the Blackwell GPU (`cu130` is the only index carrying `torch 2.13.0`). Motivates ADR-009, records BUG-017 through BUG-020, and supplies the pipeline context ADR-008 and BUG-016 depend on. Removes mojibake from the open items in topic 5 while leaving image-asset export open (BUG-010) and adding VLM-generated table structure as a new fidelity risk alongside BUG-011. |

## 11. Replacing chunking rules with structural packing, and bringing tables under the size limit

| Field | Detail |
|---|---|
| **Topic** | Determine why an incrementally extended chunking rule set kept producing under-full and torn chunks, and establish a table-splitting policy that respects a hard size limit without making the pieces uninterpretable. |
| **Date** | 2026-07-22 |
| **Findings** | The rule set authored in topic 8 had absorbed six rounds of extension and was still failing in two visible ways — a 64-character opening chunk beside ~1,500 characters of the same cover page, and clause 5.4 torn between its two sub-labels. Instrumenting the selector showed both traced to the same construct: `_structural_cut()` chose a boundary by finding the *deepest* ATX level in the candidate window, which is a proxy for section ownership that holds only while heading levels are well-formed. Marker's are not — a section written `#### 5.` whose clauses Marker had already emitted as `### 5.6` inverted the tree (BUG-021) — so the heuristic was one malformed document away from failing regardless of how many rules surrounded it. The rules also contradicted each other on fill: three helpers deliberately emitted a matched section as a chunk of its own and never packed further, so any global minimum-fill rule would have needed carve-outs for its own siblings. Re-expressing the stated intent — take whole units until the next will not fit, then move that unit forward intact — as greedy packing over a containment tree made both defects unrepresentable rather than patched, and removed eleven helpers whose interactions were the actual source of the failures (ADR-010). Two measurement results shaped decisions that intuition would have got wrong. First, on heading promotion, the semantically obvious `enclosing + 1` deviated from `dataset/expected-output.md` on 84 heading lines while level-with-the-parent matched exactly; the ground-truth pair, not the reasoning, settled it. Second, on tables, the standing exemption was costing 38 over-limit chunks with a maximum of 10,071 characters, and a survey of the corpus found Marker pads columns to the widest cell — alignment rows reach 897 characters of dashes, and the RFT summary table is 5,922 source characters carrying 1,823 characters of content. That made verbatim slicing the wrong primitive (a slice cannot carry a repeated header and spends most of its budget on padding) and made re-serialization with normalized padding the right one: normalization alone brings many tables back under the limit with no split at all, turning that 5,922-character table into 1,527 + 296. Rules for oversized rows, oversized columns, and oversized individual cells are unreachable in this corpus — the longest single row is 897 characters and no table has a fully empty header row — so they were validated against a synthetic suite scaled to `CHUNK_SIZE` rather than left unexercised. A separate generalization was measured and rejected: extending the "never close a chunk on a heading" rule to any line that renders to nothing (`<span id>` anchors, `<!-- image -->`) would have affected 19 markup-only chunks and 125 chunks ending on markup, and the user judged it wrong; only the narrow case of a heading plus the anchors trailing it was kept. |
| **Conclusion** | When an example-driven rule set stops converging, the signal is usually that the rules are encoding a *proxy* for the intent rather than the intent itself; restating the goal directly can be cheaper than a seventh rule, and here it deleted more code than it added. Ground-truth data outranks semantic reasoning for structural choices — both the heading-level rule and the table-splitting primitive were decided by measurement against real documents, and both would have been decided differently by argument alone. A hard size limit and indivisible tables cannot both be guaranteed (topic 7); the resolution is not to pick one but to make the pieces self-describing, since repeating the headers costs a few dozen characters and removes the objection that made tables indivisible. Verification has to follow the transformation: once split tables are deliberately not byte-identical to their source, the strict round-trip invariant from topic 9 no longer applies to them and must be replaced by a per-line survival check, with the residual loss surface narrowed to a single oversized cell. |
| **Relevance to Project** | Supersedes the boundary-selection algorithm described in topic 8 and closes the oversized-table policy gap left open in topic 7. Motivates ADR-010 and ADR-011, records BUG-021 through BUG-023, and revises topic 9's round-trip invariant to the three invariants the splitter now carries: no chunk exceeds `CHUNK_SIZE`, every source line survives in rendered form, and no chunk closes on a heading unless it is the last. The splitter remains experimental and uncommitted, with no automated test suite behind these invariants. |

## 12. Locating two Marker conversion failures, and what each measurement overturned

| Field | Detail |
|---|---|
| **Topic** | Determine why one source PDF died with a bare `RecursionError` and another with "a worker process died while extracting", and establish whether either is fixable from the calling script. |
| **Date** | 2026-07-23 |
| **Findings** | The two failures are unrelated and were initially conflated because they appeared in the same batch. The recursion is in `markdownify`'s DOM walk, reached from `MarkdownRenderer`; the worker death is in `pdftext`'s process pool, before any GPU stage. Four measurements each overturned the step before them. **(1) Raising `sys.setrecursionlimit` alone would have made the diagnosis impossible, not better.** The limit caps Python's frame counter and does not grow the OS stack beneath it; Windows gives the main thread 1 MB, which the default limit of 1000 is already sized around, so a raised limit trades a catchable `RecursionError` for a silent process death with no traceback. `threading.stack_size()` applies only to newly started threads, so the conversion has to move onto a spawned thread to get the headroom the raised limit implies. CPython additionally rejects a thread stack of ≥256 MB with `ValueError` rather than clamping (`THREAD_MAX_STACK_SIZE`); probing put the ceiling at 255 MB, so an initial 512 MB choice would have aborted the script on line one of every run. **(2) Stack shape cannot distinguish infinite recursion from deep recursion.** A classifier that read "repeating frame cycle ⇒ unbounded" was tested against known-shape stacks before a GPU run was spent on it, and a deliberately finite `finite(5000)` produced an identical 1-frame cycle to genuine infinite recursion — then returned normally once the limit was raised. The discriminating measurement is not the shape but whether depth-at-failure tracks the limit across two runs. **(3) The message nearest a crash is not its cause.** `Table OCR failed for block /page/28/Table/6` and `Overflow in columns: 0 >= 3 or rows: 1 >= 1` both sat immediately above the traceback and both come from `except` blocks that log and continue — the first from `marker/processors/table.py:169`, the second from `marker/renderers/markdown.py:182` — and the table stage printed its completion stats between them and the crash, ~3.5 s earlier. Grepping for the literal log strings, rather than reasoning from adjacency, moved the crash from the table processor to the renderer. **(4) Nesting does not accumulate across a document, so splitting it cannot help.** The working hypothesis was that ~2 unbalanced inline tags per page compound across 250 pages; a synthetic probe killed it. `html.parser` does not auto-close inline tags, so N unclosed `<i>` in one `<p>` gives DOM depth N+1 — but a *closed* block-level tag resets nesting: 200 such blocks still give depth 11, and one pathological block surrounded by 1,000 clean blocks is unchanged at 501. Depth is set by the single worst block. `markdownify` burns ~1.99 frames per DOM level (depth 481 converted at limit 1000, depth 501 raised at 996 frames), and the depth is bounded by the tag count rather than infinite — 1001, 3001 and 8001 all converted at limit 20000. The worker failure resolved to arithmetic: `pdftext` sizes its pool as `min(workers, pages // 10)` with a threshold of 10 and only skips the `ProcessPoolExecutor` when that lands ≤ 1, while Marker's provider defaults `pdftext_workers` to 4 — so 154- and 192-page documents all got 4 workers, and page batching does not avoid it, since a 50-page slice still yields `min(4, 5) = 4`. Marker's own CLI, server and Streamlit entry points force `pdftext_workers = 1`; only the programmatic `PdfConverter` path does not. A fifth finding was about the tooling rather than the code: several searches of the installed packages returned "no matches" because `.venv-marker/` is Git-ignored and ripgrep skips ignored files by default, so those negatives meant nothing (BUG-027). |
| **Conclusion** | Both failures are fixable from the calling script, and neither is fixable by splitting the input — the measurement that mattered most turned "split the PDFs and use `page_range`" from the obvious fix into a demonstrably ineffective one and redirected the second fix onto `pdftext_workers=1`. Three practices carried the investigation: test a diagnostic against known-shape inputs before spending a long run on it; treat log adjacency as a hypothesis and confirm the emitting line in source; and confirm a search tool can find something you know is present before trusting a negative. A recursion limit is a legitimate fix only when the depth is shown to be bounded, and on Windows it is only a fix at all when a real stack is provided behind it. |
| **Relevance to Project** | Root-causes BUG-020 and re-files it as BUG-024; records BUG-025 and BUG-027. The fixes were implemented at `b73c2e3` and removed 8 minutes later by the revert in ADR-012, so this topic is the only durable record of the mechanism. Both defects survive that revert — `markdownify` over `html.parser` is the 1.10.2 renderer path too, and `pdftext 0.6.3` carries the identical pool sizing and the same default of 4 — so the analysis applies unchanged to the environment now installed, while the code that acted on it does not. |

## 13. Marker 2.0.0 output quality on the three-document corpus, and the case for reverting

| Field | Detail |
|---|---|
| **Topic** | Assess what Marker 2.0.0 `balanced` actually produced across the current three-PDF corpus, and weigh that against the header-removal benefit that motivated the upgrade. |

| **Conclusion** | Revert to 1.10.2 (ADR-012). The trade is a known, bounded, visible defect — running headers in the reading stream, which the chunking `preprocessing()` pass and the packer already cope with — against an unbounded, invisible one.
