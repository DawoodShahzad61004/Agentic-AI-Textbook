#### 2026-07-20 — Add a marker-clause preprocessing pass ahead of splitting

* Added `preprocessing()` to `chunking/ingest.py`, run on each document's text before `temp_split()`. It targets a specific Marker-conversion defect in RFT-style source PDFs: numbered clauses (e.g. `3.1`, `5.1`) rendered inconsistently as plain paragraphs, dash-prefixed list items, or bold-labelled lines, with a single clause's body wrapped across stray blank lines by source pagination.
* The pass operates on blank-line-delimited blocks and detects runs of 2+ consecutive same-family markers (numeric `x.y`, alphabetic `(a)`, or roman `(i)`), then applies one of two transforms: give every marker in a plain-paragraph sequence the same leading list-syntax character, or promote a bold-labelled/already-headed sequence to matching-level headings with each clause's fragmented body rejoined into one paragraph. A second pass promotes italic `*Label*:` lines that sit under a heading into a one-level-deeper subheading.
* Validated against two hand-authored before/after examples (provided by the user) covering both transform paths; the plain-list case matches exactly, and the heading-promotion case matches after one explicitly agreed simplification (always merge a clause's trailing fragment through to the next marker, rather than special-casing whether that next marker was already heading-formatted in the source). An early version of the heading-promotion path silently dropped content sitting between two markers that neither one's body absorbed (e.g. a nested list under one clause); fixed by carrying that content through verbatim instead of only emitting per-marker segments.
* Sanity-checked against the two real Marker-converted RFT files currently in the local, Git-ignored `marker_results/` corpus: no crashes, one of the two files changed as expected, and the full `ingest.py` pipeline still ran end-to-end.
* Treat this as an experimental, best-effort heuristic rather than a general Markdown normalizer — it is scoped to the numbered-clause/bold-label/italic-sublabel patterns observed in this document family, not arbitrary marker styles.
* Tracked in: uncommitted addition to `chunking/ingest.py`.

#### 2026-07-20 (continued) — Validate `preprocessing()` against a full real RFT/contract document

* The user supplied `marker_results/input.md` and `marker_results/expected-output.md` — the full ~2,700-line RFT plus its General Terms and Conditions contract body, converted by Marker, with a hand-produced corrected version — as ground truth superseding the two earlier toy examples. Diffing `preprocessing()`'s output against it surfaced defects the toy examples were too small to expose.
* Fixed a critical bug: alpha (`(a)`) and roman (`(i)`) marker families were scoped globally by a bare `"alpha"`/`"roman"` key, so unrelated enumerations anywhere in the document chained together if their values happened to continue in sequence. This was silently splicing unrelated clauses together (e.g. a Section 6 clause's roman list getting glued after Section 6.20). Fixed by resetting in-progress alpha/roman runs at every heading or numeric-marker boundary.
* Fixed a second, related bug: a short marker sequence nested entirely inside a larger one (e.g. a roman sub-list inside one clause of a heading-promoted run spanning many clauses) produced its own edit whose span sat inside the outer edit's span; applying both scrambled the output. Fixed by dropping fully-nested/overlapping edits and keeping only the outermost one.
* Replaced the "always merge a clause's trailing fragment forward" rule (the simplification agreed after the toy examples) with a sentence-boundary heuristic: only merge the next paragraph fragment while the accumulated text does not yet end in terminal punctuation. The old unconditional rule was actively corrupting output — e.g. merging an entire run of unrelated glossary definitions ("DELAY EVENT", "DISPUTE", "DRAWINGS", "EAD", ...) into a single line. Also extended the (previously heading-branch-only) merge behavior to the plain branch.
* Added a third, previously unspecified transform: Marker glues internal `<span id="...">...</span>` cross-reference anchors to the front of whatever line they annotate, which was breaking heading/list detection for that line. Added `_extract_leading_spans()` to pull them onto their own preceding line(s), run as the last step of `preprocessing()`.
* Diffing against the full ground truth dropped from 1,596 to ~830 changed lines (git-diff style) across these fixes, with the earlier catastrophic corruption eliminated. The remaining diff is dominated by one unresolved ambiguity: "RFT Number: [...]" page-footer boilerplate merges inconsistently in the ground truth itself — sometimes absorbed into the preceding clause regardless of its own punctuation, sometimes left isolated from a following clause even though nothing punctuation-wise distinguishes the two cases. This was flagged to the user rather than further special-cased by guesswork.
* Tracked in: uncommitted changes to `chunking/ingest.py` building on the same-day preprocessing() addition.

#### 2026-07-20 (continued) — Fix two `temp_split()` boundary bugs found via the same document

* The user pointed out (via a pasted chunk-run excerpt) that `temp_split()` was splitting clause 5.4's "Technical Bids"/"Commercial Bids" subsections into separate chunks, and splitting clause 5.7 right before its `(a)-(e)` list, even though each clause fits comfortably under `CHUNK_SIZE` as a whole.
* Root cause 1: `_structural_cut`'s heading-hierarchy rule (Rule 2) located a subsection run's closing boundary by searching only for the *next same-level* heading; when a document uses a heading level exactly once (e.g. one-off `#####` subsections inside a single `####` clause), no same-level sibling exists anywhere else in the document, so the search fell back to end-of-document and the rule concluded the run never closes — dropping subsections that actually already fit. Fixed by also accepting the next *shallower* heading as a valid closing boundary.
* Root cause 2: the "keep a list with its lead-in paragraph/heading" helpers required the list to be flat (single indentation level), so a list with any nested sub-item was invisible to the check and fell through to generic size-based cutting. Renamed and relaxed `_flat_list_section_after_heading`/`_flat_list_section_after_paragraph` (now `_list_section_after_*`) to detect lists regardless of nesting, and added `_top_level_item_boundaries()` so the oversized-list fallback splits on top-level pointers only, keeping nested children attached to their parent pointer.
* While verifying with a full round-trip check (every chunk must reappear in the preprocessed text with nothing left over), found that the first version of `_top_level_item_boundaries()` silently dropped content: when the starting cursor was itself mid-way through a nested run (left there by a previous cut), the returned boundaries never included the cursor itself, so everything between it and the next true top-level pointer vanished. Fixed by always forcing the start position in as the first boundary. Confirmed zero dropped content across all four real documents in `marker_results/` after the fix.
* The user then pointed out that clause 5.4's heading and lead-in were still getting stranded at the end of the *previous* chunk while its subsections started the next one — Rule 2 was dropping only the first dropped subsection, not the parent heading that introduces it. Added `_enclosing_heading_start()`: when a subsection run gets pushed forward, the immediately-preceding shallower heading (if it directly owns the run, nothing else in between) is pulled forward with it, so the whole section starts fresh together.
* That exposed a second, latent bug in the same rule: once a subsection hierarchy resolves *before* the size limit (now much more common thanks to the shallower-heading fix above), the "otherwise" branch returned the raw, unsnapped character limit instead of a safe boundary — producing a mid-word cut in unrelated trailing prose that just happened to follow the hierarchy. Fixed by falling through to the existing paragraph/word-boundary rules instead of returning early. Re-verified the round-trip check (still zero dropped content) and the full pipeline on all four documents.
* Tracked in: uncommitted changes to `chunking/ingest.py`.

Every conversion failed immediately with a Docker connection error, because an NVIDIA GPU selects the vllm backend, which runs as a container (BUG-017). Guided layout decoding sends a JSON schema llama.cpp cannot convert to a GBNF grammar, so every request returned `failed to parse grammar` until `SURYA_GUIDED_LAYOUT=false` was set (BUG-018). Appending the llama.cpp directory to the user `PATH` did not reach the already-running IDE terminal, so binary resolution kept failing; a `LLAMA_CPP_BINARY` fallback to the default install path was added rather than hard-coding a machine-specific path. #### 2026-07-22 — Rewrite the splitter as structural packing, bring tables under `CHUNK_SIZE`, and fix trailing-heading boundaries

* Opened with two Marker conversion failures on the 250-page RFT volumes, both diagnosed as external rather than project defects: a `RecursionError` inside Marker's dense-table handling on a document with 56 tables (the same failure mode already recorded as BUG-020), and a spawned surya worker dying with only "a worker process died" reaching the parent. The accompanying `KeyboardInterrupt` was traced to surya's own atexit cleanup — `_stop_process()` polls liveness with `os.kill(pid, 0)`, a POSIX idiom, but signal 0 on Windows is `CTRL_C_EVENT`, so the teardown fires Ctrl+C at its own console. Cosmetic and upstream; no change made.
* The user then reported two chunking defects with the intent behind them stated explicitly: *fill each chunk with as many characters as `CHUNK_SIZE` permits, but never separate a heading from its content or split a logical section; if the complete next section cannot fit, move the entire section to the next chunk.* The first was a 64-character opening chunk sitting beside ~1,500 characters of the same cover page; the second was clause 5.4 torn between its `Technical Bids` and `Commercial Bids` subsections.
* Root cause 1 (BUG-021), upstream of the splitter: `_apply_heading_branch()` picked the promoted heading level from whichever block in the clause sequence Marker had *already* written as a heading. Marker emitted `### 5.6` and `### 5.7` while leaving 5.1–5.5 as plain text, so the whole sequence was promoted to level 3 — one level shallower than the `#### **5. INSTRUCTIONS TO BIDDERS**` section containing it. Every clause parsed as a sibling of its own parent, and `_promote_italic_sublabels()` compounded it via `last_level + 1`. Fixed by treating an existing prefix as a floor and raising it to at least the enclosing heading's level through a new `_enclosing_heading_level()`. The choice between that and the semantically obvious `enclosing + 1` was settled by measurement, not argument: `+1` deviated from `dataset/expected-output.md` on 84 heading lines, while level-with-the-parent reproduced its levels exactly.
* Root cause 2 (BUG-022): `_structural_cut()` chose boundaries by finding the *deepest* ATX level in the candidate window and pushing that run forward. At offset 0 it cut at the contents heading and `_enclosing_heading_start()` pulled it back to the `#` title, stranding 64 characters; at section 5 the inverted levels made "deepest level 4" mean the section heading plus the two bid sub-labels, so the cut split clause 5.4. Three sibling helpers worked against packing from the other side, emitting a matched section as a chunk of its own and never filling it further.
* Rather than adding a seventh rule to a set whose rules already contradicted one another, rewrote `temp_split()` as parse-then-pack (ADR-010): `_build_tree()` parses the document into `_Node` units and `_pack()` fills a chunk with whole sibling units until the next will not fit, moving that one forward intact, with `_split_node()` opening a unit only when it cannot fit an empty chunk alone. `_extend_start()` makes every heading travel with the first unit beneath it at every depth; `_lead_in_fits()` hands a short pending buffer into a unit about to be opened anyway instead of closing early. Removed `_structural_cut()` and eleven helpers that existed only to serve it; `ingest.py` went from 1,176 to 974 lines with no unreferenced functions left. Both reported cases now match the stated intent, and the corpus fell from 1,949 to 1,051 chunks at `CHUNK_SIZE=1600`.
* Next, at the user's direction, removed the standing exemption that had let tables exceed `CHUNK_SIZE` in every chunker this project has had, implementing nine supplied rules as `_split_table()` and its helpers (ADR-011). Measured the exemption's real cost first — 38 over-limit chunks, the largest 10,071 characters — then surveyed the corpus, which changed the design: Marker pads columns to the widest cell, producing alignment rows of up to 897 characters of dashes, and the RFT summary table is 5,922 source characters carrying 1,823 characters of content. That made verbatim slicing the wrong primitive (a slice cannot carry a repeated header and spends most of its budget on padding) and re-serialization the right one — normalizing padding alone satisfies rule 1 for many tables, turning that 5,922-character table into two chunks of 1,527 and 296.
* Orientation follows the rules: by row with column headers, both, or neither; by column with only row headers; then cell groups within a row or column, then boundaries inside a single cell preferring paragraph, list-item, sentence, and word in that order. `_has_row_headers()` is a documented heuristic, since Markdown has no row-header syntax; it only picks the splitting axis and whether a row label repeats, so a wrong guess degrades a chunk rather than corrupting one. Two supporting defects were found while implementing: `_table_cells()` split naively on `|`, miscounting the width of any row with an escaped or code-span pipe — harmless while tables were atomic, wrong once cells are addressed by index — and `_table_spans()` began a table at the row directly above the alignment row, so multi-level header stacks lost their upper levels.
* Rules for oversized rows, columns and cells are unreachable in this corpus (longest single row 897 characters; no table with a fully empty header row), so they were validated against a synthetic suite covering all nine rules plus multi-level headers and escaped pipes, later reworked to scale its fixtures with `CHUNK_SIZE` after the user moved that value and five expectations calibrated for 1,600 failed spuriously.
* Verification changed shape with the tables. A split table is deliberately no longer byte-identical to its source, so the strict round-trip check used since 2026-07-20 was replaced by a per-line survival check: every source line, normalized to its rendered form, must appear in some chunk. Across all nine local Markdown files in `marker_results/`, `docling_results/` and `unstructured_results/`: 0 chunks over `CHUNK_SIZE`, down from 38, and 0 missing lines. Content can now be lost only inside a single cell that exceeds the limit alone, which no table in the corpus does.
* The user then reported chunks closing on a heading whose content began the next chunk. Measured before fixing — 43 of 1,042 chunks — which showed it was a class with two distinct paths: a heading-only unit that is a *sibling* of the section it introduces, buffered onto the previous chunk, and a heading-only unit that is the *last child* of a section, flushed by the inner `_pack()` while the outer document still had text. Both now route through a restored `_trailing_heading_start()` plus a `tail_open` flag that lets a nested pack hand its trailing run back instead of emitting it; 43 → 0. This was a regression from the same-day rewrite, which had dropped the predecessor's guard in favour of a weaker check, and is recorded as such (BUG-023).
* A follow-up report showed the same defect in a second shape — a heading plus the `<span id>` anchors trailing it — fixed by letting the walk cross markup-only lines while still requiring a heading in the run. The asymmetry is deliberate: an anchor after the heading annotates what follows and travels with it, one before belongs to the body already recorded and stays.
* One approach was implemented, measured and reverted at the user's direction, and is kept on record rather than omitted: generalizing that rule so no chunk could close on *any* line rendering to nothing (`<span id>` anchors in `marker_results/`, `<!-- image -->` in `docling_results/`). It affected 19 markup-only chunks and 125 chunks ending on markup before being judged wrong and fully reverted, leaving only the narrow heading-plus-anchor case.
* `chunking/logger_config.py` gained three header lines per run at the user's request — the 1-based index of the largest chunk by token count, its token count, and its character count.
* Final verified state at `CHUNK_SIZE=1600`: 1,064 chunks over the two-volume Marker corpus averaging 233.68 tokens, against 128.14 for the same corpus before the rewrite; across all nine local Markdown files, 0 chunks over the limit, 0 missing lines, and 0 chunks closing on a heading.
* Noted but not acted on: `split_documents()` discards any chunk shorter than `MIN_CHUNK_CHARS` (50) outright rather than merging it, so its text is dropped. The markup-only chunks measured above cleared that threshold by only a few characters. Not raised as a defect and not yet recorded in `Bugs.md`.
* Tracked in: ADR-010, ADR-011; BUG-021 through BUG-023; Research topic 11; uncommitted changes to `chunking/ingest.py` and `chunking/logger_config.py`; twenty-five Git-ignored `chunk-runs/` reports.

#### 2026-07-23 — Root-cause two Marker failures, then revert Marker to 1.10.2

* **00:00–02:33:** Instrumented `codes/marker_test.py` for the two conversion failures carried over from 2026-07-22 — a bare `RecursionError` and "a worker process died while extracting" — and ran the corpus. All three sources converted (`src1.md` 01:40, `src2.md` 02:18, `src3.md` 02:33); source page counts are 154, 154 and 192.
* The starting task was narrow: bump `sys.setrecursionlimit` to learn whether the recursion was genuinely unbounded or merely deeper than the default 1000. Raising it alone was rejected before implementing, and the reason is the reverse of intuitive — the limit caps Python's frame counter without growing the 1 MB Windows main-thread stack the default is sized around, so it converts a catchable `RecursionError` into a silent process death with no traceback. `threading.stack_size()` applies only to newly started threads, so `run_with_deep_stack()` moved the conversion onto a spawned thread. A first attempt at a 512 MB stack was rejected outright by CPython (`ValueError` rather than clamping at ≥256 MB); probing put the ceiling at 255 MB and the default was set to 128 MB with the env override clamped.
* Testing the diagnostic before spending a GPU run on it killed its central claim. A classifier reading "repeating frame cycle ⇒ unbounded recursion" was exercised against known-shape stacks, and a deliberately finite `finite(5000)` produced an identical 1-frame cycle to genuine infinite recursion — then returned normally at a raised limit. Frame shape cannot separate the two cases, so `recursion_report()` was rewritten to state only *where* the recursion is and to surface depth-at-failure against the limit as the number that discriminates across two runs.
* Two hypotheses were retracted on measurement rather than argument, and both are recorded because each would have sent the work somewhere useless. The table stage was blamed first, on log adjacency: `Table OCR failed for block /page/28/Table/6` sat immediately above the traceback. It comes from `marker/processors/table.py:169`, which logs and continues; the whole table stage then printed its completion stats ~3.5 s before the crash, which was in `marker/renderers/markdown.py`. The sibling `Overflow in columns` warning is likewise a caught-and-ignored quality defect. Separately, the theory that ~2 unbalanced inline tags per page compound across 250 pages was overturned by a direct probe — a *closed* block-level tag resets nesting, so 200 blocks of 10 unclosed `<i>` reach depth 11 rather than 2200, and one pathological block surrounded by 1,000 clean blocks is unchanged. Depth is set by the single worst block, which made splitting the PDF or using `page_range` demonstrably ineffective against the recursion.
* Several ripgrep searches of the installed Marker/surya source returned "no matches" and were briefly read as evidence. They meant nothing: `.venv-marker/` is Git-ignored and ripgrep skips ignored files by default. Redone with `Select-String`, which found every string immediately (BUG-027).
* Root causes, both measured: the recursion is `markdownify` walking the document DOM, which `html.parser` nests one extra level per unclosed inline tag, at ~1.99 Python frames per level — so the default limit of 1000 buys ~480 levels (481 converted, 501 raised), and the depth is bounded rather than infinite, since 1001, 3001 and 8001 all convert at limit 20000 (BUG-024, re-filed from BUG-020). The worker death is `pdftext` sizing its pool as `min(pdftext_workers, pages // 10)` and only skipping the `ProcessPoolExecutor` when that lands ≤ 1, against a provider default of 4 — so every document here got 4 workers, and batching does not avoid it, since a 50-page slice still yields `min(4, 5) = 4` (BUG-025).
