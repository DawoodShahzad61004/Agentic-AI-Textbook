## ADR-001 — Embedding Model: `all-MiniLM-L6-v2`

| Field | Detail |
|---|---|
| **Decision** | Use `sentence-transformers/all-MiniLM-L6-v2` as the sole embedding model for the entire pipeline |
| **Date** | April 2025 |
| **Context** | The project needed a fast, locally-runnable embedding model to convert document chunks and user queries into dense vectors for semantic similarity search. The model had to run on-device (CUDA-enabled) and produce consistent-dimension outputs throughout the pipeline. |
| **Options Considered** | `all-MiniLM-L6-v2` (384-dim, fast, lightweight) · `all-mpnet-base-v2` (768-dim, higher quality) · `text-embedding-3-small` via OpenAI API (cloud, latency, cost) · `bge-small-en-v1.5` (similar size) |
| **Chosen Solution** | `all-MiniLM-L6-v2` |
| **Rationale** | Fast inference on CUDA (GPU-accelerated). Only 6 transformer layers — sub-100ms encode per batch. 384-dim vectors are compact enough for efficient HNSW indexing. Pretrained on large semantic similarity corpora, adequate for domain-specific retrieval. No API calls required — fully local. |
| **Impact** | Embedding dimension fixed at **384** across the entire project. Changing the model at any point would require re-ingesting all documents (the HNSW index dimension cannot change in-place). Lives in `embedding_manager.py`. |

## ADR-002 — Vector Store: ChromaDB

| Field | Detail |
|---|---|
| **Decision** | Use ChromaDB with local persistent storage as the vector database |
| **Date** | April 2025 |
| **Context** | Needed a vector store for storing 384-dim embeddings of document chunks and supporting fast approximate nearest-neighbor (ANN) retrieval. Required Python-native API, metadata filtering support, and local persistence without a running server process. |
| **Options Considered** | **ChromaDB** (local, Python-native, HNSW, metadata support) · **FAISS** (fast, no metadata out-of-the-box, no persistence) · **Pinecone** (managed cloud, latency, cost, data leaves machine) · **Weaviate** (more complex, requires daemon) |
| **Chosen Solution** | ChromaDB with `persist_directory=../data/vector_store` |
| **Rationale** | Simplest Python-native API (no daemon). Local persistence (two components: `chroma.sqlite3` for metadata + UUID folder for HNSW binary). HNSW index gives ~95–99% recall at sub-second latency even as corpus grows. Metadata support is essential for source filtering. FAISS rejected: lacks metadata without add-ons. Pinecone rejected: cloud-only, adds latency and cost. |
| **Impact** | Two collections used: `documents` (source chunks) and `learned_qa` (self-learning memory). Both components (`chroma.sqlite3` + UUID folder) must be kept together — losing either breaks the store. All retrieval in `retriever.py`, `vector_store.py`, and `self_learner.py` depends on this. |

## ADR-003 — Classic RAG → Agentic RAG Architecture

| Field | Detail |
|---|---|
| **Decision** | Replace the linear classic RAG pipeline with a full Agentic RAG loop |
| **Date** | April 2025 |
| **Context** | The initial pipeline was a fixed single-pass: `embed query → retrieve → prompt → answer`. This approach had no ability to self-correct when retrieval was poor, no query reformulation, and no quality gate. |
| **Options Considered** | **Classic RAG** (simple, linear, deterministic) · **Agentic RAG** (LLM decides when/how to retrieve, iterative, self-correcting) · **HyDE** (Hypothetical Document Embeddings, generate before retrieval) |
| **Chosen Solution** | Agentic RAG with a structured iteration loop (max 6 iterations) and LangChain tool-calling |
| **Rationale** | The agent can decide *whether* to retrieve, *how many times*, *with what query reformulations*, and *when to stop*. This eliminates single-point-of-failure retrieval: if one query retrieves poor chunks, the agent reformulates and tries a different angle. The quality check gate (`check_answer_quality`) catches hallucinations before returning answers. |
| **Impact** | Defined the entire architecture of `agent_query.py`. Justified the creation of `tools.py`, `self_learner.py`, and `feedback_store.py`. Introduced the MAX_ITERATIONS=6 and MAX_TOTAL_RETRIEVALS=5 hard limits to prevent runaway loops. |

## ADR-004 — LLM Provider: Groq

| Field | Detail |
|---|---|
| **Decision** | Use Groq as the primary LLM inference provider |
| **Date** | April 2025 |
| **Context** | Needed a fast, affordable inference provider for an agentic loop that makes 3–10 LLM calls per query (retrieval iterations + compression + judging). Latency per call directly affects total query response time. |
| **Options Considered** | **Groq** (LPU hardware, very fast, cheap, open-source models) · **OpenAI** (higher quality GPT models, more expensive, slower) · **Together AI** (open-source models, competitive pricing) · **Local inference** (Ollama/vLLM — no API cost but hardware constraints) |
| **Chosen Solution** | Groq with `llama-3.1-8b-instant` as primary model |
| **Rationale** | Groq runs Llama models on custom LPU silicon — dramatically faster than GPU inference (~250 tokens/sec vs ~50 tokens/sec). For an agentic pipeline making 5–10 LLM calls per query, this latency difference compounds. Both Groq and OpenAI expose OpenAI-compatible REST APIs, so switching providers later requires only changing `base_url` and `api_key`. Cost is ~10× lower than GPT-4.x equivalents. |
| **Impact** | Affects `llm_caller.py`, `agent_query.py`, and `.env` configuration. Model names must be read from `.env` (`MODEL_NAME`) to survive Groq's model deprecation cycles (both `gemma2-9b-it` and `llama3-8b-8192` were deprecated mid-project). |

## ADR-005 — Primary Model: `llama-3.1-8b-instant` (with `llama-3.3-70b-versatile` for production)

| Field | Detail |
|---|---|
| **Decision** | Use `llama-3.1-8b-instant` as the working/development model; identify `llama-3.3-70b-versatile` as the production-grade target |
| **Date** | April–May 2025 |
| **Context** | After the deprecation of `gemma2-9b-it` and `llama3-8b-8192` during development, needed to select a stable model. Two Groq models were evaluated on the criteria of latency, tool-use reliability, context window, and instruction-following. |
| **Options Considered** | **`llama-3.1-8b-instant`** (128K/8K context, extremely fast, moderate tool reliability) · **`llama-3.3-70b-versatile`** (128K/32K context, slower, much better tool-use and instruction-following) · **`llama-3.1-8b-instruct`** (similar to instant but better at multi-step reasoning, not on Groq) |
| **Chosen Solution** | `llama-3.1-8b-instant` for development; `llama-3.3-70b-versatile` recommended for production |
| **Rationale** | The 8b-instant model is adequate for rapid iteration and testing. It handles the orchestration speed required by the agentic loop. However, its instruction-following degrades at ~16K prompt tokens, and it occasionally misses tool constraints (e.g., firing all tool calls simultaneously including premature `check_answer_quality`). The 70B model is significantly better for NAC/DC/LBC compression quality and faithful merging, but is slower and more expensive. For production agentic use where answer faithfulness matters, the 70B model is the correct choice. |
| **Impact** | Observed quality gaps in Batch testing (Batches 6, 8, 10): poor analytical reasoning, acronym confusion, weak synthesis — all traceable to 8B model limitations. A hybrid model architecture (8B for retrieval orchestration, 70B for compression/judging) identified as the strongest upgrade path. Context window limit of 8,192 output tokens is a hard constraint for the instant model. |

## ADR-006 — LangChain as the LLM Framework Wrapper

| Field | Detail |
|---|---|
| **Decision** | Use LangChain's `ChatOpenAI` (not native `openai` SDK) as the wrapper for all LLM calls |
| **Date** | April 2025 |
| **Context** | Needed a framework layer to handle tool/function calling, message history management, and response parsing without writing raw HTTP requests. |
| **Options Considered** | **LangChain `ChatOpenAI`** (provider-agnostic, tool-call handling, broad community) · **Native `openai` SDK** (lower-level, tighter coupling to OpenAI) · **`langchain_groq.ChatGroq`** (Groq-specific, less portable) · **No framework (raw `requests`)** (maximum control, maximum boilerplate) |
| **Chosen Solution** | `langchain_openai.ChatOpenAI` with `base_url` pointed at Groq's OpenAI-compatible endpoint |

The tool-call handling (schema passing, response parsing, multi-turn message threading) is handled by the framework. Using `ChatGroq` was rejected because it would couple the codebase to one provider. LangChain is "glue" — not a model itself — and its overhead is acceptable given the simplification. |
| **Impact** | All three LLM instances (`llm`, `merge_llm`, `judge_llm`) are built from `ChatOpenAI`. The design proved directly useful when later testing with local TGI servers — only `base_url` and `http_client` needed to change. LangChain's `LLMChainExtractor` was subsequently *rejected* for context compression due to extra latency and dependency on LangChain's retriever format. |

## ADR-007 — Context Compression Pipeline: NAC → DC → LBC

| Field | Detail |
|---|---|
| **Decision** | Implement a three-stage semantic compression pipeline: Neighbor-Aware Compression → Deduplication Compression → LLM-Based Compression |
| **Date** | May 2025 |
| **Context** | Retrieved chunks were often: (a) split mid-sentence at chunk boundaries, losing document flow; (b) semantically redundant across multiple retrieval calls; (c) too verbose for the LLM's effective context window. All three problems were degrading answer quality and wasting tokens. |
| **Options Considered** | **Extractive compression** (SentenceTransformers cosine similarity — safe, no hallucination) · **LLM-Based Compression/LBC** (rewrite/summarize — ~27.6% reduction, hallucination risk) · **Deduplication/DC** (remove redundant sentences — low yield unless overlap is high) · **Neighbor-Aware/NAC** (merge consecutive same-source chunks — restores document flow) · **BM25 sentence compression** (lexical fallback) · **LangChain `LLMChainExtractor`** (framework-level option) · **No compression** (pass raw chunks) |
| **Chosen Solution** | Three-stage pipeline: **NAC → DC → LBC**, token-budget gated (skip if context < 500 tokens), implemented in `compress_context_pipeline()` in `context_compression.py` |
| **Rationale** | NAC addresses the chunking boundary problem first (most impactful). DC then removes redundancy that NAC may have introduced via merging. LBC finally rewrites for relevance and conciseness. LangChain `LLMChainExtractor` was rejected — extra latency and format dependency. BM25 was evaluated but is lexical-only and misses semantic paraphrases. Extractive compression is safest (no hallucination) but purely sentence-level; it was included as a fallback. LBC hallucination risk is mitigated by a faithfulness guard (see ADR-017). |
| **Impact** | `context_compression.py` implements the full pipeline. The token-budget gate (`COMPRESS_MIN_TOKENS = 500`) skips compression for small contexts to save latency. Embedding-first DC prefiltering (cosine similarity ≥ 0.92 before LLM pair comparison) identified as the next planned improvement — changes DC from O(n²) LLM calls to O(high-similarity candidates only). |

## ADR-008 — Self-Learning Mechanism: Memory Injection over Fine-tuning

| Field | Detail |
|---|---|
| **Decision** | Implement self-learning via memory injection into a `learned_qa` ChromaDB collection; reject naive auto-save and RLHF/fine-tuning for the current scale |
| **Date** | April–May 2025 |
| **Context** | The project goal was an agent that improves over time. Three mechanisms were evaluated: knowledge base growth, weight-level fine-tuning, and reinforcement learning from user feedback. |
| **Options Considered** | **Memory injection** (save validated Q&A pairs back into ChromaDB — "pseudo-learning") · **Fine-tuning on accumulated interactions** (real weight-level learning, batch process, requires ~500+ examples) · **RLHF/DPO** (thumbs-up/down as reward signal — research-grade complexity, needs scale) · **Naive auto-save** (save every answer — rejected: hallucinations become permanent) |
| **Chosen Solution** | Memory injection with confidence-gated saving, triggered every 5 successful (`OK`) interactions via `SelfLearner` in `self_learner.py` |
| **Rationale** | Memory injection is the only option achievable at the current project scale. Naive auto-save was explicitly rejected because hallucinations would become permanently retrievable, degrading future answers. The confidence gate (only `OK`-quality interactions trigger distillation) ensures only verified knowledge enters the `learned_qa` collection. Fine-tuning is the identified *future upgrade path* — the `interactions.jsonl` log is the training dataset, but requires ~500+ validated pairs before fine-tuning is worth the effort over better prompting. RLHF is research-grade overkill at single-app scale. |
| **Impact** | `self_learner.py`, `feedback_store.py`, `user_thumbdowns.json`, and `failed_variants.json` all exist because of this decision. The `LEARN_EVERY_N = 5` trigger constant is in `agent_query.py`. The retriever does hybrid retrieval across both `documents` and `learned_qa` collections. |

## ADR-009 — Structured Output Strategy: Native JSON Mode over Outlines/Guidance

| Field | Detail |
|---|---|
| **Decision** | Use native Groq `response_format: json_object` (with schema in prompt) for structured outputs; reject Outlines and Guidance for production use with remote APIs |
| **Date** | May 2025 |
| **Context** | The pipeline required reliable JSON outputs from several LLM calls (compression verdicts, merge outputs, judge verdicts, distilled Q&A pairs). LLMs frequently produced broken JSON, extra text, wrong fields, and inconsistent verdicts — causing `JSONDecodeError` exceptions and retry loops. |
| **Options Considered** | **Outlines** (FSM token masking — true constrained decoding, local models only) · **Guidance** (logit masking, same local-model constraint) · **Native Groq `json_schema` mode** (server-side enforcement, only `llama-3.3-70b-versatile`) · **Native Groq `json_object` mode** (valid JSON guaranteed, schema enforced via prompt, works with `llama-3.1-8b-instant`) · **Structured prompt + `json.loads()` + retry** (current baseline) |
| **Chosen Solution** | Native Groq structured output (`response_format: {"type": "json_object"}`) + Pydantic schema in prompt + `json.loads()` with retry. `fix_llm_output.py` handles multi-tier JSON repair. |
| **Rationale** | Outlines and Guidance both rely on logit/token masking, which requires *local model access* — i.e., direct access to the model's forward pass. With remote APIs like Groq, both frameworks fall back to sending `response_format: json_schema` to the API — they provide no actual constrained decoding benefit over just calling the API directly. `llama-3.1-8b-instant` does not support `json_schema` mode at all (only `json_object`). Outlines also imposes 40s–10+ minute schema compilation time for complex schemas. Net result: Outlines and Guidance add a dependency layer that only provides the same `response_format` passthrough that a direct API call already provides. Rejected. For truly constrained decoding in the future: local model hosting with Outlines + vLLM would be the path. |
| **Impact** | Explains the absence of Outlines/Guidance in the final pipeline. `fix_llm_output.py` handles broken JSON with greedy regex fallback and multi-tier repair. The retry loop (up to `LLM_RESPONSE_RETRY_LIMIT` attempts) is the production safety net. |

## ADR-010 — Agent State Machine: 4-Phase RETRIEVE → COMPRESS → DRAFT → JUDGE

| Field | Detail |
|---|---|
| **Decision** | Refactor the free-form agentic loop into an explicit 4-phase state machine with controlled transitions |
| **Date** | May 2025 |
| **Context** | The earlier agentic loop gave the LLM full freedom to call any tool at any time. This led to the LLM pre-emptively calling `check_answer_quality` with fabricated answers in Iteration 1 before any retrieval had occurred, batching incompatible tool calls simultaneously, and failing to transition cleanly from retrieval to answer generation. |
| **Options Considered** | **Free-form tool loop** (LLM decides all tool calls — flexible but unreliable with 8B models) · **Explicit state machine** (RETRIEVE → COMPRESS → DRAFT → JUDGE — deterministic transitions, LLM constrained per phase) |
| **Chosen Solution** | 4-phase state machine: **Phase 1 RETRIEVE** (tool_schemas = `[retrieve_documents, compress_context]`) → **Phase 2 COMPRESS** (force `compress_context()` if not already called) → **Phase 3 DRAFT** (invoke LLM with `tools=None` for free-form prose) → **Phase 4 JUDGE** (call `check_answer_quality()` as a direct Python function) |
| **Rationale** | Small 8B models lose instruction-following reliability as context grows. The state machine removes ambiguity by restricting available tools per phase — the LLM cannot call `check_answer_quality` in the RETRIEVE phase because it is not in `tool_schemas` during that phase. The DRAFT phase uses `tools=None` so the model generates prose instead of tool calls. The JUDGE phase bypasses the LLM entirely — the quality check is a Python function call. The re-loop path (INSUFFICIENT → RETRIEVE) lets the agent accumulate more evidence without discarding already-compressed chunks. |
| **Impact** | Defined the final architecture of `agent_query.py`. `check_answer_quality` was removed from `tool_schemas` and made a direct callable (see ADR-020). The `compress_done` flag tracks whether compression has occurred for the current iteration cycle. Token-budget gate in `compress_context` skips NAC→DC→LBC for small contexts (<500 approx tokens). |

## ADR-011 — Retrieval Validator & Merge Validator (LLM-as-Judge)

| Field | Detail |
|---|---|
| **Decision** | Add two LLM-as-judge validators: one to assess retrieved chunk relevance after each `retrieve_documents` call, and one to assess faithfulness of each NAC merge |
| **Date** | May 2025 |
| **Context** | Retrieved chunks were often partially or fully irrelevant to the original query. Merged chunks from NAC were sometimes fabricating claims or dropping key facts. Both problems were silently degrading final answer quality with no detection mechanism. |
| **Options Considered** | **Heuristic validators** (cosine similarity threshold, keyword matching — fast but shallow) · **LLM-as-judge** (semantic relevance scoring + per-claim fabrication/drop detection — accurate but adds latency) · **No validation** (pass everything through — fast, low reliability) |
| **Chosen Solution** | Two validators in `validators.py`: `validate_retrieval()` (per-chunk relevance → PASS/PARTIAL/FAIL/UNKNOWN verdict) and `validate_merge()` (per-claim faithfulness → OK/UNFAITHFUL verdict with `fabricated_claims` and `dropped_claims` lists). Both use `judge_llm`. |
| **Rationale** | Semantic relevance cannot be reliably checked with cosine similarity alone — a chunk can be topically adjacent but not answer the question. LLM-as-judge provides semantic understanding. The `UNKNOWN` verdict acts as a safe fallback (keeps all chunks) to avoid over-aggressive filtering. The merge validator with per-claim granularity gives specific feedback for retry prompts, enabling targeted corrections instead of full regeneration. |
| **Impact** | `validate_retrieval()` is wired into `_handle_retrieve_documents_call()` in `agent_query.py`. FAIL/PARTIAL verdicts inject a sidecar tool-role message guiding the agent to reformulate. `validate_merge()` rolls back to `source_chunks_for_merge[0]` on UNFAITHFUL verdict. Identified that paraphrases of the same fact should NOT be flagged (GOOD: "lower electricity costs" ≠ FABRICATED vs "minimize electricity costs"). |

## ADR-012 — System Prompt Architecture: Split `_ROLE_AND_RULES` + `_PROCESS_INSTRUCTIONS`

| Field | Detail |
|---|---|
| **Decision** | Split the monolithic `_BASE_SYSTEM_PROMPT` into a `_ROLE_AND_RULES` block (prepended) and a `_PROCESS_INSTRUCTIONS` block (appended last), with thumbdown/blocked-variant context sandwiched between them |
| **Date** | May 2025 |
| **Context** | As the system prompt grew with injected thumbdown history (up to ~1,800 tokens in Run 3), the PROCESS instructions were buried in the middle of the prompt. The 8B model exhibited recency bias — PROCESS instructions far from the generation point were being ignored. The model began pre-emptively batching all tool calls including premature `check_answer_quality`. |
| **Options Considered** | **Monolithic prompt** (single block, PROCESS in middle — original design) · **Split prompt** (ROLE/RULES first, contextual injection middle, PROCESS last — closest to user message) · **Per-iteration reminder** (inject a short PROCESS reminder into each tool result — targeted but verbose) |
| **Chosen Solution** | Split prompt: `_ROLE_AND_RULES` (role + hard limits + tool descriptions) prepended → blocked variants + thumbdown history injected → `_PROCESS_INSTRUCTIONS` appended last |
| **Rationale** | Transformer attention shows recency bias — the last tokens before the user message receive the highest weight on the next-token decision (which is the tool-call decision). Placing PROCESS instructions last means they are always the closest context to the generation point regardless of how large the thumbdown injection grows. The "do NOT batch tool calls" constraint specifically targets the premature-batching failure mode observed in Run 3 Iteration 1. |
| **Impact** | Prompt evolution tracked in `Prompt_Changes.txt`. Final version adds OUTPUT FORMAT constraints (plain prose, no headings, max 400 words, citations inline only, no trailing citation lists) to prevent the 11,133-char repetition-degeneration failure observed when context dilution caused the model to vomit citations in a loop. |

## ADR-013 — Thumbdown Persistence & Failed Variants Blocklist

| Field | Detail |
|---|---|
| **Decision** | Persist user thumbdowns to `user_thumbdowns.json` and all query variants that appeared in a thumbdown session to `failed_variants.json`; inject both into the system prompt on subsequent queries |
| **Date** | May 2025 |
| **Context** | Users could flag bad answers via thumbs-down. Without persistence, the agent would re-generate the same bad answer on the next identical query. The first design only blocked the final answer text; later analysis showed the agent was also reformulating queries into the same variants that had previously failed. |
| **Options Considered** | **No persistence** (agent learns nothing from thumbdowns within a session) · **Persist final answer only** (blocks exact answer re-generation) · **Persist all query variants from the failing session** (blocks the entire search trajectory) |
| **Chosen Solution** | Persist both: `user_thumbdowns.json` (full thumbdown records with feedback text, query, answer, and all variants with their retrieved chunks) and `failed_variants.json` (normalized query → list of known-bad answers). On each new query, all variants from prior thumbdown sessions are expanded into the `blocked` list and injected into the system prompt. |
| **Rationale** | Blocking only the final answer was insufficient — the agent was reformulating into the same search angles that had already failed, wasting retrieval budget. By blocking all variant queries from a thumbdown session, the agent is forced to explore genuinely different angles on subsequent attempts. Minimum feedback length of 10 chars (`MIN_FEEDBACK_LEN`) prevents empty/accidental thumbdowns from polluting the blocklist. |
| **Impact** | `feedback_store.py` manages both stores. `mark_last_bad()` rewrites the last JSONL record and updates `failed_variants.json`. The agent's `_build_system_prompt()` injects up to the most recent thumbdown records. Cap on thumbdown injection (most recent 2) recommended to prevent prompt bloat beyond the 8B model's instruction-following ceiling (~1,800 tokens). |

## ADR-014 — Provider-Agnostic Design via OpenAI-Compatible API

| Field | Detail |
|---|---|
| **Decision** | Design the entire LLM stack to be provider-agnostic via OpenAI-compatible REST API; resolve endpoint and credentials inside `main()` after `load_dotenv()`, never at module scope |
| **Date** | May 2025 |
| **Context** | Mid-project, development shifted to testing with local TGI (HuggingFace Text Generation Inference) servers. The prior design had hardcoded model names and resolved `OPENAI_BASE_URL` at module import time (before `load_dotenv()` ran), causing silent fallback to OpenAI's real endpoint and 401 errors with the custom key. A separate bug caused 404 errors when `CUSTOM_API_BASE` was set to the full chat-completions URL (e.g., `.../v1/chat/completions`) — LangChain appended `/chat/completions` again, producing double-path 404s. |
| **Options Considered** | **Module-scope constant resolution** (simple, breaks with late `load_dotenv()`) · **`main()`-scope resolution** (correct, verbose) · **`lazy_import` or property pattern** (overcomplicated) |
| **Chosen Solution** | All three `ChatOpenAI` instances (`llm`, `merge_llm`, `judge_llm`) resolve `api_key`, `base_url`, and `model` inside `main()` immediately after `load_dotenv()`. `_normalize_openai_base_url()` helper strips trailing `/chat/completions` (and `/completions`, `/responses`) from `CUSTOM_API_BASE` before passing to `ChatOpenAI`. Startup log line `[LLM] endpoint=... model=...` acts as a sanity check. |
| **Rationale** | The `load_dotenv()`-before-resolution ordering is a classic Python gotcha. The normalization helper is idempotent — already-correct root URLs pass through unchanged. Making the startup endpoint visible in logs eliminates silent misdirection to wrong providers. |
| **Impact** | Compatible with Groq, OpenAI, Together AI, Ollama, vLLM, and any OpenAI-spec server. The `llm_http_fix.py` module (see ADR-019) extends compatibility to TGI servers with non-spec-compliant tool-call response formats. `CUSTOM_API_KEY` and `CUSTOM_API_BASE` environment variables allow hot-swapping providers without code changes. |

## ADR-015 — Chunking Parameters: 1000 chars / 200 overlap

| Field | Detail |
|---|---|
| **Decision** | Set chunk size to 1000 characters with 200-character overlap using `RecursiveCharacterTextSplitter` |
| **Date** | April 2025 |
| **Context** | Document chunking parameters directly affect retrieval precision (too large = low precision, too small = broken context) and the NAC neighbor-merging strategy (consecutive chunks need overlap to be safely re-mergeable). |
| **Options Considered** | **500/100** (smaller, higher precision, more chunks) · **1000/200** (standard RAG configuration, balances precision and context) · **2000/400** (larger chunks, fewer splits, lower precision) · **Semantic splitting** (split on sentence/paragraph boundaries — more complex) |
| **Chosen Solution** | 1000 chars / 200 overlap, `RecursiveCharacterTextSplitter` from LangChain |
| **Rationale** | 1000-char chunks are the de facto RAG standard for PDFs with structured paragraphs — well-matched to the document types in the corpus. Smaller chunks improve precision but can break mid-sentence for structured technical content. The 200-char overlap ensures consecutive chunk pairs share enough context for NAC to safely merge them without losing facts at boundaries. Batch size tuned to 128–256 for GPU embedding (RTX 5050, 8GB VRAM) — beyond 512 there are diminishing returns with `all-MiniLM-L6-v2`. |
| **Impact** | `chunk_seq` metadata field (integer index within a document) is stored per chunk to support NAC's consecutive-chunk detection. Changing chunk parameters requires full re-ingestion. |

## ADR-016 — Dual Collection Strategy: `documents` + `learned_qa`

| Field | Detail |
|---|---|
| **Decision** | Maintain two separate ChromaDB collections: `documents` (source corpus) and `learned_qa` (distilled Q&A pairs from self-learning) |
| **Date** | April 2025 |
| **Context** | Self-learning via memory injection (ADR-008) required a place to store distilled Q&A pairs that is searchable at query time. The alternatives were: adding synthetic Q&A pairs back into the main `documents` collection (contamination risk), storing them in a separate file (not queryable via embedding search), or a dedicated collection. |
| **Options Considered** | **Single `documents` collection** (simpler, risk of contaminating source corpus with synthetic content) · **Flat file store** (not retrievable via similarity search) · **Separate `learned_qa` collection** (clean separation, independently queryable) |
| **Chosen Solution** | Separate `learned_qa` ChromaDB collection; retriever queries both and merges results |
| **Rationale** | Source documents and synthetic Q&A pairs have different provenance, different update cycles, and different trust levels. Keeping them separate allows per-collection tuning (e.g., different `top_k` for each). Deduplication by SHA-256 content hash prevents the same interaction from being distilled multiple times with slightly different wording. |
| **Impact** | `retriever.py` implements hybrid retrieval across both collections. `self_learner.py` manages the `learned_qa` collection. `SelfLearner.run_distillation()` upserts by content hash. Bug identified (see `Bugs.md`): `load_good(limit=10)` was returning already-distilled interactions, causing re-distillation — fix requires a watermark or `distilled: true` flag per JSONL record. |

## ADR-017 — LLM-Based Compression Faithfulness Guard (retention ratio ≥ 0.35)

| Field | Detail |
|---|---|
| **Decision** | Add a faithfulness guard to LBC: if the compressed chunk's length is less than 35% of the original, reject the compression and keep the original |
| **Date** | May 2025 |
| **Context** | LLM-Based Compression (LBC) can over-aggressively summarize chunks, dropping key facts or substituting paraphrased claims that change meaning. A hallucinated compression that replaces a specific measurement with a vague generalization is worse than no compression at all. |
| **Options Considered** | **No guard** (accept all LBC output — maximum compression, maximum hallucination risk) · **Retention ratio threshold** (reject outputs with retention < X% — simple, adjustable) · **Full faithfulness check via judge LLM** (most accurate, adds latency and cost per chunk) |
| **Chosen Solution** | Retention ratio threshold of 0.35 (if `len(compressed) / len(original) < 0.35`, keep original). Applied in `llm_based_compression()` in `context_compression.py`. |
| **Rationale** | A retention ratio below 35% is a strong signal of over-summarization — legitimate compression of a 1000-char chunk should not produce fewer than 350 chars of substantive content. The threshold is a fast, deterministic heuristic that adds zero latency. For chunks where LBC would over-compress, keeping the original is always safer than accepting a potentially hallucinated summary. |
| **Impact** | ~27.6% average context reduction measured in testing (chunks that pass the guard). Chunks rejected by the guard are kept as-is and counted as `skipped` in the compression log. The judge LLM is used for the merge validator (ADR-011) but not per-chunk LBC (too expensive). |

## ADR-021 — Centralised Configuration & Feature-Flag Gates (`config.py` + `prompts.py`)

| Field | Detail |
|---|---|
| **Decision** | Move every pipeline constant into a single `config.py` module, every prompt string into a single `prompts.py` module, and add 18 boolean feature-flag toggles in `config.py` that gate optional pipeline stages |
| **Date** | 2026-06-09 |
| **Context** | Constants were scattered across at least seven modules (`agent_query.py`, `tools.py`, `context_compression.py`, `ingest.py`, `vector_store.py`, `feedback_store.py`, `retriever.py`) — tuning any single threshold required hunting for it across files. Prompts were embedded inline in each module, so a prompt revision required editing the module that used it. There was also no way to disable individual pipeline stages (sub-query generation, NAC, DC, LBC, validators, repair tiers, draft, quality check, distillation) without commenting out code — making it impossible to measure each stage's contribution to answer quality or latency. |
| **Options Considered** | **Status quo** (constants per-module, no toggles — simplest but unmaintainable) · **Centralise constants only** (one `config.py`, but pipeline stages still hard-wired on) · **Centralise constants + add boolean toggles** (single source of truth + per-stage on/off) · **Full DI/factory pattern** (each stage a swappable class — overkill at this scale) · **CLI flags / environment variables** (verbose at the callsite, not durable across runs) |
| **Chosen Solution** | Two modules: `config.py` holds all constants and 18 named boolean feature flags (`ENABLE_*`); `prompts.py` holds every prompt string plus the `_THIN` / `_THICK` log separators. Every module that previously hard-coded a constant or a prompt now imports it from these modules. Gateable code paths are guarded by `if ENABLE_…:` checks; the per-stage `_OUTPUT_FIX` flags AND the global `ENABLE_GLOBAL_LLM_OUTPUT_FIX` master switch must both be on for an output-fix pass to run. |
| **Rationale** | Single-source-of-truth for both constants and prompts means tuning is one-file. Boolean feature flags make the pipeline explicitly composable — the same code path can run with full validation + repair on top, or stripped down to bare retrieval + answer, just by editing flags. This is the prerequisite for ablation testing (see ADR-022). The master `ENABLE_GLOBAL_LLM_OUTPUT_FIX` provides a kill-switch independent of the per-stage flags, useful when comparing "with vs without any repair anywhere". Keeping prompts in their own module (rather than co-located with constants) prevents `config.py` from becoming a 500-line wall of strings. |
| **Impact** | `agent_query.py`, `validators.py`, `context_compression.py`, and `self_learner.py` all import from `config` and `prompts` instead of holding local copies. The flag wiring is partial right now: `ENABLE_AUTO_DISTILLATION` is defined and toggled by `run_combinations.py` but `agent_query.py` never reads it (Bugs.md BUG-021), and the validators' "flag off" fall-through branch crashes (Bugs.md BUG-020). Both will be fixed in the next pass. Beyond this, the centralisation is foundational for ADR-022 (ablation harness) and for future per-environment overrides (e.g., dev vs prod constants via `os.getenv`). |

## ADR-022 — Progressive Flag-Ladder Ablation Harness (`run_combinations.py`)

| Field | Detail |
|---|---|
| **Decision** | Build a deterministic progressive-ladder test harness that runs the same query 10 times against `agent_query.py`, stepping evenly from all-18-flags-OFF to all-ON, with one log file per run |
| **Date** | 2026-06-09 |
| **Context** | The 18 feature flags introduced in ADR-021 made every stage of the pipeline optional, but without a structured way to exercise combinations, the flags were a knob without a measurement. Open questions included: which stages contribute most to answer quality? which add the most latency? which combinations crash? are any stages currently no-ops? A manual run-per-combination approach (2^18 = 262,144 combinations) is intractable; full coverage is unnecessary; what's needed is a representative sweep that's reproducible across days and obvious to read in the logs. |
| **Options Considered** | **Random combinations** (cheap but irreproducible — same bug could appear differently across days) · **Full Cartesian sweep** (262,144 runs — intractable) · **One-stage-on-at-a-time** (18 runs — measures each stage in isolation but misses interaction effects) · **Progressive ladder all-OFF → all-ON** (N runs, deterministic order, exposes cumulative effects and ordering-dependent crashes) · **Latin-hypercube / fractional factorial** (statistically efficient but harder to read in logs) |
| **Chosen Solution** | Progressive ladder of N=10 runs (configurable via `--runs`). Step 0 is all-OFF, step N-1 is all-ON, intermediate steps enable `round(step * 18 / (N - 1))` flags in fixed left-to-right `BOOL_FLAGS` order. Each run patches `config.py` in-place by regex, subprocesses `agent_query.py` with the query piped via stdin (`PYTHONUTF8=1` set), captures stdout + stderr, restores `config.py` in a `finally`, and writes one timestamped log per run to `app/run_logs/run_NNN_<ts>.txt`. Logs include the full flag combo at the top so each run is self-describing. |
| **Rationale** | Determinism wins over coverage at this stage. The progressive ladder makes it obvious from the log filenames alone which flags are on at each step, so a crash at run 4 immediately points to the flag(s) enabled between run 3 and run 4. The fixed `BOOL_FLAGS` order means the same run-N reflects the same configuration across days, which is essential for tracking regressions. Subprocess isolation (rather than in-process flag mutation) means a crash in one run cannot pollute state for the next — a critical property for the validator-crash class of bugs uncovered by the very first ladder run. |
| **Impact** | First 10-step ladder run uncovered two bugs: validators crash when their `*_OUTPUT_FIX` flag is off (BUG-020), and `ENABLE_AUTO_DISTILLATION` is wired but never read (BUG-021). Run 10 (all-ON) took ~5.7 hours, establishing a latency upper bound — the per-stage validators and repair tiers stack up significantly when all enabled. The harness will be re-used after each bug fix to confirm the fix lands at the right step in the ladder and to track total-time deltas as repair tiers are tuned. |

## ADR-024 · Separate Output Repair From Structured Parsing

| Field | Detail |
| --- |
| **Decision** | Even when LLM output repair is disabled, all structured responses must still be parsed into Python objects through `_parse_to_python()` before entering downstream logic. |
| **Date** | 2026-06-10 |
| **Context** | The new configuration architecture introduced both a global output-repair flag and stage-specific output-repair flags. Dry-run testing revealed that many validators and compression stages implicitly assumed that `fix_llm_output()` had already converted responses into structured objects. When repair was disabled, raw strings reached downstream code that immediately called `.get()`, iterated results, or expected dictionary schemas. This caused multiple crashes despite the configuration combination being theoretically valid. |
| **Options Considered** | **Keep repair mandatory everywhere** (simplest implementation but makes output-repair flags meaningless) · **Allow raw strings when repair is disabled** (breaks downstream contracts and creates inconsistent behavior) · **Maintain a separate lightweight parsing layer** (preserves structured contracts while allowing repair experimentation) |
| **Chosen Solution** | Route all non-repaired structured outputs through `_parse_to_python()`. `fix_llm_output()` remains responsible for malformed-output recovery, while `_parse_to_python()` handles normal JSON-to-Python conversion when repair is disabled. |
| **Rationale** | Output repair and structured parsing solve different problems. Repair addresses malformed LLM output; parsing converts valid structured data into application objects. Disabling one should not implicitly disable the other. Maintaining a consistent downstream contract simplifies every validator and compression stage. |
| **Impact** | Eliminated multiple crashes uncovered by `run_combinations.py`. Output-repair flags now genuinely represent optional behavior instead of hidden architecture-breaking switches. Enabled reliable testing of repaired vs non-repaired execution paths. |

## ADR-026 · Implement Exponential Backoff With Retry-After Support

| Field | Detail |
| --- |
| **Decision** | Introduce exponential backoff, jitter, and provider-supplied `retry-after` support for all transient LLM rate-limit failures. |
| **Date** | 2026-06-10 |

| **Impact** | Improved reliability during heavy dry-run execution, reduced repeated 429 failures, introduced predictable recovery behavior, and added dedicated automated tests covering retry-after handling, backoff growth, and retry exhaustion scenarios. |

## ADR-029 · Two-Track Retrieval Architecture: Keep `documents` and `learned_qa` Separate End-to-End
 
| Field | Detail |
|---|---|
| **Decision** | Maintain `documents` and `learned_qa` as two independent retrieval channels throughout the entire pipeline (retrieval, validation, dedup/merge, accumulation, compression) and combine them only at the LLM context boundary. |
| **Date** | 2026-06-11 |
| **Context** | The original architecture (ADR-016) created two ChromaDB collections but merged their results into a single ranked stream inside `RAGRetriever.retrieve()` before any downstream code saw them. Stress-test analysis identified this as a structural risk: distilled QA pairs and source documents have different provenance, different trust levels, and different conflict semantics, but merging them at retrieval erased the distinction. Source-document chunks could outrank learned-QA chunks that should have taken precedence; conversely, a stale or low-quality learned-QA entry could displace the correct source-document chunk. Validators, the dedup/merge pass, and the compression pipeline all saw mixed lists, so the agent had no place where it could express "prefer learned QA on conflict." The single `accumulated_chunks` state encoded the same flaw in the orchestrator. |
| **Options Considered** | **Status quo — single merged stream** (simplest, but provenance is lost). · **Score boost for learned QA at the merger** (cheap, but score arithmetic is fragile and doesn't survive validators dropping chunks). · **Soft prompt-only precedence** (instruct the LLM to prefer learned QA — was already in place but couldn't be enforced since the LLM sees only one labelled list). · **Two independent tracks end-to-end** (the chosen option — provenance, validation, compression, and persistence all preserve the track distinction; precedence is enforced by ordering + explicit conflict rule at the answer-context boundary). |
| **Chosen Solution** | `RAGRetriever.retrieve_separate()` queries the two collections independently and returns `{"documents": [...], "learned_qa": [...]}`. Agent state holds `accumulated_document_chunks` and `accumulated_learned_qa_chunks`. `_validate_track()`, `_accumulate_track()`, and `_compress_track()` helpers run the per-track pipeline twice without cross-track sort/dedup/merge. The two lists combine only inside `format_precedence_context_for_llm()` at the LLM context boundary, and they persist as separate fields in interaction records, thumbdown variants, and distillation inputs. |
| **Rationale** | Provenance survives validation and compression intact, so precedence can be enforced by the architecture rather than by hoping the LLM honors a prompt rule. Bugs that depend on one track polluting the other (e.g. learned-QA scores filtered out by a documents-tuned threshold, or a documents merge dropping a learned-QA chunk) become impossible by construction. The cost is duplicated validator/compressor calls per query — acceptable given how cheap the validator calls are relative to the agent's overall token budget. |
| **Impact** | Closed the long-standing architectural gap documented in `Architecture.md`. Required coordinated changes across `retriever.py`, `tools.py`, `agent_query.py`, `context_compression.py`, `feedback_store.py`, `self_learner.py`, `config.py`, and `prompts.py`, plus the new `learned_qa_store.py`. Enabled ADR-030 (precedence rule) and ADR-031 (cosine-canonical learned-QA collection). Exposed a follow-on cluster of issues that the existing single-stream architecture had hidden — see `Bugs.md` BUG-031..BUG-037. |

## ADR-030 · Learned-QA Precedence at Conflict; Combine Only at the Answer-Context Boundary
 
| Field | Detail |
|---|---|
| **Decision** | When document and learned-QA chunks would carry conflicting information, the final answer must prefer the learned-QA response. The rule is implemented by ordering the two sections in the LLM context (learned QA first), labelling them `HIGH PRIORITY` and `SECONDARY`, and prepending an explicit `[CONFLICT RESOLUTION RULE]` header. |
| **Date** | 2026-06-11 |
| **Context** | Once ADR-029 separated the two tracks, the question of how to express precedence became architectural rather than implicit. Learned-QA pairs are produced by the self-learner from interactions that already passed quality checking, so they are usable evidence about how the user wants questions answered. Source documents are the ultimate ground truth for factual claims, but they may be stale, ambiguous, or contradicted by a more recent learned correction. The system needs a deterministic rule for the conflict case — not a heuristic per-query score comparison, which is fragile. |
| **Options Considered** | **Documents-first** (default to source as ground truth — but defeats the point of self-learning, which is to capture corrections and preferred phrasings). · **Score-weighted blending** (compute a confidence per track and blend — adds latency, complicates explainability, and the per-track scores aren't directly comparable across collections anyway). · **Final-answer validator that rejects answers contradicting learned QA** (most rigorous but doubles the judge cost and adds a new failure mode). · **Prompt-level precedence rule + ordered sections** (the chosen option — cheap, explicit, and the LLM's instruction-following on conflict-resolution rules is reliable in observed runs). |
| **Chosen Solution** | `format_precedence_context_for_llm(learned_qa_chunks, document_chunks)` is the single point where the two tracks are combined into LLM-consumable text. It emits, in fixed order: a `[CONFLICT RESOLUTION RULE]` instruction, a `[LEARNED QA CONTEXT - HIGH PRIORITY]` section, then a `[DOCUMENT CONTEXT - SECONDARY]` section. Empty tracks are omitted. The same function is used for the DRAFT context and (currently) for the JUDGE context. The agent role/process prompts in `prompts.py` repeat the precedence rule in retrieval, compression, drafting, judging, and final-answer instructions, so the rule is reinforced wherever the LLM might be tempted to override it. |
| **Rationale** | Conflict precedence is a property of the answer, not of the retrieval scoring, so the right place to express it is the answer context — where the LLM actually generates. Prompt-level rules at a single combine point are auditable: one function call, one rule string, one ordering. Repeating the rule across role/process prompts hedges against the model attending to one phase's instructions and ignoring another's. |
| **Impact** | Eliminates the ambiguity that existed before separation, where merge-order in the retrieval ranker effectively chose precedence by accident. Empirically untested for true conflict cases in the dry runs to date (no document-vs-learned conflict has been observed), so the rule is correctly instructed but not yet proven under real conflict pressure. Final-answer generation is not currently re-validated for conflict-precedence compliance — recorded as `BUG-032`, with a planned final-answer validator as the remediation. |

## ADR-031 · Canonical Cosine `learned_qa` Collection With Safe L2→Cosine Migration
 
| Field | Detail |
|---|---|
| **Decision** | Funnel all access to the `learned_qa` Chroma collection through a single factory (`learned_qa_store.get_or_create_learned_qa_collection`) that guarantees the collection uses `hnsw:space = cosine`, and that safely migrates any pre-existing L2 collection in place with snapshot/restore/rollback. |
| **Date** | 2026-06-11 |
| **Context** | Dry-run inspection showed that the live `learned_qa` collection was persisted with the Chroma default L2 distance, while `documents` was created with cosine (per ADR-002 / Research topic 13). Both collections were filtered with the same `score_threshold = 0.5` and ranked by `similarity_score = 1 - dist`. On unit-normalized vectors that formula has different semantics for cosine and L2, so learned-QA results were ranked and filtered on incompatible score arithmetic — making the precedence rule from ADR-030 unsafe in practice. A second contributing problem was startup ordering: `agent_query.py` created the collection without `hnsw:space` (defaulting to L2) before `self_learner.py` requested cosine on the same name, so the cosine metadata was effectively a no-op against an already-L2 collection. Chroma does not migrate distance metric on metadata change — the underlying HNSW index has to be rebuilt. |
| **Options Considered** | **Delete and re-ingest** (correct but destroys ~374 distilled QA pairs — high cost and undermines the point of self-learning). · **Live with mixed metrics and tune thresholds per collection** (complicates the precedence rule and the validators). · **Rename the existing collection and create a fresh cosine one without restore** (loses data). · **Snapshot → recreate → restore → verify → swap atomically, with rollback** (the chosen option — zero data loss, idempotent on already-cosine collections, fails closed on any error). |
| **Chosen Solution** | `learned_qa_store.get_or_create_learned_qa_collection(client, name, batch_size)`. If the collection doesn't exist it is created with canonical cosine metadata. If it exists and is already cosine it is returned as-is. If it exists with any other space, the helper snapshots every record (ids + embeddings + metadatas + documents) in `batch_size` pages, renames the original to a UUID-suffixed backup, creates a new collection at the canonical name with cosine metadata, restores the snapshot, verifies that `count() == len(records)`, and only then deletes the backup. Any exception triggers rollback: the partial replacement is deleted (if it was created), the backup is renamed back to the canonical name, and the original error is re-raised. The factory is wired into both `agent_query.py` startup and `self_learner.py`, so there is only one canonical collection handle in the system. |
| **Rationale** | Production data must not be lost during a metric change. Two-phase migration with a verified count and rollback is the standard pattern. Centralising collection creation also eliminates the original startup-ordering bug — there is no longer any path that creates the collection at any other distance. |
| **Impact** | Live migration successfully moved 374 L2 entries to 374 cosine entries with all IDs preserved. The precedence rule from ADR-030 now operates on comparable score arithmetic. Reduced surface area: only `learned_qa_store.py` knows how the learned-QA collection is created; every other module imports the factory. Regression test added in `test_retrieval_separation.py` for the L2→cosine migration path. |

## ADR-032 · Centralised, Config-Controlled `RETRIEVAL_TOP_K` and `RETRIEVAL_TOP_L`; LLM No Longer Sets `top_k`
 
| Field | Detail |
|---|---|
| **Decision** | Move retrieval-depth control out of the `retrieve_documents` tool schema and into two configuration constants in `config.py`: `RETRIEVAL_TOP_K` for the `documents` collection and `RETRIEVAL_TOP_L` for the `learned_qa` collection. The LLM cannot override either at call time. |
| **Date** | 2026-06-11 |
| **Context** | Before this change, `top_k` was a parameter on the `retrieve_documents` tool schema. The 8B model would set it idiosyncratically — sometimes 3, sometimes 10 — which made retrieval depth a function of the model's mood rather than an operating parameter. Stress-test analysis flagged this as one of the causes of unpredictable over-retrieval (see Research topic 28): in worst-case combinations of `MAX_TOTAL_RETRIEVALS` and a model-chosen `top_k`, accumulated raw chunks could approach 100 before compression. The two-track architecture also required a second depth control for the learned-QA channel, which the prior single-`top_k` schema had no way to express. |
| **Options Considered** | **Keep `top_k` on the tool schema, add `top_l` too** (preserves the same root problem and adds another knob for the model to misuse). · **Drop `top_k` from the schema, replace with a single config constant** (was the first iteration during this work, but the new two-track architecture demanded two distinct constants). · **Two config constants, schema with no depth parameters at all** (the chosen option — `RETRIEVAL_TOP_K` for documents, `RETRIEVAL_TOP_L` for learned QA, both env-overridable, neither exposed to the LLM). · **Adaptive top-k based on prior retrieval quality** (interesting but premature — there's no signal yet to drive it). |
| **Chosen Solution** | `config.py` declares `RETRIEVAL_TOP_K = int(os.getenv("RETRIEVAL_TOP_K", "5"))` and `RETRIEVAL_TOP_L = int(os.getenv("RETRIEVAL_TOP_L", "5"))`. `RAGRetriever.retrieve_separate()` consumes both as defaults. The `retrieve_documents` tool schema and docstring no longer expose any depth parameter. Working defaults are 5/5; both are env-overridable for ablation runs. |
| **Rationale** | Operating parameters belong to operators, not to a tool-using model. Centralising them in `config.py` makes them visible in ladder runs, ablation harnesses, and reproducibility audits, and removes a class of "the model retrieved too many chunks" variance from the dry-run logs. Two separate constants are needed because the two collections serve different roles — small numbers of high-precedence learned QA, larger candidate pools of source documents — and may diverge as tuning continues. |
| **Impact** | Retrieval depth is now deterministic per run. Ablation runs via `run_combinations.py` can sweep over `RETRIEVAL_TOP_K` and `RETRIEVAL_TOP_L` independently. Tool-call surface area reduced — one fewer parameter for the model to get wrong. Regression test added in `test_retrieval_separation.py` covering configured per-track limits. |

## ADR-033 · Centralised Logging Via `logger_config.py` (No Per-File Logging Setup)

| Field | Detail |
|---|---|
| **Decision** | Replace every `print()` / `file.write()` diagnostic statement across the project with `logging` module calls routed through a single configuration module (`logger_config.py`). Every module imports `logging` and does `logger = logging.getLogger(__name__)` at module scope; configuration (handlers, levels, formatters, file targets) lives only in `logger_config.py` and is applied once per process via an idempotent `setup_logging()` call at each entry point. |
| **Date** | 2026-06-15 |
| **Context** | Before this change, the project produced ~370 unstructured `print()` calls across 14+ production modules, plus a handful of direct `open()`/`write()` blocks (notably for `llm_data_check.txt` and `llm_json_tries.txt` from `fix_llm_output.py`). Output had no level filtering, no timestamps, no per-module attribution, and no way to retain a full run's trace short of capturing terminal scrollback. Repeated dry runs were already losing diagnostic information when the operator forgot to redirect stdout or the batch-run UI overwrote earlier output. Two organisational approaches were on the table: configure `logging` per-module (each file builds its own handler and formatter) or configure it once centrally and have each module just `getLogger(__name__)`. |
| **Options Considered** | **Status quo — keep `print()` everywhere** (simplest, but no level filtering, no retained traces, and the diagnostic file writes in `fix_llm_output.py` were already inconsistent with that pattern). · **Per-module `logging.basicConfig` calls** (decentralised, but each file would duplicate handler lists, formatters, and file paths — the configuration footprint grows with every new module). · **Central `logger_config.py` module with one `setup_logging()` function** (the chosen option — configuration lives in one place; each module's only required change is `print(x)` → `logger.info(x)`). · **Structured-logging library (`structlog`, `loguru`)** (more features but adds a non-stdlib dependency and a learning curve for diagnostic-quality output that stdlib `logging` already produces). |
| **Chosen Solution** | New module `logger_config.py` exporting `setup_logging(log_dir, app_name, console_level)`. The function is idempotent via a `_CONFIGURED_ATTR` flag on the root logger so it's safe to call from any of the entry points (`agent_query.py`, `ingest.py`, `run_batch.py`, `query.py`, `test_output_fixes.py`, `test_llm_caller.py`, `run_combinations.py`, top-level `main.py`). It installs one console handler at INFO and one per-run debug file handler at DEBUG (`{app_name}_{YYYYMMDD_HHMMSS}.debug.log` under `run_logs/`). Diagnostic loggers `llm_data_check` and `llm_json_tries` are configured with `propagate=True` so their output reaches both the console at effective level and the debug file at DEBUG. A custom `_DynamicStdoutHandler` re-points to `sys.stdout` at emit time so batch-run tee/redirect setups don't lose console output. Every module does `logger = logging.getLogger(__name__)` at module scope. `print()` is preserved exclusively for interactive REPL prompts, the batch-run progress UI, the test-console formatter, and JSON/JSONL data writes. |
| **Rationale** | A central setup module is the minimum-code-change route to gaining timestamps, per-module attribution, level filtering, and retained per-run trace files. Per-file setup would have multiplied the configuration footprint by the number of modules and required updating each module again whenever a handler or formatter changed. `getLogger(__name__)` is the stdlib-recommended pattern and gives every log line a free module-name tag without any per-module configuration. The choice to drop the originally-planned separate `.error.log` came from a dry-run observation: errors are already visible on console at ERROR level *and* captured in the per-run debug file, so the dual-file split doubled the log-management surface for no extra signal. The choice to keep DEBUG out of the console came from a subsequent observation that third-party libraries (`httpcore`, `httpx`, `groq._base_client`) flood the terminal with thousands of DEBUG lines per query — useful in a file, unusable on stdout. |
| **Impact** | One new module (`logger_config.py`), one call site per entry point (`setup_logging(app_name="…")`), and a mechanical `print()` → `logger.<level>()` conversion across ~14 production modules. Per-run debug files now retain the full DEBUG trace (including third-party HTTP traffic and Groq SDK retry timings) so dry-run analysis no longer depends on terminal scrollback. Surfaced two bugs during rollout — `BUG-038` (mechanical conversion silently dropped some print/write blocks) and `BUG-039` (severity-level mismatches inherited from the conversion). Both closed same-day. The original `agent_query.error.log` and `agent_query.debug.log` files from the brief dual-file design are now stale and can be deleted. Future work: an audit of remaining `print()` callsites in `run_batch.py` and `query.py` to confirm the preserved ones are genuinely user-facing rather than diagnostic. |

## ADR-034 · Defer LangGraph Adoption; Keep Hand-Rolled State Machine

| Field | Detail |
|---|---|
| **Decision** | Continue with the hand-rolled phase state machine in `agent_query.py` for the foreseeable future. Do not port the pipeline to `LangGraph`. Leave the existing `langgraph` declaration in `requirements.txt` as a transitional artefact until a follow-on cleanup pass either removes it (if no migration is planned in the near term) or imports it (if a future ADR reverses this decision). |
| **Date** | 2026-06-15 |
| **Context** | The pipeline has grown into a multi-phase loop (RETRIEVE → COMPRESS → DRAFT → JUDGE, with iteration budgets, retry paths, thumbdown injection, two-track per-stage handling, and protocol-enforcement nudges). LangGraph is the natural off-the-shelf framework for this kind of workflow: it provides a typed `StateGraph`, named nodes and conditional edges, native checkpointing for resume-after-failure, parallel fan-out branches with automatic merge, human-in-the-loop pause/resume, and time-travel inspection of past checkpoints. The question was whether the current orchestrator's complexity has crossed the threshold where adopting LangGraph would pay off, or whether the hand-rolled state machine is still cheaper to maintain than the framework migration would cost. |
| **Options Considered** | **Port `agent_query.py`'s state machine to a LangGraph `StateGraph` now** (clean architecture, native parallel branches, native checkpointing, but a substantial rewrite of all phase orchestration, protocol enforcement, two-track helpers, and the test harnesses, with no guaranteed runtime speedup). · **Adopt LangGraph only for the parts that benefit most** (parallel sub-query retrieval, parallel per-track validation — but partial adoption means two orchestration patterns coexist in the codebase). · **Build a minimal in-house checkpointing layer** (JSON or SQLite checkpoint per phase boundary — gets the resume-after-failure benefit without LangGraph). · **Defer; keep the hand-rolled state machine** (the chosen option — the present orchestrator is already working, well-traced under the new logging architecture, and the remaining pipeline issues — `BUG-031..037` from the post-separation dry run — are about correctness, not orchestration). |
| **Chosen Solution** | Defer LangGraph adoption. The state machine in `agent_query.py` remains the orchestrator. The `langgraph` package stays in `requirements.txt` as a declared-but-unused dependency until a follow-on cleanup pass either removes it or a future ADR reverses this decision. |
| **Rationale** | LangGraph does not make any individual node faster — its real value is in *parallel fan-out*, *conditional early exit*, *durable checkpoint recovery*, and *human-in-the-loop pause/resume*. For this project's specific phase sequence, the compression/draft/judge tail is strictly sequential (NAC must finish before DC; DC before LBC; LBC before draft; draft before judge) so the framework cannot parallelise the longest path. The genuine parallel opportunities (multiple sub-queries during RETRIEVE; per-track validation during VALIDATE) would benefit from concurrency but can be implemented with `asyncio.gather` or a thread pool without the architectural cost of a framework port. Durable checkpoint recovery requires a persistence backend (SQLite, Postgres, JSON files) that the project doesn't currently use; `InMemorySaver` would only recover within a live process, which the current `try/except` retry paths and the exponential-backoff logic in `llm_caller.py` (ADR-026) already handle for the dominant failure modes (Groq 429, transient HTTP errors). The framework's value rises sharply once the orchestrator includes human-in-the-loop review steps, long-running workflows that may span deployment cycles, or genuinely parallel retrieval strategies — none of which are present today. |
| **Impact** | No code changes today. The decision is documented so that future contributors don't re-litigate the same evaluation. `langgraph` remains a declared dependency until a follow-on cleanup removes it. The decision is explicitly revisitable: when (a) parallel sub-query retrieval is implemented, or (b) human-in-the-loop review enters the pipeline, or (c) long-running workflows that must survive process restarts become a requirement, this ADR should be re-opened. |

## ADR-038 · Split `generate_answer` Into `generate_draft` / `check_answer_quality` / `auto_distillation`, Mirroring `app/agent_query.py`'s Budget-Gated JUDGE Loop

|---|---|

| **Context** | With `app_workflow/` having reached rough feature parity with `app/` after the June 17–19 build-out, a direct timing and answer-quality comparison was needed. Both projects define a bare `config` module at their respective roots, so importing both into a single Python process causes module-name collisions — `app.config` and `app_workflow.config` cannot coexist as the same imported name without one shadowing the other when both are added to `sys.path` simultaneously. |
| **Options Considered** | **In-process comparison** (import both pipelines into one script) — simplest code, but blocked by the `config` module collision described above; would require renaming or restructuring one project's modules just for benchmarking, which wasn't acceptable. · **Subprocess isolation per system** (the chosen option) — each worker subprocess only puts its own project's directories on `sys.path`, so no collision occurs; results are passed back via sentinel-delimited stdout (`%%BENCH_ELAPSED%%=`, `%%BENCH_ANS_START%%` / `%%BENCH_ANS_END%%`) parsed by the orchestrator. · **Two separate benchmark scripts, one per system** — avoids the collision without subprocesses, but loses the single-file, single-invocation convenience and makes the side-by-side average comparison harder to keep in sync. |
| **Chosen Solution** | One `benchmark.py` that doubles as orchestrator and worker: `python benchmark.py workflow` or `python benchmark.py agent` runs only the requested system 3 times via `subprocess.run([sys.executable, "benchmark.py", "--_mode=…", QUERY])` and **appends** a self-contained results block to `benchmark_results.txt` (revised from an initial version that ran both systems automatically and overwrote the file). A 2-minute `time.sleep()` was inserted between consecutive runs within one invocation to let Groq's per-minute rate limits recover. |
| **Rationale** | Subprocess isolation is the only option that avoids the `config` module collision without restructuring either production project, and keeps the benchmark tool fully external to both pipelines (no changes needed inside `app/` or `app_workflow/` to support it). Append-mode output lets `python benchmark.py workflow` and `python benchmark.py agent` be run independently (e.g. on different days) while still building up a comparable `benchmark_results.txt`. |
| **Impact** | `benchmark.py` exists as a 321-line standalone tool at the project root; neither `app/` nor `app_workflow/` were modified to support it. Despite the 2-minute inter-run delay, side-by-side runs of both pipelines still triggered Groq `429` rate-limit retry storms (confirmed in `agent_query_20260619_185829_debug.log` and `rag_langgraph_20260619_183828_debug.log`), making wall-clock comparisons unreliable for today's session. No further automated-benchmark work was done after this; manual pipeline-by-pipeline checking with pauses was used instead. The benchmark tool itself is not deprecated — only today's attempt to run it back-to-back without a larger gap between systems. |

## ADR-040 · Raise `LLMRateLimitAbortError` Instead of Sleeping When Backoff Exceeds Maximum

| Field | Detail |
|---|---|
| **Decision** | When `llm_invoke()`'s computed exponential-backoff delay would exceed `LLM_RATE_LIMIT_MAX_DELAY_SECONDS` (1800 s), raise `LLMRateLimitAbortError(delay)` immediately rather than sleeping for the full interval. |
| **Date** | 2026-06-20 |
| **Context** | June 19 benchmark runs produced Groq `429` storms where retry delays kept compounding — at the extreme, `llm_invoke()` would have entered a 30-minute sleep. In extended dry-run sessions (no interactive user) this is merely wasteful; once HTTP APIs were added (ADR-041), an indefinitely sleeping handler blocks the server for every other caller with no visible feedback and no way for the client to know whether to wait or abort. |
| **Options Considered** | **Sleep indefinitely** (original behaviour, no cap) — requires no new exception type, but a 30-minute handler occupies a server thread/coroutine slot with no client feedback. · **Cap sleep to `LLM_RATE_LIMIT_MAX_DELAY_SECONDS`** — bounds the wait but still blocks for up to 30 minutes, which is unacceptable for an HTTP API. · **Abort and propagate via exception** (chosen) — caller decides how to respond; CLI callers can print an actionable "retry after X seconds" message; HTTP handlers can return a `429` with `Retry-After`; the server remains responsive for other requests immediately. |
| **Chosen Solution** | `LLMRateLimitAbortError(delay: float)` — a lightweight `Exception` subclass carrying the would-be delay. Added to `app/llm_caller.py` and `app_workflow/services/llm_caller.py`. `LLM_RATE_LIMIT_MAX_DELAY_SECONDS = 1800.0` added to both `config.py` files. `app/agent_query.py`, `app_workflow/main.py`, `app/main.py`, `app/api.py`, and `app_workflow/api.py` all catch `LLMRateLimitAbortError` and surface it as an actionable message or HTTP 429. |
| **Rationale** | Aborting is the only option that keeps the HTTP server responsive under sustained rate limiting. The 1800 s threshold is generous — a delay of that magnitude almost certainly signals a quota suspension rather than a transient burst, so sleeping would just waste time. CLI callers receive a clear "retry after N seconds" message they can act on. The exception carries `delay` as a float so callers can pass it directly to `Retry-After` without recomputing it. |
| **Impact** | Any call stack that passes through `llm_invoke()` can now raise `LLMRateLimitAbortError` in addition to the existing `RateLimitError` from the Groq client. Callers that did not previously catch anything must now handle this error or let it propagate to the top-level handler. HTTP 429 responses now carry a `Retry-After` header derived from `e.delay`. |

## ADR-041 · Expose Both Pipelines Over HTTP via FastAPI (`app/api.py` and `app_workflow/api.py`)

| Field | Detail |
|---|---|
| **Decision** | Add a FastAPI HTTP server to each pipeline package (`app/api.py` on port 8000, `app_workflow/api.py` on port 8001) exposing five endpoints: `POST /query`, `POST /feedback/bad`, `GET /stats`, `POST /learn`, `POST /quit`. |
| **Date** | 2026-06-20 |
| **Context** | Both pipelines were CLI-only. Running them programmatically required spawning a subprocess (as `benchmark.py` demonstrated) or importing the package directly — both fragile options. Adding an HTTP layer enables language-agnostic clients, browser-based UIs, and automated testing without restructuring either package. June 19's benchmark work underscored that the pipelines needed a more stable programmatic interface. |
| **Options Considered** | **Flask** — synchronous, requires `threading` for concurrent requests, no built-in request validation, no auto OpenAPI docs. · **FastAPI** (chosen) — async-native, `asynccontextmanager` lifespan handles one-time startup cost (embedding load, vector-store open, LLM client init) cleanly, Pydantic request/response validation, auto-generated `/docs` (Swagger) and `/redoc` out of the box. · **Django REST Framework** — heavyweight, ORM-oriented, overkill for a single-module inference server. · **CLI subprocess wrapper** — keeps both pipelines CLI-only; adds latency and complexity for the caller without gaining any structured request/response protocol. |
| **Chosen Solution** | FastAPI with `asynccontextmanager lifespan` for startup/teardown; `asyncio.Lock` (`_query_lock`) to serialise concurrent `/query` calls (shared `agent_state` / `GraphState` dicts are not re-entrant); `asyncio.to_thread()` to dispatch blocking LLM/pipeline calls from async handlers. `app/api.py` initialises all pipeline objects directly in the lifespan (three `ChatGroq` instances, `EmbeddingManager`, `VectorStore`, `RAGRetriever`, `FeedbackStore`, `SelfLearner`). `app_workflow/api.py` delegates to the existing `services/services.py` registry and calls `build_graph()` at startup. | **Rationale** | FastAPI's async model avoids the overhead of a thread pool while still handling multiple in-flight connections; `asyncio.to_thread()` bridges the blocking pipeline calls without blocking the event loop. The lifespan context manager guarantees that expensive one-time initialisations (embedding model load, ChromaDB open) happen exactly once at startup and are cleaned up at shutdown, eliminating the per-request cost that made `benchmark.py`'s subprocess approach slow. Pydantic request models (`QueryRequest`, `FeedbackRequest`) enforce types at the boundary without adding any code beyond the model definition. `app_workflow/api.py`'s reserved-word guard (`_COMMAND_INPUTS`) prevents CLI command strings from being passed as queries, which would silently produce wrong answers. |
| **Impact** | Two new server entry points: `app/api.py` (run with `uvicorn api:app --port 8000` from `app/`) and `app_workflow/api.py` (run with `uvicorn api:app --port 8001` from `app_workflow/`). `app/` paths remain CWD-relative; `os.chdir(_APP_DIR)` at module load ensures they resolve regardless of uvicorn's working directory. `app_workflow/` paths use `__file__`-derived `_PROJECT_ROOT` (unchanged from the BUG-045 fix). `API_ENDPOINTS.txt` documents all endpoints with request/response schemas and `curl` examples. ## ADR-042 · ThreadPoolExecutor-Based Timeout Wrapper for Blocking I/O Operations

| Field | Detail |
|---|---|
| **Decision** | Wrap every long-running blocking I/O call (`llm.invoke()`, `collection.query()`, `model.encode()`) in a `concurrent.futures.ThreadPoolExecutor(max_workers=1)` thread and enforce a per-module deadline via `future.result(timeout=N)`. Caught timeouts raise a typed exception (`LLMResponseTimeoutError`, `RetrievalTimeoutError`, `EmbeddingEncodingTimeoutError`) rather than propagating `concurrent.futures.TimeoutError` directly. |
| **Date** | 2026-06-22 |
| **Context** | Unguarded calls to Groq's LLM API, ChromaDB's `.query()`, and SentenceTransformers' `model.encode()` have no enforced upper time bound. Under network degradation, provider-side queuing, or GPU contention, any of these can stall indefinitely. During the June 22 benchmark session, individual LLM calls were observed taking up to 75 s and the total `app/` pipeline wall-clock reached 28 min 28 s. Without a timeout guard, a stalled call blocks the entire pipeline — and, for the HTTP API layer added in ADR-041, the Uvicorn server thread — with no recourse for the caller. |
| **Options Considered** | **`signal.alarm(N)` (POSIX signals)** — raises `SIGALRM` after N seconds, hard-interrupting the calling thread. Not available on Windows (the project's development platform) and cannot interrupt calls that hold the GIL, which includes C extensions (NumPy inside SentenceTransformers, ChromaDB's native layer). · **Per-library timeout parameters** — Groq's `ChatOpenAI` constructor accepts a `request_timeout`; ChromaDB's `.query()` and SentenceTransformers' `encode()` do not expose timeout parameters. Partial coverage only — unacceptable for a consistent cross-module contract. · **`ThreadPoolExecutor` + `future.result(timeout=N)`** (chosen) — works on Windows, wraps any blocking call regardless of whether the library exposes a timeout, and expresses the deadline on the calling side without modifying the call itself. |
| **Chosen Solution** | `concurrent.futures.ThreadPoolExecutor(max_workers=1)` submits the blocking call and immediately calls `future.result(timeout=N)`. The calling thread unblocks after N seconds if the future has not completed; the background thread continues to completion but its result is discarded. A per-module typed exception is raised from `concurrent.futures.TimeoutError` and caught at the same or one frame above. LLM and retrieval timeouts return safe fallbacks (`LLMResult(ok=False)`, `[]`) to allow pipeline continuation; embedding timeouts are re-raised because there is no meaningful embedding vector fallback. Thresholds set to 2× the empirical p95 for LLM (150 s); ~14× p95 for retrieval (10 s); ~500× p95 for embedding (10 s) — margins calibrated after the June 22 benchmark runs (BUG-051). |
| **Rationale** | The `ThreadPoolExecutor` pattern is the only option that: (a) works on Windows, (b) is library-agnostic, and (c) requires no changes inside third-party calls. The key caveat — the background thread is not killed, only abandoned — is acceptable here because Groq calls eventually complete or fail with a provider error, ChromaDB is local and fast, and SentenceTransformers encodes from memory with no network I/O, so resource leakage is bounded. Typed exception classes give callers a precise signal without exposing `concurrent.futures` internals to every call site. |
| **Impact** | `app/llm_caller.py`, `app/retriever.py`, `app/embedding_manager.py`, `app_workflow/services/llm_caller.py`, `app_workflow/services/retriever.py`, `app_workflow/services/embedding_manager.py` — each gained one try/except block around its I/O call, one typed exception class, and `import concurrent.futures`. Three new constants added to both `config.py` files: `LLM_RESPONSE_TIMEOUT_SECONDS`, `RETRIEVAL_TIMEOUT_SECONDS`, `EMBEDDING_ENCODING_TIMEOUT_SECONDS`. The pipeline can now surface a `TIMEOUT` result kind rather than hanging indefinitely, and the HTTP API layer remains responsive even when a downstream call stalls. |

## ADR-043 · Per-Run JSON Timing Files via a Module-Level Singleton Timing Tracker

| Field | Detail |
|---|---|
| **Decision** | Introduce a module-level singleton timing tracker in each pipeline package (`app/timing_tracker.py`, `app_workflow/services/timing_tracker.py`) that records per-stage wall-clock durations using `time.perf_counter()` and flushes results to a JSON file after every `record()` call. The JSON file is named identically to the per-run debug log (same stem, `.debug.json` extension) and lives alongside it in `run_logs/`. |
| **Date** | 2026-06-23 |
| **Context** | June 22's benchmark produced per-pipeline total wall-clock averages (13:51 vs 28:28) but no per-stage breakdown. Understanding which stages account for the gap — and how much of any stage's time comes from LLM calls, retries, backoff, or framework overhead — requires probes that capture durations at each node boundary. The existing DEBUG log carries LLM timing fragments via `llm_caller.py`'s per-attempt lines, but they are buried in unstructured text, require manual parsing, and cover only LLM calls — not embedding, retrieval, compression, or draft generation. A structured, machine-readable output alongside the existing log was needed to turn benchmark run output into directly plottable per-category numbers without a log-parser. |
| **Options Considered** | **Parse timing from the existing DEBUG log** — zero new code, but requires a brittle log-parser for every analysis and cannot capture stages that do not currently emit timing messages. · **Append a timing section to the same DEBUG log** — minimal file proliferation, but mixes structured numeric data with unstructured diagnostic prose, making both harder to work with. · **Write a separate structured JSON file per run** (chosen) — keeps the debug log human-readable and the timing data machine-readable without coupling them; the identical naming scheme makes it unambiguous which JSON belongs to which run. · **Persist timing to a shared SQLite or CSV** — supports cross-run aggregation natively, but adds a schema concern and requires coordination if two server processes run simultaneously; the per-file approach inherits the natural isolation the per-run log file already provides. |
| **Chosen Solution** | Module-level singleton with a `threading.Lock`. Nine fixed categories match the nine stages probed across both pipelines. `set_json_path(path)` / `initialize(path)` called once per run from `logger_config.py` immediately after the `.debug.log` file is created — the JSON is written to disk at that point with empty lists, so it exists even if the run crashes before any stage completes. `record(category, duration)` appends and flushes synchronously on every call — no batching. Wall-clock scope for each probe covers the entire node execution including retries, exponential-backoff delays, LLM output-fix attempts, and failed attempts, so the recorded duration equals what a caller waiting on that stage would observe. For `app_workflow/services/logger_config.py`, `importlib.import_module("app_workflow.services.timing_tracker")` is used rather than a relative import to guarantee the caller obtains the canonical `sys.modules` singleton that node files also reference — see BUG-052. |
| **Rationale** | Synchronous flush-on-every-record is deliberately chosen over batching: a run that crashes mid-way still produces a partially-populated JSON with all completed stages visible, which is more useful for diagnosing long-running failures than a file that only appears when the run reaches a teardown hook. The module-level singleton (rather than a class instance passed around) avoids threading issues from multiple imports and ensures that all instrumented call sites in separate files share the same accumulated state without an explicit dependency injection step. `time.perf_counter()` is preferred over `time.time()` because it is monotonic and unaffected by system clock adjustments — important when measuring sub-second operations like embedding and retrieval. |
| **Impact** | Two new files: `app/timing_tracker.py`, `app_workflow/services/timing_tracker.py`. Both `logger_config.py` files modified to initialise the tracker after log-file creation. All pipeline stage modules in both packages instrumented with `time.perf_counter()` probes. Every run now produces a companion `.debug.json` alongside its `.debug.log` in `run_logs/`. `ENABLE_AUTO_DISTILLATION` set to `False` in both `config.py` files to prevent self-learning overhead from distorting timing measurements during benchmark runs. `run_app_queries.py` and `run_workflow_queries.py` added at the project root to automate multi-query benchmark sessions. |

## ADR-044 · FIFO Serialization Gate in `app/llm_caller.py` to Prevent Token-Quota Starvation Under Concurrent Load

| Field | Detail |
|---|---|
| **Decision** | Replace the random-jitter exponential backoff in `app/llm_caller.py` with a thread-safe FIFO serialization gate: a `queue.Queue` of per-thread `threading.Event` objects that ensures only one thread calls Groq at a time, in strict arrival order. A thread that receives a 429 retains the gate during its token-reset-window sleep rather than re-enqueuing. |
| **Date** | 2026-06-24 |
| **Context** | BUG-053: submitting two simultaneous `POST /query` requests to `app/api.py` causes one to silently fail — `llm_invoke()` returns an error after exhausting all `LLM_RATE_LIMIT_MAX_ATTEMPTS` retries, every one of which was a 429. `asyncio.to_thread()` dispatches both `run_agent()` calls into the thread pool concurrently, so both threads reach `llm_invoke()` at the same time. The first thread's LLM calls consume the Groq token-per-minute quota; the second thread hits 429 on every attempt and exhausts the retry budget. The prior `async with _query_lock:` in the `/query` handler appeared to serialize at the HTTP layer but was released before `to_thread()` dispatched the blocking work into the thread pool — `asyncio.Lock` is not a cross-thread mutex and provided no actual serialization between pipeline executions. The failure was silent: no exception propagated to the HTTP boundary, so the caller received an erroneous answer with no error signal. |
| **Options Considered** | **`threading.Semaphore(1)` (rejected)** — limits concurrency to one caller at entry, but a 429-holding thread must release the semaphore before sleeping its retry delay; any waiting thread immediately acquires it and can burn more tokens before the original 429-holder re-enters. No ordering priority: the 429-holder competes equally with new arrivals and can cycle indefinitely through 429s while newer threads starve it. · **`asyncio.Lock` at the `/query` handler level (rejected, already present but ineffective)** — `async with _query_lock:` covers the async handler body; `asyncio.to_thread()` hands the blocking work to a thread pool thread immediately, so the lock is released before the pipeline executes. Provides no serialization at the `llm_invoke()` level where contention actually occurs. · **`queue.Queue` FIFO gate inside `llm_invoke()` (chosen)** — each calling thread enqueues a `threading.Event` and blocks until the front-of-queue thread sets it. A thread that gets a 429 holds the gate (does not enqueue again), sleeps the full reset window from Groq headers, and retries. Gate released only on successful call completion. Strict FIFO ensures no starvation and guarantees the reset-window sleep is uninterrupted by any competing thread. |
| **Chosen Solution** | Three module-level globals: `_llm_queue: queue.Queue[threading.Event]`, `_llm_gate_lock: threading.Lock`, `_llm_active: bool`. `_gate_acquire(caller_tag)` takes the gate immediately if idle or enqueues a `threading.Event` and blocks on `.wait()`. `_gate_release_to_next()` pops the oldest event and calls `.set()` (waking the next thread) or marks the gate free. `llm_invoke()` calls `_gate_acquire()` once before the retry loop; 429s hold the gate and use `_wait_for_token_window()` (reads `_token_reset_until`, a shared monotonic deadline written by any 429-receiver) to sleep the remaining reset window before retrying; success calls `_apply_cooldown()` then `_gate_release_to_next()`. `_apply_cooldown()` sleeps `_cooldown_floor` seconds (derived from `x-ratelimit-remaining-tokens` headers) when the queue is non-empty, doubling on 429-recovery, halving after 3 clean successes (`_clean_success_streak`), resetting to 0 on empty queue; clamped to `[MIN_COOLDOWN_TIME, MAX_COOLDOWN_TIME]`. `_parse_groq_duration()` parses Go-style duration strings (`"1m30s"`, `"7.66s"`, `"500ms"`). `_groq_wait_seconds()` reads headers in priority: `x-ratelimit-reset-tokens` → `x-ratelimit-reset-requests` → `retry-after`. `LLM_RATE_LIMIT_BACKOFF_JITTER_SECONDS` removed from `config.py`. `async with _query_lock:` block removed from `app/api.py`'s `/query` handler. `MIN_COOLDOWN_TIME = 0.0`, `MAX_COOLDOWN_TIME = 30.0` added to `app/config.py`. |
| **Rationale** | A FIFO queue is the only primitive that combines strict ordering (a 429-holder is not disadvantaged relative to new arrivals), gate retention on failure (the reset-window wait is paid once and uninterrupted), and correct cross-thread semantics (`threading.Event` + `threading.Lock` are thread-safe; `asyncio.Lock` is not). The adaptive cooldown layer adds a secondary defence: even well-spaced calls can briefly exceed the per-minute token limit due to token-count variability per call; a floor derived from `x-ratelimit-remaining-tokens` headers absorbs this residual without requiring a full 429-cycle wait. |
| **Impact** | `app/llm_caller.py` — FIFO gate replaces jitter backoff; new module-level symbols: `_llm_queue`, `_llm_gate_lock`, `_llm_active`, `_token_reset_until`, `_cooldown_floor`, `_clean_success_streak`, `_gate_acquire`, `_gate_release_to_next`, `_wait_for_token_window`, `_apply_cooldown`, `_parse_groq_duration`, `_groq_wait_seconds`. `app/api.py` — `async with _query_lock:` removed; `request_id` (uuid4) generated per request and passed to `run_agent()` and `FeedbackStore.log()`. `app/config.py` — `MIN_COOLDOWN_TIME`, `MAX_COOLDOWN_TIME` added; `LLM_RATE_LIMIT_BACKOFF_JITTER_SECONDS` removed. `app/logger_config.py` — `ContextVar[str]`, `set_request_id()`, `get_request_id()`, `_RequestIdFilter` added. `app/agent_query.py` — `run_agent()` gains `request_id: str = ""` parameter. `app/feedback_store.py` — `log()` and `_save_thumbdown()` accept and persist `request_id`. Branch `setup_async_lock` merged into `master` on 2026-06-25; `app_workflow/services/llm_caller.py` ported in the same session — see ADR-045. |

| **Decision** | Replace the three flat-file feedback stores (`interactions.jsonl`, `user_thumbdowns.json`, `failed_variants.json`) with three MongoDB collections (`feedback_interactions`, `user_thumbdowns`, `failed_variants`) in both `app/` and `app_workflow/`. | **Options Considered** | **SQLite** — zero new dependency (stdlib `sqlite3`), queryable by `request_id`, persistent across processes. But SQLite's write concurrency is file-lock based; concurrent uvicorn workers would contend on write. · **Keep JSON/JSONL + improve** — add an in-process index over the JSONL for O(1) `request_id` lookups; use file locking for concurrent writes. Viable but invents a mini-database; maintenance burden grows with query complexity. · **MongoDB** (chosen) — native indexing (unique, ascending, `$addToSet`), multi-document transactions via sessions for atomic two-step thumbdown writes, client-side connection pooling, and no file-locking contention under concurrent workers. `pymongo` was already a natural choice given the document-oriented feedback schema. |
| **Chosen Solution** | New `app/db.py` and `app_workflow/services/db.py` modules with lazy singleton `MongoClient`, `get_db()` (reads `MONGODB_URI` and `MONGODB_DB_NAME` from env), `_ensure_indexes()` (idempotent, guarded by `_indexes_ensured` flag), and three public collection accessors. `FeedbackStore` rewritten to use `insert_one` / `find_one` / `update_one` on MongoDB collections. `api.py` updated to call `failed_variants_col()` directly instead of maintaining an in-process dict. |
| **Rationale** | MongoDB's document model maps directly onto the existing JSON feedback schema with zero schema migration: each JSONL line becomes one document. Unique indexes on `request_id` and `normalized_query` provide O(1) lookups by key. `$addToSet` upsert for `failed_variants` prevents duplicate variant strings without requiring a read-modify-write cycle. Multi-document sessions enable the atomic thumbdown write path (ADR-048). The `MONGODB_URI` / `MONGODB_DB_NAME` env vars allow both pipelines to share the same database instance in the current single-machine setup or split onto separate instances in a future multi-machine deployment. |
| **Impact** | `interactions.jsonl`, `user_thumbdowns.json`, and `failed_variants.json` are no longer written. Two new files added (`app/db.py`, `app_workflow/services/db.py`). `FeedbackStore` in both packages fully rewritten. `app/api.py` loses the `failed_variants_store` dict and JSON helpers; gains direct `failed_variants_col()` calls. MongoDB must be running (replica-set mode for transactions — see ADR-048) before either API server starts. `MONGODB_URI` defaults to `mongodb://localhost:27017`; `MONGODB_DB_NAME` defaults to `rag_db`. |

## ADR-047 · Request-ID-Based `/feedback/bad` Replaces In-Memory Last-Result Lookup

| Field | Detail |
|---|---|
| **Decision** | Change `app/api.py`'s `POST /feedback/bad` endpoint to accept `request_id: str` as a required field in the request body, and look up the interaction in MongoDB by that ID via `feedback_store.mark_bad(request_id, feedback)`, rather than calling `feedback_store.mark_last_bad()` which relied on the in-memory last-result sidecar. |
| **Date** | 2026-06-27 |
| **Context** | The original `/feedback/bad` endpoint called `mark_last_bad()`, which fetched variants from the process-level `last_result` dict (or `last_variants_with_chunks` sidecar in `app_workflow/`) populated by the most recent `/query` call. This had two correctness constraints: (1) the call had to arrive in the same process that handled the `/query` (no multi-worker safety); (2) the call had to arrive before the next `/query` overwrote `last_result`. These constraints were never formally documented in `API_ENDPOINTS.txt`, making them invisible to API callers. The addition of `request_id` tracing (ADR-044/045) and the MongoDB migration (ADR-046) together removed both constraints: interactions are now persisted by `request_id` immediately at `/query` time, with their variants embedded, and are queryable in any process for as long as the document exists. |
| **Options Considered** | **Keep `mark_last_bad()` as-is** — no API change, but retains the hidden process-affinity and ordering constraints indefinitely. · **Accept `request_id` as optional, fall back to `mark_last_bad()` if absent** — backward compatible but preserves the old failure mode for callers that omit the field. · **Require `request_id`, use MongoDB lookup** (chosen) — breaks the process-affinity and ordering constraints cleanly; the `request_id` has been included in every `/query` response since ADR-044, so callers already have it. |
| **Chosen Solution** | `FeedbackRequest` Pydantic model updated to include `request_id: str` as a required field. `POST /feedback/bad` calls `feedback_store.mark_bad(request_id, feedback)`. `mark_bad` does `interactions_col().find_one({"request_id": request_id})`, then opens a MongoDB session transaction to mark the interaction `USER_THUMBSDOWN` and (if feedback is long enough) write a thumbdown record. `API_ENDPOINTS.txt` updated to document `request_id` as required and to remove the "must call immediately after `/query`" constraint. |
| **Rationale** | Making `request_id` required is preferable to optional because an optional field leaves the old failure mode in place for callers that forget to send it. Every `/query` response already includes `request_id` (since ADR-044), so requiring it is not a burden on callers that already consume the field. The MongoDB lookup makes the endpoint safe for any number of concurrent workers and for calls arriving seconds, minutes, or hours after the original `/query`. |
| **Impact** | `FeedbackRequest` model in `app/api.py` gains `request_id: str`. `mark_last_bad()` is no longer called by `/feedback/bad`; it remains in `FeedbackStore` for internal use by CLI-mode callers (e.g. `app_workflow/`'s `cmd_bad` node which still uses the last-result sidecar). `API_ENDPOINTS.txt` updated. Callers that were not passing `request_id` will receive an HTTP 422 validation error until they update. |

## ADR-048 · MongoDB Session Transactions for Atomic Two-Step Thumbdown Write

| Field | Detail |
|---|---|
| **Decision** | Wrap the two-step thumbdown write (mark interaction `USER_THUMBSDOWN` + insert thumbdown record) in a single MongoDB session transaction so both writes commit or both roll back, eliminating the partial-write failure mode where an interaction is marked bad but no thumbdown record is ever stored. |
| **Date** | 2026-06-27 |
| **Context** | The thumbdown write path has always been two distinct writes: first, update the interaction's `quality` field to `USER_THUMBSDOWN`; second (conditional on feedback length ≥ `MIN_FEEDBACK_LEN`), insert a new document into `user_thumbdowns`. Under the old JSONL/JSON file stores, these were two separate file mutations with no rollback capability — if the process crashed after the first write, the interaction would be marked bad but no thumbdown record would ever appear. Under MongoDB without transactions, the same partial-write risk persists: if `update_one` succeeds but the process dies before `insert_one` completes, the thumbdown is lost while the interaction quality shows `USER_THUMBSDOWN`. MongoDB multi-document transactions, available in replica-set mode, eliminate this risk by making both writes atomic. |
| **Options Considered** | **Accept partial writes** — the original behaviour; the interaction is marked bad even if the thumbdown record is lost, which is the safer of the two partial states (the user's intent is recorded), but downstream thumbdown-injection logic never fires for those queries. · **Idempotent retry loop** — detect partial state on next call and repair, but this requires a read-before-write and a custom reconciliation policy. · **MongoDB session transaction** (chosen) — built-in atomicity with no application-level reconciliation needed; available in replica-set mode which is already required for the project. |
| **Chosen Solution** | Both `mark_last_bad()` and `mark_bad(request_id)` in `FeedbackStore` open a session with `get_client().start_session()` and call `session.start_transaction()`. The `update_one` and the `_append_thumbdown` `insert_one` both receive `session=session`. `_append_thumbdown` gains an optional `session=None` parameter so it can participate in the caller's transaction when provided, or run without one when called standalone. The same pattern is applied in both `app/feedback_store.py` and `app_workflow/services/feedback_store.py`. |
| **Rationale** | MongoDB transactions are the simplest correct solution: one `with` block, no custom reconciliation, no retry policy. The replica-set requirement is already imposed by the project (a standalone `mongod` does not support multi-document transactions), so this decision adds no new infrastructure constraint. Wrapping `_append_thumbdown` with an optional `session=` parameter rather than always opening a new session inside it is the correct pattern for functions that may be called from either a transactional or non-transactional context. |
| **Impact** | `mark_last_bad()` and `mark_bad()` in both `FeedbackStore` classes now require a replica-set MongoDB instance; they will raise `InvalidOperation` if called against a standalone `mongod`. `_append_thumbdown` gains `session=None` parameter in both packages. MongoDB must be started with `replSetName: rs0` in `mongod.cfg` and `rs.initiate()` run once before either API server uses the thumbdown path. |

## ADR-049 · Adaptive Branch Budget Heuristic for Query Variant Count in `app_workflow/`

| Field | Detail |
|---|---|
| **Decision** | Introduce `adaptive_branch_budget(query)` — a zero-LLM heuristic that returns 1, 2, or 3 based on query word count and conjunction keyword detection — and inject the budget into the variant-generation system prompt so the LLM cannot exceed it. |
| **Date** | 2026-06-29 |
| **Context** | `generate_query_variants` previously instructed the LLM to generate "2 to 3" variants regardless of query complexity, then passed all variants through retrieval. Short, unambiguous queries (e.g. "what is ABA?", 4 words) were generating 3 variants that were semantically near-identical, wasting retrieval budget on redundant sub-queries. Longer conjunction queries ("compare ABA and DIR approaches", 7 words with "compare") genuinely benefit from 3 variants covering each clause and contrast angle. A zero-LLM heuristic was preferred over a learnable model to avoid adding latency, cost, or a second LLM call before retrieval has even begun. |
| **Options Considered** | **Always use 3 variants** (prior behaviour) — maximum coverage but wastes budget on short/unambiguous queries and saturates post-retrieval dedup with near-identical chunks. · **Always use 1 variant** (no expansion) — eliminates redundancy but loses the coverage benefit of multi-angle sub-queries that is the entire point of variant generation. · **LLM-decided budget** — add a first-pass LLM call to estimate needed complexity; adds latency and cost for every query before any retrieval occurs. · **Rule-based heuristic** (chosen) — word count is a reliable proxy for query specificity; conjunction keywords reliably signal multi-clause queries that benefit from parallel sub-queries. Zero LLM cost, sub-millisecond execution. |
| **Chosen Solution** | `adaptive_branch_budget(query)`: strip and split on whitespace; if `len(words) <= BRANCH_BUDGET_SHORT_WORD_COUNT` (4) return 1; if any word is in `BRANCH_BUDGET_CONJUNCTION_KEYWORDS` return 3; if `len(words) <= BRANCH_BUDGET_MEDIUM_WORD_COUNT` (8) return 2; else return 3. The budget is passed to `_build_system_prompt(max_variants)` which appends a `RETRIEVAL BUDGET: <n>` line to the system prompt so the LLM is explicitly instructed not to exceed the computed limit. `generate_query_variants()` calls `adaptive_branch_budget()` first, then `pre_retrieval_filter()` (ADR-050), before returning variants to the graph. Four new constants in `app_workflow/config.py`: `BRANCH_BUDGET_SHORT_WORD_COUNT`, `BRANCH_BUDGET_MEDIUM_WORD_COUNT`, `BRANCH_BUDGET_CONJUNCTION_KEYWORDS`, and the existing `PRE_RETRIEVAL_SIM_THRESHOLD` (added in the same session). |
| **Rationale** | Word count is the cheapest available signal for query complexity. Conjunction keywords (`"and"`, `"or"`, `"both"`, `"versus"`, `"vs"`, `"compare"`, `"difference"`, `"how"`, `"why"`, `"explain"`) are reliably associated with multi-clause or comparative intent. The override to 3 on conjunction detection is conservative: it fires only when the query explicitly signals multi-angle intent, not on every long query. The system prompt injection closes the loop: the LLM is notified of its budget and is less likely to generate more variants than will survive pre-retrieval filtering. |
| **Impact** | `app_workflow/nodes/query_variants.py` — `adaptive_branch_budget()` added; `_build_system_prompt()` gains `max_variants: int` parameter. `generate_query_variants()` calls `adaptive_branch_budget()` before LLM and passes the result to `_build_system_prompt()`. Four new constants in `app_workflow/config.py`. `app/` is unaffected. |

## ADR-050 · Pre-Retrieval Cosine Similarity Filter for Query Variant Deduplication

| Field | Detail |
|---|---|
| **Decision** | Introduce `pre_retrieval_filter(variants, query_embedding)` in `app_workflow/nodes/query_variants.py` that (1) removes inter-variant near-duplicates using pairwise cosine similarity at `PRE_RETRIEVAL_SIM_THRESHOLD = 0.95`, then (2) ranks surviving variants by cosine similarity to the original query embedding and caps the list to the adaptive budget from ADR-049. |
| **Date** | 2026-06-29 |
| **Context** | The LLM's variant generation is stochastic and occasionally produces semantically near-identical sub-queries (e.g. "motor delays in autism" and "motor skill delays in ASD" from the same parent query). When both reach retrieval, they compete for the same chunks, the retrieve fan-in accumulates near-duplicate content, and the post-retrieval validation and compression stages must process the redundancy — wasting LLM calls. A pre-retrieval filter eliminates duplicates before any retrieval cost is paid. See Research topic 38 for the Jaccard-vs-cosine analysis that justified using cosine here. |
| **Options Considered** | **No dedup before retrieval** (prior behaviour) — all variants reach retrieve; duplicates discovered by `post_retrieval_filter_node` (ADR-051) or absorbed by the compression pipeline. Cost is paid for every redundant retrieve call and its downstream validation. · **Jaccard token-overlap dedup** — computationally cheap but fails on paraphrase pairs (different vocabulary, same meaning) which are the dominant failure mode. Rejected on evidence from Research topic 38. · **Cosine similarity on embeddings** (chosen) — the query embedding is already computed by `EmbeddingManager` at the start of `generate_query_variants`. Embedding each short variant adds <5 ms on CUDA. Cosine captures semantic equivalence regardless of surface wording. |
| **Chosen Solution** | `pre_retrieval_filter(variants, query_embedding)`: embed all variants in one batch via `services.embedding_manager.generate_embedding()`; compute pairwise cosine matrix; iterate in order — mark a variant as duplicate if its cosine to any prior survivor is ≥ `PRE_RETRIEVAL_SIM_THRESHOLD`; rank remaining survivors by cosine to the original query embedding (descending); return the top-`budget` entries. The original query embedding is passed in from `generate_query_variants()` which already holds it. `PRE_RETRIEVAL_SIM_THRESHOLD = 0.95` added to `app_workflow/config.py`. |
| **Rationale** | 0.95 cosine is a conservative high-similarity threshold: at this level, pairs are almost certainly paraphrases with no distinct retrieval angle. The rank-by-query-similarity step ensures the retained variants are the ones most semantically aligned to the user's actual intent rather than arbitrary survivors. Two-phase design (dedup then rank-and-cap) is important: dedup first ensures we aren't accidentally dropping a high-quality unique variant by ranking before removing duplicates. |
| **Impact** | `app_workflow/nodes/query_variants.py` — `pre_retrieval_filter()` added; `generate_query_variants()` calls it after LLM generation and before returning. `app_workflow/config.py` — `PRE_RETRIEVAL_SIM_THRESHOLD = 0.95` added. No other files modified. `app/` unaffected. |

## ADR-051 · Post-Retrieval Deduplication by Retrieved-Chunk Frozenset Fingerprint

| Field | Detail |
|---|---|
| **Decision** | Introduce `post_retrieval_filter_node` in a new `app_workflow/nodes/post_retrieve.py` module as a barrier node inserted in the graph between the retrieve fan-in and the two parallel validation nodes. The node identifies variants whose retrieved chunk sets are byte-for-byte identical (fingerprinted as `frozenset((content, source))` tuples) and strips the duplicate variant's chunk contributions from the accumulated retrieval lists. Results are written to new `GraphState` fields `post_filtered_document_chunks` and `post_filtered_learned_qa_chunks`. |
| **Date** | 2026-06-29 |
| **Context** | Even after pre-retrieval cosine filtering (ADR-050), two variants with cosine similarity below the 0.95 threshold may retrieve exactly the same top-K chunks — especially for narrow domain corpora where the vector store has limited coverage. In those cases, the `retrieve` fan-in accumulates duplicate chunk copies, and the validation and compression stages must process and eventually discard the redundancy at higher cost. A post-retrieval dedup pass that checks actual chunk content catches these cases at the lowest possible cost (no LLM call, pure set operations). |
| **Options Considered** | **No post-retrieval dedup** — rely on NAC (cosine-based chunk-level dedup inside compression) to handle duplicate chunks. Cost: NAC is a compression node; duplicates arriving at NAC must first survive retrieval validation (one LLM call per track) and dedup-merge (another LLM call pair), paying LLM costs for content that will eventually be dropped. · **Content-hash dedup inside `validate_retrieval.py`** — simple deduplicate-by-content logic inline in each validator node. Mixes chunk-identity concerns with validation concerns; harder to unit-test and maintain separately. · **Dedicated barrier node** (chosen) — clean separation of concerns; runs before any LLM call in the post-retrieve phase; writes to clearly named `post_filtered_*` state fields so downstream nodes can distinguish filtered from unfiltered content explicitly. |
| **Chosen Solution** | `post_retrieval_filter_node(state)`: build per-variant chunk fingerprints as `frozenset((c["content"], c["source"]) for c in chunks_for_variant)` for both document and learned-QA tracks; iterate variants in order — mark as duplicate if its frozenset exactly matches a prior survivor's frozenset; collect chunks from surviving variants only; write to `post_filtered_document_chunks` and `post_filtered_learned_qa_chunks`. Graph rewired: `retrieve → post_retrieval_filter_node → {validate_document_retrieval, validate_learned_qa_retrieval}`. Validation nodes read `post_filtered_*` first, falling back to raw `retrieved_*` accumulators when the filter node has not run. Two new `NotRequired[list[dict]]` fields added to `GraphState` in `state.py`. `post_retrieval_filter_node` exported from `nodes/__init__.py`. |
| **Rationale** | Frozenset equality on `(content, source)` pairs is a deterministic, zero-cost duplicate check. It only fires when two variants truly retrieved the same set of chunks — a strong signal that the retrieval trajectories are equivalent and one is fully redundant. The barrier-node placement is important: it runs once after all parallel `Send` branches have completed their fan-in, before any further LLM processing begins. The `NotRequired` annotation on the new state fields ensures backward compatibility: code paths that bypass the node (e.g. tests or future graph variants) still receive valid (empty-`None`) field state. |
| **Impact** | New file: `app_workflow/nodes/post_retrieve.py`. `app_workflow/state.py` — two new `NotRequired` fields. `app_workflow/graph.py` — new node + rewired edges. `app_workflow/nodes/validate_retrieval.py` — reads `post_filtered_*` first. `app_workflow/nodes/__init__.py` — new export. `app/` unaffected. |

## ADR-052 · Separate Per-Collection Similarity Thresholds for Document and Learned-QA Retrieval

| Field | Detail |
|---|---|
| **Decision** | Replace the single `score_threshold` parameter in `app_workflow/services/retriever.py`'s `retrieve_separate()` with two independent parameters: `doc_score_threshold` (default `DOCUMENTS_MIN_SIMILARITY`) and `learned_score_threshold` (default `LEARNED_QA_MIN_SIMILARITY`), each configurable independently in `app_workflow/config.py`. |
| **Date** | 2026-06-29 |
| **Context** | `retrieve_separate()` previously applied one `score_threshold` value to both the `documents` and `learned_qa` collections. Log analysis (Research topic 39) revealed that the two collections have different score-distribution profiles: `documents` chunks (source PDFs/textfiles, 1,181 chunks) span a wider cosine range against typical queries; `learned_qa` chunks (distilled Q&A pairs semantically tuned to prior queries) cluster at higher cosine scores. Using a single threshold either leaves noisy document chunks in (threshold too low) or discards relevant learned-QA entries (threshold too high). Separate thresholds allow each collection to be tuned to its own score distribution independently. |
| **Options Considered** | **Single shared threshold** (prior behaviour) — simpler config, but conflates two distinct retrieval populations with different score characteristics. · **Per-query dynamic threshold** (adaptive, e.g. derived from the score histogram) — more accurate but requires reading the score distribution after retrieval, adding latency and complexity. · **Fixed separate thresholds** (chosen) — zero runtime cost, directly config-driven, tunable per collection from log evidence without changing any retrieval logic. |
| **Chosen Solution** | `retrieve_separate(query, top_k, top_l, doc_score_threshold=DOCUMENTS_MIN_SIMILARITY, learned_score_threshold=LEARNED_QA_MIN_SIMILARITY)` — each threshold is applied independently to its collection's ranked list before returning. `DOCUMENTS_MIN_SIMILARITY = 0.5` and `LEARNED_QA_MIN_SIMILARITY = 0.5` added to `app_workflow/config.py` as initial conservative values (log-based tuned targets 0.55 and 0.58 documented in Research topic 39 for a future update). Call sites in `app_workflow/nodes/retrieve.py` and `app_workflow/services/tools.py` updated to pass the named keyword arguments explicitly. |
| **Rationale** | The two collections have structurally different embedding populations. Documents are indexed as raw text chunks; their cosine scores against a short user query span a wide range and require a lower floor to avoid dropping relevant but specific chunks. Learned-QA entries are synthetic Q&A pairs whose embeddings are inherently closer to conversational queries; their score floor can be set higher without recall loss. Separate constants make the tuning explicit, visible, and auditable in `config.py` rather than hardcoded inside retrieval logic. |
| **Impact** | `app_workflow/services/retriever.py` — `retrieve_separate()` signature changed (backward-incompatible: callers that passed `score_threshold` as a positional arg must switch to keyword args). `app_workflow/nodes/retrieve.py` and `app_workflow/services/tools.py` — call sites updated. `app_workflow/config.py` — `DOCUMENTS_MIN_SIMILARITY` and `LEARNED_QA_MIN_SIMILARITY` added; the old `MIN_SIMILARITY` constant is no longer used by `retrieve_separate()` (it may still be referenced by other callers; not removed). `app/` unaffected. |

## ADR-053 · Evidence-Based Tuning of `RETRIEVAL_TOP_K`, `RETRIEVAL_TOP_L`, `DOCUMENTS_MIN_SIMILARITY`, and `LEARNED_QA_MIN_SIMILARITY` From A/B Log Comparison

| Field | Detail |
|---|---|
| **Decision** | Update four retrieval config constants in `app_workflow/config.py` from their conservative initial values to values derived from a controlled five-log A/B comparison: `RETRIEVAL_TOP_K` 5 → 4, `RETRIEVAL_TOP_L` 5 → 4, `DOCUMENTS_MIN_SIMILARITY` 0.50 → 0.53, `LEARNED_QA_MIN_SIMILARITY` 0.50 → 0.57. |
| **Date** | 2026-06-30 |
| **Context** | ADR-052 (2026-06-29) introduced per-collection similarity thresholds and set both to 0.50 as a conservative initial value, with Research topic 39 identifying 0.55 and 0.58 as tentative tuned targets based on score-distribution shape. On 2026-06-30, the new `extract_logs.py` utility was used to run a controlled A/B comparison across five debug logs: the same two representative queries (one simple in-domain; one complex cross-domain with three query variants) were each executed under three config combinations — `K=5/0.50/0.50` (previous default), `K=4/0.55/0.60` (aggressive reduction), and `K=4/0.53/0.57` (intermediate). LLM call counts, INSUFFICIENT verdict frequencies, rate-limit-pause counts, and answer correctness were compared across the resulting five debug logs. The Research topic 39 tentative recommendation (0.55/0.58) was not a tested combination; the comparison surfaced 0.53/0.57 as empirically optimal over both extremes tested. |
| **Options Considered** | **Keep 0.50/0.50** (`K=5`, original default) — simple in-domain query: 148 LLM calls, 19+ rate-limit pauses, 1 INSUFFICIENT retry. Complex cross-domain query: 205 calls, 3 INSUFFICIENT verdicts, 2 full retrieval retries. Lowest per-chunk filter rate; highest total LLM cost by 3–5×. · **Use 0.55/0.60** (`K=4`, aggressive) — simple query: 42 LLM calls, 3 pauses, 0 INSUFFICIENT. Complex 3-variant "ASD" query: 37 calls, 0 INSUFFICIENT — but 2 of 3 query variants retrieved zero chunks because the threshold was too high for multi-domain corpus coverage; the LLM hallucinated the domain meaning of "ASD" rather than admitting insufficient context. Lower cost on simple queries; correctness regression on multi-domain queries. · **Use 0.53/0.57** (`K=4`, intermediate, `langgraph_api_20260630_125641.debug.log`) — simple query: 30 LLM calls, 3 pauses, 0 INSUFFICIENT. Complex "ASD" query: 30 calls, 0 INSUFFICIENT, no retrieval starvation, correct domain answer. Best on all three dimensions: cost, verdict quality, accuracy. |
| **Chosen Solution** | `RETRIEVAL_TOP_K = 4`, `RETRIEVAL_TOP_L = 4`, `DOCUMENTS_MIN_SIMILARITY = 0.53`, `LEARNED_QA_MIN_SIMILARITY = 0.57` in `app_workflow/config.py`. All four values remain env-overridable. |
| **Rationale** | The 0.53/0.57 pair is the only combination tested that simultaneously avoids low-quality chunk inflation (0.50 failure mode) and retrieval starvation on multi-domain queries (0.55/0.60 failure mode). The cross-domain hallucination observed at 0.55/0.60 is a correctness regression — the LLM confidently produced a wrong answer rather than routing to `no_context_answer` — which is strictly worse than a higher LLM call count. Evidence was derived from production debug logs with real queries, not synthetic test data. The A/B log comparison methodology is reusable and repeatable for future threshold adjustments as the corpus grows. |
| **Impact** | Supersedes the tentative 0.55/0.58 targets from Research topic 39. `RETRIEVAL_TOP_K` and `RETRIEVAL_TOP_L` each reduced from 5 to 4, cutting the maximum retrieved-chunk count per variant by one. Combined effect on observed production queries: 3–5× reduction in LLM calls vs. the 0.50/0.50 default with no observed accuracy regression across the two tested query types. Config constants remain env-overridable; the A/B comparison methodology (Research topic 40) is the reference for any future threshold revisit. |

## ADR-054 · LLM Provider Expansion: Hugging Face Inference Providers Router Adopted Over Google Colab Tunnel

| Field | Detail |
|---|---|
| **Decision** | Reject Google Colab + tunnel (`ngrok`/`localtunnel`) as a hosting path for production `judge_llm`/repair-tier calls; adopt the Hugging Face Inference Providers router (`https://router.huggingface.co/v1`, OpenAI-compatible) as a second LLM provider alongside Groq, accessed via `langchain_openai.ChatOpenAI` |
| **Date** | 2026-07-01 |

| **Options Considered** | **Colab + tunnel** — genuinely free GPU, wide model choice, but violates Colab's Terms of Service for unattended/server-like usage backing a production pipeline, has no stable endpoint (tunnel URL changes every session restart, session dies after ~90 min idle / ~12h max), and GPU availability is not guaranteed. ## ADR-056 · Answer-Quality Judge Upgraded to Structured Multi-Verdict Output (`GROUNDED` / `PARTIALLY_FABRICATED` / `OVERCLAIMED` / `OFF_TOPIC` / `UNKNOWN`)

| Field | Detail |
|---|---|
| **Decision** | Replace `GROUNDING_PROMPT`'s free-text `OK` / `INSUFFICIENT — <sentence>` output with a structured JSON verdict object, evaluated against three rules (exhaustive per-sentence traceability, relevance, and a new completeness/calibration rule) instead of two, and make judge-call failure default to `"UNKNOWN"` instead of the previous fail-open `"OK"` |
| **Date** | 2026-07-02 |
| **Context** | The prior judge graded only "relevance" and whether "key claims" (not all claims) were traceable to retrieved chunks. This let an answer built from one true grounded claim padded with several fabricated ones pass as `OK`, because the judge had no mandate to check every sentence and no axis at all for whether the answer's scope/confidence matched how much evidence it was actually given. Judge-call failure (timeout, malformed response) also silently defaulted the verdict to `"OK"` — a fail-open gate protecting the entire self-learning knowledge base with a single lenient check. |
| **Options Considered** | Keep the binary free-text verdict and append more instruction text (cheap, but doesn't close the "key claims" sampling loophole — the judge still has no mandate to check every sentence) · reuse the codebase's own compression-safety judge pattern already proven for the identical underlying fabrication risk (`_DC_JUDGE`-style: exhaustive per-sentence check + structured JSON output with a fabricated-claims list) · build a dedicated trained reward model / PRM (rejected — no training data yet, see Research topic 10) |
| **Chosen Solution** | Rewrote `GROUNDING_PROMPT` to require sentence-by-sentence traceability (not just "key claims"), added Rule 3 for completeness/calibration (answer scope and confidence must match evidence volume), and changed the output to JSON: `verdict` (one of `GROUNDED`/`PARTIALLY_FABRICATED`/`OVERCLAIMED`/`OFF_TOPIC`/`UNKNOWN`), `unsupported_claims: []`, `scope_mismatch`, `overall_reason`. `check_answer_quality.py` parses this via a new `fix_llm_output("grounding_judge", ...)` schema (`GroundingJudgeSchema`, added to the existing 8-schema registry), validates the verdict against a `_VALID_VERDICTS` set, and falls back to `"UNKNOWN"` on any judge-call or parse failure. `QUALITY_PASS_VERDICT = "GROUNDED"` is the single source of truth for pass/fail. |
| **Rationale** | Reuses a judge pattern already validated elsewhere in the codebase for the identical underlying risk rather than inventing new judge architecture. Splitting `OVERCLAIMED` (every claim technically true, but scope/confidence exceeds the evidence) from `PARTIALLY_FABRICATED` (some claims outright invented) lets future routing treat the two differently — a strip-and-caveat pass versus a full retry — even though today's routing still treats every non-`GROUNDED` verdict the same way. Failing closed to `UNKNOWN` removes a fail-open gate that let a transient judge failure silently pass every answer. |
| **Impact** | `app_workflow/services/prompts.py` (`GROUNDING_PROMPT` rewritten), `app_workflow/services/fix_llm_output.py` (new `GroundingJudgeSchema` + `"grounding_judge"` registry entry, new `ENABLE_ANSWER_QUALITY_OUTPUT_FIX` config flag), `app_workflow/nodes/check_answer_quality.py` (rewritten to consume the JSON verdict and log `unsupported_claims` count), `app_workflow/routes.py` (`route_after_quality_check` now branches on `verdict == QUALITY_PASS_VERDICT`). `generate_answer.py` and `api.py` both had a second, independent `.startswith("INSUFFICIENT")` assumption on the same state field, fixed for consistency in the same pass. Differentiated routing per non-passing verdict (e.g. strip-and-caveat for `OVERCLAIMED` vs. full retry for `PARTIALLY_FABRICATED`) is not yet implemented — today all non-`GROUNDED` verdicts route the same way. |

## ADR-057 · `combine_tracks` Registered With LangGraph `defer=True` as a True Fan-In Barrier

| Field | Detail |
|---|---|
| **Decision** | Register the `combine_tracks` node with LangGraph's `defer=True` option instead of relying on default fan-in behavior |
| **Date** | 2026-07-02 |
| **Context** | `combine_tracks` has two predecessors of unequal depth — the document track (NAC → DC → LBC, 3 stages) and the learned-QA track (DC → LBC, 2 stages) — so they land in different LangGraph supersteps. | **Options Considered** | Manually gate the node body with a "both tracks marked complete" flag (works, but pushes barrier logic into node code and has to be reimplemented if a third parallel track is ever added) · restructure the learned-QA track to artificially match the document track's depth with a no-op stage (changes pipeline topology to work around a scheduling detail, not a real requirement) · use LangGraph's built-in `defer=True` node option, designed for exactly this situation |

| **Rationale** | `defer=True` is the framework's own answer to "a node has multiple predecessors of unequal path length" — simpler and more robust than hand-rolled completion-flag logic, and it generalizes automatically if a third track is ever added to the graph. |
| **Impact** | `app_workflow/graph.py`. Confirmed via manual log inspection (and `graphify update .`) that `combine_tracks` now fires once per request with both `document_chunks` and `learned_qa_chunks` populated, resolving the "multiple drafts per request" and "draft built from partial context" symptoms in Bugs.md BUG-062. |

## ADR-059 · Conservative-Grounding Prompt Pattern Applied to All Generation-Stage Prompts (Answer, Draft, Answer-From-Draft)

| Field | Detail |
|---|---|
| **Decision** | Replace the single-line `generate_answer` prompt and `generate_draft`'s inline "Be thorough and complete" prompt with three structured, anti-hallucination prompts (`_GENERATE_ANSWER_PROMPT`, `_GENERATE_ANSWER_FROM_DRAFT_PROMPT`, `_GENERATE_DRAFT_PROMPT`) |
| **Date** | 2026-07-02 |
| **Context** | The prior `generate_answer` prompt — "Answer the following question using only the provided context" — constrains *where* facts come from but not *how much* to claim relative to how much evidence exists; observed failure mode was a single thin retrieved chunk producing a confident, fully itemized, largely fabricated answer. `generate_draft.py`'s prompt was worse in this respect — it explicitly instructed the model to "be thorough and complete," directly encouraging padding. |
| **Options Considered** | Append a short "don't hallucinate" caveat to the existing one-line prompts (cheap, but Research topic 19 already found vague negative instructions are far less effective than named anti-patterns plus worked examples for steering model behavior) · apply the structured prompt pattern already proven in this codebase for the equivalent judge-side risk (`_REDUNDANCY_JUDGE_PROMPT`'s role-sentence → output-contract → worked-GOOD/BAD-examples → named-anti-patterns → explicit-output-format structure) to the generation side instead of only the judging side |
| **Chosen Solution** | Added `_GENERATE_ANSWER_PROMPT`, `_GENERATE_ANSWER_FROM_DRAFT_PROMPT`, and `_GENERATE_DRAFT_PROMPT` to `prompts.py`, all requiring: explicit FULL/PARTIAL/INSUFFICIENT self-classification of context coverage before answering; claims restricted to verbatim or direct paraphrase of context only (no inference, extrapolation, or "typical fact" filling); an explicit rule that one relevant chunk is not license for a full itemized answer; and paired GOOD/BAD worked examples per rule. `_GENERATE_DRAFT_PROMPT` uses the same grounding rules but frames the output as a working draft ("this will be reviewed and rewritten, but must already be honest") rather than a final answer. `generate_draft.py` rewired to `_GENERATE_DRAFT_PROMPT.format(query=..., context=...)`. |
| **Rationale** | Named anti-patterns plus worked GOOD/BAD pairs are the pattern this project's own prior research (Research topic 19) found most reliable for steering instruction-tuned models away from a specific failure mode — reused here on the generation side rather than an ad hoc caveat. |
| **Impact** | `app_workflow/services/prompts.py` (three new prompts), `app_workflow/nodes/generate_answer.py` and `app_workflow/nodes/generate_draft.py` (wired to the new prompts instead of inline strings). Directly enables ADR-058's draft-as-synthesis-input flow — a synthesis step is only as trustworthy as the draft and context it is given. |

| **Decision** | Add an optional `config: RunnableConfig` parameter to every graph node function and every downstream LLM-invocation helper (`llm_invoke()`, `_invoke_once()`, the four validators, the `fix_llm_output.py` repair functions, `self_learner.py`'s distillation path), forwarding it explicitly all the way to `llm.invoke(messages, config=config, ...)` |

## ADR-068 · Central Tracing Policy: `instrument_namespace()` + `TraceSpec`-Based Automatic Function Tracing

| Field | Detail |
|---|---|
| **Decision** | Replace manual per-function `@traced_operation(name)` decoration with a single `instrument_namespace(globals(), group, exclude={...})` call appended to the bottom of each of the 17 `app_workflow/` node/service modules, and centralize all trace-shaping policy (what counts as a traceable function, which arguments to include/exclude, how to summarize large values, what the trace name looks like) in one `operation_tracing.py` module via a `TraceSpec` dataclass registry |
| **Date** | 2026-07-13 |
| **Context** | The project already had three independent tracing backends (LangSmith, Phoenix, Langfuse) wired ambient/callback-style at the LangGraph node level (ADR-063/064/066/067), but visibility stopped at node boundaries — the LLM/validator/compression helper functions called *inside* each node were invisible as individual trace entries in any backend, since only the outer node (or specific `llm.invoke()` calls picked up by LangChain's own callback instrumentation) produced trace observations. Manually adding a tracing decorator to every function needing coverage would require touching every call site individually and would silently miss newly added helpers. |
| **Options Considered** | **Per-function manual `@traced_operation(name)` decoration** — explicit and readable, but requires remembering to decorate every new function across 17 modules and doesn't scale. · **`instrument_namespace(globals(), group)` called once per module** (chosen) — automatically wraps every module-defined function and class method in `RunnableLambda`-based tracing, closing coverage gaps for future helpers without per-function decoration; needs an `exclude` set to skip functions already covered by the graph's own node-level tracing, avoiding double-wrapping the top-level LangGraph node function. · **Leave function-level tracing permanently manual/opt-in** — rejected; the 2026-07-08/07-09 debug-log quality audits (Research topics 51, 55) already relied on manually grepping `.debug.log` files for per-function detail, and a systematic solution was overdue. |
| **Chosen Solution** | `instrument_namespace(globals(), group, exclude={...})` in `operation_tracing.py`, called once at the bottom of each of 17 `app_workflow/` node and service modules (e.g. `query_variants.py` appends `_instrument_namespace(globals(), "Query Variants", exclude={"generate_query_variants"})`). Each wrapped function is registered with a stable display name `f"{group} / {name}"` and traced via `@traced_operation`, which wraps the call in a `RunnableLambda` inheriting the ambient LangChain/LangGraph `RunnableConfig` so it nests correctly under the graph's existing trace hierarchy and is visible to all three backends simultaneously. A `TraceSpec` dataclass (added later the same day) — holding `input_builder`/`output_builder` callables — lets specific functions (retrieval, embeddings, LLM calls, validators, storage) shape what actually gets recorded instead of dumping raw arguments/return values. A `_summarize()` recursive serializer bounds trace payload size (`_MAX_TEXT_CHARS = 2_000` char previews, `_MAX_COLLECTION_ITEMS = 20` item caps, numpy arrays reduced to shape+dtype, depth-limited at 3 levels), and `_include_argument()` filters out noisy arguments (`self`, `cls`, `config`, `callbacks`, `client`, `handler`) from trace inputs. |
| **Rationale** | A single append-only call per module (rather than N decorators per module) means every current and future function in a traced module gets coverage automatically, directly closing the "helper functions invisible inside node boundaries" gap without ongoing maintenance burden. Centralizing the trace-shaping policy in one file, rather than scattering per-function trace customization across 17 modules, keeps the "what does a trace look like" decision auditable and consistent — matches this project's established pattern of centralizing cross-cutting policy in one file (`config.py` for feature flags, `prompts.py` for prompt strings, per ADR-021). |
| **Impact** | New `app_workflow/services/operation_tracing.py` (final size ~333 lines across two same-day passes: +99 initial, +234 expansion). Two-line `instrument_namespace(...)` call appended to the bottom of all 17 `app_workflow/` node + service modules. Three constants (`_EXCLUDED_ARGUMENTS`, `_MAX_TEXT_CHARS`, `_MAX_COLLECTION_ITEMS`) were initially kept private inside `operation_tracing.py` to keep the tracing setup self-contained, then moved into `config.py` on request so the tracing-policy limits are user-configurable alongside every other pipeline constant. The `TraceSpec`/`_summarize`/`_include_argument` machinery is the single point of control for trace payload shape across the entire `app_workflow/` pipeline — any future node or service function automatically inherits this policy with zero per-function code. `app/` is unaffected — this instrumentation is scoped to `app_workflow/` only, matching the precedent set by ADR-063/064/066/067. |

## ADR-069 · Dedicated `LangfuseHandler` (`logging.Handler` Subclass) Mirrors Every Log Record as a Langfuse Event, Independent of `_TracingHandler`

| Field | Detail |
|---|---|
| **Decision** | Add a new `logging.Handler` subclass, `LangfuseHandler`, in `app_workflow/services/langfuse_logging.py`, registered as a fourth root log handler (alongside console, file, and the existing `_TracingHandler`) at `DEBUG` level, that converts every `LogRecord` into a Langfuse `event` observation attached to the active trace — rather than extending `_TracingHandler` (ADR-064) to also cover Langfuse |
| **Date** | 2026-07-13 |
| **Context** | `_TracingHandler` (ADR-064, 2026-07-09) already mirrors log records onto active LangSmith runs and Phoenix spans via a run-id lookup. Langfuse was added as a third tracing backend the next day (ADR-066/067), but its callback-based, non-ambient tracing model (Research topic 56) means the same run-id-lookup mechanism `_TracingHandler` uses for LangSmith/Phoenix doesn't apply the same way — Langfuse's Python SDK exposes log-to-trace attachment through its own `get_client()`-based event-creation API tied to whatever trace/observation is ambient in the current OpenTelemetry context (populated by Langfuse's own OTel-native SDK), not through a LangChain `run_id` registry lookup like Phoenix's `OpenInferenceTracer.get_span(run_id)`. |
| **Options Considered** | **Extend `_TracingHandler` with a third branch for Langfuse** — keeps all log-mirroring logic in one handler, but couples three backends' very different attachment mechanisms (run-id registry lookup for LangSmith/Phoenix vs. ambient-OTel-context event creation for Langfuse) into one function, and risks one backend's failure/latency affecting the others within a single `emit()` call. · **Separate dedicated `LangfuseHandler`** (chosen) — isolates Langfuse's event-creation mechanism and its own failure modes (missing/disabled Langfuse config, re-entrancy from the Langfuse SDK's own internal logging) from the existing LangSmith/Phoenix mirroring path entirely. On handler *level*: **`INFO`** (initial choice) — fewer events shipped to Langfuse, but silently drops the same class of node-level `logger.debug(...)` detail that BUG-070 had already found missing from `_TracingHandler` (67 of 127 `logger.*` calls across `app_workflow/nodes/*.py` are `logger.debug`). · **`DEBUG`** (chosen) — ships every log line regardless of level, at the cost of thousands of extra event rows per trace on a full pipeline run. |
| **Chosen Solution** | `LangfuseHandler.emit(record)` formats the log message, lazily calls Langfuse's `get_client()`, and creates a Langfuse event carrying the formatted message, logging level (mapped to Langfuse's DEBUG/DEFAULT/WARNING/ERROR scale), logger name, request ID, and file/function/line metadata; Langfuse automatically associates the event with whichever trace/observation is currently active. A `ContextVar`-based re-entrancy guard prevents log records emitted *during* the Langfuse SDK's own internal calls (e.g. its export/flush machinery) from feeding back into `LangfuseHandler` and recursing. First registered in `logger_config.py` at `INFO`, then changed to `DEBUG` the same session (matching `_TracingHandler`'s independent-of-console-level design from BUG-070) so no node-level detail is dropped before mirroring. Any Langfuse-side failure (missing client, disabled tracing, network error) is caught and silently tolerated so logging never affects the application. |
| **Rationale** | Reuses the "mirror `logging` onto the active trace" pattern already validated by `_TracingHandler`, but as its own handler rather than a shared one — consistent with how this project has treated each new tracing backend as an independently toggleable, independently failing concern (`ENABLE_PHOENIX_TRACING`, `ENABLE_LANGFUSE_TRACING`) rather than a monolithic tracing layer. The re-entrancy guard directly anticipates the same feedback-loop risk already documented for `_TracingHandler`-adjacent code — the Langfuse SDK's own `logging.getLogger("langfuse")` output could otherwise re-enter `LangfuseHandler.emit()` if not excluded. The `INFO` → `DEBUG` level change was a deliberate reversal, not an oversight: DEBUG-level messages carry exactly the granular pipeline detail (per-node intermediate state, retry/backoff detail, per-chunk validation reasoning) that `operation_tracing.py`'s function-level tracing (ADR-068) is meant to make visible, so filtering them out at the handler defeats the point of adding this handler at all. The thousands-of-extra-rows cost was judged acceptable because Langfuse's own trace UI supports filtering/searching observations after ingestion — the volume is a viewing-time concern, not a capture-time one, so it is cheaper to over-capture and filter on read than to under-capture and lose detail permanently. |
| **Impact** | New `app_workflow/services/langfuse_logging.py` (+74 lines). `app_workflow/services/logger_config.py` modified (+14/-6) to instantiate `LangfuseHandler` at `DEBUG` and register it as the fourth root handler. New `app_workflow/tests/test_langfuse_logging.py` (+43 lines; 2 tests passing). Combined with `_TracingHandler` (ADR-064) and `operation_tracing.py`'s `instrument_namespace()` (ADR-068), every log line and every instrumented function call in `app_workflow/` now surfaces in whichever of the three tracing backends is enabled. `app/` is unaffected. |
| **Impact** | `app/llm_setup.py` only — `app_workflow/services/llm_setup.py` is unchanged and still fully on `CUSTOM_API_BASE`. `app/` now requires `GROQ_API_KEY`, `MODEL_NAME`, `HF_API_BASE`, `HF_TOKEN`, and `JSON_FIX_MODEL_NAME`; it no longer consumes `CUSTOM_API_BASE`/`CUSTOM_API_KEY`/`CUSTOM_API_MODEL_NAME` (those remain required for `app_workflow/`). Architecture.md's description of `llm_caller.py` as "a thin wrapper around `ChatOpenAI` that routes to Groq's OpenAI-compatible endpoint" now only describes `json_fix_llm`'s HF-router traffic within `app/` — `llm`/`merge_llm`/`judge_llm` bypass `ChatOpenAI`-based routing entirely via native `ChatGroq`. `app/` and `app_workflow/` have diverging LLM provider configurations for the first time since the `610c4b8` sync. |

## ADR-070 · Run the Full Workflow Benchmark Against One Long-Lived API Process

| Field | Detail |
|---|---|
| **Decision** | Use `useful_but_not_valuable_Files/run_all_workflow_batches.py` to start `app_workflow/api.py` once, wait for readiness through `GET /stats`, execute all configured query / feedback / stats / learn entries consecutively against that same process, summarize failures, and shut the server down through `POST /quit` with process-level fallbacks. Expand the catalog to 15 batches / 100 numbered scenarios while allowing targeted runs by commenting batches or entries in/out. |
| **Date** | 2026-07-14 |
| **Context** | The benchmark needed to exercise feedback refinement, learned-QA accumulation, forced distillation, tracing, and a broad range of retrieval/grounding edge cases under realistic sustained load. Restarting the API between batches would repeatedly reload models/services, fragment traces and logs, discard process-local state, and prevent later scenarios from observing earlier feedback/learning effects. A fixed startup sleep would be unreliable because model/vector-store initialization time varies by machine and cache state. |
| **Options Considered** | **Restart per batch** — stronger batch isolation but invalidates cross-batch learning/feedback tests and adds repeated startup cost. · **Run every request in-process without HTTP** — faster and easier to introspect, but bypasses FastAPI request validation, endpoint behavior, readiness, request IDs, and shutdown semantics. · **One long-lived HTTP API with readiness polling** (chosen) — exercises the deployed interface and preserves sequential runtime effects, at the cost of deliberate cross-scenario state and failure propagation. |
| **Chosen Solution** | The runner owns one subprocess, polls `/stats` every 250 ms for up to five minutes, maps string entries to `/query` and typed entries to `/feedback/bad`, `/stats`, or `/learn`, sends no artificial inter-request delay, records non-2xx/exception failures without silently losing the suite summary, then calls `/quit`; if graceful shutdown fails it escalates locally to `terminate()` and `kill()`. The numbered catalog spans disambiguation, empty retrieval, multi-source reasoning, hallucination risk, dataset analysis, disparities, grounding, self-learning, feedback refinement, and edge cases. |
| **Rationale** | The purpose is a sustained system benchmark, not an isolated unit-test matrix. A single process exposes accumulated learned-QA and feedback behavior, long-tail provider latency, service degradation, and persistence failures that short isolated runs can hide. Readiness polling makes startup synchronization evidence-based rather than time-based. |
| **Impact** | Commit `cdb1f71` introduced the runner; the July 14 working expansion grew it to 15 batches / 100 scenarios. The run updated the shared learned-QA Chroma store as an expected side effect. Results are not statistically independent because earlier scenarios can affect later retrieval/learning; isolated regression tests remain necessary for causal comparisons. |

## ADR-071 · Resolve Workflow Feature Flags Per Request and Carry Them in `GraphState`

| Field | Detail |
|---|---|
| **Decision** | Allow `POST /query` to accept any subset of 20 `ENABLE_*` boolean overrides (organized into nine functional groups), resolve them once against `app_workflow/config.py` defaults, store the complete effective mapping in `GraphState["switches"]`, and make every affected route/node/service read the request-scoped values rather than process-global constants. |
| **Date** | 2026-07-14 |
| **Context** | The expanded benchmark needs to compare workflow configurations without editing `config.py` and restarting the long-lived API between requests. Direct module-level constants are process-wide and cannot safely express consecutive requests using different combinations. The override surface spans graph routing and deeply nested helper calls, so partial propagation would produce misleading hybrid configurations. |
| **Options Considered** | **Edit environment/config and restart per configuration** — simple but slow, fragments sustained runs, and prevents per-request experiments. · **Mutate imported module globals around each request** — minimal code change but unsafe under concurrent requests and prone to leaked configuration after exceptions. · **Pass individual booleans through every function** — explicit but creates large, brittle signatures. · **Resolve a typed API object into one state dictionary** (chosen) — validates the public schema, centralizes fallback behavior, and gives routing plus nested services one consistent effective configuration. |
| **Chosen Solution** | `WorkflowSwitches` exposes optional Pydantic boolean fields; `_build_initial_state()` excludes `None`, `resolve_switches()` overlays recognized booleans on `DEFAULT_SWITCHES`, and the result is stored in the initial state. `get_switches(state)` is the sole runtime accessor and falls back to defaults for CLI/legacy states. Routes consult it for graph-shape choices; nodes pass the same dictionary into validators, compression helpers, output repair, and self-learning functions that lack direct state access. Disabled fixed-topology stages become pass-through nodes where necessary. |
| **Rationale** | Request state is already the LangGraph execution contract and is isolated per invocation. Resolving once prevents different layers from interpreting omitted values differently, preserves `config.py` as the source of defaults, avoids shared mutable global state, and makes switch combinations traceable/reproducible from the request plus state. |
| **Impact** | Commit `1340c10`; new `app_workflow/services/switches.py`; `GraphState` gains optional `switches`; `QueryRequest` gains optional `WorkflowSwitches`; routing, query variants, retrieval validation/deduplication, NAC/DC/LBC, answer-quality checking, output repair, QA generation, commands, and auto-distillation now honor per-request values. Byte-compile, import, graph-build, default, override, and fallback smoke checks passed. The API docs at `http://localhost:8001/docs` expose the nested switch schema. |

## ADR-072 · Keep Docling, Unstructured, and Marker-PDF Converters as Evaluation Utilities; Do Not Replace Production Ingestion Yet

| Field | Detail |
|---|---|
| **Decision** | Preserve all three converters under `useful_but_not_valuable_Files/document-loaders-codes/` as reproducible comparison utilities. Keep the existing production ingestion path unchanged. Do not promote raw Marker Markdown to the authoritative RAG representation or replace the current loader stack until candidates are compared under explicit retrieval-quality and structural-fidelity criteria and the chosen path includes asset validation, UTF-8 normalization, page-aware cleanup, heading repair, and complex-table handling. |
| **Date** | 2026-07-15 |
| **Context** | Docling, Unstructured, and Marker-PDF were explored as document-to-Markdown ingestion candidates. Batch-capable scripts now exercise each library over the same recursive `source/` tree and preserve outputs by relative path. ## ADR-073 · Run Marker as an Isolated GPU Microservice (Out-of-Process) Rather Than Installing `marker-pdf` Into `app_workflow/`

| Field | Detail |
|---|---|
| **Decision** | Deploy Marker (`marker-pdf 1.10.2` + `surya-ocr 0.17.1` + a CUDA torch build) as a standalone GPU Docker container (`marker_service/`) exposing a `POST /convert` HTTP endpoint, and have `app_workflow/` call it over HTTP via `marker_loader.py`, instead of importing `marker-pdf` into `app_workflow/`'s own Python 3.14 environment |
| **Date** | 2026-07-24 |
| **Context** | ADR-072 (2026-07-15) had deferred adopting Marker for production ingestion pending a quality bake-off, keeping it as an evaluation utility only. This session moved to actually wire a Marker-backed loader into `app_workflow/`. The blocker is a hard dependency conflict: `marker-pdf`'s stack requires `transformers` 4.x and (on `marker-pdf 2.0.0`) `pillow<11`, but `app_workflow/` runs Python 3.14 with `sentence-transformers` (the embedding backbone of the entire pipeline) pinned to a `transformers` 5.x floor, and `pillow<11` has no Python-3.14 wheel and will not compile from source there. Installing Marker in-process would either break embeddings (transformers downgrade) or fail the build outright (pillow). A brief in-process attempt during the session did get `marker-pdf` installed behind a `pillow>=12` override, but that leaves a fragile, override-dependent single environment carrying two mutually hostile ML stacks. |
| **Options Considered** | **Install `marker-pdf` into `app_workflow/`'s venv behind dependency overrides** — tried; works for a moment but forces `transformers`/`pillow` overrides that risk silently breaking `sentence-transformers` embeddings and must be re-justified on every dependency bump; rejected as unmaintainable. · **Maintain a second Python 3.12 virtualenv (`.venv-marker`) on the host and shell out to it** — avoids the container but is not portable (Windows wheels, baked paths), still couples two CUDA torch builds to one machine's driver, and offers no process/GPU isolation. · **Isolated GPU Docker microservice with an HTTP boundary** (chosen) — gives Marker its own Python 3.12 + CUDA-13.0 torch stack and its own model cache, fully decoupled from `app_workflow/`'s environment; the only integration surface is a stable `POST /convert` contract. |
| **Chosen Solution** | New top-level `marker_service/`: `server.py` (FastAPI, `POST /convert` + `GET /health`, one `PdfConverter` built at boot via `asyncio.to_thread`, conversions serialised behind a `threading.Lock`, `pdftext_workers=1` — BUG-077); `Dockerfile` (python:3.12-slim, CUDA-13.0 `torch==2.13.0+cu130`, frozen `requirements.txt` carried from the validated `.venv-marker`, build-time `download_font()` pre-seed, late `gcc`/`libc6-dev` for Triton JIT); `docker-compose.yml` (nvidia GPU passthrough, persistent `marker-models` cache volume, port 8002). `app_workflow/ingestion/marker_loader.py` becomes a thin HTTP client POSTing each PDF to `MARKER_SERVICE_URL/convert` (default `http://localhost:8002`, `config.py`), keeping its `load_documents(file_paths) -> list[Document]` signature so callers are agnostic to the transport. |
| **Rationale** | The dependency conflict is intrinsic (two ML stacks with incompatible `transformers`/`pillow` floors), not a version-pin accident, so the only durable fix is environment isolation. A container additionally gives independent GPU-model caching, restart isolation (a Marker crash cannot take down the RAG API), and a portable, reproducible build — none of which an override-laden shared venv or a host-local second venv provides. The stable HTTP contract means `app_workflow/` and Marker can each upgrade their ML stacks independently. This advances ADR-072's "don't productionise raw Marker yet" into "productionise the *transport* while keeping raw-Markdown-quality caveats (Research topic 61) unresolved" — the loader is now available and switchable, but still defaults off. |
| **Impact** | New `marker_service/` component (server/Dockerfile/compose/requirements/README), independent of both pipelines. `app_workflow/ingestion/marker_loader.py` rewritten from an in-process converter to an HTTP client; new `MARKER_SERVICE_URL`/`MARKER_SERVICE_TIMEOUT` config + env vars. Running the Marker loader now requires the sidecar container to be up and GPU-reachable; when it is down or a PDF fails, the loader logs and skips that file so the rest of the batch still ingests. `app/` is unaffected. See ADR-074 for the ingestion-pipeline refactor that consumes this loader, and Research topic 62 for the dependency-conflict analysis. |

## ADR-074 · Unified, Switchable `app_workflow/` Ingestion Pipeline (Loader × Splitter Matrix) With In-Memory Loading and a `POST /ingest` Endpoint

| Field | Detail |
|---|---|
| **Decision** | Replace the monolithic `app_workflow/ingestion/ingest.py` with a coordinated five-module ingestion package driven by `ingestion_requests.run_ingestion(...)`, selecting the loader (Marker vs. Unstructured) and splitter (custom vs. recursive) from two `config.py` switches (`ENABLE_MARKER_LOADER`, `ENABLE_CUSTOM_SPLITTER`) that a `POST /ingest` request body can override per run; load everything in memory (no persisted intermediate Markdown/JSON) |
| **Date** | 2026-07-24 |
| **Context** | Introducing the Marker HTTP loader (ADR-073) meant `app_workflow/` needed a loader/splitter it could select at runtime rather than a single hardcoded path. The prior `ingest.py` bundled discovery, loading, splitting, and storage into one file with a fixed loader; the exploratory `custom_splitter.py` additionally had its own `discover_files()` and wrote Marker Markdown to disk. Both the earlier exploration (writing `.md`/`.json` intermediates) and the new microservice model made persisted intermediates unnecessary — Marker output arrives over HTTP and is chunked immediately. `app_workflow/` also needed an HTTP way to trigger ingestion for the benchmark/runner tooling. |
| **Options Considered** | **Keep one hardcoded loader/splitter and swap by editing `config.py` + restart** — simplest, but can't vary per request and forces a process restart to compare loaders. · **Add ad-hoc boolean branches inside the existing `ingest.py`** — less code churn but keeps discovery/loading/splitting/storage entangled and leaves `custom_splitter`'s disk-writing `discover_files()` as a second, divergent discovery path. · **Factor into a five-module package with a single `run_ingestion` coordinator and shared `discover_files()`** (chosen) — one recursive discovery, four interchangeable components (2 loaders × 2 splitters), switch resolution in one place, and a stable summary contract; components import lazily so importing the package (e.g. at API startup) doesn't pull Marker/Unstructured deps unless actually used. |
| **Chosen Solution** | `ingestion_requests.py` owns `discover_files()` (recursive `rglob` over `data_files/` for `SUPPORTED_EXT`, order-preserving de-dup) and `run_ingestion(enable_marker_loader=None, enable_custom_splitter=None)`, which resolves each switch via `_resolve()` (`None` → `config.py` default, explicit bool → override), lazily imports and runs the chosen loader then splitter, embeds via `EmbeddingManager`, upserts into the `documents` collection via `VectorStore.add_documents_in_batches`, and returns a summary dict. `marker_loader.py` (HTTP, PDF-only) and `unstructure_loader.py` (Unstructured + in-memory tabular→JSON + `JSONLoader`) are the two loaders; `custom_splitter.py` (Marker-Markdown-aware) and `recursive_splitter.py` (`RecursiveCharacterTextSplitter` + per-source `chunk_seq`) are the two splitters — both consume/return LangChain `Document`s. `custom_splitter` lost its own `discover_files()`, Markdown reader, local `Document` dataclass, and `main()`. `POST /ingest` in `api.py` accepts an optional `IngestRequest` (the two switch overrides) and runs `run_ingestion` off-thread. `write_chunk_run()` + the `tiktoken` encoder moved to `services/logger_config.py`; `ingest.py` and `marker_logger_config.py` deleted. |
| **Rationale** | Centralising discovery and switch resolution removes the divergent second discovery path and makes the four loader×splitter combinations a single, testable matrix. Loading in memory (Marker over HTTP, tabular converted in-RAM) drops the disk-intermediate step the earlier exploration used, so nothing needs cleanup and re-ingestion is idempotent from source. Lazy component imports keep the heavy Marker/Unstructured dependency trees out of the API's import path unless a run actually selects them. The `POST /ingest` endpoint gives the benchmark tooling and future callers a uniform, off-thread trigger consistent with the pipeline's other endpoints. Defaults stay `False` so behaviour is unchanged until a caller opts in — consistent with this project's config-flag conventions (ADR-021). |
| **Impact** | `app_workflow/ingestion/` reorganised (net `+952 / −511` across the session): new `ingestion_requests.py`, `unstructure_loader.py`, `recursive_splitter.py`; rewritten `marker_loader.py`; trimmed `custom_splitter.py`; deleted `ingest.py`, `marker_logger_config.py`. `api.py` gains `POST /ingest`; `config.py` gains the ingestion section (switches, `DATA_FILES_DIR`, `CHUNK_RUNS_DIR`, extension sets, chunk sizes, `TOKEN_ENCODING`); `services/logger_config.py` gains `write_chunk_run` + the token encoder. `data_files/` becomes the recursive ingestion root. A known caveat carries forward: the Marker loader silently ingests only PDFs, so a mixed corpus under `ENABLE_MARKER_LOADER=True` drops non-PDFs — use the Unstructured loader or a separate pass. `app/ingest.py` is untouched and remains `app/`'s ingestion path. See ADR-073 and Research topic 62. |
