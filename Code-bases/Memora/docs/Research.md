
## 1. Embeddings & Embedding Models

| Field | Detail |
|---|---|
| **Topic** | What embeddings are and how they work in RAG |
| **Date** | Early project (April 2025) |
| **Findings** | Embeddings are dense numerical vectors that encode the semantic meaning of text. The model `all-MiniLM-L6-v2` (SentenceTransformers) produces 384-dimensional vectors. Text is encoded via `model.encode(text, normalize_embeddings=True)` to produce unit-length vectors. Similarity search is then performed by comparing query vectors to stored chunk vectors. Embedding models are **not** the same as chat/generation models — they convert text to vectors; they do not generate language. |
| **Conclusion** | `all-MiniLM-L6-v2` was chosen as the embedding model: fast, runs on CUDA, 384-dim output, well-suited for semantic retrieval over document chunks. Embedding dimension fixed at 384 for the entire project. |
| **Relevance to Project** | Core of the retrieval pipeline. Every document chunk, every user query, and every learned QA pair is embedded and stored/queried via this model. Lives in `embedding_manager.py`. |

## 2. Vector Databases & Similarity Search

| Field | Detail |
|---|---|
| **Topic** | ChromaDB as the vector store; HNSW indexing; ANN search |
| **Date** | April 2025 |
| **Findings** | ChromaDB stores two components: `chroma.sqlite3` (metadata, document text, IDs) and a UUID-named folder (binary HNSW index with raw float vectors). Both must exist together — deleting either breaks the store. HNSW (Hierarchical Navigable Small World) is ChromaDB's default ANN index. It provides ~95–99% recall at a fraction of the cost of brute-force exact search. For the current corpus (~1,181 chunks), exact search is still feasible but HNSW future-proofs the system. Chroma was evaluated against FAISS and Pinecone; Chroma was chosen for its simplicity, local persistence, and Python-native API. |
| **Conclusion** | ChromaDB with persistent local storage (`../data/vector_store`) is the vector store. Two collections are used: `documents` (source chunks) and `learned_qa` (self-learning memory). FAISS and Pinecone were rejected: FAISS lacks metadata support out-of-the-box; Pinecone is cloud-only and adds latency/cost. |
| **Relevance to Project** | All retrieval in `retriever.py`, `vector_store.py`, and `self_learner.py` depends on ChromaDB. The HNSW index is what makes sub-second retrieval possible even as the corpus grows. |

## 3. RAG Architecture Fundamentals

| Field | Detail |
|---|---|
| **Topic** | Classic RAG vs Agentic RAG pipeline structure |
| **Date** | April 2025 |
| **Findings** | Classic RAG is a linear pipeline: `ingest → embed → store → query → retrieve → answer`. An Agentic RAG adds a decision loop on top: the agent decides *whether* to retrieve, *how many times*, *with what query reformulations*, and *when to stop*. The full stack layers are: `Python Code → Framework Wrapper (LangChain/ChatOpenAI) → Provider Client → API Endpoint → Actual Model → Response`. The chat/generation model (e.g. `llama-3.1-8b-instant`) is entirely separate from the embedding model (`all-MiniLM-L6-v2`). LangChain is "glue" — not a model itself. |
| **Conclusion** | Adopted Agentic RAG with a structured iteration loop (max 6 iterations), tool-calling (`retrieve_documents`, `check_answer_quality`), and a self-learning distillation step triggered every 5 successful interactions. |
| **Relevance to Project** | Defines the entire `agent_query.py` architecture and justifies the existence of `tools.py`, `self_learner.py`, and `feedback_store.py`. |

## 4. Context Compression Strategies

| Field | Detail |
|---|---|
| **Topic** | Semantic compression methods for RAG: Extractive, LLM-Based, Deduplication, Neighbor-Aware |
| **Date** | May 2025 |
| **Findings** | A full hierarchy of compression approaches was researched and implemented. **Extractive compression** (sentence extraction via SentenceTransformers cosine similarity to query) is the safest — no hallucination risk, faithful to source. **LLM-Based Compression (LBC)** rewrites/summarizes chunks using the LLM; achieved ~27.6% reduction in testing; carries hallucination risk, mitigated by a faithfulness guard (if retention ratio < 0.35, keep original). **Deduplication Compression (DC)** scans for semantically redundant sentences across chunks; in practice, true sentence-level redundancy is rare unless chunk overlap is high or docs are duplicated. **Neighbor-Aware Compression (NAC)** merges consecutive chunks from the same source (identified by `chunk_seq` metadata) before compression — restores document flow lost by chunking. The recommended pipeline order is: `Retrieval Validation → NAC → DC (light) → LBC (heavy) → Answer Validation`. The production-stage pipeline at `compress_context_pipeline()` in `context_compression.py` implements this. LangChain's `ContextualCompressionRetriever + LLMChainExtractor` was also evaluated as a framework-level option. **BM25 sentence compression** (`rank_bm25`) was evaluated as a lexical fallback for technical content. |
| **Conclusion** | The three-stage NAC → DC → LBC pipeline was adopted. Embedding-first DC prefiltering (cosine similarity ≥ 0.92 before LLM pair comparison) is the next planned improvement — changes DC from O(n²) LLM calls to O(high-similarity candidates only). Sentence-level semantic extraction with SentenceTransformers was chosen as the extractive compression method. LangChain `LLMChainExtractor` was rejected due to extra latency and dependency on LangChain's retriever format. |
| **Relevance to Project** | Directly implements `context_compression.py`. Controls what context the LLM actually sees, which determines answer quality and faithfulness. The token-budget gate (`COMPRESS_MIN_TOKENS`) skips the pipeline for small contexts to save latency. |

## 5. LLM Provider Evaluation — Groq vs OpenAI

| Field | Detail |
|---|---|
| **Topic** | Provider selection for the generation LLM; model deprecation management |
| **Date** | April–May 2025 |
| **Findings** | Groq runs open-source models (Llama, Mixtral) on custom LPU hardware, making inference very fast and cheap. OpenAI runs proprietary models (GPT-4.x) on NVIDIA GPUs. Both expose OpenAI-compatible REST APIs, so `ChatOpenAI` from LangChain wraps either by simply changing `base_url` and `api_key`. The model `gemma2-9b-it` and `llama3-8b-8192` were both deprecated on Groq mid-project; replacement is `llama-3.1-8b-instant` (for speed) or `llama-3.3-70b-versatile` (for quality/tool-use). The `llama-3.1-8b-instant` context window is 128,000 tokens input / 8,192 tokens output. The larger `llama-3.3-70b-versatile` has 128,000 / 32,768 — much better for complex agentic loops. Tool-use reliability is significantly better in the 70B model for respecting constraints like "max 5 retrieval calls." |
| **Conclusion** | Groq with `llama-3.1-8b-instant` is used as the primary model. `llama-3.3-70b-versatile` is recommended for production agentic use. Model names should be read from `.env` (`MODEL_NAME`) to avoid hardcoded deprecation failures. `CUSTOM_API_KEY` and `CUSTOM_API_BASE` environment variables allow hot-swapping providers without code changes. |
| **Relevance to Project** | Affects `llm_caller.py`, `agent_query.py`, and `.env` configuration. The OpenAI-compatible design means the entire pipeline is provider-agnostic. |

## 6. Structured Output Libraries — Outlines & Guidance

| Field | Detail |
|---|---|
| **Topic** | Constrained generation libraries for guaranteeing JSON/schema outputs |
| **Date** | May 2025 |
| **Findings** | **Outlines**: Uses Finite State Machine (FSM) token masking for true constrained decoding — but *only* with local models (HuggingFace/vLLM/llama.cpp). With remote OpenAI-compatible APIs (Groq, OpenAI), `outlines.from_openai()` falls back to sending `response_format: json_schema` — the API handles generation, not Outlines. FSM masking is therefore unavailable on Groq. `Choice(VerdictOutput)` throws `TypeError` on remote backends. Using `VerdictOutput` (a plain TypedDict/Pydantic class) instead does work, as Outlines converts it to `json_schema`. Outlines' schema compilation can take 40s–10+ minutes for complex schemas. **Guidance**: Same fundamental limitation — logit masking requires local model access. With Groq, `gen()` and `select()` degrade to prompt-engineering + post-hoc parsing. **Native Groq `json_schema` mode**: The correct approach for remote inference is `response_format={"type": "json_schema", "json_schema": {..., "strict": True}}` with a Pydantic model's `.model_json_schema()`. This gives server-side schema enforcement (the only real enforcement available). Supported models on Groq for `json_schema`: `llama-3.3-70b-versatile` (not `llama-3.1-8b-instant`). |
| **Conclusion** | Outlines and Guidance are **rejected** for production use with the Groq backend. They add a dependency layer that only provides `response_format: json_schema` passthrough anyway. Native Groq structured output mode is used instead for judge calls. For truly constrained decoding in future, local model hosting with Outlines + vLLM would be the path. |
| **Relevance to Project** | Explains the absence of Outlines/Guidance in the final pipeline. LLM output parsing uses a structured prompt + `json.loads()` with retry logic instead. |

## 7. Agentic RAG & Self-Learning Loop

| Field | Detail |
|---|---|
| **Topic** | Self-learning mechanism design; memory injection vs fine-tuning vs RLHF |
| **Date** | April–May 2025 |
| **Findings** | Three real self-learning mechanisms were evaluated: (1) **Memory injection** — save validated Q&A pairs back to ChromaDB (`learned_qa` collection). Next similar queries retrieve these as additional context. This is "pseudo-learning" — the knowledge base grows, not the model weights. (2) **Fine-tuning on accumulated interactions** — log query+answer pairs, periodically fine-tune a local model (e.g. Mistral 7B via Unsloth). Real weight-level learning but batch process, not continuous. (3) **RLHF/DPO** — capture thumbs-up/down per answer as reward signal. Research-grade complexity. Naive auto-saving every answer was explicitly rejected: hallucinations become permanent, retrieval degrades, memory fills with noise. The safe design is: agent answers → user feedback or confidence threshold → only then save. The trigger is every 5 successful interactions (`self_learner.py`). User thumbdown records are persisted to `user_thumbdowns.json`; failed variants to `failed_variants.json`. These are injected into the system prompt on subsequent identical/similar queries so the LLM avoids repeating bad patterns. |
| **Conclusion** | Memory injection with confidence-gated saving was adopted (option 1). The `SelfLearner` class in `self_learner.py` manages the `learned_qa` Chroma collection. `feedback_store.py` handles thumbdown persistence. Fine-tuning (option 2) is the identified future upgrade path once enough validated interactions are logged. |
| **Relevance to Project** | Central to the project's unique value proposition. `self_learner.py`, `feedback_store.py`, `user_thumbdowns.json`, and `failed_variants.json` all exist because of this investigation. |

## 8. Retrieval Ranking Algorithms

| Field | Detail |
|---|---|
| **Topic** | Alternatives to cosine similarity for chunk ranking: MMR, BM25, cross-encoder reranking, RRF |
| **Date** | April–May 2025 |
| **Findings** | **Current**: cosine similarity via ChromaDB distances. **BM25** (Best Matching 25): keyword-frequency ranking; excels at exact term matching (model names, IDs, numbers, code snippets) where dense embeddings fail. Uses TF-IDF + document length normalization. Library: `rank_bm25`. **MMR (Maximal Marginal Relevance)**: balances relevance vs diversity — prevents retrieving 5 chunks that all say the same thing. Formula: pick next chunk that is relevant to query but dissimilar to already-selected chunks. Best immediate upgrade. **Cross-Encoder Reranking**: a smaller model reads (query + each chunk) together and scores relevance; far more accurate than embedding similarity alone; model `cross-encoder/ms-marco-MiniLM-L-6-v2`; adds latency. **RRF (Reciprocal Rank Fusion)**: combines rankings from multiple retrieval methods; simple formula; relevant because `retriever.py` already merges `documents` + `learned_qa` collections — RRF would make that merger smarter. **Hybrid Search**: BM25 + vector similarity combined; standard in production RAG (Elasticsearch, Qdrant, modern pipelines). |
| **Conclusion** | The recommended upgrade path is: (1) Add MMR for diversity, (2) Add BM25 hybrid scoring, (3) Add cross-encoder reranking on top-10, pass top-5 to LLM. Not yet implemented — current pipeline uses cosine similarity only. |
| **Relevance to Project** | Affects `retriever.py`. MMR is the highest-value near-term improvement. BM25 is critical if the corpus grows to include technical documents, code, or logs with exact identifiers. |

## 9. Chunking Strategy Investigation

| Field | Detail |
|---|---|
| **Topic** | `RecursiveCharacterTextSplitter` settings; token budget math; chunk size trade-offs |
| **Date** | April 2025 |
| **Findings** | `RecursiveCharacterTextSplitter` tries separators in priority order: `"\n\n"` → `"\n"` → `" "` → `""`. It always tries to keep chunks semantically whole before breaking at smaller granularity. Settings used: `chunk_size=1000` chars, `chunk_overlap=200` chars. Token math: 1000 chars ≈ 250 tokens (at ~4 chars/token for English). With `top_k=5`, each retrieval adds ~1,250 tokens to context — well within the 128K limit. Chunk overlap of 200 chars (~50 tokens) prevents concepts straddling a chunk boundary from being lost. Smaller chunk sizes (800 chars) can improve retrieval precision for dense academic prose. Larger chunks (1500+ chars) risk embedding quality degradation — the vector averages too many concepts. CSV files are not queryable via RAG (RAG searches semantically; structured data requires SQL/Pandas). |
| **Conclusion** | `chunk_size=1000, chunk_overlap=200` is retained as the default. For future improvement with academic PDFs: `chunk_size=800, chunk_overlap=100` may improve precision. The `chunk_seq` metadata field (sequential chunk index per source) was added to support Neighbor-Aware Compression. |
| **Relevance to Project** | `ingest.py` uses these settings. `chunk_seq` metadata enables NAC in `context_compression.py`. |

## 10. Process Reward Models (PRMs) for Agents

| Field | Detail |
|---|---|
| **Topic** | Evaluating whether to adopt a PRM for step-level scoring of agent decisions; ToolPRMBench findings |
| **Date** | May 2025 |
| **Findings** | Four PRM categories exist: (1) **LLM-as-a-judge** — prompt a strong LLM to score each agent step; zero training cost but high inference cost and uncalibrated for domain. (2) **General PRMs** — trained on broad domains (math); ~50% accuracy on tool-using tasks, barely above random — training distribution mismatch. (3) **Agent-specialized PRMs** (e.g., WebShepHerd-8B for web agents) — slightly better but still weak transfer to RAG tool-use. (4) **Tool-specialized PRMs** (ToolPRM-GRPO) — trained on tool-using preference pairs; achieves 78.6% avg accuracy on ToolPRMBench, beating GPT-5 (74.4%). GRPO (reinforcement learning) generalizes to OOD tools (+21.8%) while SFT-trained variants overfit (-13.6% to -20.4%). The current `check_answer_quality` in `tools.py` is a hand-coded heuristic PRM (checks refusal language, minimum length, word overlap). It's brittle — a 200-word answer that copies chunk text verbatim passes; a tight 150-word synthesis fails. |
| **Conclusion** | LLM-as-a-judge is the recommended first upgrade to `check_answer_quality`: replace the heuristic with a prompted judge call: "Does this answer (a) only use facts from chunks, (b) directly address the question, (c) avoid verbatim copying? Return OK or INSUFFICIENT." One extra LLM call per query. Training a ToolPRM is future scope — needs ~500+ thumbdown records before fine-tuning a reward model is worthwhile. General PRMs were rejected. |
| **Relevance to Project** | Informs `tools.py` `check_answer_quality()` design. The `user_thumbdowns.json` and `interactions.jsonl` logs are the ground-truth data that would train a domain-specific PRM eventually. |

## 11. Python Environment & Dependency Management

| Field | Detail |
|---|---|
| **Topic** | `uv` vs `pip + venv`; Python version compatibility; PyTorch GPU installation pitfalls |
| **Date** | April 2025 |
| **Findings** | `uv init` + `uv venv` creates an isolated Python project environment (equivalent to `python -m venv .venv` + `pip`). Python 3.14 was found to be unstable for the ML stack (PyTorch, SentenceTransformers, Chroma). Python 3.11 is the recommended version. Critical issue: `uv add -r requirements.txt` performs dependency resolution and can downgrade GPU PyTorch to the CPU wheel if `torch` is not explicitly pinned with `+cu128` suffix. The fix is to exclude torch from `requirements.txt` and install it separately: `pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu128`. Mixing `pip` and `uv` installs in the same environment can create inconsistent package state, especially for compiled libraries like PyTorch. Final working environment uses `torch==2.11.0+cu128`, `CUDA 12.8`, RTX 5050 GPU. |
| **Conclusion** | Python 3.11 + `pip` (not `uv add`) for torch. Requirements split into `requirements.txt` (all non-torch deps) + manual GPU torch install. Current environment is stable with confirmed `torch.cuda.is_available() == True`. |
| **Relevance to Project** | Setup reproducibility. The GPU torch install is required for fast embedding (CUDA-accelerated `all-MiniLM-L6-v2` encoding). Without GPU, ingestion of 1,000+ chunks takes significantly longer. |

## 12. GPU Ingestion Performance

| Field | Detail |
|---|---|
| **Topic** | Slow ingest performance on RTX 5050 GPU despite CUDA availability |
| **Date** | April 2025 |
| **Findings** | Root cause was not the GPU — it was per-batch ChromaDB writes. Original code called `collection.add()` inside a loop, once per batch of 16 chunks. ChromaDB's SQLite persistence layer is slow for frequent writes. Additionally, `show_progress_bar=True` in `generate_embedding()` added I/O overhead on every batch call. The `torch.cuda.empty_cache()` call after every batch forced CUDA memory management overhead repeatedly. Fix: (1) Embed all chunks in one large GPU pass (batch_size=128 or 512), (2) single bulk `collection.add()` call after all embeddings are ready, (3) disable progress bar during batch ingestion, (4) remove `empty_cache()` from the inner loop. Result: N/batch_size ChromaDB writes collapsed to 1 write; GPU fully utilized. With 1,181 chunks, observed 512-chunk batches processing correctly in two bulk inserts. |
| **Conclusion** | `vector_store.py` updated to bulk-embed then bulk-insert. Batch size of 128–512 is suitable for RTX 5050 (8GB VRAM) with `all-MiniLM-L6-v2`. Larger batch sizes give diminishing returns beyond 256. |
| **Relevance to Project** | `vector_store.py` `add_documents_in_batches()` and `ingest.py` `BATCH_SIZE` constant. Important whenever re-ingesting documents. |

## 13. ChromaDB Distance Metric Bug Investigation

| Field | Detail |
|---|---|
| **Topic** | Incorrect cosine similarity scores due to wrong ChromaDB distance space |
| **Date** | May 2025 |
| **Findings** | ChromaDB defaults to L2 (squared Euclidean) distance. The code computed `similarity_score = 1 - dist`. With L2 on unit-normalized vectors, `dist = ‖a−b‖² = 2 − 2·cos(θ)`, so `1 - dist = 2·cos(θ) − 1` — **not** true cosine similarity. A "score" of 0.2 in the old system corresponded to actual cosine similarity of ~0.6. Ranking was unaffected (monotonic relationship), but threshold values were meaningless. Fix: set `metadata={"hnsw:space": "cosine"}` on collection creation in `vector_store.py` and `self_learner.py`. Critical caveat: `get_or_create_collection()` does **not** migrate existing collections — old persisted collections retain their L2 metric. Fix requires deleting `../data/vector_store/` and re-ingesting. After fix, `score_threshold=0.2` means true cosine ≥ 0.2, which is very permissive. Recommended threshold post-fix: 0.4–0.5 for `all-MiniLM-L6-v2`. Empirical similarity ranges for this model: 0.7–1.0 = strong match; 0.4–0.7 = related; 0.2–0.4 = loose; 0.0–0.2 = effectively unrelated. |
| **Conclusion** | Collections recreated with `hnsw:space: cosine`. Vector store re-ingested. `score_threshold` updated in `retriever.py` and `tools.py`. `MIN_SIMILARITY` in `tools.py` set to 0.5. |
| **Relevance to Project** | Directly affects all similarity-based retrieval filtering in `retriever.py` and `tools.py`. Confidence scores printed to the user during agentic runs are now correctly interpretable. |

## 14. Neighbor-Aware Compression (NAC) Spike

| Field | Detail |
|---|---|
| **Topic** | Restoring document coherence across chunk boundaries after retrieval |
| **Date** | May 2025 |
| **Findings** | Classic RAG retrieves chunks independently. When the retriever returns chunks 17 and 18 from the same source, they are adjacent sections of the original document — merging them produces a richer, more coherent context than treating them separately. NAC requires two changes: (1) **Ingest-time**: tag every chunk with `chunk_seq` (sequential integer per source file) in ChromaDB metadata. (2) **Query-time**: after retrieval, scan `accumulated_chunks` for chunks where `source == source` and `|chunk_seq_A - chunk_seq_B| == 1`. Merge those neighbor runs into single contiguous blocks. This replaces N adjacent chunks with 1 chunk, compressing context without losing information and restoring original document flow. The merge operation feeds into the DC → LBC compression stages. |
| **Conclusion** | NAC was implemented as the first stage of `compress_context_pipeline()`. The `chunk_seq` metadata field is now written by `ingest.py`. NAC reliably triggers when the retriever finds consecutive sections from the same source — common for detailed factual queries. |
| **Relevance to Project** | `context_compression.py` NAC stage. `ingest.py` `chunk_seq` metadata. Particularly valuable for the ASD document corpus where related facts span consecutive sections. |

## 15. Academic Reference — ToolPRMBench Paper

| Field | Detail |
|---|---|
| **Topic** | "ToolPRMBench: A Benchmark for Process Reward Models in Tool-Using Agents" |
| **Date** | Read May 2025 |
| **Findings** | ToolPRMBench evaluates PRMs across 4 tool-using benchmarks (ToolTalk, GTA, BFCL, ToolSandbox) with 17 models. Key findings: (1) API-based LLMs (GPT-5 74.4%, Claude-4.5-haiku 75.1%) perform strongly as LLM-as-a-judge PRMs. (2) General PRMs trained on math (~50% avg) do not transfer to tool-using. (3) ToolPRM-GRPO (RL-trained, tool-specialized) achieves 78.6% avg — best overall, beating API LLMs. (4) SFT-trained PRMs overfit and degrade OOD (-13.6% to -20.4%); GRPO generalizes OOD (+21.8%). (5) Scaling model size helps but is not sufficient without specialized training. (6) Errors in tool-using agents often arise from failing low-level tool constraints (wrong argument format, missing state preconditions), not misunderstanding user intent. The benchmark uses offline sampling (local single-step errors around golden trajectories) + online sampling (full agent rollouts capturing multi-step failures). |
| **Conclusion** | The paper confirms that our current `check_answer_quality` heuristic is an inadequate PRM. LLM-as-a-judge is the right near-term upgrade. The thumbdown/interaction logs are the right substrate for eventually training a domain-specific reward model. GRPO-style RL training is the long-term aspiration if scale permits. |
| **Relevance to Project** | Directly informs the evaluation strategy for the agent's answer-quality checker. Validates the architecture choice to log all interactions and thumbdowns — this is the data needed for reward model training. |

## 16. LLM Output Failure Taxonomy — Cataloguing the Problem Space

| Field | Detail |
|---|---|
| **Topic** | Systematic catalogue of all ways an LLM can return the wrong output when asked for JSON |
| **Date** | June 2026 |
| **Findings** | 40 distinct failure modes identified through literature review, Stack Overflow, and empirical observation of the project's own LLM calls. Grouped into: **syntax failures** (broken JSON, truncation, trailing commas, single quotes, unquoted keys, unescaped quotes, duplicate keys, incorrect newline escaping); **structural failures** (wrong top-level type, list-wrapped dict, array-as-object, deeply nested, partial schema hallucination); **wrapper failures** (markdown fences, Python/JS/YAML code blocks, function-call style `submit_answer({...})`, blockquotes, internal reasoning chains); **language failures** (Python booleans/nulls, JS comments, XML, YAML, dataclass/class attribute syntax); **semantic failures** (hallucinated placeholder values, wrong numeric/date formats, stringified nested JSON, refusals, multiple alternative answers, infinite repetition); **encoding failures** (unicode corruption, control character injection). No single tool handles all 40 categories — they split into three natural treatment buckets. |
| **Conclusion** | String preprocessing handles wrapper and Python-literal failures at negligible cost. `json_repair` handles structural and syntax failures without an LLM call. LLM-based repair handles format translation failures (XML→JSON, YAML→JSON, class syntax→JSON) that no deterministic heuristic can fix. This directly drove the tiered pipeline design in `fix_llm_output.py`. |
| **Relevance to Project** | Defined the complete test matrix for `test_output_fixes.py` (40 cases × 8 schemas). Each case ID maps directly to a failure mode number in this taxonomy. |

## 17. Library Evaluation — `json_repair`

| Field | Detail |
|---|---|
| **Topic** | `json_repair` library (`pip install json-repair>=0.30`) — fault-tolerant JSON preprocessing for LLM outputs |
| **Date** | June 2026 |
| **Findings** | Industry-standard layer between LLMs and strict parsers. Core capability: closing missing brackets, quoting unquoted keys, fixing missing/trailing commas, stripping markdown fences, handling strings truncated mid-token. `return_objects=True` returns a Python object directly. `strict=True` raises instead of guessing. Key confirmed limitation (empirical): `json_repair` is **syntactic only** — a structurally valid JSON with a wrong value type (e.g. `"merged_from": "two"`) or a value extracted from broken string boundaries passes through unchanged. Also confirmed: the library can sometimes guess incorrectly on ambiguous truncations, so its output must always be Pydantic-validated before use. Minimum required version: `0.30` for `return_objects=True` stability. |
| **Conclusion** | Adopted as Tier 2 in the pipeline (after preprocessing, before LLM repair). Imported as a graceful-degradation dependency — `fix_llm_output.py` functions through Tiers 1 and 3 if the package is absent. Must add `json-repair>=0.30` to `requirements.txt`. |
| **Relevance to Project** | Core dependency of `fix_llm_output.py`. Without it, truncated JSON and trailing-comma failures fall through to the LLM repair tier unnecessarily, adding latency and API cost. |

## 18. Pydantic v2 Patterns for LLM Output Schema Enforcement

| Field | Detail |
|---|---|
| **Topic** | Pydantic v2 (`model_validate`, `field_validator(mode="before")`, `model_json_schema()`) as the schema enforcement layer after JSON parsing |
| **Date** | June 2026 |
| **Findings** | Key v2 patterns adopted: `ConfigDict(extra="ignore")` silently drops hallucinated extra keys. `mode="before"` validators coerce before type checking: `None→""` for optional prose fields, `str→int` with safe `int(float(v))` fallback for integer fields, `"single string"→["single string"]` for list fields. Lax enum normalisation: `v.upper().strip()` then check against allowed set, fall back to first enum value. Per-item `try/except ValidationError` in list-schema validation enables partial recovery without aborting the whole batch. `model.model_json_schema()` is used to inject the current schema definition into the `_JSON_REPAIR_PROMPT`, making the LLM repair call schema-aware. Confirmed: Pydantic validates structure and coerces types, but cannot detect semantic extraction errors (correct structure, wrong values relative to raw text) — this gap is filled by `_Verify_And_Correct`. |
| **Conclusion** | Adopted as Tier 4 in the pipeline. All 8 project schemas have dedicated Pydantic models in `fix_llm_output.py`. The `_BaseStrict` base class applies `extra="ignore"` and `str_strip_whitespace=True` uniformly. |
| **Relevance to Project** | Replaces the project's previous `_safe_json_parse` pattern. The coercive validators handle the most common type mismatches without needing an LLM call, keeping the majority of executions in the fast path. |

## 19. Prompt Engineering — Structure for Reliable Structured-Output LLM Calls

| Field | Detail |
|---|---|
| **Topic** | Effective prompting patterns for machine-parseable JSON output from LLMs, distilled from the project's own prompt corpus |
| **Date** | June 2026 |
| **Findings** | Five structural elements consistently improve reliability across all structured-output prompts in the project: (1) **Role sentence** — one imperative line stating the model's identity and job. (2) **Output contract** — format, schema, and hard negative constraints stated upfront before any examples, before the model reads the data. (3) **Worked example** — complete input→output pair using realistic domain data (not toy `foo`/`bar`). (4) **Rules block** — positive duties first, deduplication/citation rules, hard negatives (explicit anti-pattern names) last and emphatic; listing anti-patterns by name (`Do NOT write Python code`) is more reliable than a generic "output only JSON". (5) **Input placeholder at the end** — keeps instructions dense at the top of the context window where attention is strongest; appended by string concatenation at runtime. Additional finding: first-character anchoring (`The first character of your response must be '{'`) eliminates the most common failure mode (leading prose before the JSON). `temperature=0.0` on repair LLMs maximises determinism — correct reconstruction, not creative interpretation. |
| **Conclusion** | `_JSON_REPAIR_PROMPT` and `_VALUE_VERIFY_PROMPT` in `fix_llm_output.py` both follow this structure. The same pattern governs all structured-output prompts across the project (see `_CHUNK_MERGE_PROMPT`, `_DC_SCAN_PROMPT`, `_REDUNDANCY_JUDGE_PROMPT`). |
| **Relevance to Project** | Directly applied in `fix_llm_output.py`. Documented as a reusable template in project chats for future prompt authoring. |

## 20. Ablation Testing as Pipeline Evaluation Methodology

| Field | Detail |
|---|---|
| **Topic** | Using feature-flag toggles plus a deterministic ladder runner to measure per-stage contribution to a multi-stage agentic RAG pipeline |
| **Date** | June 2026 |
| **Findings** | Ablation testing — turning each component of a system off in turn and observing the effect — is the standard methodology in ML papers for justifying that each piece of an architecture earns its place. Applied to an agentic RAG pipeline, the relevant axes are: answer quality (does the final answer still cover the query?), faithfulness (does the answer still cite real chunks?), and latency (how much does each stage cost?). Three design choices matter for making ablation actually useful on this codebase. **(1) Granularity**: gating must be at the level a researcher actually wants to test — for this project that means each compression stage (NAC, DC, LBC), each validator, each output-fix tier, sub-query generation, draft creation, quality check, and auto-distillation. Coarser gating (e.g., one "ENABLE_COMPRESSION" master flag) loses the ability to ask "does DC actually help?" — finer gating creates combinatorial overhead with no extra signal. **(2) Ordering**: pure random combinations are irreproducible across days, while a fixed progressive ladder (all-OFF → all-ON, enabling flags in a deterministic left-to-right order) makes per-stage contributions visible directly from log filenames. **(3) Isolation**: each combination must run in a fresh subprocess; in-process flag mutation risks one run's state polluting the next, which is especially dangerous for the validator-crash class of failures where a partial state can hang the loop. Full Cartesian coverage (2^18 = 262k runs) is intractable; the progressive ladder gives O(N) coverage with the same crash-localisation property by construction. |
| **Conclusion** | Adopted progressive flag-ladder over random combinations and full Cartesian. The 10-step ladder is the production default; `--runs 6` (shorter) and larger values both work for quick sanity-passes vs deep sweeps. The harness lives in `run_combinations.py`; the flags it toggles live in `config.py`. Per-stage latency budgets and quality deltas will be tracked across ladder runs as the next planned analysis once BUG-020 and BUG-021 are closed. |
| **Relevance to Project** | Directly drives `run_combinations.py` and the 18-flag design of `config.py`. First ladder run uncovered two latent flag-wiring bugs (BUG-020 validators crash on flag-off; BUG-021 `ENABLE_AUTO_DISTILLATION` never read), validating the harness on its first execution. |

## 26. Hybrid vs Two-Track Retrieval in Self-Learning RAG
 
| Field | Detail |
|---|---|
| **Topic** | Should distilled `learned_qa` chunks be merged with `documents` chunks at retrieval, or kept as parallel channels? |
| **Date** | June 2026 |
| **Findings** | A self-learning RAG accumulates two qualitatively different evidence types. Source-document chunks are *ground-truth-by-provenance* — they were ingested from a vetted corpus and represent what the system can claim with citation. Learned-QA chunks are *user-validated synthesis* — they were emitted by the agent, accepted by a quality judge, and (in this system) distilled by an LLM into rephrased Q&A pairs; their value is that they encode preferred answers, corrections, and the shape of the answer the user actually wanted, not just what the source documents permit. These two kinds of evidence have different conflict semantics: when they disagree, the right behaviour is not "trust the higher-scoring chunk" but "trust the learned correction unless the source contradicts it at a level the user would consider authoritative." That decision cannot be made by a cosine-similarity ranker that doesn't even know which collection a chunk came from. Investigating the system's prior single-stream merger revealed the standard pathologies: source-document chunks displacing learned-QA chunks during top-k truncation, learned-QA score arithmetic operating under the wrong distance metric (Research topic 13 / topic 27), and validators that received mixed lists having no place to express precedence. The literature on RAG with memory (memory-augmented retrieval, episodic/semantic separation in cognitive-architecture-inspired agents, and recent retrieval-as-tool-use papers) generally points to channel separation as the structurally simpler option. Once channels are separate, precedence becomes a single declarative rule at the answer-context boundary; if channels stay merged, precedence has to be re-implemented at every downstream stage that touches the list. |
| **Conclusion** | Two-track retrieval is the right architecture for self-learning RAG. The two channels should be queried independently with their own per-channel depth parameters, validated independently, deduplicated and merged independently, accumulated independently, compressed independently, and combined only at the LLM context boundary with an explicit conflict-resolution rule preferring the learned channel. This conclusion drove ADR-029, ADR-030, ADR-031, and ADR-032. |
| **Relevance to Project** | Directly drove the 2026-06-11 refactor across `retriever.py`, `tools.py`, `agent_query.py`, `context_compression.py`, `feedback_store.py`, `self_learner.py`, and `prompts.py`, and motivated the creation of `learned_qa_store.py`. Closes the "learned QA mixed with normal document retrieval" gap previously documented in `Architecture.md`. |

## 27. Distance-Metric Consistency Across Collections in a Hybrid Vector Store
 
| Field | Detail |
|---|---|
| **Topic** | What happens when two collections in the same vector store use different distance metrics but share a single `similarity_score` formula and a single threshold? |
| **Date** | June 2026 |
| **Findings** | The `documents` collection was created with `hnsw:space = cosine`, but the `learned_qa` collection was created without an explicit `hnsw:space` argument, falling through to Chroma's L2 default. Both collections were ranked by `similarity_score = 1 - dist` and filtered through `MIN_SIMILARITY = 0.5`. On unit-normalized vectors (which `all-MiniLM-L6-v2` produces with `normalize_embeddings=True`), the relationship between L2 squared distance and cosine similarity is `‖a − b‖² = 2 − 2·cos(θ)`. So `1 - dist` for cosine is true cosine similarity, but `1 - dist` for L2 is `2·cos(θ) − 1` — same monotonic ordering but completely different threshold semantics. A learned-QA chunk that just barely passed the 0.5 threshold under L2 corresponds to a true cosine of about 0.75 — strongly relevant; another that fell below 0.5 might still be more cosine-similar than the surviving document chunks. Result: the precedence rule from ADR-030 was applied to a learned-QA list that had been thresholded under the wrong score arithmetic, so high-priority learned QA could be silently filtered out before precedence even got a chance to apply. The root cause was startup ordering: `agent_query.py` created the collection without specifying `hnsw:space`, then `self_learner.py` later requested it with cosine, but Chroma's `get_or_create_collection()` does not migrate distance metric — the underlying HNSW index has to be rebuilt with a snapshot/restore pass. The remediation pattern is to funnel all collection access through a single factory, detect non-canonical distance metrics at startup, and migrate in place with full snapshot, count-verified restore, and rollback on any failure. |
| **Conclusion** | When a system uses multiple Chroma collections that share scoring or threshold infrastructure, every collection must use the same distance metric, and that metric must be enforced at a single creation point — not assumed to follow from metadata. Migration of a wrong-metric collection requires a full HNSW rebuild via snapshot/restore; metadata edits alone do nothing. This conclusion drove the design of `learned_qa_store.py` (ADR-031). |
| **Relevance to Project** | Directly led to `learned_qa_store.py` and the 374-entry live L2→cosine migration. Closed `BUG-030`. Generalises Research topic 13's earlier finding (cosine vs L2 score arithmetic) from a single-collection issue to a multi-collection consistency requirement. |

## 28. Context Stuffing, Prompt Bloat, and the Self-Learning Feedback Loop Risk
 
| Field | Detail |
|---|---|
| **Topic** | Failure modes when an agentic RAG retrieves too many chunks and writes its own outputs back into the retrieval pool. |
| **Date** | June 2026 |
| **Findings** | A stress-test walk of the worst-case retrieval path (`user query → over-retrieval → all chunks inserted → prompt bloat → context-window saturation → higher cost, slower inference, worse answers`) identified eight distinct mitigations, all relevant to the self-learning loop. Five of them are conceptual mitigations independent of self-learning: distillation (already implemented), memory pruning, semantic compression, selective retrieval, and knowledge extraction. Three were judged structural fixes specific to the self-learning architecture: (1) `documents` and `learned_qa` must not be mixed at retrieval — otherwise the model can no longer disambiguate "what the corpus says" from "what I previously answered," and over-retrieval from one channel pollutes precedence reasoning for the other; (2) full previous answers must never be retrieved back into the answer context — distillation should store *lessons* (compact reformulated Q&A units) rather than *conversations*; storing full answers creates a runaway loop where the agent's own tokens accumulate in its own retrieval pool, drowning out source documents over time; (3) the answer context needs a hard prompt-budget allocator that bounds total input tokens regardless of how many chunks survived retrieval and validation. Additional engineering controls that fall out of the same analysis: deduplication *across* learned-QA entries (to prevent paraphrase inflation when the same interaction is distilled multiple ways), retrieval diversity caps (max-N per source / per type), and a marginal-gain early-exit that stops retrieval when the next query is unlikely to add information. The single-stream merger architecture made several of these mitigations impossible to implement cleanly — for example, "max 2 from learned_qa, max 3 from any single document source" requires per-source counters that only make sense if the channels are tracked separately. The two-track architecture is therefore a prerequisite for the rest of the stress-test mitigations, not an alternative to them. Distillation itself needs a modification: thumbdown feedback should be a first-class input to the self-learner, not just a retrieval-time blocklist, so the system can learn what *not* to assert as well as what to assert. |
| **Conclusion** | Stress-testing the worst-case retrieval path produced a prioritised mitigation list: (1) two-track retrieval, (2) never retrieve full prior answers, (3) hard prompt-budget allocator, (4) store lessons not conversations, (5) memory decay on learned QA, (6) cross-`learned_qa` deduplication, (7) retrieval diversity caps, (8) early-exit on marginal-gain drop. Items (1) and (the architectural prerequisites for) (2) are addressed by the 2026-06-11 refactor; the remaining items are planned follow-on work. The thumbdown-modification idea (distillation should consume thumbdowns) is also planned. |
| **Relevance to Project** | Motivated the two-track refactor (ADR-029) as a prerequisite for further stress-test mitigations. Frames the planned follow-on work on memory decay, prompt budgeting, and retrieval diversity in `agent_query.py` and `self_learner.py`. Documents the open risk that the self-learning loop can amplify itself if learned-QA storage is not actively bounded. |

## 29. Python `logging` Module — Hierarchy, Level Routing, And The Per-File `getLogger(__name__)` Pattern

| Field | Detail |
|---|---|
| **Topic** | The stdlib `logging` module's mental model and the production-grade patterns used to migrate the project off scattered `print()` calls. |
| **Date** | 2026-06-15 |
| **Findings** | The `logging` module is organised around named *logger* objects fetched via `logging.getLogger(name)`. Loggers are singletons by name — calling `getLogger("foo")` twice in the same process returns the same object. The conventional per-file idiom `logger = logging.getLogger(__name__)` at module scope produces a logger whose name is the importing module's dotted name, so every log record carries the source module as free metadata. Loggers form a tree by dotted parent/child (`app`, `app.retriever`, `app.retriever.bm25`) and child records propagate up to parents by default — disabling `propagate` on a child severs it from the root and forces it to handle records on its own. Each logger and each handler has its own *level*; a record must pass both the logger's level *and* its destination handler's level to be emitted, which means a record can be visible in a DEBUG-level file but invisible on an INFO-level console without any per-call code. Repeated configuration (calling `setup_logging()` more than once, or running `basicConfig` from multiple modules) silently adds duplicate handlers, producing every record twice — the standard fix is a guard flag on the root logger (`_CONFIGURED_ATTR` in the project's setup). The five levels in use are DEBUG (verbose diagnostic — variable values, raw responses, embedding shapes, intermediate calculations, "what the code is doing"), INFO (completed events — "what the system did"), WARNING (recoverable issues — fallback used, malformed output repaired, retry required), ERROR (operation that prevented a stage from completing), CRITICAL (program-stopping failures). The DEBUG-vs-INFO distinction is the most commonly muddled in practice; the working heuristic is *"if this message disappeared from production logs tomorrow, would anyone care?"* — if no, DEBUG; if yes, INFO. Filtering options at runtime include level-based filtering on handlers, custom `logging.Filter` subclasses for arbitrary record predicates (e.g. INFO-and-WARNING-only), and separate file targets per level for after-the-fact `grep`/`tail` workflows. |
| **Conclusion** | The per-file `getLogger(__name__)` pattern combined with a single central `setup_logging()` function is the minimum-code-change migration off `print()`. It buys timestamps, level filtering, per-module attribution, and retained per-run trace files without per-call boilerplate. `propagate=True` on diagnostic-named loggers is the correct default unless a child logger must be silenced from the root's handlers. The duplicate-handler trap requires an explicit idempotency guard on `setup_logging()`. This research directly drove ADR-033 (central `logger_config.py`) and the project-wide print→logger conversion. |
| **Relevance to Project** | The new `logger_config.py` module, the project-wide `getLogger(__name__)` adoption, the `_CONFIGURED_ATTR` idempotency guard, the choice of console-INFO + per-run debug-file-at-DEBUG handler routing, the `propagate=True` setting on the `llm_data_check` and `llm_json_tries` diagnostic loggers, and the severity-level audit in `context_compression.py` and `self_learner.py` (BUG-039) all derive directly from this research. |

## 30. LangGraph As A State-Machine Framework For Agentic Pipelines

| Field | Detail |
|---|---|
| **Topic** | When LangGraph adds value over a hand-rolled state machine for an agentic RAG pipeline, and where it doesn't. |
| **Date** | 2026-06-15 |
| **Findings** | LangGraph is a state-machine framework: nodes are functions, edges are typed transitions (including conditional ones), and a *checkpointer* serialises graph state at node boundaries so a paused or crashed run can resume from the last completed node rather than the start. The framework's marketed benefits — speed, reliability, "agentic-ness" — do not all hold uniformly. **Parallelism**: LangGraph supports parallel branches that merge at a fan-in node, so independent operations (multiple sub-query retrievals; multiple retrieval strategies like BM25 + vector + KG search; per-track validators) can run as `max(branches)` instead of `sum(branches)` — genuine speedup, but only where the work is genuinely independent. **Sequential pipelines**: NAC → DC → LBC → DRAFT → JUDGE is a dependency chain (each step consumes the prior step's output), so LangGraph orchestration cannot parallelise it; runtime is identical to a plain Python `for` loop and the framework adds small but real orchestration overhead. **Checkpointing**: this is the framework's strongest claim. With a `MemorySaver` (RAM-only) checkpointer, LangGraph can recover within a live process — a transient LLM error, a malformed-JSON parse failure, a retryable timeout — without re-running already-completed nodes. With a *durable* checkpointer (SQLite, Postgres, S3, JSON files) it can also recover across process death, deployment, container restart, or human-in-the-loop pauses lasting hours. **Critical limitation**: durability requires the checkpointer to write somewhere persistent *before* the failure occurs; if state lives only in RAM and the process dies, recovery is impossible — LangGraph does not change this fundamental property of computing. **Recovery granularity**: checkpoints are at node boundaries, so a failure inside a node restarts that node from its entry, not from the failing line within it. **Time travel**: a durable checkpoint store lets the user resume from an *earlier* checkpoint, not only the most recent one — useful for "go back and try a different branch" workflows. **Human-in-the-loop**: pause/resume is native; the equivalent in a hand-rolled pipeline requires manual state serialisation and restart plumbing. **Not magic**: LangGraph does not accelerate the LLM calls, embedding calls, or vector DB calls themselves — those still take what they take. The decision criterion is therefore not "does the pipeline have multiple phases" (it does) but "does the pipeline have *independent* phases that would parallelise, *failure modes* the existing retry paths can't already recover from, or *long-running pauses* like human review that survive across deployments." |
| **Conclusion** | For this project today, none of LangGraph's three highest-value features apply: the longest path is sequential, transient failures are already handled by the existing `llm_caller.py` retry/backoff layer (ADR-026), and there is no human-in-the-loop step or long-running pause. The genuine parallel opportunities (sub-queries during RETRIEVE; per-track validation) are smaller than a full framework migration and can be implemented with `asyncio.gather` / a thread pool at much lower cost. Decision: defer LangGraph adoption (ADR-034). Re-open when (a) parallel sub-query retrieval is implemented and shows enough complexity to justify a framework, (b) human-in-the-loop review is added, or (c) workflows must survive process restarts and a durable checkpoint store is on the table anyway. |
| **Relevance to Project** | Directly drove ADR-034 (defer LangGraph). Confirms that the `langgraph` declaration already in `requirements.txt` is a transitional artefact rather than an active dependency — a follow-on cleanup can either remove it or wait until a future ADR reverses the decision. Frames the genuine parallel-execution opportunities (parallel sub-query retrieval, parallel per-track validation) as candidates for `asyncio` / thread-pool concurrency rather than framework adoption. Documents the checkpoint-recovery requirement for future workflows that span process lifetimes (e.g. user-disconnect-and-return, deployment-during-workflow). |

## 31. LangGraph Hands-On Mechanics — `StateGraph` Compilation, Conditional Edges, and Visualization
 
| Field | Detail |
|---|---|
| **Topic** | Practical `StateGraph` syntax and tooling gaps discovered while building small graphs by hand, as a follow-up to the theoretical evaluation in Research topic 30. |
| **Date** | 2026-06-16 |
| **Findings** | A `StateGraph` is built from a `TypedDict` state class, `add_node(name, fn)` calls where each node function receives the full state and returns only the fields it updates, and `add_edge`/`add_conditional_edges` calls wiring `START`/`END` sentinels to named nodes. A conditional edge takes a router function that inspects state and returns a string key, which a dict argument maps to the actual next-node name (or `END`) — this is the mechanism behind the no-context early exit wired into `tempFile.py`'s `route_after_retrieve`. The object returned while building the graph (the `StateGraph` itself) and the object returned by `.compile()` are distinct — only the compiled graph exposes `.get_graph()` for inspection/visualization; calling it on the uncompiled builder raises `AttributeError`. Visualization has two paths: `draw_mermaid()` returns plain Mermaid source text with no extra dependencies (viewable at mermaid.live), while `draw_mermaid_png()` renders an actual image but requires `playwright` plus a downloaded Chromium build (`playwright install chromium`) to do the rendering. `IPython.display.Image(...)`/`display(...)` only works inside a Jupyter kernel — in a plain terminal script it is a no-op (or errors), so the correct pattern for a script is to write the PNG bytes returned by `draw_mermaid_png()` to a file with a normal `open(..., "wb")`. Checkpointing for resumability is enabled by compiling with `checkpointer=MemorySaver()` and passing a `thread_id` inside the `config={"configurable": {...}}` argument to `.invoke()` — this is in-memory only and does not survive process death, consistent with the durability caveat already recorded in Research topic 30. A simple state-design heuristic emerged from discussion: "if I checkpoint this graph and resume tomorrow, does this value represent the current progress of this specific run?" — yes means it belongs in graph state (query, retrieved/validated/compressed chunks, draft, iteration/retrieval counters, final answer); no means it's configuration or an injected dependency (the project's 18 `ENABLE_*` flags, `MAX_TOTAL_RETRIEVALS`, `RETRIEVAL_TOP_K`/`_TOP_L`, and service singletons like `EmbeddingManager`, `VectorStore`, `RAGRetriever`, and the LLM clients) and should be passed via `config` or dependency-injected into nodes, not stored in state. |
| **Conclusion** | The mechanics are straightforward once distinguished clearly: state vs. config/dependencies, builder vs. compiled graph, and the two visualization paths (text-only vs. rendered-PNG-via-Playwright). All three mistakes made while building the first toy script (missing `__main__` guard, Jupyter-only display call, `.get_graph()` on the wrong object) were tooling/environment confusions rather than `StateGraph` design errors, suggesting the state/config split is the part actually worth getting right before any production port — consistent with the answer given when asked where the project's 18 config flags should live. |
| **Relevance to Project** | Directly informed ADR-035 (pause the in-progress migration, practice on disposable graphs first) and the design of the learning sandbox `tempFile.py`, which deliberately wires the project's real `EmbeddingManager`, `VectorStore`, `RAGRetriever`, and `learned_qa_store` into a minimal two-node graph rather than a fully synthetic example, so that the next real migration attempt at `agent_query.py` starts from a working, hands-tested mental model rather than syntax review alone. Builds directly on Research topic 30 (theoretical LangGraph evaluation, 2026-06-15). |

| **Topic** | How LangGraph resolves conflicting writes from parallel branches, and the two state-field patterns used in `app_workflow/state.py`. |
| **Date** | 2026-06-17 — 2026-06-18 |
| **Findings** | When multiple parallel `Send` branches each return a value for the same state field, LangGraph must decide what to do with multiple concurrent writes. The default behaviour is last-write-wins (the last branch to complete overwrites all prior values). For an accumulation use case — collecting retrieved chunks from multiple parallel sub-query branches — last-write-wins would silently discard all but one branch's results. The solution is `Annotated[list[dict], operator.add]`: wrapping the type with a reducer function tells LangGraph to call `operator.add(existing, new)` on each write, so the field accumulates across all parallel branches rather than being overwritten. This is the mechanism behind `retrieved_document_chunks` and `retrieved_learned_qa_chunks` in `GraphState`. `NotRequired` (from `typing`) is the correct annotation for state fields that are populated by some nodes but not others (e.g. `dedup_merge_document_pairs` is only written by `dedup_merge_documents` and only read by `validate_dedup_merge_documents` — most nodes never touch it). Using `NotRequired` avoids `KeyError` when a node tries to read a field that was never set in the current run. The distinction from Research topic 31's state-vs-config heuristic applies: `Annotated` reducers and `NotRequired` are type-level annotations on *state* fields (values that change during a run); they do not apply to config constants or service singletons. |
| **Conclusion** | Use `Annotated[list[T], operator.add]` for any field that multiple parallel branches write to and whose values should be combined. Use `NotRequired` for any field that only some nodes write. Both are necessary for the dual-track architecture because retrieval runs in parallel fan-out and the per-track validation pairs are only present when validation is enabled. |
| **Relevance to Project** | Directly drove the `state.py` design in `app_workflow/`: all `retrieved_*_chunks` fields use `Annotated[..., operator.add]`; all intermediate validation-pair fields (`dedup_merge_document_pairs`, `nac_merge_pairs_documents`, etc.) use `NotRequired`. |

## 34. Thread-Based Timeout Pattern in Python — `ThreadPoolExecutor.submit` + `future.result(timeout=N)`

| Field | Detail |
|---|---|
| **Topic** | How to impose a call-side deadline on a blocking operation that has no native timeout parameter, using only the Python standard library on any platform including Windows. |
| **Date** | 2026-06-22 |
| **Findings** | `concurrent.futures.ThreadPoolExecutor` provides a cross-platform, library-agnostic timeout mechanism: `executor.submit(fn, *args)` dispatches the call to a background thread and returns a `Future`; `future.result(timeout=N)` blocks the calling thread for at most N seconds. If the future completes within N seconds the result is returned normally; if not, `concurrent.futures.TimeoutError` is raised on the calling thread after exactly N seconds. **Critical caveat**: only the calling thread is unblocked — the background thread that is running `fn` is not cancelled, killed, or interrupted. It continues to completion (or error) in the background, still holding any OS-level resources (sockets, file handles, GPU compute slots) until it finishes. This is unavoidable in CPython's threading model: there is no safe mechanism to kill an arbitrary running thread from outside. Practical consequence for this project: Groq HTTP calls continue until the provider responds (bounded by the provider's own timeout); ChromaDB `.query()` is local and fast; SentenceTransformers' `model.encode()` runs on GPU memory with no network I/O — none of these can deadlock indefinitely, so resource leakage is bounded and acceptable. **Contrast with `signal.alarm(N)`**: POSIX `signal.alarm` can hard-interrupt the process at N seconds, but (a) it is unavailable on Windows and (b) it cannot interrupt calls that hold the GIL, which includes C extensions (NumPy inside SentenceTransformers, ChromaDB's native layer). `ThreadPoolExecutor` sidesteps the GIL constraint entirely because the background thread holds the GIL while executing the call; the calling thread only blocks on the `future.result()` call, which releases the GIL while waiting. **Calibration methodology**: observe wall-clock durations from ten benchmark runs to establish an empirical p95, then apply a safety margin (2× for the LLM where per-call variance is high; ~14× for ChromaDB retrieval and ~500× for embedding where both p95 values are stable sub-second) to set the timeout constant. Margins are deliberately asymmetric — a false positive (triggering a timeout on a legitimately slow-but-correct call) is more disruptive than a generous upper bound. |
| **Conclusion** | Use `ThreadPoolExecutor(max_workers=1) + future.result(timeout=N)` as the standard pattern for imposing call-side deadlines on blocking I/O that lacks its own timeout parameter. Accept that the background thread continues; verify it cannot deadlock or leak unbounded resources. Calibrate constants from empirical p95 + a multiplier that normal operation will never reach but that pathological hangs will. |
| **Relevance to Project** | Directly drove ADR-042 and the June 22 additions to `llm_caller.py`, `retriever.py`, and `embedding_manager.py` in both pipelines. Explains why `signal.alarm` was rejected (Windows + GIL) and why per-library timeout parameters were insufficient (ChromaDB and SentenceTransformers do not expose them). The "background thread continues" caveat informed the decision to avoid this pattern in hot paths that hold exclusive locks or accumulate unbounded resources. Builds on Research topic 34 (this topic) and ADR-042 for the implementation decision record. |

## 35. Semaphores vs. FIFO Queue for LLM Call Serialization Under Concurrent Load

| Field | Detail |
|---|---|
| **Topic** | Whether a `threading.Semaphore` or a `queue.Queue`-based FIFO gate is the correct synchronization primitive for preventing Groq token-quota starvation when multiple threads call `llm_invoke()` concurrently. |
| **Date** | 2026-06-24 |
| **Findings** | **Semaphore approach:** a `threading.Semaphore(1)` limits concurrency to one caller at any moment. The flaw appears when a thread holding the semaphore receives a 429: it must release the semaphore before sleeping the retry delay, otherwise all other threads stall indefinitely. Once it releases, any waiting thread immediately acquires the semaphore and begins burning the token window. When the original 429-holder re-acquires after sleeping, another thread may already have exhausted the quota again. The semaphore provides admission control but not ordering priority: the 429-holder competes equally with new arrivals on every re-acquisition and can cycle through all retries on 429s while new threads continuously starve it. **FIFO queue approach:** each thread places a `threading.Event` on a shared `queue.Queue` and blocks until the current gate-holder sets it. A thread that receives a 429 does NOT release the gate — it holds the event, sleeps the full token-reset window derived from Groq response headers (`x-ratelimit-reset-tokens` → `x-ratelimit-reset-requests` → `retry-after`), then retries directly with no competing calls possible during the sleep. After a successful call, `_gate_release_to_next()` pops the oldest event and wakes the next thread in strict FIFO order. This guarantees: (a) only one thread calls Groq at a time, (b) a 429-holding thread retries with no competing calls during the full reset window, (c) threads are served in arrival order with no starvation. **`asyncio.Lock` misuse:** the prior `async with _query_lock:` in `api.py`'s `/query` handler appeared to serialize at the HTTP layer, but `asyncio.Lock` is not a cross-thread mutex — it is safe only within a single asyncio event loop thread. `asyncio.to_thread()` immediately hands off blocking work to a thread pool, releasing the lock before the pipeline executes. This made the lock entirely ineffective as a concurrency guard for the threading layer where contention occurs. **Adaptive cooldown rationale:** even with a strict FIFO gate, a rapid back-to-back sequence of gate releases (each consuming a different number of tokens) can still briefly breach the per-minute token limit. An adaptive `_cooldown_floor` (derived from `x-ratelimit-remaining-tokens` headers, doubling on 429-recovery, halving on clean-success streak) absorbs this residual without requiring a full 429-cycle wait. |
| **Conclusion** | Semaphores are insufficient for the token-quota exhaustion problem because they provide no guarantee that a 429-holding thread will regain the gate before new arrivals. A FIFO gate where the 429-holding thread retains the gate during its reset-window sleep is the correct primitive: it combines strict ordering, gate retention on failure, and thread-safe semantics (`threading.Lock` + `queue.Queue`). `asyncio.Lock` is not a cross-thread mutex and must not be used for thread pool serialization. |
| **Relevance to Project** | Directly drove ADR-044 and ADR-045 and the FIFO gate implementation in both `app/llm_caller.py` and `app_workflow/services/llm_caller.py`. Explains why the prior `threading.Semaphore` design would have re-introduced BUG-053 in a different form, and why `asyncio.Lock` at the `/query` handler level was the root cause of the original failure. |

## 36. MongoDB Replica Sets and Multi-Document Transaction Requirements

| Field | Detail |
|---|---|
| **Topic** | Why MongoDB requires a replica set to support multi-document session transactions, and how to initialise a single-node replica set for local development. |
| **Date** | 2026-06-27 |
| **Findings** | MongoDB's multi-document transactions (`client.start_session()` + `session.start_transaction()`) are only available when the `mongod` instance is running as part of a replica set — they are not supported by a standalone `mongod`. This is a deliberate design constraint: replica sets maintain an oplog (operations log) that is the mechanism MongoDB uses to roll back partial transactions on failure; standalone instances have no oplog. A single-node replica set (often called `rs0`) satisfies the requirement with zero replication overhead and is the standard pattern for local development. To convert a standalone instance: add `replication: replSetName: "rs0"` to `mongod.cfg`, restart the service, then run `rs.initiate()` from a `MongoClient` connected with `directConnection=True`. The `directConnection=True` parameter bypasses PyMongo's topology-discovery phase, which would otherwise fail with `ServerSelectionTimeoutError: Primary()` if the driver tries to discover the primary before `rs.initiate()` has designated one. After `rs.initiate()` completes, standard connections (without `directConnection`) work normally and see a single-node replica set with the local `mongod` as the sole primary. `IndexKeySpecsConflict` errors can arise when two modules attempt to create an index with the same name but different options (e.g. one with `sparse=True` and one without): MongoDB rejects the second call because the existing index spec does not match — see BUG-054. The fix is to ensure all `create_index` calls for the same field produce identical specs across every module that shares the same database. |
| **Conclusion** | For local development, a single-node `rs0` replica set is the correct MongoDB setup when session transactions are needed. The steps are: (1) add `replSetName: "rs0"` to `mongod.cfg`, (2) restart MongoDB, (3) run `rs.initiate()` once via `directConnection=True`. No sharding or additional nodes required. |
| **Relevance to Project** | Directly required by ADR-048 (MongoDB session transactions for atomic thumbdown write). The `directConnection=True` trick was needed to run `rs.initiate()` successfully after restarting MongoDB with the replica-set config, which caused BUG-054's `IndexKeySpecsConflict` surface during startup. |

## 37. `DuplicateKeyError` as an Idempotency Guard for LangGraph Node Retries

| Field | Detail |
|---|---|
| **Topic** | How to use MongoDB's unique-index `DuplicateKeyError` as a low-overhead idempotency guard when a LangGraph node function may be called more than once per graph invocation due to the framework's retry machinery. |
| **Date** | 2026-06-27 |
| **Findings** | LangGraph's `run_with_retry` mechanism (used by graph compilation to handle transient node failures) can re-execute a node function after a non-fatal error. If that node performs a `collection.insert_one(record)` keyed by a field with a unique index (e.g. `request_id`), the second execution will fail with `pymongo.errors.DuplicateKeyError` because the first execution already inserted the document. Without a handler, this exception propagates out of the node and can either crash the graph invocation or trigger another retry loop. The correct handling pattern is `try/except DuplicateKeyError: logger.warning(...); return` — on a duplicate, log a warning (to preserve observability) and return cleanly. The rationale: the first `insert_one` already succeeded and persisted the record; the second call is a no-op from a data-consistency perspective. This pattern converts an otherwise fatal re-insertion error into an explicit, observable idempotency guarantee. The same pattern applies to any insert-once operation in a retry-capable context: it is semantically equivalent to the common HTTP idempotency pattern where a `PUT` with a content-addressed key silently succeeds on a duplicate. For this to work correctly, the key used for the unique index must be stable across retries — `request_id` (a `uuid4` generated once per HTTP request in `api.py` and carried in graph state) satisfies this requirement. |
| **Conclusion** | Wrap any `insert_one` that has a business-level uniqueness constraint (e.g. "one interaction log per request") in `try/except DuplicateKeyError` when the caller is a LangGraph node or any other retry-capable context. Log a warning on duplicate so the retry is visible in logs without surfacing as an error. |
| **Relevance to Project** | Directly drove the fix for BUG-055 in both `app/feedback_store.py` and `app_workflow/services/feedback_store.py`. The unique index on `request_id` in `feedback_interactions` was added for correctness (one log per request), but without the `DuplicateKeyError` guard it became a crash path under LangGraph's retry machinery. |
| **Relevance to Project** | Directly drove ADR-044 and the June 24 implementation of `_gate_acquire` / `_gate_release_to_next` / `_apply_cooldown` in `app/llm_caller.py`. Explains why the initial semaphore attempt was discarded and why FIFO ordering is strictly necessary rather than admission-control-only limiting. The FIFO gate was ported to `app_workflow/services/llm_caller.py` on 2026-06-25 (see ADR-045) — both pipelines now use the identical gate, so this research applies equally to both. Builds on Research topic 34 (ThreadPoolExecutor timeout pattern) for the threading model context. |

## 38. Cosine vs. Jaccard Similarity for Inter-Variant Query Deduplication

| Field | Detail |
|---|---|
| **Topic** | Whether cosine similarity on sentence embeddings or Jaccard similarity on token sets is the more appropriate metric for identifying semantically redundant query variants before retrieval. |
| **Date** | 2026-06-29 |
| **Findings** | 775 variant pairs were extracted from `interactions.jsonl` (pairs drawn from variant lists generated in prior sessions). Both metrics were computed for each pair. **Jaccard on token sets:** treats queries as bags of words; sensitive to exact term overlap but blind to semantic equivalence expressed with different vocabulary. A pair like `("motor control in ASD", "motor function and autism")` scores near zero Jaccard despite being semantically identical. Heavily penalises paraphrases, which are the primary source of genuine inter-variant redundancy in this pipeline. **Cosine on sentence embeddings (`all-MiniLM-L6-v2`):** encodes semantic meaning directly; near-duplicate semantic variants cluster above 0.95 cosine even when surface wording differs. The pipeline already holds an `EmbeddingManager` singleton and the query has already been embedded for retrieval, so computing cosine between variant embeddings adds milliseconds and zero additional I/O. **Threshold selection:** at cosine ≥ 0.95, pairs with clearly distinct retrieval intent (e.g. "what causes motor delays" vs "what interventions help motor delays") scored below threshold; genuinely redundant pairs (paraphrases, synonym swaps) scored above. No Jaccard threshold was found that achieved similar precision without false-positives on paraphrase pairs. **Computational comparison:** Jaccard requires tokenisation but no model call; cosine requires embedding each variant (but variants are short — sub-10-word — and the embedding model runs in <5 ms per batch on CUDA). Given that the pipeline must embed the original query anyway (for retrieval), cosine adds negligible overhead. |
| **Conclusion** | Use cosine similarity on sentence embeddings for inter-variant deduplication, with a threshold of 0.95 for the pairwise dedup pass (`PRE_RETRIEVAL_SIM_THRESHOLD`) and 0.85 for the variant-vs-query similarity ranking pass. Jaccard is insufficient for paraphrase detection and adds no precision advantage that cosine does not already provide. |
| **Relevance to Project** | Directly drove ADR-050 and the June 29 implementation of `pre_retrieval_filter()` in `app_workflow/nodes/query_variants.py`. Explains why Jaccard was considered and rejected, and why `PRE_RETRIEVAL_SIM_THRESHOLD = 0.95` was chosen as the inter-variant dedup threshold. |

## 39. Log-Based Retrieval Parameter Tuning — Evidence-Driven Selection of `RETRIEVAL_TOP_K`, `RETRIEVAL_TOP_L`, and Per-Collection Score Thresholds

| Field | Detail |
|---|---|
| **Topic** | How to derive evidence-based values for `RETRIEVAL_TOP_K`, `RETRIEVAL_TOP_L`, `DOCUMENTS_MIN_SIMILARITY`, and `LEARNED_QA_MIN_SIMILARITY` from production debug logs rather than from documentation defaults or intuition. |
| **Date** | 2026-06-29 |
| **Findings** | Production debug logs from completed `app_workflow/` runs were analysed. Justifies the decision to separate the two per-collection thresholds (the score distributions differ enough to warrant different floors) and provides the empirical basis for the initial 0.5 values and the tuned targets. |

## 40. A/B Log Comparison Methodology for Evidence-Based Retrieval Config Tuning

| Field | Detail |
|---|---|
| **Topic** | How to use matched-pair debug log comparison — same query, different config values — to derive evidence-based retrieval config values rather than relying on documentation defaults or score-distribution shape alone. |
| **Date** | 2026-06-30 |

## 45. Academic Reference — "Continual Harness: Online Adaptation for Self-Improving Foundation Agents"

| Field | Detail |
|---|---|
| **Topic** | A paper proposing that an LLM agent's *harness* (system prompt, memory, skills, sub-agents) — not just the model — should be continuously and automatically refined while the agent works, and a follow-on extension that also fine-tunes the underlying model from the same trajectory data |
| **Date** | Read 2026-07-03 |
| **Findings** | The paper studies agents playing Pokémon and defines a **harness** as the four-part infrastructure surrounding an LLM: the system prompt, persistent memory, reusable skills (higher-level procedures built from primitive tools + reasoning — distinct from tools themselves), and sub-agents (task-specialized instances, e.g. navigation/battle/puzzle). A **minimal harness** (screenshot + buttons + generic prompt only) makes almost no progress even with frontier models; an **expert harness** is hand-engineered by a human over many iterations (their prior system, "Gemini Plays Pokémon"), but the human becomes the bottleneck — every few hours a person manually edits the prompt, memory, skills, and sub-agents. **Continual Harness** removes the human from that loop: a second role, the **Refiner** (which can be the *same* underlying LLM as the acting **Agent**, just invoked differently), periodically inspects the recent trajectory, diagnoses specific failure classes (stuck navigation, lost battles, repeated reasoning, discovered facts worth remembering), and edits the harness state accordingly — all **online** (no stop/train/restart cycle — "reset-free learning") and purely **in-context** (no model-weight changes; the LLM's weights are static, only what's in its context window changes). Empirically: stronger models benefit far more from a self-improving harness than weaker ones — a **capability floor** exists below which more scaffolding does not help (e.g. Gemini Flash Lite saw almost no gain), while Gemini Pro showed harness-driven gains that were **Pareto-dominant** on a cost-vs-completion plot (lower cost *and* higher milestone completion than the minimal harness). The paper's extension, **Continual Model-Harness Co-Learning**, adds a second loop on top: gameplay rollouts are scored by a **Process Reward Model** (PRM — dense per-step reward, e.g. +2 for good navigation, -3 for a repeated mistake, versus traditional RL's sparse end-of-episode reward only); **low-reward windows** identified by the PRM are sent to a stronger **frontier teacher** model (Gemini Pro) which produces a corrected version of that trajectory segment (**relabeling**); the target open-source model (Gemma) is then fine-tuned on the relabeled trajectories via **"soft SFT"** (supervised fine-tuning on corrected-but-not-perfectly-ground-truth data). Both the harness-refinement loop and the model-fine-tuning loop consume the *same* trajectory data, and the two loops reinforce each other: a better harness produces better (cleaner) training trajectories, and a better fine-tuned model reaches previously-unseen game states, surfacing new failure modes for the harness to address next. Progress was sustained across multiple training iterations and worked starting from both early-game and mid-game checkpoints. |
| **Conclusion** | No code changes resulted from this reading session — it was a comprehension/mapping pass, not an implementation task. The paper's harness framing (prompt + memory + skills + sub-agents, refined by a Refiner distinct-in-role-but-possibly-identical-in-model to the acting Agent) maps loosely onto this project's existing architecture: `config.py`/`prompts.py` (~harness configuration), the `learned_qa` ChromaDB collection (~memory), `tools.py` (~the tools layer that skills would be built from), and the RETRIEVE→COMPRESS→DRAFT→JUDGE state machine (~the Agent loop). The project currently has **no equivalent of the paper's Refiner role** — nothing in the pipeline inspects its own run logs and edits its own prompts, thresholds, or tool set at runtime; every tuning pass to date (e.g. ADR-053's `RETRIEVAL_TOP_K`/similarity-threshold tuning via `extract_logs.py`) has been a human-driven log-analysis loop, not an agent-driven one. |
| **Relevance to Project** | Surfaces a candidate long-term direction: an agent-driven "Refiner" that periodically reads `run_logs/` (or `extract_logs.py` output) and proposes `config.py`/`prompts.py` adjustments automatically, generalizing the human A/B-log-tuning methodology already validated in Research topic 40/ADR-053. Also reinforces the project's existing tools-vs-skills distinction (Research topic — none yet dedicated, but directly relevant to `tools.py`'s current fixed two-tool design of `retrieve_documents`/`compress_context`) as a live open question for any future move toward reusable higher-level procedures. No implementation is planned yet; recorded as background reading for future architecture discussions. |

| Field | Detail |
|---|---|
| **Topic** | A paper proposing that a language model generate its own fine-tuning data and update directives ("self-edits") and learn, via reinforcement learning, which self-edits actually improve its own downstream performance |

The paper is filed as a candidate future direction for `self_learner.py`'s distillation step: instead of a fixed, un-scored rephrasing prompt, a self-edit-style approach would require (a) a way to score whether a given distilled QA pair actually improved subsequent retrieval/answer quality, and (b) an RL or preference-learning loop over the distillation prompt itself — neither of which exists today. ## 48. Continual Harness — Reference Implementation Deep Dive (`continual-harness` Repo)

| Field | Detail |
|---|---|
| **Topic** | Traced the actual reference-implementation codebase behind the Continual Harness paper (the PokeAgent Challenge harness, a separate local repository) at file/function level, to check the paper's claims against real code and extract concrete implementation patterns for the "Refiner" concept surfaced in Research topic 45 |
| **Date** | 2026-07-07 |
| **Findings** | The codebase is a two-process architecture: `server/app.py` owns the emulator and an always-running `game_loop()`; `agents/PokeAgent.py` owns the LLM agent and never touches the emulator directly — every perception/action call goes over HTTP via an `MCPToolAdapter`. The core loop is `run() → run_step() → self.vlm.get_query(...) → _handle_vlm_function_calls() → _execute_function_call_by_name()` dispatch. The paper's **Refiner** is `HarnessEvolver` (`agents/utils/harness_evolver.py`): it composes a `PromptOptimizer` instance and reuses that optimizer's text-only VLM for all of its own calls. `evolve()` runs four independent, individually try/except-wrapped passes over a trajectory window read from `trajectory_history.jsonl` — `_evolve_prompt` (delegates to `PromptOptimizer.optimize_prompt`), `_evolve_subagents` (CRUD via a `SubagentStore`), `_evolve_skills` (CRUD via a `SkillStore`, with a hand-coded "used `run_code` instead of `run_skill`" antipattern detector), and `_evolve_memory` (CRUD via a `MemoryStore` — no delete path, only "demote importance"). Each pass makes exactly one LLM call parsed as JSON. Critically, the **trigger schedule is hardcoded, not driven by the paper's stated `F`/warm-up parameters as a runtime input**: `should_evolve()` fires every 25 steps after a 25-step warm-up, then every 100 steps past step 200 — the CLI's `--optimization-window-length` flag only controls how many trajectory steps each pass *analyzes*, decoupled from how often evolution actually runs (an assumption the paper's own notation, `Ï„_{t−F:t}`, implies should be the same value). Only 2 of the paper's 4 named failure signatures (navigation loops, tool-call failures — vs. stalled objectives, missed exploration) have dedicated detector code; the other two are left for the VLM to infer unaided from raw trajectory text in the same call that proposes edits. The paper itself supplies no concrete thresholds, scoring functions, or example Refiner prompts — those details exist only in code, not in the paper text. `run_code`/`run_skill` sandboxing is **not** a real OS/process sandbox — it is plain Python `exec()` against a restricted `globals()` dict (a cut-down `__builtins__` with no `open`/`os`/`eval`, plus a `tools` dict of closures that proxy to `mcp_adapter.call_tool(...)`); every line of code ever executed there was generated by the LLM itself (same-turn for `run_code`, or a previously LLM-authored saved skill for `run_skill`) — no hardcoded or human-authored skill code exists anywhere in the stores. Persistence: `skills.json`/`subagents.json`/`memory.json` are rewritten to disk immediately on every CRUD op; prompt-evolution output is a versioned markdown snapshot and never overwrites the original base-prompt file (only an in-memory `current_base_prompt` is updated for the rest of the run); an `evolution_log.jsonl` records an audit trail of every `evolve()` call. The multi-provider `VLM` class (`utils/agent_infrastructure/vlm_backends.py`) defines one canonical Gemini-style tool-schema dict format and translates it per-provider at init; non-Gemini backends (Anthropic, OpenAI, OpenRouter) wrap their native response shape into a synthetic Gemini-like adapter object so the rest of the agent code never branches on backend — the same "provider-agnostic dispatcher" idea this project already uses for `llm_caller.py`/`llm_setup.py`, but implemented one layer deeper (full response-*shape* normalization across providers, not just `base_url`/model-name swapping). A "scaffold" in that codebase (`pokeagent`/`simple`/`simplest`/`continualharness`/`vision_only`) is a named bundle of tool surface + prompt + sub-agent access, all instantiating the same agent class — directly analogous to this project's `ENABLE_*` flag combinations in `config.py`, but expressed as named presets rather than independently toggleable booleans. Confirmed by grep and a `pyproject.toml` dependency check: **no gradient-based training code exists anywhere in the repo** — the paper's "Continual Model-Harness Co-Learning" / PRM extension (Research topic 45) has no reference implementation to study; the repo's README mentions it in one sentence only. |
| **Conclusion** | No code changes resulted from this session — it was a second, code-level comprehension pass following Research topic 45's paper-level reading. It converts that topic's "no equivalent Refiner exists in this project" gap into concrete, portable implementation choices: the four-pass CRUD structure (prompt / sub-agents / skills / memory), a fixed-step-schedule trigger decoupled from a separately-configurable trajectory-window size, and an `exec()`-in-restricted-`globals()` sandboxing pattern for any future LLM-authored dynamic tool code. The finding that the paper leaves thresholds and scoring functions fully unspecified means adopting this pattern would require inventing that logic from scratch — there is no reference default to copy, only a reference *structure*. |
| **Relevance to Project** | The four-pass structure maps unevenly onto this project's current surfaces: prompt → `prompts.py`, memory → the `learned_qa` collection, but there is no existing skills/subagents layer for a "skills" or "subagents" CRUD pass to act on — `tools.py`'s fixed two-tool design would need to grow before that part of the pattern has anything to apply to. The hardcoded-schedule-decoupled-from-window-size trigger design is a reusable idea for any future self-tuning loop, distinct in kind from the human-driven `extract_logs.py` config tuning already validated in Research topic 40/ADR-053. The `exec()`-in-restricted-namespace sandbox pattern is directly relevant background if LLM-authored dynamic tool/skill execution is ever considered for this project. No implementation is planned yet — recorded as background reading, same status as Research topic 45. |

## 49. SEAL — Reference Implementation Deep Dive (`few-shot/` ARC and `general-knowledge/` SQuAD Pipelines)

| Field | Detail |
|---|---|
| **Topic** | Traced the actual reference-implementation codebase behind the SEAL paper (a separate local repository) across both its ARC pipeline (`few-shot/`) and its SQuAD pipeline (`general-knowledge/`), to understand mechanically how "self-edits" are generated, scored, and distilled back into a persistent policy — extending Research topic 47's paper-level reading with concrete code-level mechanics |
| **Date** | 2026-07-07 |
| **Findings** | The ARC pipeline (`few-shot/self-edit.py`) runs as one process, two phases, no server. **Phase 1**: a vLLM instance samples, per task, a JSON "self-edit" — the model's own choice of augmentation flags plus training hyperparameters (learning rate, epochs, strategy). This JSON *is* the self-edit; it is literally the model choosing how it wants to be trained. **Phase 2** (`arclib/update_model.py`'s `TTT` class): for every sampled self-edit, `reset_lora()` restores a clean LoRA snapshot, the chosen augmentations build a synthetic leave-n-out training set, and an HF `Trainer` fine-tunes a disposable adapter saved to disk. **Evaluation** (`eval-self-edits.py`) loads each adapter via vLLM's dynamic `LoRARequest`, queries the held-out test grid through several augmented rephrasings, and `vote()` aggregates predictions. **Reward** (`arclib/eval.py`'s `accuracy()`) is a single binary check — did ground truth appear in the submitted attempts — with no partial credit and no dense per-step signal (contrast with Continual Harness's PRM in topic 45/48). **Selection + policy update** (`BC-self-edit.py`): only the `(prompt, response)` pairs behind *correct* adapters survive; a fresh LoRA is behavior-cloned on the pooled survivors (loss on the self-edit JSON text, not on the grid answer), then `merge_and_unload()` folds it into full-precision weights saved as `RL_trained_model` — the classic **ReST-EM** pattern (generate → filter by outcome → SFT on the filtered subset → repeat). The single most important mechanic, confirmed only after several rounds of clarifying questions against the actual code: **the disposable per-task LoRA that gets evaluated is never merged into anything and is discarded regardless of its score.** What persists across iterations is only the *text* of the self-edits behind successful outcomes, distilled back into the self-edit-*generating* policy via ordinary supervised fine-tuning. Two categorically different models exist at every iteration — a disposable "answerer" reset before every use, and a persistent "generator" that is the only thing that actually accumulates learned behavior — and the model that answers real requests and the model that generates self-edits are the *same weights* at any given checkpoint, but the versioning across iterations is entirely manual: `train_SFT.sh`'s own comment instructs the operator to point the next round's `MODEL_NAME` at the previous round's merged output directory (`models/iter1`, `iter2`, ...); nothing in the code auto-discovers "the latest checkpoint." The `general-knowledge/` (SQuAD) pipeline confirms the same inner/outer structure as a live service: `TTT_server.py` holds a ZMQ **REP** socket, which is strictly synchronous — request *N* blocks until request *N-1*'s reply is sent, so "serving" and "training" the answerer model are never concurrent. Each request trains a fresh LoRA, evaluates it against a separately-running vLLM OpenAI-compatible server via dynamic `load_lora_adapter`/`unload_lora_adapter` HTTP calls, records an `adapter_gain` reward, then deletes the adapter (`shutil.rmtree`). No checkpoint versioning exists at the inference server either — vLLM serves whichever base path it was started with, and a human must manually point `MODEL_NAME` at `models/iter{N}` and restart the server after each outer-loop SFT round. |
| **Conclusion** | No code changes resulted from this session. It deepens Research topic 47's finding: SEAL's "self-edit" concept is not a runtime model swap but a keep-the-good-text/retrain-from-scratch loop, mechanically closer to what `self_learner.py` already does at the retrieval-memory level (write validated QA pairs into `learned_qa`, no weight update) than the RL-scored-arbitrary-edit framing in topic 47 first suggested — but SEAL adds two things this project has never implemented: (a) an explicit binary reward on each candidate before it's kept, and (b) a policy that is periodically *retrained* on the record of what got kept, rather than a fixed, un-scored rephrasing prompt. |
| **Relevance to Project** | The closest RAG-work equivalent to "scoring a self-edit" would be scoring whether a distilled `learned_qa` rephrasing actually improved a later retrieval or answer — a measurement the project does not currently make (the same gap already noted in ADR-008 and Research topics 7/47). SEAL's inner/outer-loop separation (disposable per-request adapter vs. persistent, manually-versioned generator checkpoint) is a useful mental model for keeping any future "scored self-edit" experiment cleanly separated from the production `learned_qa` collection, so a bad scoring run couldn't corrupt live retrieval memory the way a bad SEAL adapter never touches the served base model. Filed as future scope, contingent on the same validated-interaction-volume prerequisite noted in ADR-008 and topic 47 — no implementation planned yet. |
| **Relevance to Project** | Extends the self-learning literature review started in ADR-008/Research topic 7 (memory injection vs. fine-tuning vs. RLHF) with a fourth, more recent design point — RL-scored self-edits — that sits between pure memory injection (implemented) and full fine-tuning (deferred). No immediate architectural impact; recorded for future reference alongside Research topic 45 (Continual Harness), which explored a related but distinct "harness self-refinement" framing read three days earlier. |

## 53. OpenTelemetry, OpenInference, and OpenInference Semantic Conventions — Fundamentals

| Field | Detail |
|---|---|
| **Topic** | Layered relationship between OpenTelemetry (OTel), OpenInference, and OpenInference semantic conventions (semconv) for AI/LLM observability |
| **Date** | 2026-07-09 |
| **Findings** | OTel is the CNCF vendor-neutral framework for collecting traces/metrics/logs from any application ("instrument once, export anywhere" via OTLP). A trace is composed of spans, each representing one unit of work, linked by trace-ID/span-ID context propagation; exporters ship spans to a backend (Jaeger, Grafana, Phoenix, etc.) without OTel itself storing anything. OTel has no built-in vocabulary for AI-specific concepts (prompts, tokens, tool calls, embeddings, retrieval, RAG). OpenInference is an open standard built on top of OTel that adds exactly this vocabulary as span attributes, without replacing or forking OTel itself. OpenInference semantic conventions (semconv) are the standardized attribute names (e.g. a canonical field for "model name" instead of every framework inventing its own `model`/`engine`/`chat_model` key) that let any OTel-compatible backend render AI-specific data (prompts, completions, token counts, tool calls, retrieval results) consistently without custom per-framework parsing. |
| **Conclusion** | This three-layer stack (OTel → OpenInference → semconv) is exactly what `phoenix_tracing.py`'s `LangChainInstrumentor().instrument()` call activates — the instrumentor auto-generates OpenInference-conformant spans from LangChain's callback system and exports them as standard OTel spans over OTLP to the local Phoenix collector. Understanding this layering was the direct prerequisite for correctly diagnosing Bugs.md BUG-071 (Phoenix's spans are real OTel spans, but OpenInference's specific LangChain tracer implementation doesn't attach them to OTel's ambient context). |
| **Relevance to Project** | Explains why `PHOENIX_COLLECTOR_ENDPOINT` in `.env` is an OTLP gRPC endpoint (`localhost:4317`) rather than a Phoenix-specific API, and why the same instrumentation approach would work largely unchanged against any other OTel-compatible backend (Langfuse, Jaeger, SigNoz) if the project ever migrates — only the exporter endpoint would change, not the instrumentation code. |

## 54. LangSmith vs. Langfuse vs. Phoenix — Self-Hosting Comparison for a No-Data-Egress RAG Project

| Field | Detail |
|---|---|
| **Topic** | Choosing an observability backend under a hard constraint (no logs/traces may leave the local network) across three LLM-observability platforms |
| **Date** | 2026-07-09 |
| **Findings** | LangSmith's self-hosted option exists but is an Enterprise add-on gated behind a paid license, aimed at Kubernetes/on-prem infra rather than a casual local deployment — ruled out on cost/complexity for a solo project. Langfuse and Arize Phoenix are both genuinely free to self-host with no feature paywall on the OSS core, but their operational footprints differ sharply: Langfuse's self-hosted stack requires Postgres + ClickHouse + Redis/Valkey + an S3-compatible blob store (Docker Compose brings this up, but ClickHouse in particular is real ongoing operational weight), while Phoenix is a single container (`pip install arize-phoenix` or one `docker run`, SQLite for dev/Postgres for prod) with no other services to operate. Feature-wise, both are near-identical on core tracing/debugging/latency/token-tracking (both are OTel-native LLM tools); they diverge on the "LLM product lifecycle" layer — Langfuse leans production-ops (mature cost dashboards, prompt versioning/deploy-label management, more mature native alerting), while Phoenix leans experimentation (best-in-class evals library, dataset/experiment comparison, and unique embedding/retrieval-drift visualization directly relevant to debugging a two-track retriever). A 14-metric side-by-side comparison across tracing GUI, debugging, I/O visibility, latency/cost tracking, dashboards, alerts, evals, datasets, custom evaluators, prompt management, experiment comparison, human feedback, and the production-improvement loop confirmed this split holds category-by-category, not just as a general impression. |
| **Conclusion** | For this project specifically (solo dev, no data-egress allowed, no existing SSO/multi-tenant need, and a two-track document/learned_qa retriever whose main open questions are retrieval-quality debugging rather than production cost-attribution), Phoenix was chosen over Langfuse: zero infrastructure weight beyond one container, no feature gating, and its retrieval/eval tooling maps more directly onto the project's actual open bugs (e.g. Bugs.md BUG-031/BUG-035-class retrieval-verdict mismatches) than Langfuse's general-purpose tracing does. Langfuse remains a candidate for later exploration if/when prompt-version management or production cost-attribution become priorities — explicitly deferred, not rejected. |
| **Relevance to Project** | Directly resulted in the `phoenix_tracing.py` module and the `PHOENIX_COLLECTOR_ENDPOINT`/`PHOENIX_PROJECT_NAME` env vars added 2026-07-09 (see Decisions.md ADR-063). LangSmith instrumentation is retained in parallel for now (both backends are actively wired and mirrored to by `_TracingHandler`) rather than removed, so the two can continue to be compared on live traffic before fully committing. |

## 55. Bridging Python's `logging` Module into LangSmith and Phoenix Traces

| Field | Detail |
|---|---|
| **Topic** | Why stdlib `logging` output (the project's existing `.debug.log` files) does not automatically appear inside LangSmith or Phoenix traces, and how to bridge the two |
| **Date** | 2026-07-09 |
| **Findings** | LangSmith and Phoenix each build their trace data from a different, independent channel than stdlib `logging` — LangSmith hooks into LangChain's callback system to build structured "runs" (`RunTree` objects) per chain/tool/LLM call; Phoenix's `LangChainInstrumentor` auto-instruments the same callback system to emit OpenInference-conformant OTel spans. Neither channel has any awareness of a project's own `logger.info(...)`/`logger.debug(...)` calls — those run through a third, separate output path (console + rotating debug-file handlers) never connected to either tracer. Bridging requires deliberately attaching each log record to whichever trace is currently active: for LangSmith, `langsmith.run_helpers.get_current_run_tree()` returns the live `RunTree` for the call currently executing (confirmed via a real LangGraph `StateGraph` test — `get_current_run_tree()` correctly returns a live object inside node execution when `LANGCHAIN_TRACING_V2=true`), and `RunTree.add_event(...)` attaches an arbitrary event to it. For Phoenix, the equivalent "current span" lookup via `opentelemetry.trace.get_current_span()` does not work with `openinference-instrumentation-langchain`'s specific tracer implementation (see Bugs.md BUG-071) — the correct lookup is `LangChainInstrumentor()._tracer.get_span(run_id)`, using the `run_id` already obtained from the LangSmith lookup, since both trackers key their internal state off the same LangChain-generated run ID. |
| **Conclusion** | A single logging handler (`_TracingHandler` in `app_workflow/services/logger_config.py`) can mirror every log record onto both an active LangSmith run and an active Phoenix span simultaneously, purely additively (it never replaces or duplicates the existing console/file logging), as long as it (a) runs independent of the console handler's level so DEBUG-level node detail isn't silently dropped (Bugs.md BUG-070), and (b) uses the run-id-based lookup for Phoenix rather than the ambient-context lookup that OTel documentation would normally suggest. This mechanism only attaches logs to a trace that is already active — a log statement fired outside any traced call (e.g. at import time, or from a thread LangChain isn't tracking) will not appear in either backend, which is inherent to how both platforms scope logs to a run/span rather than something a handler can work around. |
| **Relevance to Project** | Directly implements the log-to-trace mirroring added to `app_workflow/services/logger_config.py` on 2026-07-09 (see Decisions.md ADR-064, Bugs.md BUG-069 through BUG-071). Also produced `app_workflow/services/trace_events.py` as a necessary companion tool once it was confirmed (Bugs.md BUG-072) that LangSmith's own UI never surfaces these mirrored events despite storing them correctly server-side.

## 56. Langfuse's Callback-Based Tracing Model, Contrasted With LangSmith/Phoenix's Ambient Instrumentation

| Field | Detail |
|---|---|
| **Topic** | Why Langfuse's LangChain integration behaves fundamentally differently from LangSmith's and Phoenix's, at the mechanism level, and what that implies for wiring it into a LangGraph pipeline |
| **Date** | 2026-07-10 |
| **Findings** | LangSmith traces via environment variables alone (`LANGCHAIN_TRACING_V2=true`, etc.) — LangChain/LangGraph has built-in native support that activates globally regardless of whether any particular call site threads config through. Phoenix traces via `phoenix.otel.register()` + `LangChainInstrumentor().instrument()` — OpenTelemetry auto-instrumentation that patches the LangChain/OpenAI SDK classes at import time, also global and ambient. Both require zero per-call wiring. Langfuse (SDK v3+, this project on 4.13.2) is architecturally different: `langfuse.langchain.CallbackHandler` is an explicit LangChain callback object that only traces a call if it is actually present in that call's `config={"callbacks": [...]}`. It is not ambient — passing it once at the top-level `rag_app.invoke(...)` call does nothing for nested calls unless LangGraph/LangChain's config-propagation mechanism successfully carries it all the way down to each `llm.invoke(...)`, which (as this session found — see Bugs.md BUG-075, Decisions.md ADR-067) silently fails across a `ThreadPoolExecutor` thread-hop and across any node function that doesn't declare a `config` parameter. Separately, Langfuse's SDK is itself OTel-native under the hood (`_client/resource_manager.py`'s `_init_tracer_provider()` reuses whatever `TracerProvider` is already global and calls `add_span_processor()` on it) — which is the direct cause of the Phoenix-eviction conflict in Bugs.md BUG-076. |
| **Conclusion** | LangSmith and Phoenix are both "ambient/automatic" (env-var or OTel-patching), while Langfuse is the "explicit callback" outlier among the three backends this project has now evaluated — it requires genuine code changes (config threading) to work correctly in a multi-node, thread-hopping pipeline like this project's LangGraph graph, which the other two never needed. This is a durable architectural distinction, not a version quirk: any future addition of a fourth callback-based tracer (as opposed to an OTel- or env-var-based one) would hit the identical propagation requirement. |
| **Relevance to Project** | Directly explains why Langfuse tracing initially appeared to be wired correctly (no errors, handler constructed, passed to `.invoke()`) yet produced zero traces — and why neither LangSmith nor Phoenix ever surfaced an equivalent gap despite being adopted earlier with much less scrutiny of the propagation path. The `config` threading fix (ADR-067) is now a standing constraint: any new node or LLM call site added to `app_workflow/` must accept and forward `config` or it will silently fall outside Langfuse's trace, even though it would still be captured by LangSmith/Phoenix. |

## 57. Langfuse Scores, Datasets, and Annotations — Documentation, GitHub, and Stack Overflow Findings

| Field | Detail |
|---|---|
| **Topic** | Langfuse's evaluation-data model — Scores (structured evaluation results, numeric/categorical/boolean/text, attachable to traces/observations/sessions/dataset-runs), Datasets (reusable input/expected-output test cases, versioned, with schema validation and folder-style naming), and Annotations/Annotation Queues (the human-review workflow that produces scores and corrected outputs) — researched from official docs, then cross-checked against GitHub issues and Stack Overflow for operational gotchas |
| **Date** | 2026-07-10 |
| **Findings** | **Scores** are the universal evaluation-result object (name, value, data type, one parent — trace/observation/session/dataset-run — optional comment, optional Score Config schema); they can originate from manual UI annotation, annotation queues, SDK/API calls, LLM-as-a-Judge evaluators, or deterministic code evaluators, and Score Configs standardize the rubric (numeric range, allowed categorical values, text length) so different reviewers/evaluators produce comparable values. **Datasets** hold versioned collections of input/expected-output items (optionally schema-validated, optionally multi-modal), commonly seeded from production traces for regression testing; **Dataset Runs** (via the SDK experiment runner or UI prompt experiments) execute the current pipeline against a dataset's inputs to produce *new* outputs, which are then optionally graded by an evaluator — Langfuse does **not** automatically diff generated output against the dataset's expected output; the evaluator prompt alone decides what gets compared (e.g. a groundedness/hallucination evaluator can ignore the expected output entirely and score only against retrieved context, while a correctness evaluator can compare against it directly). **Annotations** are the human workflow (direct manual annotation or structured Annotation Queues assigned to reviewers with required Score Configs) that produces Scores and, often, corrected reference outputs suitable for promotion into a Dataset — closing a production-failure → human-review → gold-dataset-item → regression-test loop. GitHub issue review surfaced several operational gotchas independent of the docs: the same trace can be added to one annotation queue multiple times (no built-in dedup — self-hosted v3.150.0, reported 2026-04); no easy way to filter the tracing UI by "already in a queue" (workaround: custom metadata/tags applied at ingestion time, since observation tags are immutable after ingestion); queue-assignment-by-email can require internal user IDs not exposed on all self-hosted license tiers; `annotation_queues` itself has been gated behind Enterprise Edition licensing on some self-hosted deployments; dataset-run metadata/description cannot be edited after creation via the API in current SDK versions (must be decided upfront); large-scale dataset-run metric queries can hit ClickHouse memory limits on high-volume self-hosted projects; and the score-ID field name (`id` vs `score_id`) has changed across SDK/API versions, so idempotent-score examples must match the installed SDK version rather than being copied from arbitrary docs/blog posts. Stack Overflow had comparatively little Langfuse-specific material; the one clearly relevant thread confirmed a common chat-app pitfall — attaching user feedback to "the latest trace" instead of the specific message's own trace/observation ID silently misattributes feedback when a user rates an older message. |
| **Conclusion** | For this project's stated goal (evaluating which tracing backend — LangSmith, Phoenix, or Langfuse — fits best), Langfuse is the strongest of the three specifically on the Scores/Datasets/Annotations axis: Phoenix has its own evals/datasets/experiments tooling (noted as a strength in Research topic 54) but nothing evaluated hands-on this session covers annotation queues or Score Analytics (inter-rater/judge-vs-human agreement statistics) with Langfuse's depth; LangSmith's equivalent surface was only ever reviewed conceptually (Research topic 52), not hands-on. No production code was written from this research — it produced a worked-example LLM-as-a-Judge evaluation template (hallucination scoring against retrieved context only, explicitly excluding the dataset's expected output as evidence) for the `app_workflow/` Generate-Draft-from-Compressed-Context experiment, kept outside the repo as reference material for a future evaluation-harness effort. |
| **Relevance to Project** | Directly extends Research topic 52's identified gap ("systematic prompt experimentation... and a curated evaluation dataset separate from production logs" are the clearest things this project's hand-rolled tooling lacks relative to a full LLMOps platform) — Langfuse's Dataset+Experiment+Score-Analytics combination is the most complete answer to that gap of the three backends evaluated so far. If a future session builds an actual evaluation harness for `app_workflow/`'s retrieval/compression/generation pipeline, this topic and Research topic 56 (the callback-propagation mechanism it depends on) are the direct prerequisites. | |
