## Chronological Log

### April 2026 — Foundation & Infrastructure

- **Project started.** Goal: build a local Agentic RAG system over a mixed corpus (ASD medical PDFs + Adjustable Speed Drive technical documents).
- **Stack selected:** Python 3.11, ChromaDB (local persistence), `all-MiniLM-L6-v2` (384-dim embeddings via SentenceTransformers), LangChain `ChatOpenAI` pointed at Groq API (`llama-3.1-8b-instruct`), `uv` for environment management.
- **Core modules built:** `ingest.py`, `embedding_manager.py`, `vector_store.py`, `retriever.py`, `query.py`.
- **ChromaDB architecture decided:** two collections — `documents` (source chunks) and `learned_qa` (self-learning memory).
- **Chunking parameters set:** `chunk_size=1000`, `chunk_overlap=200`; `chunk_seq` metadata field added to support future Neighbor-Aware Compression (NAC).
- **GPU ingestion optimised:** bulk-embed then single `collection.add()` call; batch size 128–512 for RTX 5050 (8GB VRAM). Resolved slow-ingest bottleneck caused by per-batch ChromaDB writes.
- **Python 3.14 incompatibility identified** — downgraded to 3.11; PyTorch GPU wheel (`torch==2.11.0+cu128`, CUDA 12.8) installed separately from `requirements.txt` to avoid CPU-wheel downgrade by `uv`.

### Early May 2026 — Agentic Loop & First Dry Runs

- **`agent_query.py` built** — 4-phase agentic loop: RETRIEVE → COMPRESS → DRAFT → JUDGE.

- **Thumbdown persistence added** (`user_thumbdowns.json`, `failed_variants.json`): bad-answer records persist across sessions; blocked variants injected into system prompt on re-query.
- **First dry runs revealed two core problems:**
  - ASD acronym ambiguity (Autism Spectrum Disorder vs Adjustable Speed Drive) causing cross-domain chunk contamination.
  - `check_answer_quality` being called prematurely by the 8B model (in Iteration 1, before any retrieval).

#### 2026-06-15 — Centralised Logging Module + Severity-Level Audit; LangGraph Researched, Not Adopted

* Decided to replace the project's scattered `print()` and direct `file.write()` diagnostic output with Python's stdlib `logging` module. Researched the module first: `logging.getLogger(__name__)` per-file pattern, the level hierarchy (DEBUG / INFO / WARNING / ERROR / CRITICAL), the distinction between a logger's level and a handler's level, propagation up the parent tree, the duplicate-handler trap on repeated configuration, and the DEBUG-vs-INFO heuristic ("if this message disappeared from production logs tomorrow, would anyone care?" — DEBUG if no, INFO if yes)
* Considered configuring `logging` per-module vs. configuring it once in a central module that every other module imports a named logger from. Chose central setup because the project already has ~14 production modules with ~370 scattered `print()` calls — centralising means configuration changes stay one-file and the per-call code change is minimal (`print(x)` → `logger.info(x)`)
* Created `app/logger_config.py` — exports `setup_logging(log_dir, app_name, console_level)`. The function is idempotent via a `_CONFIGURED_ATTR` flag on the root logger so repeated calls from different entry points (`agent_query.py`, `ingest.py`, `run_batch.py`, `query.py`, `test_output_fixes.py`, `test_llm_caller.py`, `run_combinations.py`, top-level `main.py`) are safe. Defined a small `_DynamicStdoutHandler(logging.StreamHandler)` subclass that re-points `self.stream` to `sys.stdout` at emit time, so batch-run tee/redirect setups still see console logs
* Initial implementation: console handler at INFO, separate file handlers for `{app_name}.debug.log` (DEBUG-and-above) and `{app_name}.error.log` (ERROR-and-above), diagnostic loggers `llm_data_check` and `llm_json_tries` re-pointed from their original direct `open()/write()` blocks in `fix_llm_output.py` to dedicated `FileHandler`s with `propagate=False` so they wrote only to their own files. Ran a mechanical `print()` → `logger.debug/info/warning/error` conversion pass across 16 modules; preserved `print()` only for the interactive REPL prompts, the batch-run progress UI, the test-console formatter, and all JSON/JSONL data writes (feedback log, failed-variants store, thumbdown store, test transcripts)
* First dry run against the converted pipeline surfaced a real defect (logged as `BUG-038`): the mechanical conversion had *removed* — rather than converted — several `print()` and `f.write()` debug blocks that produced no observable user output. After the migration, `agent_query.debug.log`, `agent_query.error.log`, `llm_data_check.txt`, and `llm_json_tries.txt` were all created but stayed empty across complete agent runs. Cause: the conversion regex matched single-line `print(...)` calls but missed the multi-line `with open(...) as f: f.write(...)` blocks in `fix_llm_output.py`, plus debug prints that were collateral-deleted during the manual cleanup pass. #### 2026-06-24 — Benchmark Session Continued; `requirements.txt` Updated; FIFO LLM Serialization Gate, Adaptive Cooldown, and `request_id` Tracing (Separate Branch, Untested)

* Continued 10-query benchmark session on both pipelines, adding further runs to `10 Query Interaction Times.txt`.
* `requirements.txt` updated to sync all installed packages with the current environment — file approximately doubled in size (≈4 KB → 10 KB), capturing transitive dependencies accumulated since the project's start.
* Discovered that submitting two simultaneous `POST /query` requests to `app/api.py` causes one to silently fail: both threads enter `llm_invoke()` concurrently; the first thread consumes the available Groq token quota; every retry attempt in the second thread hits 429 and exhausts `LLM_RATE_LIMIT_MAX_ATTEMPTS`, causing `llm_invoke()` to return an error with no successful LLM call — see BUG-053.
* (Separate branch `setup_async_lock` — not yet merged, untested) Researched semaphores as an initial fix for BUG-053. Concluded they are insufficient: a semaphore limits concurrency at point of entry but cannot prevent a 429-holding thread from losing the gate on retry — a new arrival acquires the semaphore and burns more tokens before the failing thread is rescheduled. See Research topic 35.
* (Separate branch) Replaced the random-jitter exponential backoff in `app/llm_caller.py` with a FIFO serialization gate: a `queue.Queue` of per-thread `threading.Event` objects enforces strict arrival-order; only the front-of-queue thread may call Groq at any given time. A thread that receives a 429 does NOT re-enqueue — it holds the gate, sleeps the full token-reset window derived from Groq response headers via `_parse_groq_duration()` / `_groq_wait_seconds()` (reading `x-ratelimit-reset-tokens` → `x-ratelimit-reset-requests` → `retry-after` in priority order), then retries directly. Global token-reset deadline tracked in `_token_reset_until` (monotonic timestamp) so the wait is paid exactly once per exhaustion event. `LLM_RATE_LIMIT_BACKOFF_JITTER_SECONDS` removed from `config.py` — unnecessary when a single thread holds the gate. See ADR-044.
* (Separate branch) Added adaptive inter-call cooldown: after each successful call, if the queue is non-empty, the active thread sleeps a `_cooldown_floor` derived from `x-ratelimit-remaining-tokens` headers before releasing the gate. The floor doubles on each 429-recovery, halves after 3 consecutive clean successes (`_clean_success_streak`), and resets to 0 when the queue empties. Two new constants added to `app/config.py`: `MIN_COOLDOWN_TIME = 0.0`, `MAX_COOLDOWN_TIME = 30.0`.
* (Separate branch) Removed `async with _query_lock:` from `app/api.py`'s `/query` handler — serialization is now handled by the FIFO gate inside `llm_invoke()`. The `_query_lock` object is retained but unused, pending validation.
* (Separate branch) Added per-request tracing to `app/logger_config.py` via `ContextVar[str]`: `_request_id_var`, `set_request_id()`, `get_request_id()`, and `_RequestIdFilter` inject the current `request_id` into every log record via updated console and file format strings. `app/api.py` generates a `uuid4` per incoming request, sets it via `set_request_id()`, logs `"Request received: request_id=…"`, and passes it through to `run_agent()` → `agent_state` (`app/agent_query.py`) and `FeedbackStore.log()` / `_save_thumbdown()` (`app/feedback_store.py`), making every stored interaction traceable to its originating HTTP request.
* Branch targets `app/` only; `app_workflow/` and its `services/llm_caller.py` remain in their June 23 state.

### 2026-07-15 — Docling, Unstructured, and Marker-PDF Document-Loader Exploration; Batch Utilities Preserved

* **Three document-to-Markdown approaches explored.** Docling, Unstructured, and Marker-PDF were tested as possible ingestion tools. The work remained outside both production pipelines: neither `app/` nor `app_workflow/` was modified, and `app/ingest.py` remains the active ingestion implementation.

Each recursively discovers source files, mirrors their relative paths into a tool-specific output directory, writes UTF-8 Markdown, continues across per-file exceptions, reports converted/failed totals, and exits non-zero when failures occur.
* **Marker-PDF evaluated in detail.** `useful_but_not_valuable_Files/Marker-PDF Report.md` records results across procurement, legal, engineering, and prose-heavy documents. Marker was strong at ordinary prose recovery and useful on some simple tables, but unreliable for complex/merged tables, forms, engineering title blocks, page layout and boundaries, heading hierarchy, repeated page furniture, nested lists, reading order, and visual semantics. The tested outputs referenced 131 images without supplying the assets, and one document contained mojibake.
* **Adoption deferred.** Raw Marker Markdown is not suitable as the sole authoritative representation for layout-dependent documents. Any future production path requires asset/link validation, encoding normalization, page-aware cleanup, heading repair, structural quality checks, and richer handling or manual review for complex pages. Docling and Unstructured also require an equivalent cross-loader and downstream retrieval-quality comparison before selection. See ADR-072 and Research topic 61.
